### 🔴 Уникальные ограничения в снимке схемы не доезжают до клиента — сторож мёртв с рождения 🗓 since:2026-08-30

`getSyncSchemaSnapshot` собирает уникальные индексы запросом с `array_agg(a.attname)`. Тип результата — `name[]`, и node-postgres такой массив **не разбирает**: строка приходит как `"{code}"`. Потребитель проверяет `Array.isArray(row.columns)`, получает false и **отбрасывает запись**. Проверено на проде: `uniqueConstraints` пуст у ВСЕХ 20 таблиц снимка, включая первичные ключи, хотя сам SQL-запрос в psql возвращает строки нормально.

**Следствие:** `repairLocalSyncTables` на клиенте никогда не дедуплицировал по серверным unique — он молча уходил в локальный `PRAGMA index_list`. Гейт, который годами ничего не охранял.

**Отдельно снята прежняя формулировка этого пункта.** 2026-08-30 здесь было записано, что ремонт реплики схлопывал позиции номенклатуры с пустым артикулом (168 живых строк на проде). **Это неверно:** механизм требует, чтобы сервер объявил unique, а он не объявлял никогда. Клиентский индекс `erp_nomenclature_code_uq` частичный с шага миграций 10→11, поэтому локальный фолбэк тоже не схлопывал. Ошибка родилась из чтения кода без проверки того, что реально приезжает по проводу.

**Чинить осознанно, не заодно.** Приведение типа (`array_agg(a.attname::text)`) ОЖИВИТ путь, который УДАЛЯЕТ строки из реплики парка. Порядок: сначала прогон, который печатает, что дедуп удалил бы, потом включение. Фильтр частичных индексов (`indpred IS NULL`) уже на месте — без него оживший дедуп схлопывал бы легальные дубли (пустой артикул, освобождённый логин).

### 🟡 Настроить доверенную зону антивируса на парке 🗓 since:2026-08-04

Техника ADR-0002 сама по себе поведенческий анализ не гасит. На каждой машине разово: папка `%LOCALAPPDATA%\Programs` в исключения **и** `MatricaRMZ.exe` + `matricarmz-watchdog.exe` как **доверенные приложения** («не проверять активность / не проверять сетевой трафик»). Файлового исключения мало — HIPS/System Watcher гасится именно доверенным приложением. Домена/GPO на заводе нет (решение владельца 2026-08-04), поэтому раскладка вручную; подпись кода отложена до появления домена или возможности купить сертификат публичного CA.

**Инструмент есть с 2026-08-26** — [`scripts/client-ops/`](../scripts/client-ops/README.md) (перенесён из `biblio` по мандату владельца, brain D-050): печатает готовые строки под фактические пути машины, умеет экспорт/импорт эталонной конфигурации на парк.

**С v3.14.0 ручного ввода строк больше нет, и доставка на парк решена.** Помощник складывает оба списка в файлы **того формата, который Касперский принимает кнопкой «Импорт»** на своих экранах (формат снят побайтово с живого экспорта: UTF-16LE + BOM, CRLF; папка обязана кончаться `\`). Ключи `-MergeExclusions` / `-MergeTrusted` переносят прежний экспорт дословно, поэтому вопрос «заменит ли импорт список целиком» снят. Установщик кладёт помощник на Рабочий стол **архивом под паролем `111`** (ZipCrypto — распаковывает встроенный проводник) плюс памятку: пароль не секрет, он лишь делает архив непрозрачным для сканера, иначе неподписанный `.ps1` съедается до того, как для него заведено исключение (**M94**).

Пункт остаётся жёлтым по двум причинам, обе — про людей, а не про код: **исключения по-прежнему вносит человек** в окне Касперского (`avp.com` команды «добавить исключение» не имеет, Самозащита правку извне блокирует), и **на парк это фактически не разложено** — сценарий владельца «приостановить защиту → распаковать → запустить → импортировать → включить защиту» ещё не прогонялся ни на одной машине парка. Закрывать пункт **по факту раскатки**, а не по факту наличия инструмента.

Админ здесь ничего не выигрывает: он проходит `canAccessFile` безусловно. Это убирает из выдачи id файлов, которых нет ни на одной карточке — из чужого чата, картинок чужих заметок, файлов с чужого Рабочего стола, — то есть ровно те, ради которых самовыдача и затевалась бы.

   **Заодно починен каталог источников.** `GET /reports/builder/meta` не смотрел на актора **вообще**: выборка честно отказывала, а список таблиц с колонками уезжал любому, кто дотянулся до конструктора — вместе с `refresh_tokens`, `permissions`, `chat_messages`, `notes`. Значит одна смена права ничего не изменила бы на глаз: строка «Файлы» осталась бы в списке и отвечала бы отказом при построении. Теперь каталог фильтруется теми же правами, что и выборка.

   **Остались ещё три канала перечисления id — сузить их этой правкой не удалось:**
   - **`attribute_values` в том же конструкторе** (разбор ниже) — отдаёт `valueJson`, где лежат и вложения карточек, и **чужие ярлыки Рабочего стола** (`ui_profile_json`);
   - **`GET /changes`** отдаёт строки с `tableName='file_assets'` и `rowId` = id файла любому обладателю `updates.use` (базовое право оператора), без фильтра по актору. Такие строки создаёт заявочное удаление файла не-владельцем;
   - **локальная реплика.** `ui_profile_json` — обычный EAV-атрибут, `attribute_values` синкается всем, а построчный фильтр pull'а режет только `password_hash` и пару HR-полей. Это отдельная проблема приватности: чужой рабочий стол виден целиком.

   **Остался узкий канал — `attribute_values` в конструкторе отчётов.** Источник отдаёт колонку `valueJson` и открывается ЛЮБЫМ одним правом из пяти (`masterdata.view` / `engines.view` / `parts.view` / `employees.view` / `supply_requests.view`), а строки **не фильтруются по типу сущности-владельца**. Отсюда две беды: (1) оператор с одним лишь `parts.view` читает EAV-значения сотрудников, включая `attachments`, то есть id кадровых документов; (2) шире файлов — он вообще читает атрибуты типов, которые ему не положены. `redactReportRows` (H4) режет только строки с «чувствительными» ИМЕНАМИ атрибутов (зарплата/паспорт/ИНН/СНИЛС), а `attachments` и, скажем, `birth_date` в этот список не входят. Показательно, что путь доступа к файлу (`eavRowGrantsFileAccess`) как раз требует права на тип сущности — конструктор отчётов над теми же данными слабее.

   **Лечение (предложение, не сделано):** фильтровать строки `attribute_values` по праву на тип сущности — переиспользовать `permsForEntityTypeCode` из `fileAccessService`. Не сделал сам: это меняет то, что видят операторы в уже собранных отчётах (тип сущности приходит в строке ДИСПЛЕЙНЫМ именем, а не кодом — нужна аккуратная сшивка), а фильтр по умолчанию падает в `masterdata.view` и может срезать больше, чем ожидается. **Решение владельца.**

### Три живых договора с одним внутренним номером «20/ГОЗ-25» — решение владельца 🗓 since:2026-08-17

Дублей по **номеру договора** (`number`) среди живых нет ни одного (проверено 2026-08-17 на проде). Но по **внутреннему** номеру (`internal_number`) есть живая коллизия — три действующие записи с `20/ГОЗ-25`:

| id | создан | `number` | двигателей |
|---|---|---|---|
| `a16948e4` | 2026-02-11 | `2527187908521442245215425/641/25/РП2025-953/571П` | **71** |
| `e853b7c5` | 2026-07-06 | `2626187922481435541247710` | **32** |
| `51cc4843` | 2026-07-02 | `20` | 1 |

Это **не дубли одного договора** — номера разные, значит и договоры разные; сломан именно внутренний номер, который по смыслу («20-й договор ГОЗ-25») обязан быть уникальным. `51cc4843` с номером `20` выглядит недозаполненной заготовкой: похоже, в поле «Номер договора» набрали внутренний номер. Разобрать может только владелец — какой внутренний номер у двух июльских договоров правильный, и не сносить ли заготовку (у неё привязан 1 двигатель, его надо переподвесить).

**Гейт уникальности заведён 2026-08-17** (по ок владельца): `shared/src/domain/contractInternalNumber.ts` + `backend-api/src/services/contractNumberGuard.ts` (серверная половина) + `entityService.setEntityAttribute` (клиентская). Новую коллизию набрать больше нельзя — жёсткая блокировка, не warning ([[feedback-data-integrity-over-convenience]]). **Гейт не чинит уже накопленное:** он срабатывает на запись, а три существующие записи лежат как есть. Пока владелец не разберёт их, правка внутреннего номера у двух из трёх будет отбиваться — это ожидаемо и правильно (сначала освободить номер, потом занять).

### Трёхзначный код договора неоднозначен — 69 договоров на 36 кодов 🗓 since:2026-08-17

Конвенция завода (её ИИваныч сам вывел в `learning_md` 2026-08-17): трёхзначный код = последние три цифры номера **до первого слэша**. ### Осиротевший ключ в `authorized_keys` прода — чей? 🗓 since:2026-08-17

При ротации ключа PC40 (2026-08-17) сверка отпечатков вскрыла запись с комментарием «PC40, 2026-05-23», у которой **нет приватной пары на PC40** — ни один локальный `~/.ssh/*.pub` с ней не совпадает. По комментарию это PC40, но действующим ключом PC40 был другой (от 2026-05-22), значит комментарий врёт или приватный ключ утрачен. Пока владелец не установлен, запись **не удалялась**: если она принадлежит третьей машине (в `PROJECT_STATE` упоминалась «машина-2»), удаление отрежет ей доступ к проду.

Авторизованный ключ без известного владельца — это открытый доступ, который никто не контролирует. Разрешить одним из двух: (а) владелец подтверждает, что третьей машины нет → строку снести; (б) третья машина есть → зайти с неё, сверить отпечаток `ssh-keygen -lf` своего ключа и переименовать комментарий по-честному.

**Ключ снят с прода 2026-08-17** по решению владельца («третьей машины нет»): строка удалена из `authorized_keys` (бэкап сделан рядом с файлом), осталось три ключа с известными владельцами. Пункт закрыт; ниже — история, из которой выросли два других хвоста.

> **Закрыто целиком 2026-08-19.** Директива brain `2026-08-19-three-zero-cost-fixes-before-the-onprem-move` требовала снять осиротевший ключ — он уже был снят 17.08 (brain читал раздел по заголовку и не заметил строку о закрытии). Тем же днём по решению владельца **досрочно снят и fallback** — прежний ключ PC40 от 2026-05-22 (плановая дата была 24.08): PC40 сутки ходил на прод новым ключом, страховка отработала вхолостую. Бэкап сделан рядом с файлом, доступ проверен новым соединением сразу после правки. **В `authorized_keys` прода осталось ровно два ключа** — PC40 и RMZ4VAL, оба с известными владельцами (отпечатки в репо не пишем — сверять `ssh-keygen -lf` на месте). Раздел оставлен ради урока «сверять по отпечаткам, а не по комментариям» и истории двух выросших из него хвостов.

**Попытка разрешить по логам (2026-08-17) не удалась — и вскрыла вторую проблему.** `journalctl -u ssh` даёт три отпечатка (старый ключ PC40 — сотни входов, RMZ4VAL — десятки, новый PC40 — единицы), а осиротевший — **ни разу** — но это **не доказательство**, что ключ мёртв: окно журнала начинается только с `Aug 17 11:19` (рестарт сервиса сегодня), а спящая машина за такое окно и не должна была появиться. Долгого журнала нет: **`/var/log/auth.log` — 0 байт с mtime `May 10`** (`auth.log.1` — 15 КБ от `May 5`), то есть rsyslog не пишет sshd-аутентификацию больше трёх месяцев, и durable audit-trail входов на прод отсутствует. **Дырка закрыта 2026-08-17.** Причина оказалась ровно та: `/etc/rsyslog.d/50-default.conf` — 1127 байт `NUL`, а он несёт правило `auth,authpriv.* → /var/log/auth.log`. rsyslog при этом рапортовал `active`. Восстановлен из пакетного эталона `/usr/share/rsyslog/50-default.conf`, сервис перезапущен, проверено новым входом: `auth.log` пишет `Accepted publickey … SHA256:…`. Подробности и диагностический признак — GOTCHAS **M85**; грабля ложного скана — **M86**.
