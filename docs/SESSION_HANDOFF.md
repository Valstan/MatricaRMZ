## Следующий шаг

**Развилка R3 — нужен ответ владельца, до него шаг не начинать.**

Ввод `users` / `user_section_access` в sync-контракт невыполним, пока зеркало держат триггеры: `updateSeqAndCollect` (`backend-api/src/services/sync/applyPushBatch.ts:501-530`) — единственное место, где строке проставляется `last_server_seq`, а `rebuild_user*` пишут мимо пути записи приложения. Инкрементальный pull страницует по seq → таблица не приезжает никогда. Холодный снапшот падает в фолбэк на пустой для триггерных таблиц ledger-state → клиент получил бы ноль строк, офлайн-гейт закрыл бы доступ всем. И `applyPushBatch` **молча игнорирует** таблицу без обработчика, хотя ledger-seq выдаётся до его вызова — ledger и PG разошлись бы беззвучно.

Три варианта (§R3 плана + `PENDING_FOLLOWUPS` §Развилка B3/R3):

1. Сначала R4, потом R3 — но зависимость круговая (`listEmployeesAuth` и клиентский офлайн-гейт ещё читают EAV).
2. **Шаг публикации** — триггер строит содержимое строки, приложение сразу после EAV-записи публикует её через `writeSyncChanges` и получает seq. **Рекомендация сессии:** круг разрывается без cutover'а, а «не забыть опубликовать» можно сделать невыразимым, спрятав публикацию внутрь `setEmployeeAuth` / `setEmployeeSectionAccess`.
3. Дуальная запись на переход.

Полный чек-лист поверхности (102 пункта, 58 блокеров, каждый перепроверен по коду) — [`docs/plans/b3-r3-surface.md`](plans/b3-r3-surface.md). **Картирование не повторять** — оно стоило 2.5M токенов.

Если владелец выберет вариант — начинать с чек-листа; клиентских цепочек миграций **три**, а не две (план не знал про `android-app/src/db/migrate.ts`).

## Что не сработало

- **Идти по чек-листу R3 «сверху вниз».** Всё бы собралось и гейты позеленели, а сломалось бы у людей: строки без seq не приезжают, а холодный клиент получил бы пустую реплику `users` и закрыл доступ всем. Урок: у зеркала, которое держит триггер, **нет пути в инкрементальный синк** — сначала путь записи, потом контракт.
- **`prebuild-install --runtime electron`** для нативных модулей: `node-abi@3.85` не знает Electron 43, а готовых бинарей под его ABI (**148**) нет **ни в одной** опубликованной версии `better-sqlite3-multiple-ciphers` — максимум `electron-v146`. Единственный путь — сборка из исходников, то есть компилятор обязателен.
- **`electron-builder install-app-deps` без компилятора** — сносит рабочие Node-ABI бинари **перед** сборкой и, провалившись, оставляет 35 красных тестов `electron-app`. Перед экспериментами с ABI копировать оба `build/Release/better_sqlite3.node` в сторону.
- **Строгое чтение булева через распакованный текст** — после `jsonb #>> '{}'` строка `"true"` и булев `true` неразличимы. Смотреть надо `jsonb_typeof`. Поймал только прогон на живом PG.
- **Первая починка шумного сторожа** убрала ERROR вместе с info-строкой: обычный `logInfo` на проде отфильтрован уровнем логирования, видимость даёт только `critical: true`.
