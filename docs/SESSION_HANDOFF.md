## Текущая нитка

План — [`docs/plans/engine-rmz-numbers-2026-10.md`](plans/engine-rmz-numbers-2026-10.md). Третий номер двигателя, сквозной и не переиспользуемый: префикс `RMZ` + цифры по порядку, принадлежит **созданию карточки** (повторный заезд = новая карточка = новый номер). Строки реестра `erp_engine_numbers` не удаляются никогда — это и история, и гарантия, что номер не выдадут второй раз.

**Решения владельца 27.10:** номер рождается на сервере, нумерация сплошная (блоки на компьютеры отклонены — дали бы пропуски) · существующие двигатели нумеруются по дате прихода на завод (самый ранний = `RMZ1`), **уточнение 28.10: карточки без даты прихода идут первыми** · заброшенные пустые карточки номер не тратят · причина удаления спрашивается обязательно · в списке три отдельные колонки рядом (`Номер | Внутр. № | РМЗ`).

**Разбивка:** 1 — контракт + таблица + реплика (#1493, смержен) · 2 — сверка-выдача `reconcileEngineNumbers()`, пометка удалений, обязательная причина, бэкфилл-скрипт (#1494, смержен) · фикс обработчика применения номера в `applyPushBatch` + сторож транспортного шва (#1496, смержен) · 3 — показ (колонка, шапка, подстановка вместо пустых номеров в подписях/печатях/отчётах, поиск) (#1495, смержен) · 4 — экран истории «Номера РМЗ» (#1497, смержен). После серии — **финальный проход по периметру** (brain #166): грепом «через какую ещё дверь двигатель называют номером», включая `web-admin` и планшет.

## Контекст

- **Экран «Номера РМЗ» читает реплику, а не сервер** (`engineRmzNumbersHistory.ts`): список обязан открываться офлайн. Опознание карточки берётся из `erp_engine_cards`, недостающее — из `snapshot_json`; снимок строится только для неактивных строк (у живой «что было» открывается самой карточкой), ключи читаются и `camelCase`, и `snake_case`, битый JSON не роняет экран.
- **Ключ реестра — `entities.id` двигателя:** `erp_engine_numbers.id` равен id карточки, поэтому список читает реплику одним `inArray`, а отчёты — одной выборкой на весь отчёт (`Snapshot.rmzByEngineId` из `loadSnapshot`, терпимо к отсутствию реплики), без join.
- **Номер РМЗ — запасной, а не третий в подписи:** в пикерах, гейте дубля, шапке наряда, актах и отчётах он подставляется **только когда документного и внутреннего нет**. Где номер уже показан отдельной колонкой (список, карточка), он стоит третьим рядом с двумя прежними.
- **Инвариант, который нельзя ломать:** номер РМЗ **не** подставляется в `stamped_number` строк деталей (решение 15.07.2026, PR #216). Там личный номер экземпляра детали; одинаковый номер схлопнул бы 6 поршней в один.
- **Имена полей:** удаление карточки живёт в `card_deleted_at`/`card_deleted_by`, а не в базовом `deleted_at` контракта (базовое означает удаление строки синка, а строки реестра не удаляются — иначе история уехала бы из pull и номер выдали бы второй раз).
- **Причина удаления — существующим каналом:** `audit_log` (`action='engine.delete'`, `payload.reason`), актор создания/удаления — из `ledger_tx_index`. Отдельного поля в контракте не завели: второй канал однажды разошёлся бы с первым. На клиенте причина обязательна (`engine:delete` отбивает пустую, карточка спрашивает через `promptText`).
- **Карточка, удалённая до первой сверки, номера не получает:** номера не было — расходовать нечего. Окно практически отсутствует: сверка идёт после каждого push-батча.
- **Сверка не рекурсирует:** собственные записи идут с `skipEngineNumberReconcile` — журнал и pull штатные, но поводом для нового прохода они не служат.
- **Попутно закрыт разрыв (в #1493):** `erp_engine_cards` был в контракте с E3, но отсутствовал в обеих PG-картах pull — холодный снапшот отдавал по двигателям пустоту. Сторож `mirrorTables` его не видел: карточки не входят в `SERVER_MIRROR_TABLES`.
- **Прод-замеры 27.10:** живых двигателей 2570, дата прихода есть у ~1903, пустых заброшенных карточек нет по конструкции (deferred create).
- **Нумерация на проде выполнена 28.10** (сверка на рестарте primary, бэкфилл-скрипт не понадобился): реестр 2580 строк, из них 2574 активных и 6 помеченных удалёнными, `engine_rmz_seq.last_value = 2580`, живых без номера — 0. Порядок тот, что просил владелец: `RMZ1…RMZ663` — карточки без даты прихода, `RMZ664` — 08.02.2023, дальше по дате прихода. Пять номеров сверх dry-run-замера — карточки, заведённые клиентами за эти часы: нумерация уже живёт обычной работой, а не разовым прогоном.
- **`release_registry` на проде отстал на 37 выпусков** (последняя запись — 3.54.0): `release:ledger-publish` падает `401 token_invalid`, потому что `MATRICA_LEDGER_RELEASE_TOKEN` — обычный access-token с TTL (по умолчанию 168 ч), а не вечный ключ. В парке журнал никто не читает, поэтому выкат 3.91.0 прошёл без него.
- **Прод-доступ:** `ssh -o ConnectTimeout=15 matricarmz`; psql — `cd ~/MatricaRMZ/backend-api && set -a && . ./.env && set +a && psql -X -f …`; кириллицу читать из файла (`scp`).

## Что не сработало

- **`@matricarmz/ledger` подключается собранным `dist`.** После правки `ledger/src/types.ts` бэкенд продолжает падать на «Property does not exist», пока не прогнан `corepack pnpm -C ledger build`. Симптом обманчив: typecheck ругается на `pgSyncTables.ts`, а виноват несобранный пакет.
- **ABI-танц `better-sqlite3` (PC79).** Тесты `electron-app` падают `NODE_MODULE_VERSION 148 ... requires 137`, когда в `build/Release` лежит Electron-ABI. Лечение: подложить Node-ABI из `.verifier-electron/abi-backup/better_sqlite3.node` (+ `better_sqlite3.mc.node` для multiple-ciphers), а Electron-ABI там же лежит как `electron-better_sqlite3*.node` — вернуть перед запуском стенда. Тем же симптомом падают давние `erpEmployeeCardsReplica.guard.test.ts`/`migrate.test.ts` — это состояние машины, а не регресс.
- **`clientOpsArchive.test.ts` («архив с именами UTF-8») на этой машине краснеет в полном прогоне** (антивирус/`7za`, лимит 5 с, одиночно 4.3 с) — вне зоны правки, судить о гейте по нему нельзя.
- **`corepack pnpm -r test` на этой машине — только с `--workspace-concurrency=1`**, и он останавливается на первом красном пакете: после красного добивать пакеты руками.
- **CDP-драйвер: `vis('input[placeholder]')` находит не тот поиск.** Первым в списке идёт поле «Поиск беседы…» из панели чата — оно видимо по размерам, хотя панели на экране нет. Смоук PR-4 из-за этого писал в чат и видел «поиск не фильтрует». Искать поле по фрагменту ЕГО подсказки (`includes('номер РМЗ')`), а не по слову «Поиск».
