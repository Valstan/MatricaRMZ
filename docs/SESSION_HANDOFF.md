**Просьба владельца 07.09 (сделано, ждёт релиза): каскад отбора в «Движении двигателей по заказчикам».** Заказчик → договор → марка: пока родитель пуст, список полный; выбрали заказчиков — в договорах остаются только их договоры, в марках — только встречающиеся у отобранных. Механизм объявляемый (`cascadeFrom` у фильтра + `linkedIds` у опции, чистая `cascadeVisibleOptions` в shared), связи строит `buildFilterCascadeLinks` в клиентском `reports/options.ts` по карточкам двигателей — списка марок у договора в данных нет. Выбранное, выпавшее из каскада, снимается: иначе отчёт фильтровался бы тем, чего в списке уже не видно. **Живого CDP-смоука не было** — фикстуры стенда (одна марка, без договоров) каскад не показывают; проверка глазами — на боевых данных после выката. По просьбе владельца тем же ходом каскад перенесён в отчёт **«Двигатели»** (блок 3 «Отбор»): трио переставлено в порядок ступеней и в пресете, и в секции. Попутно вскрылось, что фильтр «Заказчики» значил в отчётах **разное**: «Движение» дочитывал заказчика с договора, «Двигатели» брал только поле карточки, «Наряды» — без `counterparty_id` и без разделов договора. **Решением владельца 07.09 сведено к одной трактовке** (`resolveEngineCounterpartyId` + `buildContractCounterpartyIndex` в `reports/context.ts`): заказчик ищется всеми доступными путями — поле карточки, при пустом — заказчик договора (и раздел, и легаси-атрибут), — и одинаково во всех отчётах по двигателям. Тест гоняет три отчёта на одной фикстуре и требует одинакового отбора. Класс — GOTCHAS **M111**. **Цифры отчётов «Двигатели», «Стадии» и «Наряды» при отборе по заказчику вырастут** (перестали теряться двигатели с пустой карточкой) — на боевых данных это увидится после выката.

## Следующий шаг

1. **Приёмка первого рабочего дня — вечером понедельника 07.09.** Воскресное наблюдение (см. выше) закрыло всё, что не зависит от парка; осталось ровно то, что зависит.   
   ```
   ssh matricarmz 'tail -5 /var/log/matricarmz/backup.log; sudo journalctl -u matricarmz-backend-primary --since "-24h" | grep -icE "23505|duplicate"'
   ```
   **Приёмка правки поллера уже частично снята в ночь выката и выглядит убедительно:** за 3,5 часа — **76 строк `slower than its tick`** (проход съедал тик и подавлялся флагом) и **два 409**, оба в секунды рестарта primary при выкатах. То есть самоконфликт тика закрыт, а остаток — другой случай: уходящий процесс не отменяет свой опрос на `SIGTERM`, и его запрос пересекается с запросом поднявшегося. Лечится отменой опроса в graceful shutdown; отдельная мелкая правка, не срочная. Утром досмотреть за сутки:
   ```
   ssh matricarmz "sudo journalctl -u matricarmz-backend-primary --since '2026-09-06 21:19' | grep -cE '409|Conflict'; sudo journalctl -u matricarmz-backend-primary --since '2026-09-06 21:19' | grep -c 'slower than its tick'"
   ```
   Сплошность номеров за день (ноль = дыр нет):
   ```
   ssh matricarmz "sudo -u postgres psql -d matricarmz -At -c \"select (max(server_seq)-min(server_seq)+1)-count(*) from ledger_tx_index where server_seq > 1800032;\""
   ```
2. **Снос каталога цепочки — отдельным OK владельца, не раньше вечера 07.09** (план §J2 шаг 7): архив `tar -I zstd` на Я.Диск → сверка размера и хэша → удаление каталога → снятие `MATRICA_LEDGER_DIR` последним. После этого откат невозможен (M30), порядок в плане обязателен.
3. **Переименовать «Рабочий стол» → «Верстак» и разложить скрипты обслуживания** — просьба владельца 07.09, отложена сознательно: 90 мест в интерфейсе перед самым выкатом не трогал. ## Что не сработало

- **Автомерж снова съел коммит, досланный после вооружения.** Это второй раз, запись из прошлого handoff'а не спасла. PR показывал «слит», а мой второй `git push` молча воссоздал ветку с коммитом, которого в `main` нет. Ловится только сверкой по **содержимому** `main` (`git show origin/main:<файл> | grep …`), не по статусу PR. Вооружать автомерж последним действием.
- **Ожидание «процесса нет» вместо «работа закончена».** Ждал ночной бэкап проверкой «нет процесса», а запускал её до времени его старта по cron — условие было истинным сразу и ожидание завершилось бы за пять минут до начала бэкапа. Ждать надо появления записи о **завершении сегодняшним числом**, а не отсутствия процесса.
- **Длинный текст с кавычками через `git commit -m` и `gh pr create --body`.** Двойные кавычки внутри сообщения рвут строку в Git Bash, и `git add` получает куски текста как пути. Сообщения коммитов и тела PR — только через файл (`-F`, `--body-file`).
- **«Парк не заходил ни разу за сутки» чуть не стало симптомом.** Ноль heartbeat'ов за 24 часа выглядит как отказ синхронизации ровно до того момента, как посмотришь на день недели: 06.09 — воскресенье. Прежде чем разбирать тишину, проверить, ожидалась ли она по календарю.
- **Вывод «значит, снаружи» из тишины в собственном логе.** Записал в доки «второй потребитель вне бокса» на основании того, что у secondary нет строк про опрос, — при том что логирование там гейтится по streak. Через сутки после того, как сам же записал M103. Такой вывод требует положительной улики изнутри, а не отсутствия улик.
- **Цифры из AI-отчёта принял за замер.** «~200 конфликтов за 12 часов» из отчёта в чате — артефакт выборки (`limit: 200` за двое суток, поданный в промпт как «за окно»), а мой исходный счёт по журналу (~30/сутки) был верным. Успел сказать владельцу, что мой замер занижен, — не был. Числа из `logAnalysisAgentService` цитировать нельзя, пока не починен `:190/:200`.
- Грабли вынесены в [`GOTCHAS.md`](GOTCHAS.md), а не сюда: **M105** (предел строки V8 у файла состояния), **M106** (`pgrep -f` через ssh находит саму ssh-команду), **M107** (два генератора номеров против одного первичного ключа), **M108** (409 у `getUpdates` — второй потребитель токена, а не потеря пакетов).
