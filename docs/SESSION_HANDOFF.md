## Контекст

- **Ключевой факт замера (меняет акцент PR-1):** кэш страниц помогает **записи** pull, а не чтениям. Upsert 2000 строк с двумя индексами: 56.1 мс (max 205.3) → 9.2 мс (max 15.3). Чтение 240k строк: 160.6 → 158.0 мс, plaintext столько же — время уходит на материализацию строк в JS, расшифровка не при чём. Обещать «списки в разы быстрее» нельзя.
- **Вторая болезнь, которую кэш не лечит:** 25 страниц перечитывают свои списки по общему пульсу после каждого синка (`ui/services/liveDataService.ts`, `hooks/useLiveDataRefresh.ts`) — это PR-3.
- **Прод:** `3.92.0`, оба порта отвечают порознь (M100), `/updates/status` → `3.92.0`, `lastError: null`. Диск прода — 82% (1.8 ГБ свободно).
- **Открытых PR:** нет (PR-1 ещё не открыт — ветка локальная).
- **Замеры** лежат вне репо: `%TEMP%/opencode/sqlite-bench{,2,3}/bench.mjs`. В репо их не кладём — воспроизводятся за минуту.
- **Грабли гейта:** на этой машине `-r test` флейкует от перегруза; красный тест вне зоны правки перепроверять одиночным прогоном. `electron-app` целиком (1994 теста) — зелёный.

## Что не сработало

- **Гипотеза «всё в RAM → списки в разы быстрее»** — опровергнута замером (≈2%). Гипотезу проверили до кода, поэтому в PR-1 не попало ложное обещание.
- **Тест «заблокировать поток и поймать паузу»** — нестабилен: гистограмма не фиксирует паузу, если её таймер ещё не тикал. Логику сводки проверяем через инъекцию `readLag`, реальную гистограмму — отдельным тестом жизненного цикла.
