## Что не сработало

- **Имя прода и базы — `matricarmz`; ошибка в одну букву даёт два разных «прод сломался».** `ssh matricrmz` → «Could not resolve hostname» (это не сеть и не fail2ban — просто не найден блок `Host`), `psql -d matricrmz` → `FATAL: database "matricrmz" does not exist` (это не поломка: в списке баз только `matricarmz` + шаблоны, данные на месте — 95 строк в `client_settings`, живой бэкенд держит 5 соединений с `matricarmz` в `pg_stat_activity`). Живое имя БД — дефолт в коде (`backend-api/src/database/db.ts`); канон (`AGENTS.md` §Prod server) пишет верно. В дереве на боксе (`~/MatricaRMZ/backend-api/.env`) встречается устаревшая строка `PGDATABASE=matricrmz` — не путать с живым именем. Сверка: `ssh -G matricarmz` (без сети) и `sudo -u postgres psql -lqt`.
- **SQL через пайп из PowerShell** (`Get-Content | ssh`) — psql спотыкается о BOM. Рабочая форма: запрос **одной командой** в `ssh '… -c ''…$$литерал$$…'''` (литералы — долларовые, `$` в PowerShell не интерполируется внутри одинарных кавычек).
- **«Нет проверок» ≠ «проверки зелёные».** `gh pr checks` на PR в конфликте с `main` отвечает «no checks reported» — Actions-сьютов не создаётся, workflow не триггерится; это выглядело как «GitHub не реагирует на форс-пуш». Причина — конфликт, снимается ребейзом на свежий `origin/main` (после него проверки идут сразу). Разбор — грабля [M234](gotchas/M234.md). Второе следствие оттуда же: локальный прогон гейта относится к состоянию кода на момент прогона — правка после прогона его обесценивает (так уехала тип-ошибка, которую поймал только CI).
- **`gh api graphql` режет permission-гейт**, `gh api -X POST …/merge` → 404. Слияние — только `gh pr merge <n> --squash --body-file <UTF-8 файл>` (заголовок брать из самого PR).
- **Живая приёмка кнопок строки ленты не проверялась на живом клиенте:** заведённая ручная запись **не доезжает до ленты** (в `operations.list` строка есть, в панели «История ремонта» — нет). Воспроизводится и на **неизменённом** коде (A/B через `git stash`: штатный `cdp-manual-entry-undo.mjs` падает теми же 6 шагами) ⇒ это **не регресс** промта #141; причина не исследована (вне границ задачи) ⇒ инвариант «кнопки строки в левой ячейке» держит сторож по исходнику, а не живой смоук.
- **Sync-гейт закрытия красный после squash-merge** («branch has no upstream — never pushed»), хотя всё в `main` ⇒ локальная ветка удаляется принудительно, линия переводится на базу от `origin/main`; грабля [M232](gotchas/M232.md).
- **`gh pr merge --squash --delete-branch` сносит рабочий worktree (26.11.2026, полоса 6).** gh сначала пробует удалить папку worktree (ветка выбрана в ней) — операция не атомарна: `.git`-файл worktree и корневые dot-папки (`.claude/`, `.github/`, `.gitignore`) удаляются, а остальное остаётся (на Windows удаление обрывается на занятых процессами файлах). Итог: в своей рабочей папке `git` начинает видеть **главный клон** (с чужими правками соседней линии!), индекс пуст (`ls-files` → 0). Починка: `.git`-файл + админ-каталог `.git/worktrees/<имя>/` (`HEAD`, `commondir`, `gitdir`), `git read-tree HEAD`, `git checkout HEAD -- <снесённые пути>`; грабля [M237](gotchas/M237.md). Правило: `gh pr merge --squash` **без** `--delete-branch`, ветку сносить руками после остановки стенда (backend держит `better_sqlite3.node` — пока он жив, `rm`/копирование ABI-файла падают).

- **Карта нумерации по идентификатору строки слепа к показу.** Строка без `id` в карту не попадает (номер пустой), две строки с одинаковым `id` делят один номер ⇒ сквозной счёт идёт с пропусками и повторами. Поэтому показ берёт номер **по позиции**, а карта (`productionProgramNumbering`) осталась только для поиска по `id`. На боевых данных ПП таких строк не было (пустых — 0, одинаковых — 0) ⇒ гипотеза отвергнута **замером**, а не правдоподобием.
- **Прод-зонд: `>` в PowerShell пишет UTF-16** — выгрузка запроса/JSON читалась как мусор. Рабочий путь — запись через node (`fs.writeFileSync`) либо base64-обёртка; прод — `ssh matricarmz` + `sudo -u postgres psql -d matricarmz` (без `.env`).
- **Чтение локальных кредов PG гейт хоста режет** (`HOST_CAPABILITY_UNAVAILABLE`) — локальный PG берём через документированный логин в [`machines/parts/PC79/toolchain.md`](machines/parts/PC79/toolchain.md).
- **Коммит уехал в чужую ветку** (грабля [M238](gotchas/M238.md)) — в папке полосы была выбрана чужая ветка. Починка: `git branch -f <своя> <sha>` (сохранить коммит) + `git reset --soft HEAD~1` в чужом воркауте (её файлы не трогаются) + `git restore --source=HEAD --staged --worktree -- docs/…` (убрать свои правки из чужого дерева).
- **Гейт режет запись вне рабочего каталога** (`HOST_CAPABILITY_UNAVAILABLE` на `write`/`edit` и на `git worktree remove` за пределами папки сессии) ⇒ свой закрывающий воркаут держим **внутри** папки полосы (`.claude/worktrees/m3/faza/.claude/worktrees/…` — под правилом `.gitignore` `.claude/*`, в чужом `git status` не виден).
