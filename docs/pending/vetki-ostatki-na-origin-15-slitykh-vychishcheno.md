# 🟢 Ветки-остатки на origin: 15 слитых вычищено, причина найдена 🗓 since:2026-09-04

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг»

**Было:** на origin висели 15 веток кроме `main` — от 31.07 до 04.09, включая четыре `release/*`. Запись в `SESSION_HANDOFF` «веток кроме `main` нет» врала с июля: её переписывали из шаблона, не проверяя.

**Причина, а не симптом:** у репозитория **выключена** настройка `delete_branch_on_merge` (проверено `gh api repos/Valstan/MatricaRMZ --jq .delete_branch_on_merge` → `false`). Поэтому ветка остаётся, даже когда PR смержен; флаг `--delete-branch` у `gh pr merge` спасает только те мержи, где его не съел сетевой обрыв. **Решение владельца:** включать ли автоудаление — это настройка репозитория, из сессии не трогаю; включается на GitHub в Settings → General → «Automatically delete head branches». Пока выключено, остатки будут копиться снова.

**Как проверялось, что удалять безопасно** (три независимых признака, все обязаны сойтись — по одному судить нельзя):

1. **У каждой ветки есть смерженный PR.** `gh pr list --state all --limit 400 --json headRefName,state,mergedAt` один раз, потом сопоставление локально — 15 из 15 `MERGED`.
2. **Вершина ветки старше момента мержа.** Это ключевой признак: если в ветку дописали после мержа, дописанного в `main` нет. Разброс по всем 15 — от 2 до 89 минут ДО мержа, ни одной дописанной.
3. **Squash-коммит каждого PR лежит в истории `main`** (`git log origin/main --grep "(#NNN)$"`) — 15 из 15 найдены.

**Чем НЕ проверять:** `git merge-base --is-ancestor` и `git diff main...branch` при squash-мерже **вводят в заблуждение** — вершина ветки не является предком `main`, а трёхточечный диф показывает изменения, которые давно в `main`. По ним все 15 веток выглядели «не слитыми», хотя слиты все.

**⚠️ Грабля, на которую наступили прямо здесь: проверка «пусто» неотличима от «проверка не состоялась».** После удаления я проверил остаток так:

```bash
rem=$(git ls-remote --heads origin | grep -v '^main$')
[ -z "$rem" ] && echo "осталась только main"
```

`ls-remote` в тот момент не дошёл до GitHub (сеть, M101), вернул пустоту — и условие отрапортовало **чистоту, которой не было**: одна ветка осталась и всплыла только при следующем взгляде. Отчёт владельцу уже ушёл с неверным «осталась только main». Правильная форма отделяет отказ команды от пустого результата:

```bash
out=$(git ls-remote --heads origin 2>&1); rc=$?
if [ $rc -ne 0 ] || [ -z "$out" ]; then echo "ПРОВЕРКА НЕ СОСТОЯЛАСЬ — не считать за чистоту"; else echo "$out"; fi
```

Тот же класс, что «`ssh … || break` — это не „дождался“, а „сеть моргнула“» и «`grep -c` в логе — не признак отсутствия алертов». Общее правило: **пустой вывод — это ответ только тогда, когда команда завершилась успешно.** При нестабильной сети (а она тут нестабильна, M101) проверять надо и код возврата.

**Сделано 04.09:** 15 веток удалены через `gh api -X DELETE repos/.../git/refs/heads/<branch>`; на origin осталась только `main` (перепроверено формой выше, с разбором кода возврата). Коммиты не потеряны — они достижимы со страниц смерженных PR, а четыре релизных точки держат теги (`v2026.731.1440`, `v3.8.0`, `v3.9.0`, `v3.12.0` — проверено, все на месте). Два удаления с первого раза «упали» на обрыве до GitHub, а не на отказе — повтор показал, что одно из них на самом деле прошло. Локальные `refs/remotes/origin/*` после этого чистятся `git remote prune origin`, а застрявший от обрыва ref — `git update-ref -d refs/remotes/origin/<branch>`.
