## Что осталось

### 1. Остальные списки (механика готова, подключение — 4 строки на список)

Кнопка живёт в общем поле списка (`components/ToolbarSearchField.tsx`) — она уже рисуется
везде, где список передал поля. Осталось сказать списку, какая у него сущность:

```tsx
const { choice, fieldId, select } = useSearchField({ kind: 'engine', query });
// в ToolbarSearchField: fieldOptions={searchFieldOptionsForRows('engine', rows)}
//               fieldChoice={choice} onSelectField={select}
// в фильтре:       { fieldId } (useListDeepFilter) либо matchesQueryInSearchField(...)
```

Списки, где кнопки ещё нет: контрагенты, сотрудники, наряды, заявки на снабжение,
номенклатура и её справочник, складские документы, этапы работ, марки двигателей, свойства
инструмента, отчёты (двигатели / на заводе / этапы).

**Оговорка:** список, который ищет НА СЕРВЕРЕ (номенклатура и складские документы по
страницам), сузить по полю нечем — сервер поле не называет (см. п. 2). Для таких списков
кнопку либо не включать, либо сначала научить сервер.

### 2. Серверный слой (L3) и глубокий поиск по содержимому карточек (L2.5) — решение владельца

При выбранном поле эти два слоя **выключены**, и об этом сказано прямо в интерфейсе
(`SEARCH_FIELD_NARROWED_NOTE`): оба ищут по всем значениям сразу и **не называют поле
совпадения**, а суженная выдача не должна содержать вхождений вне выбранного поля.

Варианты (выбор владельца):

- **а) оставить как есть** — сужение работает по строкам списка и справочников (L1/L2),
  серверный слой в суженной выдаче не участвует. Сделано так.
- **б) учить слои называть поле** — L2.5 отдаёт id сущностей; L3 (`backend-api/src/routes/search.ts`
  → `globalSearchService.ts`) ищет по тяжёлым справочникам на сервере. Это работа на
  бэкенде: каждый источник должен отдавать своё поле совпадения, и тогда серверный слой
  можно будет включить в суженную выдачу.

### 3. Проверка живьём (CDP) — не гонялась

Правка UI (кнопка в палитре и в списках) — живой смоук на стенде `verifier-electron` не
прогонялся: стенд общий с двумя параллельными линиями, а смена ABI `better-sqlite3` в
общем `node_modules` уронила бы их тестовые прогоны. Гейты CI (typecheck + lint + тесты)
зелёные; приёмка глазами владельца — за ним.

## Грабли

- **Поле реестра ≠ поле строки.** Реестр описывает сущность вообще (палитра, справочники,
  список), а строка списка может быть другой формы: у контракта в справочнике есть
  `displayName`, а в строке списка — `number` и `counterparty`. Поле, которого в строке нет,
  обещает **пустую выдачу**, а оператор решит, что поиск сломан. Поэтому кнопка спрашивает
  реестр через `searchFieldOptionsForRows(kind, rows)` — предлагает только те поля, что в
  строках есть. Сторож `SearchField.guard.test.ts` проверяет и то, что каждое поле реестра
  достижимо хотя бы в одной из форм строки.
- **Выбор поля не переживает перезапуск списка** — как и режим «точный / ≈ Похожие»: ушёл со
  списка — выбор сброшен. Сброс ВИДЕН (кнопка снова «Искать везде»), иначе перенос выбора на
  другой список дал бы пустую выдачу молча.
- **Уровни палитры и выбор поля — разные вещи.** Уровни («Авто / Эта страница / Справочники /
  Сервер») отвечают «откуда смотреть», поле — «по какому полю». Сливать их в один
  переключатель нельзя: «Искать везде» перестанет означать «везде».
