# Шаг 8a релиза (APK на прод) нечем проверить, и его уже пропускали 🗓 since:2026-08-25 🟡

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг»

На выкате v3.11.0 выяснилось, что **APK версии 3.10.0 на прод не заливали вовсе**: в `/opt/matricarmz/updates/android/` последним лежал 3.9.0. Планшеты сутки стояли на предыдущей версии, и заметить это было неоткуда — health-check и `/updates/status` показывают только Windows-канал, а Диспетчер честно отвечает `up-to-date`, потому что для него свежайший APK — тот, что лежит. Нужен либо шаг проверки в релизном чек-листе («`/dispatcher/update-plan?platform=android&current=<предыдущая>` обязан вернуть `update`»), либо перенос заливки APK в сам workflow. Родственная грабля — **M92** (`gh release download` молча отдаёт обрезанный файл), из-за неё же битый APK легко уехал бы на прод незамеченным.

**Прогон 02.11 (релиз 3.99.0): шаг отработал, но вручную.** Шаг 8a в релизном процессе есть (добавлен 17.08, `eb85650a`) и в этот раз сработал: APK `MatricaRMZ-3.99.0.apk` залит через `scp` (48 303 865 Б), `update-plan?platform=android&current=3.98.0` вернул `action: update` с sha256, сверенным с локально скачанным (`5ca16340…1584be`) — то есть проверка на обрезанный файл (M92) сделана; прежний `3.98.0.apk` снесён по решению владельца, `/updates/file/MatricaRMZ-3.98.0.apk` отдаёт 404.

**Хвост:** пункт остаётся открытым именно потому, что заливка APK не автоматизирована — её до сих пор делает человек, и пропустить шаг по-прежнему можно (как на v3.11.0). Нужен перенос заливки в workflow или гейт в CI, который не даст смержить релиз без `android-vX.Y.Z`-тега и без проверки `update-plan`.
