# 🟡 Утиль и этапы ремонта: решения владельца (промт #170) — состав главных деталей, блокировка по неглавным деталям, возврат детали из локации «утиль» 🗓 since:2026-11-26

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг и отложенное»
**План:** [util-stage-gate-2026-11](../plans/util-stage-gate-2026-11.md)

Задача #170 («Утиль: ремонт не начинаем, пока деталь не отремонтирована») сделана по коду.
Открыты четыре вопроса — три из них закрыты по умолчанию (см. план), и ждут подтверждения.

## 1. Главные детали (критерий утиля) — состав зафиксирован, но подтвердить

Владелец называет **картер, головку и блок**; набор критериев в программе до промта
наполнялся одними картерами (историческое правило D-#9). Сделано: набор по умолчанию
расширен на `картер`/`головка`/`блок` (`shared/src/domain/scrapCriterion.ts`,
`SCRAP_MAIN_PART_NAME_PARTS`), флаг наполнения версионирован, чтобы состав дошёл до парка.

**Что нужно от владельца:** подтвердить, что головка и блок — критерий утиля (их уход в
утиль уводит двигатель в утиль), или оставить критерием только картер. Точный перечень
деталей владелец не помнит, поэтому набор остаётся открытым: одна галка на карточке детали.

**Чего не делать:** не добавлять критерии задним числом в код — набор живёт на карточках
деталей (EAV-атрибут `scrap_criterion`), а не в программе.

## 2. Блокировать по всем утильным деталям или только по главным

Сделано по предложению промта: **блокирует только утиль двигателя** (глобальный статус
карточки или уход главной детали в утиль), а по неглавной утильной детали (маслонасос)
этап заводится, оператору показывается подсказка «В дефектовке есть утильная деталь».

**Альтернатива (решение за владельцем):** блокировать этап по ЛЮБОЙ утильной детали в
дефектовке. Тогда подсказка не нужна, но ремонт двигателя с утильным маслонасосом станет
невозможен без «отремонтирована» по каждой детали.

## 3. Возврат детали в ремонтный фонд — обратное складское движение

«Деталь отремонтирована» зовёт существующий занос в ремонтный фонд
(`warehouse:repairFund:intake`). НО: при проведении дефектовки деталь УШЛА в локацию
«утиль» (движение делает сервер, `defectConductService`), и обратного движения из этой
локации занос не делает — остаток в локации «утиль» остаётся.

**Что нужно:** решение владельца — считать ли это расхождением и доводить ли его
перепроведением акта дефектовки (деталь помечается «годна к ремонту» → сторно прихода по
утилю и приход в ремфонд), или оставить как есть (деталь физически в утиле, а учёт —
в ремфонде). До решения — как есть, с предупреждением в окне.

## 4. Живая приёмка и перебор расхождений

- Окно гейта глазами владельца: оба исхода, подсказка по неглавной детали.
- Перебор расхождений на боевых данных: IPC `engines:scrap:consistency` (двигатели, у
  которых в текущем заезде есть и этап ремонта, и статус утиль). Список разбирает владелец:
  по каждому — кто главнее по факту.
