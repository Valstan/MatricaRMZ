# ⏳ Клиент не отправлял атрибуты нового сотрудника — причина найдена, класс лечится 🗓 since:2026-11-16

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «⏳ Ждёт внешнего окна / события»

**Источник:** инцидент от 16.11.2026 — оператор СИЗ (машина PC63): «когда добавила сотрудника, он перестал отображаться в карточках спецодежды». План нити — [`siz-client-pending-attributes-2026-11.md`](../plans/siz-client-pending-attributes-2026-11.md).

## Что установлено

- Клиент создал сотрудника и **опубликовал на сервер только строку `entities`**; строки `attribute_values` (ФИО, должность, табельный, даты) не ушли — на её машине они висят в `pending` (617 строк на 16.11, у остальных клиентов парка — ноль).
- Сервер их никогда не видел: в логах сервиса нет ни одного отказа по `attribute_values`.
- Серверное зеркало СИЗ берёт сотрудников по ФИО → без атрибутов нет строки зеркала → **нет карточки СИЗ ни у кого**. Под потерями — 6 сотрудников, заведённых этим клиентом (05–12.11).
- Автолечение сервера видит `critical` по этой машине, но скипает его (`daily_budget_exceeded`) — починки не происходит.

## Что сделано 16.11.2026

- Скрипт восстановления [`restoreEmployeesFromDrafts.ts`](../../backend-api/src/scripts/restoreEmployeesFromDrafts.ts): атрибуты берутся из recovery-черновиков самих операторов (данные принадлежат им), пишутся обычным путём синка; dry-run по умолчанию. Данные сотрудников в доки не переносятся.
- **Восстановление на проде (по решению владельца):** dry-run показал 6 сотрудников и 77 строк атрибутов; запись через журнал синка (seq 6052676); зеркало СИЗ — dry-run «создать 6, погасить 0», затем создано 6 карточек и опубликовано (seq 6052677–6052682). Проверка: атрибуты на сервере по всем шестерым, «сотрудников без атрибутов» — 0, живых строк зеркала 435 → 441. Клиенты тянут изменения штатно (PC26 уже на 6052682).
- **Переносимая находка отправлена в мозг** письмом [`2026-11-16-client-pending-queue-and-manual-repair.md`](../../mailbox/to-brain/2026-11-16-client-pending-queue-and-manual-repair.md): клиентский снимок — окно в очередь клиента; ручная команда починки в обход дневного бюджета autoheal.

## Что осталось

1. ~~**Причина в клиенте** — почему строки `attribute_values` не уходили (617 → 548 → 0 после ремонта)~~ — **найдена 25.11.2026** (см. ниже и граблю [M227](../gotchas/M227.md)). Класс лечится: сервер называет отброс по LWW, клиент не возвращает подтверждённые сервером строки в очередь.
2. ~~**Сторож, чтобы не повторялось молча**~~ — **сделан 16.11.2026**: клиент показывает застрявшие pending-строки (порог 15 мин), сервер при `critical` помечает отложенное лечение (`deferred`) и поднимает тревогу владельцу, в «Диагностике клиентов» видно очередь и причину отсрочки. План — [`stuck-pending-guard-2026-11.md`](../plans/_archive/stuck-pending-guard-2026-11.md).

## Разбор 25.11.2026: та же машина, тот же класс (4 строки)

- **Симптом:** алерт «очередь застряла» на PC63 каждые 10–30 минут; 4 строки `attribute_values`, `updated_at` = 17.11 13:12:17 (карточка сотрудника «Викулов Александр Анатольевич» — `birth_date` и `hire_date`), `errorCount` = 0. Данные **на сервере были** (те же значения и та же метка времени, seq 6290505/6290506), курсор pull'а стоял на голове журнала.
- **Что исключили:** права (ни одного `server.authz.denied`), битые ссылки (нет `server.sync.reference_denied`), конфликт по seq (нет `sync_conflict`), отказ по LWW на уровне ID (в журналах обоих инстансов пусто). Сервер строки **не отклонял**.
- **Причина (грабля [M227](../gotchas/M227.md)):** сервер для совпадающего содержимого (no-op) не меняет номер строки ⇒ pull её не привозит ⇒ у клиента строка навсегда остаётся «synced без номера» ⇒ клиентское самолечение `requeueUnconfirmedRows` возвращает её в `pending` по кругу. Плюс на сервере отброс по LWW на уровне ПАРЫ шёл молча (без записи в `skipped`).
- **Ремонт машины (25.11.2026, по решению владельца):** команда `force_full_pull_v2` (тот же путь, что 16.11) — пересборка реплики из сервера. Приёмка: снимок 14:05:02 — `attribute_values` pendingCount **4 → 0**, stuckCount 0, errorCount 0; реплика после пересборки совпала с сервером (440 сотрудников, 2568 двигателей, 4976 сущностей); тревоги по PC63 прекратились (последняя — 13:26, до ремонта).
- **Класс лечится кодом** (правка с граблей M227): сервер называет отброс по LWW (`lww_rejected`), клиент помнит подтверждённые сервером строки и не возвращает их в очередь, тревога в чат идёт от владельца комнаты тревог (раньше отказ по членству глушил отчёт оператора).
- **Отдельно:** шум тревоги (окно анти-флуда живёт в памяти инстанса, а инстансов два) — [`alyarm-zastryavshej-ocheredi-flood-mezhdu-instansami.md`](alyarm-zastryavshej-ocheredi-flood-mezhdu-instansami.md).

## Ремонт клиента PC63 (16.11.2026, по решению владельца)

- Штатная команда починки поставлена серверным механизмом (`client_settings.sync_request_type`): `force_full_pull_v2` — пересборка реплики из сервера. `reset_sync_state_and_pull` не подошёл: он только сбрасывает курсор, очередь не разгребает; `reinstall` — команда внешнего watchdog'а, приложение её не исполняет.
- Клиент подтвердил: **ackStatus = ok** (12:07:09). Снимок после ремонта: `attribute_values` pendingCount **0** (было 617 → 548 → 0), errorCount 0, локальных строк 53 659 → 52 671. Autoheal-сигнал: **critical → observe** (driftCount 5 → 2, driftRatio 0.45 → 0.18), действие больше не требуется.
- Данные шестерых восстановленных на сервере до ремонта — ремонт их не снёс.
