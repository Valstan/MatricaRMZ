# 🟡 Обобщённые позиции: три PR-кандидата после E2-доклада 🗓 since:2026-09-17

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг»

Памятка «как работать родителями сегодня» — `docs/WAREHOUSE.md` §«Обобщённая позиция и варианты». Реализация — по слову владельца, каждый пункт своим PR.

- **🟡 Импорт базового списка съедает родителя.** `backend-api/src/scripts/importBasePartsList.ts`, блок «In-place присвоение артикула»: существующая деталь с тем же именем и пустым артикулом получает первый артикул из списка; `parent_nomenclature_id` не проверяется, и родитель с вариантами теряет статус. ✅ Усыновление закрыто кодом: `selectAdoptions` пропускает строку-родителя (`loadParentIds` по `parent_nomenclature_id`) и печатает «родитель пропущен» в dry-run и в apply; запуск скрипта переведён на entry-guard, `selectAdoptions` под unit-тестом, dry-run прогнан на dev-БД. Остаток: артикулы пропущенного родителя создаются обычными деталями — вариантами под неё их заводит человек (автосборка вариантов в разовом скрипте — отдельная работа).
- **🟡 `part_id` строки листа без правила «родитель или вариант».** Пикер деталей в актах (`RepairChecklistPanel`) родства не знает — одна деталь ложится в лист и родителем, и вариантом; отчёты и требование в снабжение видят две позиции. Сначала решение владельца (лист хранит родителя, вариант — уточнение при выдаче?), затем правило в `shared/src/domain/engineInventoryLines.ts` + пикер со свёрткой вариантов (`collapseNomenclatureVariants` уже есть в `ui/utils/nomenclatureParent.ts`).
- **🟡 Остатки агрегируются только сводом.** «Свод по обобщённым» в остатках — представление; регистры, резерв и требование считают родителя и вариант разными позициями. Лечение: агрегат по родителю в сервисе остатков/резерва (`warehouseService.ts`, прогноз уже раскрывает родителя на варианты — `warehouseForecastService.ts:856`), чтобы приход на вариант закрывал потребность в родителе.
