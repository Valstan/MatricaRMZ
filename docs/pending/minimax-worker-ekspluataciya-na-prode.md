## 1. Главный блокер — токен пула в комнате — ✅ СДЕЛАНО 22.11.2026

(read-only → `403`). На боксе лежит только read-only `SECRETS_TOKEN`, и **пишущий токен на бокс

### Блок команд (исправлен пред-полётом 22.11.2026, вторая сессия)

```bash
# 0. каталог профилей аккаунтов: /opt/minimax-accounts НЕ существует, а /opt принадлежит root —
#    юнит воркера работает от valstan и сам этот каталог создать не может (иначе первая же
#    аренда упадёт на materializeProfile → тихий уход на DeepSeek)
sudo mkdir -p /opt/minimax-accounts && sudo chown valstan:valstan /opt/minimax-accounts
# 1. свежий dist: ворота «один агент за раз» (PR #1904) в выложенном 22.11 dist НЕТ —
#    выкладка в 14:56 шла из артефакта, собранного до #1904 (коммит 15:12).
#    Без этого два одновременных вопроса = два mcode exec (~800 МБ) на 1536 МБ → OOM
bash ~/MatricaRMZ/scripts/prod-ops/deploy-backend.sh
# 2. пин адресов MiniMax (без него агент на боксе не доходит до MiniMax: резолверы бокса
#    отдают недоступные Akamai-адреса — проверено вживью, все 5 хостов таймаутят на 443)
sudo python3 ~/MatricaRMZ/scripts/prod-ops/minimax-dns-pin.py
# 3. юниты: воркер + таймер пина
bash ~/MatricaRMZ/deploy/systemd/install-backend.sh
sudo systemctl enable --now matricarmz-minimax-dns-pin.timer
sudo systemctl start matricarmz-minimax-dns-pin.service
sudo systemctl enable --now matricarmz-minimax-worker.service
# 4. включить звено — ПОСЛЕ успешного прогона воркера (иначе аккаунты пула тратятся впустую).
#    Именно sed, не echo >>: файл /etc/matricarmz/matricarmz.env принадлежит root:valstan (640) —
#    сервисный пользователь в него не пишет, а echo >> упал бы с Permission denied
sudo sed -i 's/^MATRICA_AI_PROVIDER=.*/MATRICA_AI_PROVIDER=minimax/' /etc/matricarmz/matricarmz.env
sudo systemctl restart matricarmz-backend-primary.service
```

**Проверка после шага 3:** `curl -fsS http://127.0.0.1:3010/health` → `{"ok":true,"pool":"configured",…}`,

### Пред-полёт 22.11.2026 (вторая сессия, MiniMax Code) — что сверено вживью

**Зелёное (проверено на боксе):** пин-скрипт в режиме `--check` находит живые адреса для всех
пяти хостов; MiniMax Code CLI 0.7.4 на месте; в env бокса есть `SECRETS_TOKEN` и `SECRETS_VAULT_URL`
(токен пула берётся из комнаты read-only, отдельной переменной не нужно); транспорт бэкенда
дополнительных переменных не требует (`MATRICA_MINIMAX_WORKER_URL` и токен воркера имеют дефолты,
совпадающие с дефолтами юнита); `MATRICA_AI_PROVIDER=deepseek` — **звено ещё не включено**, файл env
не менялся с 19.11; оба инстанса бэкенда `active`, юнитов MiniMax на боксе нет, пина в `/etc/hosts`
нет.

**Красное (три находки, все три тихо ломали бы нитку):**

1. **Выложенный `dist` старше ворот #1904.** В `backend-api/dist/minimaxWorker/server.js` на боксе
   нет ни `createAgentGate`, ни `agentsActive` — то есть сборка до коммита 7105a1a7 (15:12), тогда
   как выкладка 22.11 шла в 14:56. Включать воркер на этом dist — значит разрешить два одновременных
   `mcode exec` (~380 МБ каждый) на боксе в 1536 МБ без swap ⇒ OOM-killer снимает крупнейший процесс
   (ровно тот класс, что #1904 и закрывает). Поэтому шаг 1 в блоке — **свежая выкладка dist**
   (`deploy-backend.sh` берёт последний успешный артефакт `backend-dist` с main; он уже включает
   #1904), и только после неё — запуск воркера.
2. **`/opt/minimax-accounts` не существует, `/opt` — root.** Юнит работает от `valstan`
   (`User=__MATRICA_USER__`), поэтому каталог профилей он не создаст: `materializeProfile` упадёт
   на `mkdir` с EACCES → ответ 502 → fail-open на DeepSeek. То есть «воркер включён, а ИИваныч всё
   равно отвечает DeepSeek'ом» — тихий отказ, который выглядел бы как «пул не даёт аккаунт».
3. **Файл env владельцу не принадлежит.** `/etc/matricarmz/matricarmz.env` — `root:valstan`, режим
   640: `echo '…' >> …` от сервисного пользователя упал бы с Permission denied. Запись — через
   `sudo sed -i` (заодно меняет значение, а не добавляет вторую строку с тем же ключом).

**Граница гейта в этой сессии (второй рантайм):** гейт отказал не только на записи в системные пути,
но и на **штатных скриптах репозитория** — `bash scripts/prod-ops/deploy-backend.sh` и
`bash deploy/systemd/install-backend.sh` (оба через ssh). Ответ гейта:
`HOST_CAPABILITY_UNAVAILABLE: this Runtime host cannot prompt for permission`. Read-only ssh,
`git pull`, `curl`, `npm i -g --prefix ~/.local` проходят. Обходить нельзя ⇒ весь блок — владельцу;
слово владельца в том же ходе снимает блок (грабля **M213**).

**Живой прогон уже сделан (22.11.2026):** воркер поднялся вручную с бокса, запрос дошёл до пула и получил
честный отказ `503 {"error":"no_free_accounts","reason":"pool_empty"}` — контур живой, пул на сегодня
исчерпан (141 аккаунт, 124 использованы сегодня, 138 закреплены за потребителями). Первый аккаунт
появится в окне вендорского сброса (МСК 00:00/03:00) — это механика пула, не наш блокер.

## 3. Замер RAM — до включения звена

Контейнер **1536 МБ, swap запрещён ядром**; рядом postgres, два инстанса бэкенда и nginx.
У Сарафана `mcode exec` — пик 381 МБ по node-процессам, и там воркер один раз убивался по OOM.
Потолок кучи CLI вынесен в конфиг воркера: `MINIMAX_NODE_MAX_OLD_SPACE_MB` (по умолчанию 320).
Ворота «один агент за раз» (#1904) — вторая защита: два CLI-процесса одновременно не поднимутся.

**Замер делает сессия** — одной командой на боксе:
`bash scripts/prod-ops/measure-minimax-worker-ram.sh` (смоук — `measure-minimax-worker-ram.test.sh`,
12 проверок, гоняется в CI). Скрипт снимает RSS во время запроса к воркеру, печатает пик по агенту и
по воркеру и смотрит `dmesg`; `--dry-run` проверяет окружение, не тратя аккаунт пула. Ядро должно не
снять процессы: в отчёте — `ядро процессы не снимало (чисто)`, а код возврата не 3.

Включение — **пункт 4 блока выше** (`sudo sed -i` по `MATRICA_AI_PROVIDER`). **Рестартить оба

**Порядок после выкладки фикса:** выкладка → `sed` → рестарт primary → рестарт secondary →
живой вопрос оператора.

**Приёмка — ✅ пройдена 22.11 в части «пул пуст» (воркер не ответил → ушли на DeepSeek, ответ
пришёл, `answerSource=deepseek`, а не 400).** Ждём часть «пул дал аккаунт»:
- в журнале воркера — `minimax worker: ответ готов` с id взятого аккаунта;
- в `ai_chat_requests.answer_source` — `engine` (ответил воркер);
- при пустом пуле — честный отказ воркера (`503 pool_empty`) и уход на DeepSeek, **а не 500 и не 400**

- в `/health` воркера — `agentsActive`/`agentsQueued` (доказательство, что ворота #1904 на месте).

**Пул пуст до вендорского сброса (МСК 00:00/03:00)** ⇒ первый честный ответ `engine` ждёт после
полуночи; до этого приёмка идёт по пути «воркер не ответил → ушли на DeepSeek», и это правильное
поведение, а не поломка.
