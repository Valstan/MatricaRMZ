## 1. Главный блокер — токен пула в комнате — ✅ СДЕЛАНО 22.11.2026

Пулу нужен `Authorization: Bearer skm_…` — **токен комнаты с правом записи**
(read-only → `403`). На боксе лежит только read-only `SECRETS_TOKEN`, и **пишущий токен на бокс
не кладём** (зафиксированное решение владельца: комната — то, чем бокс восстанавливают).

**Сделано (22.11.2026, сессия по прямой просьбе владельца):**

- Заведена **служебная комната `matricarmz-minimax`** (self-serve provisioning, имя «MatricaRMZ» —
  чтобы расход пула шёл в тот же проект учёта). Её rw-токен — в комнате `matricarmz` под ключом
  **`KARMAN_MINIMAX_TOKEN`**.
- **Пишущий токен самой комнаты `matricarmz` не используется**: иначе бокс (у него read-доступ)
  добыл бы себе право **записи в комнату восстановления**. Радиус поражения сужен до пустой
  служебной комнаты.
- **Приёмка с бокса:** ключ читается токеном `SECRETS_TOKEN`; `GET /api/secrets/self` этим токеном →
  `slug=matricarmz-minimax`, `canWrite=true`; `POST /api/minimax/renew` с несуществующим
  `account_id` → **404 «Аккаунт не найден в пуле»** — пуль токен принял (read-only дал бы 403),
  аккаунт не израсходован.
- Комната **не «девственная»** (её токен уже использован) ⇒ повторный `provision` на этот slug даст
  409, а не тихо отзовёт наш токен.
- Канон обновлён: `AGENTS.md` §Prod server и `docs/OPERATIONS.md` §8а (список ключей комнаты —
  13, перепроверено вживью).

**Что осталось:** релиз кода на прод, установка юнита, MiniMax Code CLI и DNS-пин на боксе, замер

**Уточнение 22.11.2026 (после живой проверки):** релиз **не нужен** — код воркера уже на боксе
(выкладка `backend-dist`, приёмка 3001/3002/nginx), MiniMax Code CLI 0.7.4 тоже установлен
(`npm i -g --prefix ~/.local @minimax-ai/code`, без root). Остались **три команды, которые не пускает
локальный гейт** (запись в системные пути на проде: `/etc/hosts`, `/etc/systemd/system`,
`/etc/matricarmz/*.env`; гейт не умеет спросить и отказывает — обходить нельзя, тот же класс, что
чистка старого APK):

```bash
# 1. пин адресов MiniMax (без него агент на боксе не доходит до MiniMax: резолверы бокса
#    отдают недоступные Akamai-адреса — проверено вживью, все 5 хостов таймаутят на 443)
sudo python3 ~/MatricaRMZ/scripts/prod-ops/minimax-dns-pin.py
# 2. юниты: воркер + таймер пина
bash ~/MatricaRMZ/deploy/systemd/install-backend.sh
sudo systemctl enable --now matricarmz-minimax-dns-pin.timer
sudo systemctl start matricarmz-minimax-dns-pin.service
sudo systemctl enable --now matricarmz-minimax-worker.service
# 3. включить звено — ПОСЛЕ успешного прогона воркера (иначе аккаунты пула тратятся впустую)
echo 'MATRICA_AI_PROVIDER=minimax' >> /etc/matricarmz/matricarmz.env
sudo systemctl restart matricarmz-backend-primary.service
```

**Проверка после шага 2:** `curl -fsS http://127.0.0.1:3010/health` → `{"ok":true,"pool":"configured",…}`.

**Живой прогон уже сделан (22.11.2026):** воркер поднялся вручную с бокса, запрос дошёл до пула и получил
честный отказ `503 {"error":"no_free_accounts","reason":"pool_empty"}` — контур живой, пул на сегодня

появится в окне вендорского сброса (МСК 00:00/03:00) — это механика пула, не наш блокер.

## 2. Установка на проде (после выката кода с этим PR)

```bash
# от сервисного пользователя, из корня клона
bash deploy/systemd/install-backend.sh          # поставит и юнит воркера
sudo systemctl enable --now matricarmz-minimax-worker.service
curl -fsS http://127.0.0.1:3010/health          # {"ok":true,"service":"minimax-worker",…}
```

**Предусловия на боксе:** MiniMax Code CLI (`MINIMAX_CLI`, по умолчанию `mcode`),
каталог профилей (`MINIMAX_ACCOUNTS_DIR`, по умолчанию `/opt/minimax-accounts`),
**DNS-пин MiniMax** (ADR-0017 «Сарафана») и адрес ручек пула
(`KARMAN_MINIMAX_API_URL` либо выводится из `SECRETS_VAULT_URL`).

## 3. Замер RAM — до включения звена

Контейнер **1536 МБ, swap запрещён ядром**; рядом postgres, два инстанса бэкенда и nginx.
У Сарафана `mcode exec` — пик 381 МБ по node-процессам, и там воркер один раз убивался по OOM.
Потолок кучи CLI вынесен в конфиг воркера: `MINIMAX_NODE_MAX_OLD_SPACE_MB` (по умолчанию 320).

**Шаг владельца:** после установки — `systemctl status matricarmz-minimax-worker` + замер RSS
(`ps -o rss= -C node` во время живого вопроса) и убедиться, что ядро не снимает процессы.

## 4. Включение звена и приёмка

```bash
# /etc/matricarmz/matricarmz.env
MATRICA_AI_PROVIDER=minimax
# затем
sudo systemctl restart matricarmz-backend-primary.service
```

Пока переменная не задана, поведение прежнее — DeepSeek напрямую.

**Приёмка (живой вопрос оператора):**
- в журнале воркера — `minimax worker: ответ готов` с id взятого аккаунта;
- в `ai_chat_requests.answer_source` — `engine` (ответил воркер) или `deepseek` (ушли на страхователя);
- при пустом пуле — честный отказ воркера (`503 pool_empty`) и уход на DeepSeek, **а не 500**;
- в журнале бэкенда — `llm: воркер MiniMax не ответил — ухожу на платного страхователя`.

## 5. Открытые вопросы к владельцу

   отдельный грант на конкретный ключ/ручки? Сейчас реализовано «токен в комнате» — тем же приёмом,
   что и `MAX_ALERT_TOKEN`.
2. **Когда включать звено:** сразу после установки или после первого живого прогона на тестовом
