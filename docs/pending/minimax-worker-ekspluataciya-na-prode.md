# ⏳ MiniMax-воркер на проде: код готов, остались шаги владельца 🗓 since:2026-11-22

**Нитка:** промт КАРМАНА `#56` + план `#57` («MiniMax-воркер на проде Матрицы РМЗ для ИИваныча»).
**Код слит в `main` (PR #1900, 22.11 13:58 МСК)** — воркер, транспорт бэкенда и юнит systemd;
остались шаги владельца ниже (план — [`docs/plans/minimax-worker-for-iivanych-2026-11.md`](../plans/minimax-worker-for-iivanych-2026-11.md)).

**Что именно осталось за владельцем и почему это нельзя сделать из сессии:**
прод без слов владельца не трогаем (постулаты 17/30), а выдача токена с правом записи —
это действие в комнате Кармана, которое может сделать только человек.

## 1. Главный блокер — токен пула в комнате

Пулу нужен `Authorization: Bearer skm_…` — **токен комнаты с правом записи**
(read-only → `403`). На боксе лежит только read-only `SECRETS_TOKEN`, и **пишущий токен на бокс
не кладём** (зафиксированное решение владельца: комната — то, чем бокс восстанавливают).

**Шаг владельца:** в комнате `matricarmz` положить ключ **`KARMAN_MINIMAX_TOKEN`** — токен
комнаты Кармана с правом записи.

- Рантайм читает комнату **сам** (`backend-api/src/services/karmanVaultClient.ts`, кэш 5 минут) —
  править `/etc/matricarmz/matricarmz.env` **не нужно**; перезапускается только воркер.
- Без токена воркер отвечает честно: `503 token_missing` с указанием ключа, а бэкенд уходит
  на платного страхователя (DeepSeek) — вопросы операторов при этом не теряются.

## 2. Установка на проде (после выката кода с этим PR)

```bash
# от сервисного пользователя, из корня клона
bash deploy/systemd/install-backend.sh          # поставит и юнит воркера
sudo systemctl enable --now matricarmz-minimax-worker.service
curl -fsS http://127.0.0.1:3010/health          # {"ok":true,"service":"minimax-worker",…}
```

**Предусловия на боксе:** MiniMax Code CLI (`MINIMAX_CLI`, по умолчанию `mcode`),
каталог профилей (`MINIMAX_ACCOUNTS_DIR`, по умолчанию `/opt/minimax-accounts`),
**DNS-пин MiniMax** (ADR-0017 «Сарафана») и адрес ручек пула
(`KARMAN_MINIMAX_API_URL` либо выводится из `SECRETS_VAULT_URL`).

## 3. Замер RAM — до включения звена

Контейнер **1536 МБ, swap запрещён ядром**; рядом postgres, два инстанса бэкенда и nginx.
У Сарафана `mcode exec` — пик 381 МБ по node-процессам, и там воркер один раз убивался по OOM.
Потолок кучи CLI вынесен в конфиг воркера: `MINIMAX_NODE_MAX_OLD_SPACE_MB` (по умолчанию 320).

**Шаг владельца:** после установки — `systemctl status matricarmz-minimax-worker` + замер RSS
(`ps -o rss= -C node` во время живого вопроса) и убедиться, что ядро не снимает процессы.

## 4. Включение звена и приёмка

```bash
# /etc/matricarmz/matricarmz.env
MATRICA_AI_PROVIDER=minimax
# затем
sudo systemctl restart matricarmz-backend-primary.service
```

Пока переменная не задана, поведение прежнее — DeepSeek напрямую.

**Приёмка (живой вопрос оператора):**
- в журнале воркера — `minimax worker: ответ готов` с id взятого аккаунта;
- в `ai_chat_requests.answer_source` — `engine` (ответил воркер) или `deepseek` (ушли на страхователя);
- при пустом пуле — честный отказ воркера (`503 pool_empty`) и уход на DeepSeek, **а не 500**;
- в журнале бэкенда — `llm: воркер MiniMax не ответил — ухожу на платного страхователя`.

## 5. Открытые вопросы к владельцу

1. **Форма сервисного гранта:** достаточно ли токена в комнате (`KARMAN_MINIMAX_TOKEN`), или нужен
   отдельный грант на конкретный ключ/ручки? Сейчас реализовано «токен в комнате» — тем же приёмом,
   что и `MAX_ALERT_TOKEN`.
2. **Когда включать звено:** сразу после установки или после первого живого прогона на тестовом
   вопросе? По умолчанию оставляем `MATRICA_AI_PROVIDER` как есть (DeepSeek), пока владелец не скажет.
3. **Бюджет очков:** у Сарафана пул общий и тратится на посты. Нужно ли ограничивать воркер по
   частоте (например, не чаще раза в N минут на аккаунт), или хватит естественной очереди вопросов?
