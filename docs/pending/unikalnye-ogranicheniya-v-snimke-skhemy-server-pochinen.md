# 🟡 Уникальные ограничения в снимке схемы: сервер починен и выкачен, клиент пока только отчитывается 🗓 since:2026-08-30

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг и отложенное»

`getSyncSchemaSnapshot` собирает уникальные индексы запросом с `array_agg(a.attname)`. Тип результата — `name[]`, и node-postgres такой массив **не разбирает**: строка приходит как `"{code}"`. Потребитель проверяет `Array.isArray(row.columns)`, получает false и **отбрасывает запись**. Проверено на проде: `uniqueConstraints` пуст у ВСЕХ 20 таблиц снимка, включая первичные ключи, хотя сам SQL-запрос в psql возвращает строки нормально.

**Следствие:** `repairLocalSyncTables` на клиенте никогда не дедуплицировал по серверным unique — он молча уходил в локальный `PRAGMA index_list`. Гейт, который годами ничего не охранял.

**Отдельно снята прежняя формулировка этого пункта.** 2026-08-30 здесь было записано, что ремонт реплики схлопывал позиции номенклатуры с пустым артикулом (168 живых строк на проде). **Это неверно:** механизм требует, чтобы сервер объявил unique, а он не объявлял никогда. Клиентский индекс `erp_nomenclature_code_uq` частичный с шага миграций 10→11, поэтому локальный фолбэк тоже не схлопывал. Ошибка родилась из чтения кода без проверки того, что реально приезжает по проводу.

**Шаг 1 сделан 04.09 (PR «fix(sync): unique constraints reach the client»):** сервер отдаёт `array_agg(a.attname::text)`, потребитель принимает и текстовую форму `"{a,b}"` (`pgArrayColumns`, тест-сторож). **Unique уходят только клиентам ≥ 3.20.0** (`SCHEMA_UNIQUE_SAFE_CLIENT_VERSION`, `?client_version=`): клиент хеширует снимок вместе с unique, и их появление сменило бы хеш всему парку (до v3.5.0 — пересборка базы), а сборки до 3.20.0 применяют дедуп без режима отчёта. Остальным — пусто, как было; `users:publisher-check` запрашивает unique явно. Клиент: `UNIQUE_DEDUP_APPLY = false` в `syncService.ts` — по серверным unique дедуп **только отчитывается** (`repair <table> unique dedup REPORT ONLY would delete id=… (survivor=…, key=…)` в локальном логе + одна строка `warn` в серверный `client-*.log` с `action=repair_unique_dedup_report` и разбивкой по таблицам). Локальный фолбэк (`PRAGMA index_list`) для таблиц без серверных unique работает как прежде. **Шаг 2 — после релиза клиента и недели отчётов парка:** `grep repair_unique_dedup_report backend-api/logs/client-*.log` на боксе; если удаляемое — только настоящие дубли, перевести флаг в `true` отдельным релизом. Фильтр частичных индексов (`indpred IS NULL`) на месте — без него дедуп схлопывал бы легальные дубли (пустой артикул, освобождённый логин).
