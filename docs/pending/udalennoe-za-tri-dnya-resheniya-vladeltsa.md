# 🟡 «Удалённое за 3 дня»: решения владельца (промт #169) 🗓 since:2026-11-26

🗓 since:2026-11-26 · нитка «Журнал действий: конкретный объект и ссылка; удалённое за 3 дня» (ветка `feat/audit-object-links-deleted-history-2026-11-26`)

**Что сделано кодом:** вкладка «Удалённое» (рядом с «Журналом» и «Изменениями») — список удалённого за три дня с кнопками «Посмотреть» (без восстановления), «Восстановить» и «Удалить окончательно» (с подтверждением); в строке видно, что удалено, когда, **кем**, в каком разделе и куда объект вернётся («Двигатели → Д-100»). Журнал действий теперь называет конкретный объект и раздел, а у удалённого объекта ссылки нет — в строке сказано словами. **Замер на живых данных (26.11.2026):** стендовая БД, все 1756 строк `audit_log` — раздел «Прочее» **0** (было 57), подпись «Выполнил действие» **0**; живой сервер (`GET /admin/audit/list`) — «Прочее» **0** из 1756 (было 1592), строк с названным объектом **189** (было 7), за последние сутки «Прочее» **0**. Правило не знало ключей карточек СИЗ, номенклатуры, листа ремонта и документа склада; теперь раздел строки берётся из реестра вкладок программы и считается **на показе** (иначе у старых строк «Прочее» осталось бы навсегда).

**Развилки промта, закрытые по умолчанию** (по правилу §«Промты проекта — раздел КАРМАНА»: «закрыть по умолчанию, записать в PENDING, вынести владельцу»):

| Развилка | Решение по умолчанию | Почему так |
|---|---|---|
| «Три дня» — срок хранения или окно показа | **И то, и другое**: показываем записи с `deletedAt` за последние 3 дня; старше — удаляем окончательно перед сборкой списка | критерий приёмки промта требует и «не показываются», и «удаляются окончательно» |
| Что попадает в историю удалений | **Виды, где в программе есть мягкое удаление и имя**: двигатели, договоры, контрагенты, заявки, наряды, справочники, сотрудники, файлы | промт просит «по всем типам объектов»; перечень — в `shared/src/domain/deletedObjects.ts` |
| Кто может восстанавливать | **Новое право `deleted.restore`**, по умолчанию только суперадмин (поимённо, как `audit.view`) | восстановление меняет данные |
| Восстановление может быть неполным | **Честно предупреждаем** в подтверждении: вернётся объект, связи могут остаться битыми | риск назван в промте до реализации |
| «Удалить окончательно» — след в журнале | **След остаётся** в журнале действий, из списка запись исчезает | журнал — не место для тихой потери |
| Клиент без сервера | **Список пустой с честной причиной** (список и восстановление собирает сервер) | сервер отбивает клиентский «undelete» без номера журнала (`applyPushBatch`) |

**Что осталось открытым (ждёт владельца):**

1. **Покрытие видов объектов.** Сейчас в списке: двигатели, договоры, контрагенты, заявки, наряды, записи справочника, сотрудники (EAV), файлы. **Не покрыты:** детали (`directory_parts`), инструменты (`directory_tools`), документы склада (`erp_document_headers`), карточки СИЗ (`erp_employee_cards`) — для них у клиента нет готового payload-конвертера в журнал изменений, а второй конвертер заводить нельзя (глобальная линза). Нужен выбор владельца: расширять покрытие или оставить как есть.
2. **Срок хранения журнала действий.** Открытие карточек пишет в журнал много строк; срок хранения и разбивка по типам не заданы (риск из промта). Сейчас журнал растёт без уборки.
3. **Проставить вид пачкой.** Вид (ГОЗ / гражданка) почти ни у кого не заполнен — замер 25.11.2026: из 61 неудалённого заказчика вид не заполнен у 59. Отдельная работа, в этот промт не входила.
4. **Полевая приёмка глазами владельца.** CDP-смоук на стенде не гонялся (стенд — общий ресурс машины, соседняя полоса его занимала).
