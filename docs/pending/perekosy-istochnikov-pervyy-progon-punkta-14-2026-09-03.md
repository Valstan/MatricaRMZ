# 🟡 Перекосы источников — первый прогон пункта 14 (2026-09-03) 🗓 since:2026-09-03

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг и отложенное»

Проверка «читает ли модуль то хранилище, куда пишут» после переездов EAV→строгие таблицы. Метод: шесть линз по коду + опровергатели на каждую находку + сверка с прод-данными (read-only). Прод-цифры на 03.09: `operations` — `engine_inventory` 2293 живых, `defect` 11 живых / 1625 удалённых, `completeness` 21 / 1623; EAV-кейспейсы `part_engine_brand` 707, `part` 129, `workshop_ref` 7, `warehouse_ref` 6, типа `workshop` нет вовсе; `directory_parts` 1087 живых, из них 1036 с brand-links; `erp_engine_assembly_bom` 7 (все active+default) и 24 живых brand-link; сотрудников 408, с `workshop_id` 266, с `department_id` 144, **только с цехом 264**.

**Закрыто в этом же PR** (каждое — с красным тестом до правки): разрез зарплатного свода (цех + подразделение, было только `department_id` → 264 из 408 в «(не указано)»); фильтр «Марка двигателя» в «Плане закупок по нормам» (читал колонку, снесённую миграцией 0047 → пустой обязательный фильтр, теперь 24 марки); гейт ссылок при удалении марки (не видел `directory_parts.brand_links_json` → отпускал марку с 1036 деталями как «без связанных»); «Справочники» больше не предлагают заводить цех/склад в мёртвых EAV-типах (так появились 7+6 сирот); поле «Цех» в браузерной админке (резолвилось перечислением сущностей типа, которого нет → всегда пусто, теперь по `/workshops`); «Аудит двойного учёта» печатал UUID вместо названия детали.

**Открытое — нужно решение владельца или заметная переделка:**

1. 🔴 **«Потребность в деталях» построена на почти мёртвом источнике.** `presets/warehouse.ts` (`buildPartsDemandReport`) читает живые `operations` типов `defect`/`completeness` — их на проде 32 против 2293 актов `engine_inventory`, куда переехала дефектовка. Отчёт снабжения печатает ~1,4 % данных (не пусто — потому и не заметили). Перевод на `engine_inventory` + `answers.engine_inventory_items` — вопрос семантики: что считать потребностью (утиль, недокомплект, оба), поэтому не делал сам.
2. 🟡 **«Совместимость деталей по маркам»** (`presets/catalogs.ts:411`) строится из EAV `part_engine_brand` (707 связей — снимок на момент миграции) вместо `directory_parts.brand_links_json` (1036 деталей со связями). Деталь, привязанную после перехода, в отчёте не найти. Переделка — на REST-номенклатуру, как у соседей по файлу.
3. 🟡 **«Журнал движений деталей»: номер и тип документа всегда пустые.** `presets/warehouse.ts:387` читает локальную `erp_document_headers`, которую создаёт клиентская миграция 0006 и не наполняет ни один писатель; на сервере 55 строк, доступны только по REST.
4. 🟡 **Серверный `isScrap` почти потерял слагаемое от дефектовки:** `getDefectChecklistScrapMap` фильтрует `operationType='defect'` (11 живых). Флаг не всегда ложен — `isScrapAttr`/`isStatusRejected` работают, — но двигатель, забракованный в новом флоу и не отмеченный атрибутом, покажется «не забракован». Решение: один предикат утиля на клиент, веб-админку и сервер.
5. 🟡 **Денормализованные счётчики деталей марки** (`parts_kinds_count`/`parts_total_qty`): копия обновляется только с двух экранов, живой счёт есть рядом. Снести копию или пересчитывать в единственной точке записи — решение владельца.
6. 🟢 Фильтровать зарплатный свод по цеху (сейчас фильтр только по подразделениям, `optionsSource: 'departments'`); разрез уже считается по цеху.

**Опровергнуто проверкой** (не багов): кнопка «Новый склад» в карточке номенклатуры недостижима (`canCreate` не выставляется), поэтому мёртвых складов ею не наплодить; «Прайс-лист услуг» неверное имя детали показать не может; зеркало доступов в карточке сотрудника **не протухшее** — сегодня EAV и есть база записи, а строгая таблица её производная (переезд обеих — на R4b, как и записано в плане).

**Вторая половина прогона (те же сутки, 26 находок → 12 подтверждено, 6 спорных, 8 опровергнуто).** Опровергнуты все находки вида «таблица мертва»: у них нет читателя, а значит и расходиться нечему (`change_log` 162 тыс. строк, `client_settings_bak_20260717` (снесена с прода 31.10), `erp_stock_reservations`, `t_bulk_*`) — это мусор на диске, он в 🔴-пункте про диск, а не перекос.

**Закрыто в PR той же сессии** (каждое — со сторожем и красной проверкой): утечка закрытых нарядов и серверный `permissions-view` (см. 🔴 выше); проба «реплика налита» теперь спрашивает обе таблицы, а не одни `users`; клиентский гейт разделов держал контрагентов под именем `counterparty`, которого в базе нет (живой тип — `customer`), из-за чего гейт на их карточках не срабатывал вовсе; вкладка «Журнал» в браузерной админке открывалась по праву `updates.use`, а сервер требует `audit.view` — три её запроса отвечали 403; вкладка «Группы марок» не входила ни в один раздел, хотя её данные закрыты «Производством» — плитка показывалась тем, кому раздел не выдан, и открывалась отказом.

**Открытое из второй половины — решение владельца или заметная переделка:**

7. 🔴 **Реестр норм ремонта на проде пуст, а два экрана на нём стоят.** `repair_norm_sets`/`_lines`/`_brand_links` — 0 строк: перенос `warehouse:migrate-bom-norms` (В-59 519 строк, В-84 539, УТД-20 276) не прогонялся. Следствие стало видимым только после починки фильтра в первой половине: экономист впервые может выбрать марку в «Плане закупок по нормам» — и получает пустую таблицу; страница «Нормы ремонта» пуста всегда. **Решение:** прогнать перенос (dry-run → `--apply`) или снять отчёт. Независимо от выбора — расщепить подпись «набор норм не найден ИЛИ сервер недоступен»: сейчас она врёт одному из двух случаев.
8. 🟡 **Складские регистры доезжают до клиента только холодным снимком** — клиентские отчёты по складу («Оборотная ведомость», «Готовность к сборке») считают по фотографии на день установки машины и расходятся с экраном «Склад → Остатки» ровно на все документы, проведённые с тех пор.
9. 🟡 **«Кадровый реестр сотрудников» у табельщика пуст:** период по умолчанию — текущий месяц, а `hire_date` в реплике оператора есть только на нём самом (`pullReadFilter`). Причина невидима: человек читает это как «данных нет».
10. 🟡 **Офлайн-фоллбек «Склад → Остатки» фильтрует по коду склада как по uuid** — при обрыве связи список молча пуст, колонка «Склад» пуста всегда. Рядом: офлайн-список документов читает клиентские `erp_document_headers/lines`, которые никто не наполняет, и отвечает «успех, 0 строк» вместо «связи нет».
11. 🟡 **Синк-контракт vs клиентская схема:** apply молча выбрасывает шесть полей `erp_nomenclature`, которые контракт кладёт в провод (`directory_kind`, `directory_ref_id` и др.) — офлайн-фильтры по ним пусты; `component_type_id` есть на сервере с миграции 0053, но в контракте его нет вовсе, и карточка офлайн шлёт `null` явно.
12. 🟡 **Список деталей в карточке марки** включается правом `parts.edit`, а пишется через `erp.dictionary.edit`: технолог правит и получает «не сохранилось по N деталям».
13. 🟡 **Владельца наряда клиент берёт из `performed_by`, сервер — из `row_owners`**, сверки нет: наряд без строки в `row_owners` серверный конструктор отчётов показывает всем. Разово заполнить и читать одно поле везде.
