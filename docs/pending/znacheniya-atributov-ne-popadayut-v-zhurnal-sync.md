# ⏳ Значения атрибутов попадают в БД сервера, но не в журнал — клиенты их не видят 🗓 since:2026-11-25

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «⏳ Ждёт внешнего окна / события»

**Источник:** разбор по промту КАРМАНА **#146** («Подсказка выбора контрагента в договоре: новые не видны»), 25.11.2026. Симптом закрыт правкой поля выбора (PR #2029); **этот пункт — про корневую дыру в синке**, из-за которой подписи и значения не доезжают.

## Что установлено (живые данные, прод, 25.11.2026)

- **2 228 из 54 944** живых строк `attribute_values` на сервере имеют `last_server_seq IS NULL` ⇒ они **не попали в журнал** (`ledger_tx_index`) ⇒ pull их клиентам не привозит **никогда**. У `entities` таких строк нет ни одной.
- **Реплики клиентов замерли в один и тот же момент:** у всех машин `tables.attribute_values.maxUpdatedAt` = 1795607871625 (14:57:51 MSK), тогда как на сервере строки были до 14:57:55.993. Новые значения атрибутов (название, ИНН, КПП, адрес) до клиентов не доехали ни разу.
- **Кандидат в коде:** правило «no-op» (`isUnchangedAttributeValueRow` / `findUnchangedAttributeValueRows` в `backend-api/src/services/sync/syncWriteService.ts`) сравнивает строку **по паре** (`entity_id` + `attribute_def_id`), а не по id. Пара уже есть на сервере (возможно, под другим id) ⇒ клиентская строка выпадает из журнала ⇒ её id никогда не становится известен машинам. Второй кандидат — remap по паре в `applyPushBatch`. Точный путь «в БД без журнала» дописать не удалось.
- Правило no-op само по себе нужно (журнал — лог изменений; без него одна машина раздувала журнал на 3.6 млн записей в сутки, инцидент 03.11.2026) ⇒ **менять надо аккуратно**: сравнение по id + явная передача серверного id.

## Что осталось (решение за владельцем)

1. **Правило no-op — по id, а не по паре** (или по паре, но с записью id серверной строки в журнал). Проверяемо: после правки `select count(*) from attribute_values where deleted_at is null and last_server_seq is null` на проде идёт к нулю, а журнал не пухнет (счётчик записей по одной машине — как в инциденте 03.11).
2. **Бэкфилл уже накопленного:** строки, не попавшие в журнал, до клиентов не приедут никогда — их надо разово завести в журнал (или пересобрать реплики через `force_full_pull_v2` после починки — тогда значения приедут из БД).
3. **Сторож на будущее:** «строка в БД без `last_server_seq`» ⇒ событие в «Критические события» (сейчас видно только по факту «подсказка не работает»).

**Не сделано:** правок на сервере не делали (журнал — опасная зона, решение за владельцем), бэкфилл не накатывали, прод-выкатки этого пункта не было.

**Смежное:** грабля [M228](../gotchas/M228.md) — «в БД есть» и «клиент это видит» — разные утверждения; проверять надо номер в журнале, а не наличие строки в таблице.
