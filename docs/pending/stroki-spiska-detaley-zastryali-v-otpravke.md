## Что нашлось

1. **Строки ушли на сервер и лежат там.** Клиентский `updated_at` этих строк = 23.11 09:06:21
   (это и есть «самая старая» в алерте). Таких строк — **541**, и она пушила их **2164 раза**
   (4 попытки на строку). Все 541 **есть** в `erp_engine_inventory_lines` на сервере —
   **541 из 541** (сверка по `ledger_tx_index.row_id`).
2. **Застрял не push, а LWW.** У **всех 541** строк серверная копия **новее** клиентской
   (`server_newer = 541`, `equal = 0`) ⇒ каждая отправка отвергается как устаревшая. Запись
   идёт через `onConflictDoUpdate` с условием `updated_at <= excluded.updated_at` — это LWW,
   а не слепой INSERT, поэтому 23505 по этой таблице **невозможен**; в серверном журнале
   23–24.11 её `client_id` не упоминается вовсе.
3. **Отвергнутая строка не снимает `pending` на клиенте.** Клиент шлёт её снова и снова: по
   одной строке (`9c74afdc…`) в журнале **12 отправок** — 4 в 09:06:21 и ещё 8 с 14:21:58 до
   14:27:09, причём **payload не менялся** (`updated_at` в нём один и тот же) ⇒ это ретрай, а не
   новые правки. Серверная копия этой строки — 14:35:09, то есть новее клиентской.
   ⇒ **Класс бага:** «сервер отверг строку как устаревшую ⇒ клиент не снимает `pending` ⇒
   бесконечный повтор той же строки». Кандидат в бэклог; лечится **в клиенте** (снятие
   `pending` по подтверждённому отвержению), а не прод-записью.
   **Класс шире алерта:** строк, у которых клиентская версия старше серверной, у неё сейчас
   **775** (из всех, что она пушила с 23.11), а не только 541 из алерта.
4. **Pull на этой Android-машине не отработал ни разу.** `sync_state`: `last_pulled_server_seq = 0`,
   `last_pulled_at` — пусто, при этом `last_pushed_at` есть ⇒ push ходит, pull — нет.
   В её клиентских логах на сервере: `TypeError: Failed to fetch` (23.11 и 24.11 10:49:53 /
   10:52:29), `sync deferred: offline` (23.11 17:20–18:06, вход другого оператора),
   `slow sync run: 335194ms pulled:0 pushed:0`.
5. **Массовость:** по всем 13 Android-машинам парка pull отработал лишь **на двух** (август и
   ноябрь) ⇒ это не её частный случай, а общая беда планшетного парка. Снимков диагностики
   (`scope='client'`) с Android-машин на сервере — **0**: их шлёт только win32-парк.
6. **Вероятная причина непроходящего pull — объём (гипотеза, не факт).** На проде
   `erp_engine_inventory_lines` = **456 542 строки / 297 МБ**; сирот (строки без листа) — 0.
   Для планшетной реплики такой объём — тяжёлый pull. Связано с
   [парком, который скачивает 209 МБ строк](park-skachaet-209-mb-strok-kotorymi-poka-ne-umeet.md)
   и [строгой таблицей списка деталей](spisok-detaley-dvigatelya-strogaya-tablitsa-erp-engine.md).
7. **Данные целы, а её листы целы:** все её `operation_id` (205 шт.) есть в `operations`,
   orphan-строк в таблице нет.

## Второй симптом того же класса: история ремонта с планшета не уходит на сервер (25.11.2026)

**Промт КАРМАНА #112 + план #114.** Симптом владельца: на планшете история ремонта видна,
на стационарах — нет, на сервер не уходит. Это **тот же класс** («строка создана локально,
а на сервер не уехала»), только в другой таблице — `operations` вместо
`erp_engine_inventory_lines`, и с другим набором причин.

**Что сделано по коду (24–25.11.2026, PR линии 1):**

1. **LWW-отказ назван.** Сервер больше не отбрасывает устаревшую строку молча: отказ
   приходит с причиной `lww_rejected` (`backend-api/src/services/sync/applyPushBatch.ts`,
   константа — `shared/src/domain/syncSkipReasons.ts`). Клиент по этой причине **снимает
   `pending`** (`electron-app/src/main/services/sync/skipReasonPolicy.ts` +
   `syncService.ts`): серверная копия новее, её привезёт pull, а ретрай больше не крутит
   очередь. До правки отказ был безымянным — клиент не знал, что строку больше не надо
   слать (пункт 3 разведки выше).
2. **Конфликт по seq в `operations` больше не роняет весь батч:** per-row отказ вместо
   `sync_conflict` на весь пакет (иначе клиент делал reset + полный pull и начинал заново).
3. **`operations` не вытесняется бюджетом push.** Раньше первые четыре таблицы
   (`entity_types` → `entities` → `attribute_defs` → `attribute_values`) забирали весь
   бюджет 1200 строк, и пачка `operations` не собиралась **вовсе** — без единой ошибки.
   Теперь под `operations` резерв, а отсечение таблицы бюджетом **называется в логе**
   (`push budget cut table=…`), а не молчит.
4. **Гейты сведены в одну правду** (`shared/src/domain/repairHistoryWriteGate.ts`):
   UI-гейт ленты истории, IPC `workSheets:stages:save` и серверный гард смотрят на одно
   и то же право — ручная запись `operations.edit`, метка этапа `work_sheets.edit` **ИЛИ**
   `operations.edit`, строка этапа работ `work_sheets.edit`. Прежний UI-гейт был
   `engines.edit` ⇒ «нажал, а запись не уходит» (см. развилку о семантике гейта ниже).

**Что осталось за владельцем (снимка нет — планшета у нас нет):** чек-лист разбора ниже.

6. **Ожидаемый результат после разбора:** одна из шести точек §5–§9, §12 названа точно.

## Решения владельца и ход работы (25.11.2026, вечер)

**Решения владельца:** (1) снять очередь на боевой машине сейчас — команда
`reset_sync_state_and_pull`; (2) 3.146.0 **не** выкатывать (APK уже на проде, фикса
класса в нём нет) — фикс едет в **3.147.0**; (3) чинить класс и наблюдаемость
Android-парка.

**Команда машине выдана** (слот `client_settings.sync_request`): id
`6e555427-286e-492e-b1c7-0330a343fed1`, тип `reset_sync_state_and_pull`, 25.11 16:41 МСК.
Машина на связи последний раз была 15:25 ⇒ команда дождётся её. Данные на сервере
полные, пересборка реплики их не потеряет.

**Доконена механика класса** (разведка read-only, 16:00–16:40 МСК):

1. **Строки ведёт клиент, а не сервер.** На листе стоит маркер E3 (`rowsIn =
   'erp_engine_inventory_lines'`, `rows` в `meta_json` пуст) ⇒ сервер из JSON строки не
   выводит; 2411 из 2770 листов парка — в режиме E3.
2. **Повторный push неизменённой строки пишет в журнал.** 1244 записи журнала на 622
   строки (по две на строку): каждый повтор создавал новый `last_server_seq` и новую
   запись ⇒ номер строки ехал, и следующий push упирался в «серверная копия новее».
3. **Отказ по устареванию для этой таблицы не был назван** ⇒ уходил с причиной
   `conflict`, а клиент снимает `pending` только по `lww_rejected`.
4. **Правило «журнал — лог ИЗМЕНЕНИЙ» и «отказ назван» были применены к другим
   таблицам** (`attribute_values`, `operations`) — до строк списка деталей руки не
   дошли (M227, продолжение — M230).
5. **Класс был слеп**: снимок клиента снимал 5 таблиц (без строк списка деталей), уходил
   после pull'а (на машине с провисшим pull'ом — никогда), ошибка отправки глоталась ⇒
   android-парк не прислал ни одного снимка `scope='client'` (0 из 26 524, все с
   win32-префиксами) ⇒ автолечение очередь не видело.

**Взято в работу** (план [`docs/plans/sync-stuck-queue-2026-11.md`](../plans/sync-stuck-queue-2026-11.md),
совет — [`docs/council/2026-11-25-sync-stuck-queue-inventory-lines/`](../council/2026-11-25-sync-stuck-queue-inventory-lines/99-verdict.md)):

- сервер: неизменённая строка не пишется в журнал (общий детектор no-op на реестре
  полей), отказ по устареванию назван `lww_rejected`, одна устаревшая строка не роняет
  push всей машины;
- клиент: снимок уходит из локального сторожа (когда очередь застряла, а цикл синка
  висит), в снимке есть таблица строк списка деталей, отказ отправки логируется на
  сервер;
- релиз 3.147.0 — вместе с PR #2026 (клиент помнит подтверждённые сервером строки).

**Осталось:** полевая приёмка на планшете (снимок `scope='client'` от android-машины
пришёл; очередь не растёт) и релиз 3.147.0.
