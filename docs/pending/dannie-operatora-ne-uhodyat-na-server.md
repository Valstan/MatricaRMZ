## ПРИЧИНА НАЙДЕНА БЕЗ СНИМКА (24.11.2026, read-only разведка на проде)

Клиент оператора найден по снимку парка: **PC63, логин `hapik`, клиент 3.135.0**, на связи
была последний раз **20.11 15:14** (парк сейчас на 3.143.0 — её машина отстаёт на 8 выпусков).

В серверном логе за 20.11 — **ровно одна ошибка записи**, и она про ПП:

```
Failed query: insert into "erp_production_program_rows" (...) values (...)
cause: duplicate key value violates unique constraint "erp_production_program_rows_pkey"
code: 23505, detail: Key (id)=(0bb47d75-…) already exists
severity: ERROR — "backend unhandled rejection"
```

**Что это значит:** дверь плана (`replaceProductionProgramRows`) брала все строки программы
**только живые** (`deleted_at IS NULL`). Строку `0bb47d75…` сняли из плана (мягко удалили
в 14:19), а клиентская реплика отстала и в 14:20 прислала **тот же id** снова. Дверь не
нашла id в выборке и сделала **слепой INSERT** → PostgreSQL отказал по первичному ключу
(23505) → транзакция пала целиком → запрос ушёл необработанным отказом (Express 4 не ловит
отказ async-обработчика) → **у оператора план не сохранялся, а строка в очереди синка
висела и висела** (20.11 11:49 сервер сам поднял алерт «stuck pending: 3 строки»).

**Данные при этом не потерялись:** строка на сервере ЕСТЬ (проверено на проде —
`0bb47d75…`, программа `6689db6f…`, Д12А-525А / 2И12КТ2513, снята из плана 20.11 14:19).
Терялось **сохранение**: каждый её следующий пуш падал тем же 23505, и очередь не двигалась.
Версия владельца про «расхождение по структуре базы» **не подтверждается** — в логах нет
ни одного отказа по схеме; схема отдаётся в режиме `warn`.

## Починка причины (сделано 24.11.2026)

- **Дверь ПП:** id, занятый строкой (в том числе мягко удалённой), ведёт себя как
  обновление, а мягко удалённая строка **восстанавливается** — вместо слепого INSERT.
  Чистое правило вынесено в функцию `planProductionProgramRowWrite` (проверяется без БД).
- **Честная ошибка вместо висящего отказа:** роут `PUT /production-program/:id/rows`
  ловит ошибку базы и отвечает внятным текстом, а не выпускает «unhandled rejection».
- **Сторожи:** `backend-api/src/tests/productionProgramService.test.ts` — правило
  (вставка / обновление / восстановление) + проверка, что дверь берёт ВСЕ строки
  программы, включая мягко удалённые, и что роут ловит ошибку.
- **Смоук на стенде — ПРОГНАН (24.11.2026), 9/9 PASS.** Сценарий 20.11 воспроизведён на
  локальной БД через HTTP-дверь (правка серверная, Electron-клиент не нужен): план →
  снятие строки → повторная отправка набора с отставшей строкой → **сохранение проходит,
  строка возвращается в план, нумерация п/п сплошная**. **Негативный контроль:** тот же
  смоук на коде **без** фикса падает — запрос **зависает** (таймаут 20 с), и в серверном
  логе ровно та ошибка, что была 20.11 на проде: `23505 … unhandled rejection`.
  Значит, смоук проверяет именно этот дефект, а не «что-то рядом».
  Смоук: `.verifier-electron/smoke-pp-rows.mjs` (сценарий), запуск — `.verifier-electron/run-pp-smoke.ps1`.

## Что уже сделано по коду — клиент предупреждает оператора (23.11.2026)

**Правило из мандата Мозга («перед сбросом клиент предупреждает оператора, что
неотправленное остаётся в файле экспорта») — сделано.** Пока файл-выгрузка лежит на машине,
оператор видит баннер «Неотправленные данные лежат файлом на этой машине: N записей. На
сервере их нет» + причину (расхождение схемы / прерванная полная загрузка / ручной сброс) +
имена файлов; кнопки «Показать файл в папке» и «Скопировать отчёт» (отчёт **не** уходит на
сервер — данные лежат на машине, администратору нужен сам файл). Причина выгрузки едет в
сам файл (`reason` в JSON). План:
[`docs/plans/pending-export-operator-warning-2026-11.md`](../plans/pending-export-operator-warning-2026-11.md).

**Чего это не делает:** не чинит данные оператора (нужен снимок) и не трогает прод.

## Правила (из плана #83, обязательны к исполнению)

- Не обновлять клиент у оператора до снимка: новая сборка = новая версия схемы клиента =
  возможна пересборка базы.
- Не проталкивать серверные таблицы через клиент: там backstop, и его обход ломает
  владельцев данных (`shared/src/domain/ledgerAuthz.ts`).
- Персональные данные в отчёте — **путь и код, без значений** (D-041).
- Если часть данных безнадёжно восстановима — доложить объём и способ, а не «сделано».

**Порядок работ:** снимок → разбор по трём состояниям (строки в локальной БД / только в
`pending-export` / карантин или серверная таблица) → починка причины → перенос в
штатный путь записи → приёмка (объёмы и контрольные ключи, без выгрузки ПДн) → разбор в
репозиторий и письмо в пул Мозга.
