# ⏳ Претензия 23.11: данные, внесённые оператором в клиент, не уходят на сервер — разбор и спасение 🗓 since:2026-11-23

**Промты КАРМАНА:** **#82** (задача владельца) + **#83** (план).

**Задача владельца (23.11):** у оператора внесено много данных в программу, но они не
уходят на сервер; нужно проверить клиент на машине оператора, вытащить данные и положить
в базу правильно. Версия владельца: «вероятно, расхождение по структуре базы данных».

**План #83 разобран** (три возможные причины различаются: не хватает миграции клиента;
сменилась серверная схема; таблица серверная — клиент её не пишет вовсе). Правильный
путь спасения — **штатная дверь записи домена**, не ручной SQL в проде.

## Что проверено с сервера 23.11 (read-only, без правок)

- **Отказов по схеме в серверном логе нет** (за 18–23.11): есть только `sync schema
  guard ok {"tables":55,"mode":"warn"}` и `client_settings schema compatibility check
  completed`. То есть версия владельца про «расхождение по структуре базы» **в логах
  сервера не подтверждается** — либо сброса базы у этого клиента не было, либо причина
  в другом (серверная таблица / backstop).
- **Схема отдаётся в режиме `warn`**, а не `enforce` ⇒ несовпадение сейчас не отказывает
  в пуше, а предупреждает. Значит «данные не уходят» по другой причине.
- Единственная найденная ошибка пуша за тот же период — 20.11, **дубликат ключа** при
  вставке строки производственной программы (`erp_production_program_rows_pkey`,
  `23505`): клиент повторно прислал строку, которая на сервере уже есть. Это реплей
  после частичной отправки, а не «данные не уходят» целиком.

## Чего не хватает (зависимость от владельца)

1. **Снимок машины оператора** — доступ к машине либо копия папки
   `%APPDATA%\MatricaRMZ\` (`matricarmz.sqlite` + `-wal` + `-shm`,
   `pending-export-*.json`, `ledger/`, логи). **Пока снимка нет — на машине ничего не
   чинить**: пересборка локальной базы удаляет её вместе с неотправленным, и данные
   остаются только в файле экспорта, а реплей может не пройти.
2. **Логин/машина оператора** — чтобы отделить её синк от чужих в общем логе.
3. **Слово владельца на прод-запись** — данные кладутся на сервер только по его слову.

## Правила (из плана #83, обязательны к исполнению)

- Не обновлять клиент у оператора до снимка: новая сборка = новая версия схемы клиента =
  возможна пересборка базы.
- Не проталкивать серверные таблицы через клиент: там backstop, и его обход ломает
  владельцев данных (`shared/src/domain/ledgerAuthz.ts`).
- Персональные данные в отчёте — **путь и код, без значений** (D-041).
- Если часть данных безнадёжно восстановима — доложить объём и способ, а не «сделано».

**Порядок работ:** снимок → разбор по трём состояниям (строки в локальной БД / только в
`pending-export` / карантин или серверная таблица) → починка причины → перенос в
штатный путь записи → приёмка (объёмы и контрольные ключи, без выгрузки ПДн) → разбор в
репозиторий и письмо в пул Мозга.
