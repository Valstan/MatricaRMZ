## СЕРВЕРНАЯ ПРИЧИНА НАЙДЕНА БЕЗ СНИМКА (24.11.2026, read-only разведка на проде)

Клиент оператора найден по снимку парка: **машина PC63, клиент 3.135.0**, на связи была
последний раз **20.11 15:14** (парк сейчас на 3.144.0 — её машина отстаёт на 9 выпусков).

В серверном логе за 20.11 — **ровно две ошибки записи**, и обе про ПП:

```
Failed query: insert into "erp_production_program_rows" (...) values (...)
cause: duplicate key value violates unique constraint "erp_production_program_rows_pkey"
code: 23505, detail: Key (id)=(0bb47d75-…) already exists
severity: ERROR — "backend unhandled rejection"
```

**Что это значит:** дверь плана (`replaceProductionProgramRows`) брала все строки программы
**только живые** (`deleted_at IS NULL`). Строку `0bb47d75…` сняли из плана (мягко удалили
в 14:19), а клиентская реплика отстала и в 14:20 прислала **то же id** снова. Дверь не
нашла id в выборке и сделала **слепой INSERT** → PostgreSQL отказал по первичному ключу
(23505) → транзакция пала целиком → запрос ушёл необработанным отказом (Express 4 не ловит
отказ async-обработчика) → **у оператора план не сохранялся, а строка в очереди синка
висела и висела** (20.11 11:49 сервер сам поднял алерт «stuck pending: 3 строки»).

**Данные при этом не потерялись:** строка на сервере ЕСТЬ (проверено на проде —
`0bb47d75…`, программа `6689db6f…`, Д12А-525А / 2И12КТ2513, снята из плана 20.11 14:19;
на сервере по ней: `deleted_at` задан, `sync_status = synced`, `last_server_seq` есть).
Терялось **сохранение**: каждый её следующий пуш падал тем же 23505, и очередь не двигалась.
Версия владельца про «расхождение по структуре базы» **не подтверждается** — в логах нет
ни одного отказа по схеме; схема отдаётся в режиме `warn`.

**Важно (уточнение 24.11):** эта дверь — **серверная**. Клиент 3.135.0 её не «старее»:
он к ней отношения не имеет. Починка выпущена (v3.144.0 на проде) ⇒ серверный симптом
«план не сохраняется» у неё больше не воспроизводится. Но **этим её проблема не
закрыта** — см. следующий раздел.

## Обновление: правило уточнено (24.11)

Прежнее правило «не обновлять клиент до снимка» держалось на посылке «пересборка локальной
базы удаляет неотправленное». **Для сборок до 19.08 это так. С тех пор в клиенте есть
выгрузка неотправленного в `pending-export-*.json`** (коммит `e47478e7`, PR #633) и её
автореплей после первого успешного синка (`exportPendingRowsToDisk` → `replayPendingExports`).
На 3.135.0 этот механизм **есть** ⇒ обновление **не уничтожает** неотправленное, а
переносит его в файл и (когда sync заработает) возвращает в базу.

Поэтому:

- **Обновлять её машину нужно** — иначе pull не пойдёт никогда (клиентский баг).
- **Снимок до обновления всё равно обязателен** — как страховка: файл-выгрузка лежит
  только на её машине, а добраться до машины можно только через владельца/оператора.
- `updates_enabled = false` на её машине держим **до снимка**, дальше вернуть `true`.
- Если владелец снимок откладывает — можно обновить и без него (данные не пропадут: они
  в файле-выгрузке и на сервере), но тогда забрать сам файл уже не получится.

## Правила (из плана #83, обязательны к исполнению)

- **Снимок — до обновления** (файл-выгрузка лежит только на машине). Само обновление
  неотправленное не уничтожает — выгружает в файл и возвращает реплеем, — но файл без
  доступа к машине не забрать.
- Не проталкивать серверные таблицы через клиент: там backstop, и его обход ломает
  владельцев данных (`shared/src/domain/ledgerAuthz.ts`).
- Персональные данные в отчёте — **путь и код, без значений** (D-041); логины операторов в
  отслеживаемые файлы не пишем (D-041) — отделять её синк можно по машине и `client_id`.
- Если часть данных безнадёжно восстановима — доложить объём и способ, а не «сделано».
