# 🟡 Долги, вскрытые аудитом Telegram-каналов 06.09 🗓 since:2026-09-06

**Раздел:** [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md) → «🟡 Техдолг и отложенное»

Аудит шёл про бота, но нашёл соседние поломки. Ни одна не про бота — все про то, что мы о своих отказах не узнаём.

1. **Счётчик молчащих отказов не может напечататься в принципе.** `logBotPollSilentCounter` (`syncPipelineSupervisorService.ts:246`) пишет обычным `logInfo`, а `utils/logger.ts:16-21` в prod-режиме выбрасывает весь INFO без `{critical:true}`. Плюс структурная ошибка: `lastMetricsLogAt = now` и сброс `lastMetrics*` стоят **выше** отсечки `if (deltaFailures <= 0) return` (`:227-262`), а форс-вызов при каждом восстановлении (`:374`) снова сдвигает окно — счётчик не доживает до своего дедлайна. Это тот самый счётчик, который был заведён, чтобы такие отказы не были молчаливыми.
2. ~~**Ложные числа в AI-отчётах.**~~ — **закрыто 08.09** (успело выстрелить второй раз: ночной алерт доложил «200 сетевых сбоев за 12 часов» при 28 фактических). `criticalEventCount` считается по окну, а не по длине выборки; выборка поднята до 1000 и, если упёрлась в лимит, число помечается `countIsLowerBound` — «не меньше чем»; добавлена разбивка `byCode` (сколько раз за окно случился каждый код), чтобы модели незачем было выводить число из размера списка; `recentLogLines` режется тем же окном; легенда промпта прямо запрещает считать по длине списков. Гарантия — `logAnalysisWindowNumbers.test.ts`.
3. **Мина в логгере:** `utils/logger.ts:11` — значение `MATRICA_LOG_MODE=production` (самое естественное для прода) включает **dev**-режим. Сейчас переменная не задана, мина спящая.
4. **`resolveChatIdByLogin` — второй, невидимый путь к `getUpdates`** (`telegramBotService.ts:123-133`): гейта по роли инстанса нет (в отличие от супервизора), `offset` не передаётся, отказ не логируется совсем. Живёт в обработчике `POST /sync/push`, то есть может сработать на любом инстансе. Минимум — `logWarn` в ветке отказа и гейт `shouldRunBackgroundJobs`.
5. **409 не доходит до владельца:** `criticalEventsService.ts:415-423` даёт ему `warn`/`network`, а нотификатор (`criticalEventsTelegramService.ts:80-86`) шлёт только `fatal` и `error`.
6. ~~**`audit-deps.sh:88`** безусловно печатает «alert sent»~~ — **закрыто 07.09**: `telegram_send` возвращает код доставки, а вызывающий пишет либо «alert sent», либо «ALERT NOT SENT (telegram unavailable)»; находки в любом случае печатаются в лог, то есть при мёртвом канале запись остаётся единственным следом и она есть. Гарантия — смоук `scripts/prod-ops/audit-deps.test.sh` в CI (job `prod-ops-backup`).
7. **Нет отката env у двух ops-скриптов:** `audit-deps.sh:7` и `watch-failed-auth.sh:8` читают строго `~/MatricaRMZ/backend-api/.env` без отката на `/etc/matricarmz/matricarmz.env`, хотя `scripts/prod-ops/README.md:134` обещает откат всем. Исчезнет файл — замолчат тихо.
8. **Второй путь бэкапа без единого канала оповещения:** systemd `matricarmz-nightly-backup.timer` (00:00, `dist/scripts/nightlyBackup.js`, ~41 мин) дублирует cron-овый 03:17, а `grep -c telegram` по нему — 0: его отказ будет молчаливым. Либо подключить алерт, либо выключить как наследие.
9. **Гигиена секрета:** токен видели в `argv` процесса, то есть в `ps` он открыт любому пользователю бокса. Не доказано, что это не был наш собственный диагностический `grep`, — но передавать токен аргументами не стоит нигде.
10. ~~**Бот молча отбрасывает команды «чужого» отправителя и не проверяет свой ответ**~~ — **закрыто 10.09** (кроме `migrate_to_chat_id`, см. конец пункта). Теперь в журнале: `telegram bot ignored a message: sender is not the superadmin` (`chatId`, `chatType`, `fromUsername`, без текста; раз на пару «чат + отправитель» за жизнь процесса), `telegram bot membership changed` (бота добавили/убрали — номер чата виден из апдейта), `telegram bot reply failed` на неудачный ответ команде или кнопке и разовое предупреждение, если у суперадмина нет Telegram-логина (тогда обновления не разбираются вовсе). Гарантия — `syncPipelineBotUpdateTrace.test.ts`. Исходная запись (2026-09-10, стоило владельцу трёх безответных `/sync_chat_id`): `processBotUpdates` (`syncPipelineSupervisorService.ts`) сверяет `from.username` с `telegram_login` карточки суперадмина и при несовпадении делает `continue` без единой строки в журнале — а в карточке оказался не тот логин. `handleCommand` игнорирует результат `sendTelegramMessageToChat`: неудачный ответ тоже бесследен. Минимум — `logWarn` (с `chat.id`, `chat.type`, без текста) на отброшенное сообщение из чата, где бот ещё не отвечал, и на неудачную отправку; заодно логировать `my_chat_member` — это закрывает и способ «взять chat id из апдейта», о котором просил brain (D-083). Там же: `migrate_to_chat_id` (группа → супергруппа) не разбирается нигде.
