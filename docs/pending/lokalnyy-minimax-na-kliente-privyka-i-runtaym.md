# ⏳ Локальный MiniMax на клиенте: код выпущен (v3.142.0), ждём комнату «Кармана», рантайм в CI и смоук на живой машине 🗓 since:2026-11-23

**Нитка:** промты КАРМАНА `#59` (задача) + `#62` (план v2) + решения владельца `#61` (D-243) и `#63` (D-244).
**Код:** PR (эта ветка) — клиентский модуль `electron-app/src/main/services/localMiniMax/`, путь записи
локального ответа (`aiChatPushPolicy.ts`), метки источника ответа (`shared/domain/aiChatSchedule.ts`).
**Зона:** клиент. Серверный воркер MiniMax (промты #56/#57, PR #1900/#1904) не трогали.

## 0. Что починено 25.11.2026 (живой прогон на стенде lane3 нашёл три поломки)

Модуль был выпущен 23.11 без единого живого прогона. Смоук на стенде (backend 3004, CDP 9225)
показал, что **локальный ответ не доезжал до сервера вообще**, и что модуль не смог бы
запуститься на машине парка. Починено три вещи:

1. **Источник ответа терялся в push'е клиента.** Поле в реплике называлось `serverAnswerSource`,
   а общий реестр sync (`shared/src/sync/registry.ts`) берёт поле по имени `answerSource` ⇒
   `answer_source` уезжал на сервер **пустым**, сервер отвергал такой ответ
   (`sync_policy_denied: ai_chat_not_pending`), а вопрос оставался в `processing` до
   `reclaimStale`. Поле переименовано в `answerSource` (колонка SQLite прежняя — `answer_source`,
   миграции не нужно). Сторож `aiChatAnswerSourcePush.test.ts` сверяет имена полей реестра с
   колонками реплики — расхождение теперь ловится тестом, а не молчаливой потерей ответа.
2. **Гонка «ответ готов раньше первого пуша».** Если первый пуш вопроса не дошёл (сервер был
   недоступен, а «Карман» — доступен), ответ приходил в пуше, который для сервера был «новая
   строка», и политика обнуляла ответ ⇒ очки пула потрачены, ответ потерян. Теперь новая строка
   с клиентским источником рождается сразу отвеченной (серверный источник подделать нельзя).
3. **`mcode.cmd` не запускается.** Node не исполняет `.cmd` без `shell` (EINVAL), а `shell`
   открыл бы окно консоли ⇒ модуль на машине парка не ответил бы никогда. Клиент теперь
   находит настоящий JS-вход (сначала одноимённый файл рядом, потом путь внутри shim npm) и
   запускает его **рантайм-node модуля** (`node.exe` из extraResources) — окна нет, `detached`
   по-прежнему выключен (грабля M214).

Заодно: относительные пути внутри bundle (`node`, `mcode`) теперь разрешаются от каталога
самого `config.json` — раньше всегда от resources-каталога, и в dev-режиме модуль объявлялся
«не настроенным»; мост к базе в dev ищется в `electron-app/resources/local-minimax/`.

**Живой прогон 25.11 (стенд lane3):** вопрос → claim → «Карман» → агент → ответ «локальный
модуль ответил на машине оператора» с меткой **«считал этот компьютер»**; на сервере строка
легла как `answered` + `answer_source=local_minimax`; новых видимых окон во время прогона
не появилось (проверено по факту появления, не по факту `spawn`).

## 1. Что сделано (код)

- **Модуль на машине оператора** (`localMiniMax/`):
  - `karmanPool.ts` — клиент «Кармана»: `GET /api/minimax/accounts/available` (заголовки `X-MiniMax-Project`
    = имя клиентской комнаты, `X-MiniMax-Area` = машина в аудите комнаты), `POST /api/minimax/renew`,
    `POST /api/minimax/activations`. Честная пустота (200 + `account: null` + `reason`) отличается от
    поломки и от «нет права записи» (403).
  - `agentProfile.ts` — профиль MiniMax Code: каталоги (`MCODE_CONFIG_DIR`, `MINIMAX_DATA_DIR`,
    `MAVIS_DATA_DIR`) и токен-стор `auth.json`; ключ записи выводится из абсолютного пути каталога
    авторизации (`com.minimax.mcode.oauth.prod.en` + base64url(sha256(путь + "\0" + clientId))).
    `refreshToken` — непустая заглушка: рантайм иначе считает запись битой и отказывается работать.
  - `agentRunner.ts` — молчаливый запуск: `windowsHide: true`, **не** `detached` (грабля M214),
    прокси-переменные вычищены, потолок кучи V8, разбор `exec.result`.
  - `dbBridge.ts` + `resources/local-minimax/matrica-db-mcp.mjs` — read-only доступ агента к локальной
    реплике: базу держит приложение (она зашифрована SQLCipher, ключ под DPAPI — из отдельного
    процесса недоступен), агент спрашивает по именованному каналу Windows (без порта и правила
    брандмауэра); пишущие операторы отбивает сам SQLite.
  - `deepseekClient.ts` — резерв с машины: Anthropic-совместимый эндпойнт DeepSeek, **клиентский**
    ключ (свой баланс, D-244).
  - `localMiniMaxEngine.ts` — оркестратор: claim ленивый (аккаунт берётся на первый вопрос, D-240/
    D-244), цепочка «локальный MiniMax → DeepSeek с клиента → сервер», состояние для панели.
- **Путь записи ответа** (главное техническое, план #62 п. 5): клиент берёт свой вопрос в работу
  (`status=processing` — claim) и кладёт ответ сам; серверная дверь — новая ветка в
  `backend-api/src/services/sync/aiChatPushPolicy.ts` (автор своего `processing`-вопроса пишет
  `answer_text` + `answer_source` из клиентских). Без claim'а серверный воркер ответил бы вторым, и
  платный DeepSeek сгорал бы впустую.
- **Источник ответа**: `answer_source` расширен клиентскими значениями (`local_minimax`,
  `deepseek_client`); серверные `engine`/`deepseek` не тронуты (их писатель — в зоне первой нитки).
- **Панель**: строка статуса показывает, кто считает — «этот компьютер» или сервер; снят прежний
  однозначный «считает сервер».
- **Сторож** `prodOnlyAiChat.guard.test.ts` заменён на `localAiChatBoundary.guard.test.ts`: новая
  граница (локальное звено есть, вопрос всё равно уходит на сервер, claim и ответ — только author's,
  следы opencode по-прежнему снимаются, каталог нового модуля в список сносимых не попал).
- **Гейты зелёные:** `pnpm -r typecheck`, `typecheck:test`, `pnpm -r lint`, тесты — electron-app
  2535, backend-api 1608, shared 2110 (все пакеты по отдельности: на этой машине `pnpm -r test`
  умирает на границе пакетов — грабля из профиля машины).

## 2. Что осталось за владельцем (три шага, ни одного ручного на машине парка)

### Шаг 1. Комната «Кармана» для клиентов — `matricarmz-clients` (D-244)

Клиентский доступ должен быть **отдельной комнатой** с тем же владельцем (тогда тот же пул MiniMax),
а в ней — только клиентский ключ DeepSeek. Продовые ключи (приватный SSH-ключ бокса, Android-keystore,
hotline-секрет) клиентам не достаются.

- В «Кармане» есть self-serve provisioning: `POST /api/secrets/provision` с `Authorization: Bearer
  <VAULT_PROVISION_KEY>` создаёт комнату и **один раз** отдаёт rw-токен.
- **Единственный ручной шаг:** положить `VAULT_PROVISION_KEY` в CI-секреты «Матрицы РМЗ» и один раз
  вызвать provisioning; выданный токен — в CI-секрет. Повторный provisioning вернёт 409 (комната
  живая) — токен хранится в CI-секрете.
- Комната должна называться `matricarmz-clients` (имя в `X-MiniMax-Project` = имя комнаты; иначе
  renew ответит 409 «аккаунт выдан другой комнате»).
- В комнате положить **клиентский** ключ DeepSeek (отдельный от продового).

### Шаг 2. Сборка рантайма в CI (без рук на машине)

**Код выпущен в v3.142.0 (23.11.2026)** — парк получит модуль вместе с программой. Но рантайма
в сборке нет (его кладёт CI, см. ниже), поэтому на машине модуль честно пишет «локальный модуль не
настроен» и считает сервером. Шаг остаётся открытым ровно из-за этого.

Клиентская машина не имеет Node.js, а MiniMax Code требует Node 22.19+. Значит, инсталлятор везёт
рантайм. Конвейер уже разложен:

- `electron-app/build/before-pack.cjs` создаёт каталог `build/local-minimax/` и пустой `config.json`
  (если CI не положил свой) ⇒ сборка без рантайма не падает, а клиент честно пишет «локальный модуль
  не настроен» и считает сервером.
- `extraResources`: `build/local-minimax/**` → `local-minimax/runtime`, `resources/local-minimax/**` →
  `local-minimax/app`.
- **Что должен положить CI** в `electron-app/build/local-minimax/`:
  - `config.json` — `{ karmanUrl, karmanToken, project: "matricarmz-clients", deepseekApiKey, node: "bin/node.exe", mcode: "bin/mcode.js" }`;
  - `bin/` — Node.js (22.19+) и `mcode` из `@minimax-ai/code` (0.7.4 — та версия, на которой снят живой прогон).
- ⚠️ **`mcode` — это JS-вход** (`bin/mcode.js` или настоящий путь к скрипту пакета), а не `mcode.cmd`:
  Node не исполняет `.cmd` без `shell`, а `shell` открыл бы окно консоли. Если CI всё же положит
  shim `.cmd`, клиент сам найдёт JS-вход рядом или внутри shim (`resolveMcodeEntry`) и запустит его
  рантайм-node модуля. Пути внутри `config.json` разрешаются **от каталога самого config.json**.
- ⚠️ `electron-app/build/local-minimax/` в `.gitignore` — **токен в git не попадает никогда**.
- ⚠️ Подпись (ADR-0003): рантайм — это `.exe`/`.dll`/`.node`, их надо подписать тем же контуром, что
  и watchdog; неподписанные файлы Касперский съедает (грабля M94).

### Шаг 3. Смоук на живой машине парка + замер RAM

**Сделано 25.11 на стенде lane3** (живой клиент, живой сервер): вопрос → claim → аккаунт у
«Кармана» → агент → ответ с меткой «считал этот компьютер», на сервере строка
`answered` + `answer_source=local_minimax`, ни одного нового видимого окна. Осталось на боевой
машине парка (у нас её нет):

- Вопрос оператора → ответ **от локального MiniMax** на БОЕВОМ рантайме (не на подделке), метка
  «считал этот компьютер», **ни одного окна** (по факту появления, а не по факту `spawn` — M214).
- Локальный модуль сломан → ответ от prod-MiniMax; он недоступен → DeepSeek с клиента; и с машины
  не достучаться → DeepSeek с сервера; нет сети → **честный отказ оператору**, а не вечное «думает».
- Пул пуст → честный отказ «аккаунты кончились», а не тишина; очки несработанного аккаунта не сгорели
  зря.
- **Замер RAM `mcode exec` на клиентской машине** (пик у «Сарафана» 381 МБ, OOM-прецедент P164):
  замеров по парку не было (D-200). Пока замера нет — ограничение одно: потолок кучи V8 512 МБ в
  окружении прогона.
- **Проверить, доходит ли DeepSeek с РФ-IP** до Anthropic-совместимого эндпойнта (он режется с
  РФ-IP, `docs/ai-chat/DIRECT.md`) — иначе звено «резерв с клиента» не работает вовсе.

## 3. Отклонение от формулировки D-243 — на решение владельца

**D-243 задаёт цепочку:** локальный MiniMax → MiniMax на проде → DeepSeek (с клиента) → DeepSeek
(на проде). Реализовано: **локальный MiniMax → DeepSeek с клиента → сервер** (prod-MiniMax и
DeepSeek сервера — внутри серверного звена).

**Почему так:**

1. **claim и «prod-MiniMax вторым звеном» несовместимы.** Пока клиент держит вопрос
   (`processing`), серверный воркер его не берёт — иначе ответили бы оба. Значит, prod-MiniMax не
   получает шанса, пока вопрос у клиента.
2. **Локальный MiniMax и prod-MiniMax берут аккаунты из ОДНОГО бесплатного пула.** Когда пул пуст,
   второе звено всё равно не ответило бы ⇒ терять нечего.
3. **«DeepSeek с клиента» третьим звеном не получается без серверной координации:** сервер после
   неудачи prod-MiniMax сразу уходит на свой DeepSeek (fail-open, D-243), то есть платный вызов
   успевает раньше клиентского.

**Что это значит на практике:** когда пул MiniMax исчерпан (сейчас он почти всегда исчерпан), клиент
платит **своим** DeepSeek-ключом, а не серверным. Это ровно смысл D-244 №3 («ключ DeepSeek для клиентов
— отдельный: свой баланс, своя ротация; продовый DeepSeek остаётся последним страховочным звеном»).

**Если владелец хочет буквально порядок D-243**, нужна серверная правка: сервер должен ждать
`grace`-окно, прежде чем уходить на свой DeepSeek (иначе клиент не успеет). Это правка в зоне первой
нитки (`llmProvider`/`aiChatAnswerService`) ⇒ в эту нитку не входила.

**Второе отклонение — имена источника ответа.** План #62 п. 6 предлагал значения
`local_minimax` / `minimax_prod` / `deepseek_client` / `deepseek_server`. Серверные два уже названы
`engine` / `deepseek` первой ниткой (#1900) — их писатель в чужой зоне, поэтому оставлены как есть;
добавлены два клиентских. Смысл полон, набор из четырёх.

## 4. Чего в коде нет (и почему)

- **Рантайма в репозитории нет** (см. шаг 2): Node.js и `mcode` — артефакты сборки, в git им не
  место; без них клиент честно живёт в режиме «считает сервер».
- **Живого прогона настоящего MiniMax Code не было**: 25.11 путь прогнан на стенде на ПОДДЕЛКАХ
  (поддельный «Карман», поддельный `mcode`, отдающий `exec.result`) — проверены клиентский путь,
  молчание, запись ответа, push с источником и метка в панели. Настоящий рантайм MiniMax Code и
  настоящий пул аккаунтов «Кармана» не трогались: это боевые ключи и деньги ⇒ шаг 3 на машине парка.
- **MCP-мост к базе проверен юнистом, не на живой реплике**: чтение идёт через настоящий
  better-sqlite3 в приложении, но на зашифрованной боевой базе первый прогон ещё не сделан.
