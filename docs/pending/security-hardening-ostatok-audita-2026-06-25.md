6. **🔴 Доказательство доступа к файлу пишет сам проситель** 🗓 since:2026-08-20, объём уточнён 2026-08-21. `canAccessFile` признаёт доступ, если id файла найден в «контексте, который актор вправе видеть». Беда в том, что почти любой такой контекст **актор создаёт сам**, и предпосылка «надо знать UUID» ничего не стоит: полная таблица `file_assets` отдаётся конструктору отчётов и SQL-тулам ИИваныча по одному `files.view` (`backend-api/src/routes/reports.ts:365-367`, `services/ai/llmTools.ts:626`), а `files.view` и `reports.view` оба входят в базовый набор оператора (`shared/src/domain/permissions.ts:369`).

   **Закрыто 2026-08-21** (этап 0 плана [`desktop-and-human-labels-2026-08`](plans/_archive/desktop-and-human-labels-2026-08.md)): в EAV-ветке (4) свободный текст перестал быть каналом — требуется файловый атрибут, настоящая ссылка на id и право на тип сущности. `full_name`, `ui_profile_json`, самодельный атрибут с произвольным кодом больше не работают.

   **Открыто — тот же класс, четыре канала:**
   - **Ветка 2 (заметки)** `fileAccessService.ts` — своя заметка признаётся доказательством, а `notes` в ledger помечена `open`: пишем `body_json` с чужим id → доступ. Прав сверх базовых не нужно.
   - **Ветка 1 (чат)** — сообщение самому себе с `FileRef` в `payload_json`; `chat_messages` тоже `open` (`shared/src/domain/ledgerAuthz.ts:123`).
   - **Ветка 5 (ИИваныч)** — `question_file_json` авторится клиентом; ограничение только рейт-лимитом.
   - **Ветка 4, остаток** — `attribute_defs` и `entity_types` в ledger `open` (`ledgerAuthz.ts:130-131`), а неизвестный код типа сущности **fail-open** (`:160`) и падает в `default → masterdata.view`. Значит оператор изготавливает свой тип, свой def с кодом `attachments` и корректный `FileRef` — allow-list его пропустит. Плюс проще: `masterdata.edit` разрешает писать `attachments` на любую справочную сущность, а `own_employee` — на свою карточку.

   **Заплатками на ветки это не лечится** — каждая из них обслуживает законный сценарий (файл из чужой заметки, присланный в чат, вложение карточки), и отличить его от подделки на этом слое нечем. Настоящее лечение — **связь несёт происхождение**: строка-доказательство должна помнить, кто её создал, и грант выдаётся, только если это не сам проситель. Это вопрос к схеме связей **Матрицы 4** (переносимая формулировка — brain [#178](../../brain_matrica/cross-project-ideas/ideas/178-access-evidence-the-requester-can-forge.md)).

   **Сужено 2026-08-25 (не закрыто).** Ветки 1 и 2 приведены к той же дисциплине, что уже спасла ветку 4: доказательством считается **поле, которое ФАЙЛ И ЗНАЧИТ**, а не совпадение id где-нибудь в JSON. Заметка разрешает файл только блоком `{kind:'image'|'file', fileId}` (`noteBodyGrantsFileAccess`), сообщение чата — только при `messageType='file'` и `payload.id === fileId` (`chatPayloadGrantsFileAccess`). Что это убрало: id в тексте заметки, id в её ссылке, голый массив id, и — отдельный **случайный** грант — id, попавший в `breadcrumbs` обычной ссылки на раздел (`deep_link` их принимает как свободные строки, и ссылка на экран выдавала доступ к файлу ни за что). Что осталось ровно как было: подделать можно сам файловый блок заметки и саму файловую строку чата — оба пишутся клиентом. То есть **дыра сузилась до одной формы вместо четырёх, но не закрыта**; на «п.6 сделан» это не тянет.

   **Перечисление id: широкий канал закрыт 2026-08-25** (решение владельца). Таблица `file_assets` в конструкторе отчётов и в SQL-тулах ИИваныча (`reports.ts`, `services/ai/llmTools.ts`, `services/ai/analyticsService.ts`) переведена с `files.view` (есть у ЛЮБОГО оператора) на `admin.users.manage` — как прочие служебные таблицы. Админ здесь ничего не выигрывает: он проходит `canAccessFile` безусловно. Это убирает из выдачи id файлов, которых нет ни на одной карточке — из чужого чата, картинок чужих заметок, файлов с чужого Верстака, — то есть ровно те, ради которых самовыдача и затевалась бы.

   **Заодно починен каталог источников.** `GET /reports/builder/meta` не смотрел на актора **вообще**: выборка честно отказывала, а список таблиц с колонками уезжал любому, кто дотянулся до конструктора — вместе с `refresh_tokens`, `permissions`, `chat_messages`, `notes`. Значит одна смена права ничего не изменила бы на глаз: строка «Файлы» осталась бы в списке и отвечала бы отказом при построении. Теперь каталог фильтруется теми же правами, что и выборка.

   **Остались ещё три канала перечисления id — сузить их этой правкой не удалось:**
   - **`attribute_values` в том же конструкторе** (разбор ниже) — отдаёт `valueJson`, где лежат и вложения карточек, и **чужие ярлыки Верстака** (`ui_profile_json`);
   - **`GET /changes`** отдаёт строки с `tableName='file_assets'` и `rowId` = id файла любому обладателю `updates.use` (базовое право оператора), без фильтра по актору. Такие строки создаёт заявочное удаление файла не-владельцем;
   - **локальная реплика.** `ui_profile_json` — обычный EAV-атрибут, `attribute_values` синкается всем, а построчный фильтр pull'а режет только `password_hash` и пару HR-полей. То есть **ярлыки чужих Верстаков уже лежат в локальной SQLite каждого оператора**, вместе с id файлов из чужих чатов и заметок. Ни сервер, ни право, ни сеть для этого не нужны. Это отдельная проблема приватности: чужой Верстак виден целиком.

   **Остался узкий канал — `attribute_values` в конструкторе отчётов.** Источник отдаёт колонку `valueJson` и открывается ЛЮБЫМ одним правом из пяти (`masterdata.view` / `engines.view` / `parts.view` / `employees.view` / `supply_requests.view`), а строки **не фильтруются по типу сущности-владельца**. Отсюда две беды: (1) оператор с одним лишь `parts.view` читает EAV-значения сотрудников, включая `attachments`, то есть id кадровых документов; (2) шире файлов — он вообще читает атрибуты типов, которые ему не положены. `redactReportRows` (H4) режет только строки с «чувствительными» ИМЕНАМИ атрибутов (зарплата/паспорт/ИНН/СНИЛС), а `attachments` и, скажем, `birth_date` в этот список не входят. Показательно, что путь доступа к файлу (`eavRowGrantsFileAccess`) как раз требует права на тип сущности — конструктор отчётов над теми же данными слабее.

   **Лечение (предложение, не сделано):** фильтровать строки `attribute_values` по праву на тип сущности — переиспользовать `permsForEntityTypeCode` из `fileAccessService`. Не сделал сам: это меняет то, что видят операторы в уже собранных отчётах (тип сущности приходит в строке ДИСПЛЕЙНЫМ именем, а не кодом — нужна аккуратная сшивка), а фильтр по умолчанию падает в `masterdata.view` и может срезать больше, чем ожидается. **Решение владельца.**
