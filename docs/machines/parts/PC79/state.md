## Чего на этой машине НЕТ (проверено 2026-08-21)

- **Рабочая копия — CRLF** (`core.autocrlf` на этой машине конвертирует при checkout). Следствие: многострочные якоря в скриптах правки (`node -e` / heredoc с `fs.readFileSync().replace('...\n...')`) **не совпадают** — в файле `\r\n`. При этом `sed -n … | cat -A` показывает строки без `^M`, то есть по глазам не отличить; отличает только `node -e "console.log(s.includes('\r\n'))"`. Правило: многострочные правки делать инструментом Edit (он это учитывает) либо строить якорь с фактическим EOL файла; односрочные `sed`/`replace` работают как обычно.
  - **Тесты-сторожа, сравнивающие многострочный блок с файлом, здесь краснеют от настройки Git, а не от кода** (поймано 2026-09-09 на `ListChrome.guard.test.ts`: ожидание блока CSS с `
` не совпадало с файлом в CRLF). Лечится в самом стороже — читать через `.replace(/
/g, '
')`.

- **`grep -i` НЕ складывает регистр кириллицы** (16.09.2026, C-локаль Git Bash). `grep -ri "ведомост"` находит только строки с маленькой «в»: файл, где есть лишь «Ведомости работ» (напр. `shared/src/domain/uiSections.ts`), в выдачу не попадает — и перепись вхождений выходит неполной молча. Так едва не потерялось название раздела при переименовании C1. Искать регистронезависимо шаблоном **без первой буквы** (`grep -rn "едомост"`) либо перечислять оба регистра явно. То же касается `grep -c` и любых счётчиков, на которые опирается «мы всё нашли».
- ~~Python не установлен вовсе~~ — **установлен, работает** (проверено 2026-09-08): `python -c "print(1)"` и `python script.py` идут нормально, включая многострочные правки файлов с кириллицей. Это удобнее `node -e` (тот ломает обратные кавычки, см. ниже). Скрипт правки писать инструментом Write и запускать `python <файл>`: heredoc в Bash-инструменте иногда рвётся на кавычках, а обратный слэш в обычной строке Python съедается на один уровень — якорь с экранированием не совпадает с файлом. Строки с экранированием писать как r-строки.
- **Правка файла с BOM через Python удваивает BOM, и PowerShell перестаёт видеть `param()`** (14.09.2026). `io.open(p, encoding='utf-8')` BOM **не снимает** — он остаётся в строке символом `﻿`; запись через `encoding='utf-8-sig'` добавляет второй. Файл на глаз целый, а `powershell` падает «Непредвиденный атрибут CmdletBinding» — потому что перед `param()` оказался невидимый символ. Читать `encoding='utf-8-sig'` либо явно `s.lstrip('﻿')` перед записью. Сторож на BOM у скриптов обслуживания — `clientOpsBundle.guard.test.ts`.
- ~~Прежняя запись (устарела, оставлена для истории)~~: **Python не был установлен** (проверено 2026-08-30): `python3`/`python` в Git Bash перехватываются заглушкой Microsoft Store (`Python was not found`, exit 49). Для однострочных правок файлов и разбора JSON использовать `node -e`, а не `python3 - <<PY`.
  - **Заглушка проходит проверку `command -v python3`** (выучено 2026-09-07): она существует как файл, поэтому гейт «есть ли инструмент» её пропускает, а запуск падает с 49 — и скрипт идёт дальше с пустым результатом разбора. Проверять запуском (`python3 -c 'print(1)'`), а не наличием; иначе смоук-тест не делает SKIP, а сыплет ложными отказами (поймано на `scripts/prod-ops/audit-deps.test.sh`).

- **Нет `zstd` и `flock`** (проверено 2026-09-03; `gpg`, `tar`, `sha256sum` есть). Из-за этого `scripts/prod-ops/backup-encrypted.test.sh` здесь печатает `SKIP` — смоук-тест бэкапа гоняется только в CI (job `prod-ops-backup` в `Lint`). Правя `backup-encrypted.sh`, судить о нём по прогону CI, а не по локальному «ok».
- **Из трёх ops-смоуков здесь идёт только один** (проверено 2026-09-18). `backup-encrypted.test.sh` → `SKIP` (нет `zstd`), `audit-deps.test.sh` → `SKIP` (нет рабочего `python3`, см. ниже), **`deploy-backend.test.sh` — гоняется полностью** (16 проверок): он намеренно обходится `node` + `tar`, которые здесь есть, а сеть, systemd и ожидание заменены шимами. То есть правку `deploy-backend.sh` можно и нужно проверять локально, а не только по CI.
- **`python3` — заглушка Microsoft Store**, а не интерпретатор: `command -v python3` её находит, запуск выходит с кодом 49 («Python was not found; run without arguments to install from the Microsoft Store»). Поэтому проверять python **запуском**, а не наличием — гейт по наличию пропустит скрипт внутрь и даст каскад ложных отказов вместо честного SKIP.

- **Код на JS/TS вставлять только через Write/Edit** (или `node script.js`, где скрипт записан Write'ом). `node -e "…"` в Bash-инструменте ломает обратные кавычки: bash исполняет `` `OAuth ${token}` `` как подстановку команды, в файл ложится пустое место, а скрипт рапортует «updated» — молча (поймано 2026-09-03, лечилось `typecheck`).
  - **Обратный слэш не переживает путь до Bash-инструмента даже в цитированном heredoc** (`<<'JS'`, где подстановок быть не должно). Выучено 2026-09-07: `'\\u0000'` дошло до node как `'\u0000'`, то есть как сам байт NUL — скрипт «заменил» NUL на NUL, отрапортовал успех, размер файла не изменился, и это заметно только по размеру. Симптом общий: правка с escape-последовательностью тихо не срабатывает. **Экранирующий слэш собирать кодом** (`String.fromCharCode(92) + 'u0000'`) либо писать скрипт инструментом Write.
  - **Управляющие символы в тексте команды блокируются целиком:** Bash-инструмент отказывает с `command contains control characters`. Значит, ни сырой NUL, ни другой control-байт нельзя ни передать аргументом, ни сматчить в `sed`/`Edit` — только через файл-скрипт и работу с `Buffer` по байтам.
- **Длинные сообщения коммитов и тела PR — только через файл** (`git commit -F <файл>`, `gh pr create --body-file <файл>`). Двойные кавычки внутри текста рвут строку в Git Bash: `git commit -m "…\"цитата\"…"` разваливается, и `git add` получает обрывки текста как пути (`error: pathspec 'dir' did not match`). Поймано 2026-09-06 на сообщении с цитатой имени файла.
- **Кавычки в ssh-команде не доезжают до прода ни в каком виде** (30.09.2026, парк-аудит E3): ни двойные в двойных, ни одинарные в файле `.ps1`, ни `--%` — удалённый bash получал команду голой (`syntax error near (`(). Режет сам тракт PowerShell → native ssh, а не конкретная обёртка. Правило: удалённая команда — **без кавычек вовсе**: SQL/скрипт — scp-файлом в `/tmp` (`-f /tmp/x.sql`, потом `rm`), `;` — бэктиком `` `; ``, `$VAR` удалённого env — бэктиком `` `$VAR `` (голый `$VAR` раскрыл бы локальный PowerShell в пустоту). Образец — рабочий `parkaudit.ps1` (в скретчпаде; в репо не кладём — одноразовый).
  - **Скрипт, отданный по ssh через stdin, обязан быть в LF** (25.10.2026). Рабочий приём для команд с кавычками/`&`/`?`: `Get-Content -Raw x.sh | ssh matricarmz bash -s`. Но файл, записанный здесь инструментом Write, — **CRLF**, и удалённый bash падает на последней строке `bash: line N: $'\r': command not found` (команда при этом уже выполнилась — смоук «зелёный», а код возврата 1). Писать такие скрипты с `\n` (или прогонять через `-replace "\r\n", "\n"`), а `curl` с `?platform=…&current=…` гнать только из файла — иначе `&` уйдёт в фон локальной оболочкой.

## Изменения состояния системы на PC79 (2026-11-04)

Включены при подготовке локальной сборки с подписью (ADR-0003, M190):

| Что | Где | Значение | Зачем |
|---|---|---|---|
| Developer Mode | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock` | `AllowDevelopmentWithoutDevLicense=1` | штатная галочка; **сама по себе симлинки не разрешает** |
| Симлинки | `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem` | `SymlinkEvaluation=1` | то же — без повышения прав не работает |

Обе настройки **не помогли**: `New-Item -ItemType SymbolicLink` продолжает отвечать «требуется привилегия администратора». Причина — привилегия `SeCreateSymbolicLinkPrivilege` выдаётся при повышении прав, а не через реестр. Рабочий путь для локальной сборки — запуск с повышенными правами (`-Verb RunAs`), тогда `winCodeSign` распаковывается и сборка идёт до конца.

- **Повышение прав через RunAs работает:** `Start-Process powershell -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File','<скрипт>' -Verb RunAs` — UAC подтверждается владельцем, скрипт выполняется с полными правами. Удобно для задач, которым нужен HKLM или `SeCreateSymbolicLinkPrivilege`.
- **Пользователь `valstan` состоит в группе «Администраторы», но токен фильтрованный** (`whoami /groups`: «Group used for deny only»). Поэтому `IsAdmin` = False, запись в HKLM напрямую запрещена, `Remove-Item Env:…` запрещён политикой безопасности.
