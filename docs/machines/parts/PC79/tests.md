## Флаки и грабли прогона

- **⚠️ `pnpm -r --workspace-concurrency=1 test` умирает на границе пакетов (14.11.2026, релиз v3.127.0):** рекурсивный прогон стабильно роняется после пакета android-app (процесс исчезает, красного теста нет, лог обрывается на полуслове) — два раза подряд, при зелёном коде. **Рабочий путь на этой машине: гонять пакеты по отдельности** (`corepack pnpm -F @matricarmz/shared test`, затем `backend-api`, `electron-app`, `android-app`) — так всё зелёное (1841 / 1400 / 2335 / 85). Рекомендация из PENDING про `-r test` на малоядерной машине здесь подтвердилась, но симптом другой: не «красный», а «процесс умер».
- **⚠️ Тот же Electron-флак, но в CI (23.11.2026, PR #1938):** джоб «Test» на раннере упал на `engineBulkIntakeService.test.ts` с «Electron failed to install correctly» — причина та же, что в пункте выше, только на стороне GitHub: `failed to create '.../node_modules/.pnpm/electron@43.0.0/node_modules/electron/dist/electron': File exists (os error 17)`. **Первый пуш той же ветки был зелёный** — значит гонка с postinstall-распаковкой Electron, а не код. Рабочий путь: `gh run rerun <id> --failed` — прогон зелёный. В теле PR пишется строка «первый прогон упал на гонке распаковки Electron, перезапуск — зелёный». Искать тут регресс своего кода — не искать.
- **⚠️ `engineStrictView.test.ts` («первый сейв виден сразу, без синк-круга») — граница 5 с на этой машине (23.11.2026):** файл то зелёный (2,7 с), то красный (5,17 с) — таймаут 5000 мс при лимите теста 5 с. К **моему** коду отношения не имеет (карточка двигателя и синк), падал и до правок. **Рабочий путь:** прогон файла одиночно на простое машине; при параллельном прогоне двух пакетов краснеет гарантированно (проверено 23.11: `backend-api` в одном прогоне с `electron-app` упал на `syncPipelineBotPollAbort.test.ts` — тот же таймаут, одиночно 4/4 зелёные). Авторитетный гейт — CI: там тот же набор зелёный.
### ⚠️ Прогон тестов здесь: грабли `pnpm -r test`

**Флейк `android-app/src/core/boot.test.ts` закрыт 2026-09-14** (был главным содержанием этого раздела). Наблюдение 2026-08-31 — 2026-09-06: тест «без логина SyncManager честно отказывает (auth required), не падая» падал с `expected true to be false` при параллельном прогоне и оставался зелёным в одиночку. Списывали на перегруз. **Это был настоящий баг тестового контура, а не тайминг** (GOTCHAS **M128**): `sessionSidecarStore` шимился только для браузерного таргета, в vitest работал настоящий (sync `node:fs`), а `app.getPath` шима отдаёт фиктивный `/android/appData` → сессия уезжала в реальный файл `<диск>:\android\appData\MatricaRMZ\auth-session.json`, **один на все параллельные воркеры**. Логин любого другого тест-файла подхватывался fallback'ом `getSession` — «без логина» видел чужую сессию. Лечение: шим включён и для vitest (`android-app/shimsPlugin.ts`), сторож — `authOverShims.test.ts` «сессия не уезжает в файл». На этой машине после правки 6 полных прогонов пакета подряд зелёные (до неё краснело примерно два из трёх).

- Проверять так: `corepack pnpm -F @matricarmz/android-app exec vitest run src/core/boot.test.ts`.
- Прогон перед релизом — `corepack pnpm -r --workspace-concurrency=1 test`: на этой машине ~4 минуты.
- **⚠️ Локальный `typecheck` не покрывает файлы тестов — CI проверяет их отдельным гейтом `typecheck:test`.** `pnpm -r typecheck` гоняет `tsc -p tsconfig.json`, а тестовые файлы в него не входят; их типизирует `tsconfig.vitest.json` (строже — `noUncheckedIndexedAccess`), и его проверяет только CI-шаг `typecheck:test`. Локально это выглядит как «зелёный тип», который на CI краснеет (поймано 31.10.2026 на `clientOpsArchive.test.ts`: `TS2532: Object is possibly 'undefined'`). Перед пушем правок тестов гонять `corepack pnpm -F @matricarmz/electron-app typecheck:test`.
- **⚠️ `-r test` останавливается на первом красном пакете** (`ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`), и это опаснее самого флейка. Порядок пакетов — `shared`, `android-app`, `backend-api`, `electron-app`; красный `android-app` означает, что **два последних пакета не запускались вовсе**, а в выводе это видно только по отсутствию их строк «Test Files». Судить о гейте по такому прогону нельзя: после красного добить руками `-F @matricarmz/backend-api test` и `-F @matricarmz/electron-app test`. Поймано 2026-09-06 — едва не ушло в мерж как «гейт пройден».
- **`--workspace-concurrency=1` не даёт полной гарантии** (16.09.2026): в прогоне гейта C3 красным стал `src/main/services/clientOpsArchive.test.ts` («читает и архив с именами в UTF-8»), хотя concurrency была единица. В одиночку файл зелёный за 484 мс, пакет целиком (`-F @matricarmz/electron-app test`) — 1014 зелёных. Тест распаковывает zip и чувствителен ко времени; правило прежнее — красный вне зоны правки перепроверять одиночным прогоном, но теперь известно, что `concurrency=1` его не исключает.
- **2026-10-31: тот же `clientOpsArchive` разобран до корня — и грабля оказалась не «7za с `-mcu=on`», а чтением свежезаписанного файла.** Замер с инструментацией: сам `7za` отрабатывает за 20–60 мс, а задержка сидит **между возвратом `execFileSync` и `readFileSync`** — чтение файла, только что записанного внешним процессом, блокирует **антивирус** (Defender, real-time на этой машине) до ~10 с. `-mcu=on` ни при чём: вне vitest он даёт 19–20 мс на 40 итераций подряд — просто на неверном пароле этот тест читал свежий файл вторым по счёту, и задержка прилетала именно к нему. Причина — чтение, а не флаг. **Лечение (сделано):** фикстуры собираются в `beforeAll` с бюджетом 180 с, тесты меряют только разбор готового буфера (0 мс), прогон пакета стабильно зелёный. Заодно найден и починен **прод-дефект**: на неверном пароле путь «мусор в zlib» (1 прогон из 256, когда контрольный байт заголовка случайно совпал) отдавал оператору английский «incorrect header check» — теперь переводим в нашу внятную ошибку. Подробности — [M182](../gotchas/M182.md).
- **Флейк `electron-app/src/main/services/engineStrictView.test.ts` («первый сейв виден сразу, без синх-круга») — 2026-11-05.** Тест поднимает настоящий Electron, и в параллельном прогоне всего пакета он не укладывается в 5 с (падает по таймауту), в одиночку проходит за 1,4 с. Проверять так: `corepack pnpm -F @matricarmz/electron-app exec vitest run src/main/services/engineStrictView.test.ts`. Правок кода он не требует — это нагрузка машины, на CI зелёный.
- **Грабля пайпа:** `corepack pnpm -r test 2>&1 | tail -40` возвращает код `tail`, то есть **0 при красных тестах**. Не судить о гейте по exit code такой команды — смотреть текст либо не пайпить.
- **Electron-ABI собирается** (с 2026-08-29, после установки VS Build Tools). `corepack pnpm -F @matricarmz/electron-app exec electron-builder install-app-deps` проходит и собирает из исходников: готовых бинарей под ABI Electron 43 (**148**) нет ни в одной версии `better-sqlite3-multiple-ciphers` — максимум `electron-v146`. Поэтому компилятор здесь обязателен, prebuild не спасёт.
- **⚠️ ABI-танец, без него грабли в обе стороны** (подробности — `SKILL.md` скилла `verifier-electron`): один общий pnpm-инстанс `better-sqlite3*` обслуживает и `electron-app` (Electron-ABI), и vitest (Node-ABI). Перед запуском стенда — `install-app-deps`; **перед прогоном тестов вернуть Node-ABI**, иначе 35 красных в `electron-app`. Самый быстрый способ — заранее скопировать оба `build/Release/better_sqlite3.node` и подкладывать обратно.
- **⚠️ Падение воркера vitest на нативе (24.11.2026) — это не красный тест:** полный прогон `electron-app` на этой машине иногда умирает не красным тестом, а крашем форка: `#  Assertion failed: (env) != nullptr` + «Worker exited unexpectedly», и в сводке — «1 failed | 319 passed» с **неисполненными** тестами (напр. 2750 из 2760). Нативный модуль (`better-sqlite3`) упал под нагрузкой — тесты не успели выполниться, а не провалились. **Рабочий путь:** `corepack pnpm -F @matricarmz/electron-app exec vitest run --maxWorkers=2` — на этой машине прогон уходит зелёным целиком (321 файл, 2749 тестов). Флаг `--minWorkers` в vitest 4 **не существует** (`Unknown option`). Судить о гейте по сводке «Tests passed», а не по факту падения форка.

### ⚠️ Подрывные проверки сторожей — только при погашенном стенде (выучено 2026-10-06)

**Пилот opencode (добавлено 2026-10-12, синхронизация с `Computer`)**: `opencode` не указан в профиле — добавить после первого прогона. Порт `3080` для `serve`; конфиг `~\.config\opencode\opencode.jsonc` (без `model`); узел в `userData/opencode-nodes.json`. Сервис `opencode` ещё не установлен на PC79 — установить перед пилотом (см. план `docs/plans/opencode-nodes-2026-10.md`).

Проверка «сторож краснеет на откат» временной правкой исходника через PowerShell (`Get-Content -Raw | -replace | Set-Content -Encoding utf8`) кладёт на диск **мохибайку**: `Get-Content` без `-Encoding` читает UTF-8-без-BOM как системный ANSI, ASCII-паттерн при этом находится, и испорченное пишется обратно. Если в этот момент поднят стенд, Vite-HMR тут же подхватывает испорченный файл в живой клиент — оператор видит кракозябры вместо подписей (поймано вживую во вкладке «История ремонта»: кнопки и заголовки столбцов). После восстановления файла всё чисто, но впечатление остаётся. Правило: **подрыв — либо node-скриптом (байтово безопасно), либо при погашенном стенде; после подрыва — `git diff` на отсутствие лишнего, а не только возврат файла**.
