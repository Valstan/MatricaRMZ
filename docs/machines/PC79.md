## Запросы к прод-БД с этой машины (2026-09-09)

Читающий SQL на проде удобнее гнать **скриптом через stdin**, а не строкой в кавычках:

```bash
# скрипт пишем Write'ом в скретчпад, затем:
ssh -o ConnectTimeout=20 matricarmz "bash -s" < <путь к скрипту>
```

- Внутри скрипта окружение берётся из env-файла сервиса (`set -a; . /etc/matricarmz/matricarmz.env; set +a`), пароль не печатается и в репо не попадает; `psql` на проде лежит в PATH.
- **Почему не одной строкой:** SQL с кавычками, `$`-подстановками и `\echo` через `ssh "…"` рвётся дважды — сначала в Git Bash, потом в удалённом shell. Тот же класс, что «длинные сообщения коммитов — только через файл» выше.
- Значение секрета можно проверить, не читая его: `printf '%s' "$VAR" | sha256sum` — так снят хэш чата оповещений 09.09.

Java читает PKCS12 штатно (с Java 9 это дефолтный тип), Gradle подписывает им без оговорок. Проверить, что ключ действительно валиден для Java, с этой машины нечем — для этого есть ручной workflow «Check Android signing secrets».
- **Пароль хранилища = пароль ключа.** У PKCS12 разные пароли поддерживаются не всеми инструментами, а расхождение вылезает только в момент подписи, то есть на релизном теге.
- ⚠️ **`-subj "/CN=…"` в Git Bash молча превращается в путь Windows.** MSYS видит ведущий слэш и подставляет `C:/Program Files/Git/CN=…`, openssl отвечает «subject name is expected to be in the format …» — выглядит как ошибка синтаксиса, а не как подмена аргумента. Лечится префиксом `MSYS_NO_PATHCONV=1` у команды. Тот же класс граблей, что CRLF и обратные кавычки выше: аргумент не доезжает до инструмента в том виде, в каком написан.
- Секреты репозитория ставятся из файла, не строкой: `gh secret set ANDROID_KEYSTORE_BASE64 < <файл с base64>` — пароль и base64 не попадают ни в историю команд, ни в лог сессии. Проверка кодирования до заливки — `base64 -w0 ks > a && base64 -d a | cmp - ks`.

### ⚠️ `openssl rand` здесь пишет CRLF — пароль ломается молча (выучено 2026-09-13)

Стоило двух красных прогонов гейта подписи. `openssl rand -base64 24 > .pw` в Git Bash кладёт в файл **CRLF**, и привычное `tr -d '\n'` снимает только LF — в пароле остаётся хвостовой `\r`. Дальше расходятся два потребителя одного файла:

- `openssl pkcs12 -passout file:.pw` берёт байты **вместе с `\r`** — хранилище создано паролем из 33 символов;
- `gh secret set … < .pw` хвостовой пробельный символ **срезает** — в секрет уезжают 32.

Итог: локально `openssl` открывает хранилище, а Java на раннере отвечает `keystore password was incorrect` — и выглядит это как «неправильно залитый секрет», хотя залито ровно то, что в файле. Правило: **пароль не должен иметь ни ведущих, ни хвостовых пробельных символов** (`tr -d '\r\n'`), тогда любое подрезание транспортом — no-op. Проверять до заливки: `wc -c < .pw` и `od -c .pw | tail`.

Тот же класс, что CRLF-якоря и обратные кавычки выше: файл на этой машине содержит не то, что кажется по виду.
