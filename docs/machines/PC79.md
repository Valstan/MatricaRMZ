### ⚠️ Правка файлов из PowerShell: `-Encoding utf8` пишет BOM (выучено 2026-10-06)

Правил `App.tsx` через `Get-Content -Raw | -replace ... | Set-Content -Encoding utf8` — и получил **две** поломки сразу:

1. **`-Encoding utf8` в Windows PowerShell пишет UTF-8 С BOM.** Файл без BOM получил BOM: в `git diff` это первая строка `+import React…` вместо `-﻿import React…`, то есть правка одной строки выглядит правкой четырёх. Часть файлов в репозитории BOM имеет намеренно (`App.tsx`) — снятие BOM там тоже лишняя строка в диффе, которая не имеет отношения к задаче.
2. **Кириллица в выводе консоли — кракозябры** (`Get-Content`/`Select-String` без `-Encoding utf8` показывают «Этапы ремонта» как `?⠯? ६???`). Проверять результат такой правки глазами через PowerShell нельзя: правка может быть верной, а покажется мусором.

Рабочий путь на этой машине — **правка через node-скрипт** (`fs.readFileSync` / `fs.replace` / `fs.writeFileSync`) с проверками: «строка встречается ровно 1 раз», «после правки нет `�`», «BOM был — вернуть». Многострочные шаблоны собирать построчно (`split(/\r?\n/)`): файлы в репозитории CRLF, и шаблон с `\n` просто не находится. Проверка результата — `git diff`, а не вывод команды.

### Смоуки стенда: что нужно знать перед запуском (2026-09-08)

### ⚠️ ABI: `install-app-deps` НЕ пересобирает уже существующий бинарь

Выучено 2026-09-08 (стоило запуска, который упал «Критическая ошибка базы данных»). Один общий pnpm-инстанс `better-sqlite3*` обслуживает и Electron (ABI 148 у Electron 43), и vitest (Node-ABI 137 у Node 24). Если в `build/Release/` уже лежит `.node`, `electron-builder install-app-deps` **рапортует `finished`, ничего не пересобрав** — под Electron уезжает Node-ABI, клиент падает на инициализации БД (`NODE_MODULE_VERSION 137 … requires 148`), само-лечение стирает локальную реплику и уходит в аварийный режим обновления.

Лечится сносом артефакта перед сборкой:

```bash
rm -rf node_modules/.pnpm/better-sqlite3@12.11.1/node_modules/better-sqlite3/build \
       node_modules/.pnpm/better-sqlite3-multiple-ciphers@12.11.1/node_modules/better-sqlite3-multiple-ciphers/build
corepack pnpm -F @matricarmz/electron-app exec electron-builder install-app-deps
```

Перед прогоном тестов — вернуть Node-ABI тем же приёмом (снести `build` и поставить готовые бинари, см. раздел про `prebuild-install` выше). Проверять не по слову `finished`, а по `mtime` файла `build/Release/better_sqlite3.node`: старая дата = пересборки не было. **Дополнение 19.10.2026:** если бинарник подменялся **руками** (копией `.node`), этого мало — `install-app-deps` судит о сборке по метке `.forge-meta` и, увидев в ней `x64--148`, за две секунды отчитается `finished`, ничего не собрав, хотя под меткой теперь лежит Node-бинарник; снимай обе метки (или `build` целиком) перед сборкой под Electron.

## Запросы к прод-БД с этой машины (2026-09-09)

Читающий SQL на проде удобнее гнать **скриптом через stdin**, а не строкой в кавычках:

```bash
# скрипт пишем Write'ом в скретчпад, затем:
ssh -o ConnectTimeout=20 matricarmz "bash -s" < <путь к скрипту>

- Значение секрета можно проверить, не читая его: `printf '%s' "$VAR" | sha256sum` — так снят хэш чата оповещений 09.09.
- **Bash-инструмента здесь нет — оболочка PowerShell**, поэтому `< файл` не работает. Рабочий вызов (30.09, проверен на разборе этапов ремонта):

  ```
  `cmd` передаёт stdin побайтно, так что CRLF-ловушка (см. раздел про `core.autocrlf` выше) не срабатывает. Скрипт с `psql … <<'SQL'` внутри работает как есть.

## Ключи подписи Android — теперь на этой машине (2026-09-13)

Прежнее хранилище жило на PC40 и пропало вместе с ним; ключ перевыпущен отсюда (`PROJECT_STATE.md` §«Подпись Android-клиента»). На PC79 лежит `%USERPROFILE%\.matricarmz-keys\` — `matricarmz-release.keystore` (PKCS12) + `.pw`. **Вне репо, в Git не попадает.** Копии вне этой машины пока нет — это открытый хвост (`PENDING_FOLLOWUPS` §Android п.1).

- **Java и `keytool` здесь НЕ установлены**, поэтому хранилище сделано `openssl` (он есть, 3.5.7): самоподписанный RSA-4096 + `openssl pkcs12 -export -name matricarmz`. Java читает PKCS12 штатно (с Java 9 это дефолтный тип), Gradle подписывает им без оговорок. Проверить, что ключ действительно валиден для Java, с этой машины нечем — для этого есть ручной workflow «Check Android signing secrets».
- **Пароль хранилища = пароль ключа.** У PKCS12 разные пароли поддерживаются не всеми инструментами, а расхождение вылезает только в момент подписи, то есть на релизном теге.
- ⚠️ **`-subj "/CN=…"` в Git Bash молча превращается в путь Windows.** MSYS видит ведущий слэш и подставляет `C:/Program Files/Git/CN=…`, openssl отвечает «subject name is expected to be in the format …» — выглядит как ошибка синтаксиса, а не как подмена аргумента. Лечится префиксом `MSYS_NO_PATHCONV=1` у команды. Тот же класс граблей, что CRLF и обратные кавычки выше: аргумент не доезжает до инструмента в том виде, в каком написан.
- Секреты репозитория ставятся из файла, не строкой: `gh secret set ANDROID_KEYSTORE_BASE64 < <файл с base64>` — пароль и base64 не попадают ни в историю команд, ни в лог сессии. Проверка кодирования до заливки — `base64 -w0 ks > a && base64 -d a | cmp - ks`.

### ⚠️ `openssl rand` здесь пишет CRLF — пароль ломается молча (выучено 2026-09-13)

Стоило двух красных прогонов гейта подписи. `openssl rand -base64 24 > .pw` в Git Bash кладёт в файл **CRLF**, и привычное `tr -d '\n'` снимает только LF — в пароле остаётся хвостовой `\r`. Дальше расходятся два потребителя одного файла:

- `openssl pkcs12 -passout file:.pw` берёт байты **вместе с `\r`** — хранилище создано паролем из 33 символов;
- `gh secret set … < .pw` хвостовой пробельный символ **срезает** — в секрет уезжают 32.

Итог: локально `openssl` открывает хранилище, а Java на раннере отвечает `keystore password was incorrect` — и выглядит это как «неправильно залитый секрет», хотя залито ровно то, что в файле. Правило: **пароль не должен иметь ни ведущих, ни хвостовых пробельных символов** (`tr -d '\r\n'`), тогда любое подрезание транспортом — no-op. Проверять до заливки: `wc -c < .pw` и `od -c .pw | tail`.

Тот же класс, что CRLF-якоря и обратные кавычки выше: файл на этой машине содержит не то, что кажется по виду.

- **Main-процесс Electron HMR не покрывает** (только renderer): правки `main/` (сервисы, IPC-регистры) требуют перезапуска клиента (`kill electron` + `start-electron.ps1 -Cdp`), иначе смоук идёт по старому коду main при новом рендере. Бэкенд — аналогично (перезапуск через `stop.ps1` + добить порт 3011).
- **Выражение для `Runtime.evaluate` обязано начинаться с `return`.** Обёртка либы — `(async () => { HELPERS <выражение> })()`: голый IIFE `(…)(…)` выполняется, но его значение отбрасывается — драйвер получает `undefined` без ошибки, и это выглядит как «элемента нет». Все рабочие драйверы пишут `return …` первым словом.

## Замеры прода read-only: зонд-скрипт и grep-ловушки (2026-10-11)

- **`ssh "… | grep -c bot poll"` не проходит: режется сам тракт PowerShell → ssh** — удалённый bash получает команду голой и падает `grep: poll: No such file or directory`. Правило (общее для этой машины): шаблон grep для прода — либо без пробела, либо вообще не grep: отправь `.mjs`/`.sql` файлом через `scp` и запусти на боксе (`node /tmp/x.mjs`, потом `rm`).

- **`grep 409` по journalctl врёт в обе стороны:** ловит `.409Z` в ISO-штампах и hex в UUID. Считать только поточному тексту (`terminated by other getUpdates`, `HTTP 409`) или подчёркнутым тегам (`pipeline_bot_poll`).

- **Многострочный SQL через here-string в `psql -f -` доезжает битым** (2026-10-20): строка `$sql | ssh … 'psql … -f -'` то роняет парсер (`ERROR: multiple decimal points` на ровном `to_char`), то теряет символы в uuid-литерале (`…-555555555` вместо `…-555555555555`). - **Скриншот WinForms-окна из сессии агента: `CopyFromScreen` падает «Отказано в доступе»** (у процесса нет доступа к рабочему столу), а **`PrintWindow(hwnd, hdc, 2)` по `MainWindowHandle` — работает** и отдаёт содержимое окна (проверено на окне обслуживания: видны вкладки, подписи кнопок, ход сбора). Рецепт: P/Invoke `PrintWindow` + `GetWindowRect`, `Bitmap(w,h)`, `$g.GetHdc()`, `PrintWindow(..., 2)`, сохранить PNG и прочитать его глазами. Скриншот вкладки — `.verifier-electron/probe-ops-cleanup-tab.png`.
- **UI Automation читает окна обслуживания** (`UIAutomationClient`: `FindAll`/`FindFirst` по `NameProperty`, `TreeScope::Descendants`) — так вкладки и кнопки подтверждаются без скриншота. А вот нажатие кнопки через `InvokePattern` не завелось («Неоднозначное совпадение» на `GetCurrentPattern`): для действий надёжнее запускать сам скрипт с ключами (`-Verify`), UIA держать для чтения.
- **Временные пробы `.ps1` в скретчпаде — тоже в UTF-8 с BOM.** `write`-инструмент кладёт файл без BOM, Windows PowerShell 5.1 читает кириллицу как ANSI, и проба падает «Ожидалось ")"», хотя файл цел (та же M110, что и для репо-скриптов). Лечение — перезапись с `New-Object System.Text.UTF8Encoding($true)` и сразу `Parser::ParseFile`.
- **`opencode-cleanup.ps1 -Verify` нашёл на PC79 пилотную раскладку** (задача `MatricaRMZ-OpenCode-serve-valstan`, правило «MatricaRMZ - OpenCode serve (входящий, LAN)», папка `C:\ProgramData\MatricaRMZ-OpenCode`) и **ни одного процесса узла** — фильтр по пути бинаря не путает личный CLI владельца с узлом. Снять раскладку (задачу/правило/папку) — кнопкой «Снять раскладку узла» от администратора.
