## 1. Вердикт

**Вердикт.** Кнопку нейросети в ПП делать — но только как тонкую обёртку над существующей функцией «Добавить списком»: агент разбирает введённый текст на номера, **проверку дублей не переписывает**, а действие зовёт ту же доменную проверку и ту же дверь записи `applyRows`; ни одной новой проверки «уже есть» в коде агента. **Уверенность: средняя** (уверен в правиле и в цене ошибки; не уверен в границах клиентского реестра инструментов — это не моя зона).

**Доменная добавка (устав, три строки).**
- **Участок:** планирование производства — добор двигателей в стрроки программы и разбор проблемных номеров. Ремонтный поток (приёмка → разборка → дефектовка → комплектование → сборка → отгрузка) фича **не трогает**: пишется только строка плана и примечание.
- **Затор:** главный затор завода — **начало сборки** (ручной подбор деталей из обезличенного ремфонда), `docs/zavod/FACTORY_MODEL.md:46`. ПП этот затор **напрямую не кормит**; кормит косвенно — снимает ручную переписку номеров и ручной разбор пачки, т.е. ускоряет вход двигателя в поле зрения плановой службы. Второй затор, который фича кормит прямо: **ручной перебор номера по списку в Excel → ошибка «забыли одного»**.
- **Инвариант:** «строка плана без договора не имеет группы» — проблемные строки живут внутри программы отдельной группой «Требует данных» и сами уезжают в свой договор. Плюс инвариант партии/экземпляра: **один двигатель — одна карточка — одна строка в плане**; повторный заезд того же номера = **другая** карточка (значит и другая строка). Обезличивание деталей, маршрутный лист, сдельщина/нормо-часы, подписи и ответственный — не затрагиваются (правок в ремонтном потоке нет).

## 2. Инвариант потока (вопрос 1) — проверяемые утверждения

После добавления по команде агента обязано остаться верным:

1. **Ни одна строка плана не появляется дважды по одному двигателю.** Сегодня это гарантирует **только клиент** — `alreadyInProgram` (по `engineId` карточки и по номеру): `electron-app/src/renderer/src/ui/components/ProductionProgramAddEnginesByNumbersDialog.tsx:255-260`. На сервере уникачности нет: `backend-api/src/services/productionProgramService.ts:525-556` проверяет только формат полей.
2. **Повтор номера внутри одного списка не даёт двух строк** — `parseEngineBulkIntake` схлопывает по канон-ключу `normalizeLookupCompact`: `shared/src/domain/engineBulkIntake.ts:64-79`.
3. **Номер, совпавший с несколькими карточками, не выбирается молча** — `productionProgramEngineMatch` возвращает `ambiguous`: `shared/src/domain/productionProgram.ts:1588-1598` (номер в базе не уникален, `erp_engine_cards_number_idx` — не уникальный индекс, комментарий там же). Для завода это **не абстракция**: повторный заезд двигателя = две карточки с одним номером.
4. **Отгруженный двигатель в план не попадает** — `productionProgramEngineHint` даёт тон `block` (`shared/src/domain/productionProgram.ts:342,348`), `productionProgramEngineProblem` → `forbidden` (`:1511-1513`).
5. **Чужая строка плана не снимается.** Перед записью строки читаются **с сервера** (`ProductionProgramAddEnginesByNumbersDialog.tsx:168-174`; `productionProgram:get` читает сервер, а не реплику — `electron-app/src/main/ipc/register/productionProgram.ts:153-155`), и локальная правка ложится поверх: `productionProgramMergeRows` (`shared/src/domain/productionProgram.ts:1429-1444`).
6. **Запись идёт только одной дверью** — `applyRows` (`electron-app/src/renderer/src/ui/pages/ProductionProgramPage.tsx:698-704`) → автосохранение → `productionProgram:saveRows` (`electron-app/src/main/ipc/register/productionProgram.ts:219-251`); сторож: `electron-app/src/renderer/src/ui/pages/ProductionProgramPage.guard.test.ts:139-148`.
7. **Строка без договора/карточки живёт в группе «Требует данных» и сама уезжает в свой договор** — `PRODUCTION_PROGRAM_PENDING_GROUP_LABEL` (`shared/src/domain/productionProgram.ts:1457`), проход перепроверки `productionProgramResolvePendingRows` (`:1664`).
8. **Этапы, наряды, акты, ППО-отчётность, склад не меняются.** ПП пишет только строку плана и примечание (`docs/plans/production-program-bulk-add-and-list-tools-2026-11.md:11`).
9. **Карточка из ПП не заводится** — «нет карточки» = строка без карточки в блоке «Требует данных», а не новая карточка (`docs/plans/production-program-bulk-add-and-list-tools-2026-11.md:29`).
10. **Отметка оператора на строке остаётся пустой** — `operatorNote: null` у добавляемых строк (`ProductionProgramPage.tsx:1879-1883`; «её ставит оператор, руками» — `ProductionProgramPage.tsx:1779-1780`), и шапка программы (срок, подписи) агентом не трогается: подписи живут отдельной дверью `productionProgram:setRowOperatorNote` (`register/productionProgram.ts:265-271`).

## 3. Что агент НЕ должен переписывать (вопрос 2)

Агент — **инициатор**, не **судья**. Правило дублей, грамматику номеров и сборку строки он не трогает, а **зовёт**:

| Что | Где живёт (единственный источник) |
|---|---|
| Разбор списка номеров, схлопывание повторов | `shared/src/domain/engineBulkIntake.ts:19-79` (`parseEngineBulkIntake`, `engineBulkIntakeKey`) |
| Поиск карточки по номеру + признак неоднозначности | `productionProgramEngineIndex` / `productionProgramEngineMatch`, `shared/src/domain/productionProgram.ts:1557,1588` |
| Причина строки («нет карточки/договора/контрагента/истории», «отгружен») | `productionProgramEngineProblem` + `PRODUCTION_PROGRAM_ENGINE_PROBLEM_TEXTS`, `shared/src/domain/productionProgram.ts:1473,1502` |
| Сборка строки плана | `productionProgramRowFromEngine`, `shared/src/domain/productionProgram.ts:493-520` |
| **Проверка дубля «уже в плане»** | `alreadyInProgram` — по `engineId` карточки **и** по номеру: `ProductionProgramAddEnginesByNumbersDialog.tsx:255-260` |
| Слияние с сервером (чтобы не снести чужую строку) | `productionProgramMergeRows`, `shared/src/domain/productionProgram.ts:1429` |
| Запись | `applyRows` → `productionProgram:saveRows` |
| Итог по каждому номеру (причина отказа) | `skipped: Array<{label, reason}>` — `ProductionProgramAddEnginesByNumbersDialog.tsx:272-274` |

**Конкретно проверки дублей, которые обязаны остаться в домене/приложении и не переезжать в логику агента:** (1) совпадение по `engineId` карточки; (2) совпадение по номеру двигателя; (3) повтор номера внутри одного списка; (4) неоднозначность — несколько карточек на один номер; (5) «уже отгружен» — блок.

**Почему это принципиально.** Гейт дублей в карточке двигателя уже один раз проигрывали: второй вход «пакетный приём» либо скопировал бы гейты, либо обошёл бы их — ровно этот класс описан в `electron-app/src/main/services/engineCardWrite.ts:26-29`. Агент — это **третий** вход; если он приносит свою копию правила, через месяц правил будет три, и они разойдутся.

## 4. Другие пути добавления двигателя (вопрос 3)

Их **четыре**, и сегодня они проверяют дубли по-разному:

1. **Одиночный выбор в ПП** — `ProductionProgramPage.tsx:1756-1784`. Проверки дубля **нет вовсе**: тот же двигатель можно добавить дважды через соседнюю кнопку. «Дубли не создаются» через агента тут будет фикцией.
2. **«Добавить двигатели списком» (номера)** — `ProductionProgramAddEnginesByNumbersDialog.tsx`. Единственный путь с проверкой по `engineId` **и** по номеру (`:255-260`).
3. **«Добавить в производственную программу» из списка «Двигатели»** — `electron-app/src/renderer/src/ui/components/ProductionProgramAddEnginesDialog.tsx:311-321`: проверка **только по `engineId`**, по номеру — нет.
4. **«Принять двигатели списком» (приход на ремонт)** — `electron-app/src/renderer/src/ui/pages/EnginesPage.tsx:1583-1590` → `EngineBulkIntakeDialog` → `electron-app/src/main/services/engineBulkIntakeService.ts`. Это **не путь в ПП**: он заводит **карточки**, гейт дублей карточек — в `engineCardWrite.ts:71-84`.

**Что из этого следует для нового пути.**
- Агент **не должен заводить карточки**: иначе появится четвёртый путь создания карточки рядом с единственными гейтами (`engineCardWrite.ts`). «Не найден в базе» = строка в блоке «Требует данных» без карточки.
- **«Пропущенный» двигатель** — реальный риск, и вот где: приход двигателя занимает **плановое место в договоре** (слот марки: `EngineBulkIntakeDialog.tsx:486-489` → `placeEngineIntoContractSlot`, `electron-app/src/renderer/src/ui/utils/engineContractSlot.js`). Это **другое место**, чем строка ПП: деньги/нормативы по договору ≠ строка производственной программы. Агент, добавивший номер в ПП, **не занимает слот в договоре** — и наоборот, приход с договором не создаёт строку ПП. Ответ оператору обязан это различать словами, иначе ППО увидит «двигатель в плане», у которого в договоре нет места под деньги.
- **Второй «пропущенный»**: движок добавленного двигателя в ПП живой — этап ремонта едет из карточки (`productionProgramEngineStage`), а не из строки плана. Строка плана без карточки/этапов = «номер есть, работы нет».

## 5. Как должен выглядеть ответ оператору (вопрос 4)

По каждому номеру — **одна строка, словами, без кодов и без идентификаторов**. Тексты причин уже есть готовые (`PRODUCTION_PROGRAM_ENGINE_PROBLEM_TEXTS`, `shared/src/domain/productionProgram.ts:1473-1481`) — переиспользовать, не переписывать:

| Итог | Что сказать оператору |
|---|---|
| Добавлен | «Добавлен в план — <организация, договор>» |
| Добавлен с оговоркой | «Добавлен в блок «Требует данных» — <причина словами>. Сам уедет в свой договор, когда карточку починят.» |
| Уже есть | «Уже есть в плане — не добавляли, ничего не меняли» |
| Не найден | «Карточки в базе нет — строка добавлена без карточки (в блоке «Требует данных»). Карточку заводит приход двигателей списком.» |
| Неоднозначно | «Номер «…» совпал с N карточками — выберите двигатель вручную. Ничего не добавлено.» |
| Отказ по праву | «Нет права вести производственную программу — ничего не изменено» |
| Отказ по объёму | «Список больше 500 номеров — разделите на части» (`ENGINE_BULK_INTAKE_MAX`, `shared/src/domain/engineBulkIntake.ts:22`) |

Итог одной строкой: «Добавлено N · уже было M · требует данных K · не найдено J · неоднозначно P» — плюс по каждому отказу причина. **Молчание — не ответ**: строки, которые агент не смог добавить, перечисляются поимённо, иначе оператор посчитает, что «всё добавили».

## 6. Варианты (цена и риск)

**A. Обёртка над существующей функцией (рекомендую).** Вынести тело «Добавить списком» в чистую функцию (разбор → отчёт по каждому номеру → строки + причины отказов), которую зовут и модалка, и инструмент агента; запись — та же `applyRows`. Цена: **1–2 дня** (функция + пункт в клиентском реестре инструментов + отчёт). Риск: **низкий** — правило дублей остаётся одно, тестируется существующими тестами домена.

**B. Агент зовёт существующую кнопку/обработчик как есть** (без выделения функции). Цена: **полдня**. Риск: **средний-высокий** — проверка дублей остаётся внутри компонента, у инструмента нет отдельного теста; вход «по DOM» ломается при каждой правке вёрстки. Годится только как черновик.

**C. Агент пишет строки сам** (свой парсер, свой поиск карточки, своя проверка «уже есть»). Цена: **1 день**. Риск: **высокий** — вторая копия грамматики номеров и правил дублей; разойдётся с доменом (класс brain G363 из `engineCardWrite.ts:26-29`). **Не рекомендую.**

**D. Не делать (в этом срезе).** Не давать агенту действие записи в ПП; оставить чтение (что уже есть в программе, что в «Требует данных») и подготовку списка — жмёт оператор. Цена: **полдня**. Риск: **низкий**. Обоснование: ПП — раздел с самой высокой ценой ошибки в срезе (дубль строки = два плановых места под один двигатель), а клиентского реестра инструментов и проверки прав на клиенте ещё нет (бриф, пп. 1–3). Вернуться к A, когда реестр и права готовы.

## 8. Что заставит передумать (вопрос 5, фальсификатор)

- **Сервер закроет дыру уникальности** («один двигатель — одна строка в программе»): сегодня этого нет (`backend-api/src/services/productionProgramService.ts:525-556`). Появятся — клиентские проверки дублей станут второй копией правила, и вариант C/A меняется.
- **Реплика/зеркало программ начнёт отдавать строки без минутной задержки** (сейчас задержка заложена: `register/productionProgram.ts:153-155`) — тогда гонка «две машины добавили один номер» уходит сама, и проверку можно поднять на сервер.
- **Владелец решит, что «нет карточки» = надо завести карточку** (сейчас план это запрещает: `docs/plans/production-program-bulk-add-and-list-tools-2026-11.md:29`) — тогда у инструмента две двери (приём + план) и риск второй карточки на двигатель.
- **Окажется, что операторы массово пользуются одиночным добавлением** (`ProductionProgramPage.tsx:1756`, без проверки дубля) — тогда «дубли не создаются» надо расширять на тот путь тоже, иначе фича чинит не то место.
