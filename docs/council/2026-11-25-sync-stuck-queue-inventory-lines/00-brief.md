# Бриф совета: «строка не уходит из очереди» — класс застрявшей очереди на строках списка деталей

**Глобальная линза:** готовый обработчик **есть** — правило «журнал — лог ИЗМЕНЕНИЙ» и «отказ назван» уже реализованы для соседних таблиц (`backend-api/src/services/sync/syncWriteService.ts` → `findUnchangedAttributeValueRows`; `backend-api/src/services/sync/applyPushBatch.ts` → `filterStaleBySeqOrUpdatedAt` + `LWW_REJECTED_REASON`; клиент — `electron-app/src/main/services/sync/skipReasonPolicy.ts`, `confirmedRows.ts`). **Дубль:** правило «no-op ⇒ без seq и без записи журнала» написано **второй раз** — только для `attribute_values`; для `erp_engine_inventory_lines` оно не написано вовсе. **Действие:** доработать существующие модули (обобщить детектор no-op, назвать отказ, доработать отправку снимков) — новый глобальный модуль не нужен.

## Вопрос

Почему на Android-машине кладовщика очередь отправки не снимается (624 строки, 56+ мин), хотя данные на сервере полные, — и какой набор правок закрывает **класс** целиком, а не этот случай?

## Что уже известно (факты, не пересказ)

- Разведка на проде 25.11.2026 (read-only) — `docs/pending/stroki-spiska-detaley-zastryali-v-otpravke.md` §«Третий заход».
- Лист `64dd12b9…`: 622 строки на сервере, у каждой свой номер журнала; **1244 журнальные записи на 622 строки** (по две на строку) ⇒ повторный push неизменённой строки создаёт новый seq и новую запись журнала.
- На листе стоит маркер E3 (`rowsIn`) ⇒ строки ведёт **клиент**, сервер их из `meta_json` не выводит.
- Отказов сервера за день нет: `lww_rejected` 0, `sync_policy_denied` 0, «budget cut» 0. Транспорт планшета: `Failed to fetch`, `offline`, прогоны синка до 38 минут.
- Ни одна android-машина не шлёт снимки диагностики (`scope='client'` — 26 524 снимка, все с win32-префиксами, android — 0) ⇒ автолечение (`diagnosticsAutohealService`, включено по умолчанию) очередь не видит.
- Клиентский снимок снимает **5 таблиц**; `erp_engine_inventory_lines` в него не входит ⇒ класс не виден серверу ни на одной платформе.
- Фикс класса «подтверждено сервером, но без номера» (PR #2026, `e9ee3c70`) слит **после** тега `v3.146.0` ⇒ в 3.146.0 его нет, а APK 3.146.0 уже лежит на проде.

## Ограничения

- Прод не трогаем (только read-only). Решение по боевой машине — за владельцем (уже принято 25.11: `reset_sync_state_and_pull`).
- Правки — в существующие модули; новый глобальный модуль запрещён (результат линзы).
- Миграций схемы не делаем; серверные правки не должны ломать старых клиентов (парк на 3.145.0).

## Бюджет

Советников — 2 (`sync`, `client`), лимит ответа — 1 страница каждый, по 2–3 варианта с ценой и фальсификатором. Раунд 2 — только если конфликтов два и больше.

## Критерий успеха

1. Повторный push неизменённой строки списка деталей **не** создаёт запись журнала и **не** двигает `last_server_seq`.
2. Отказ по устареванию для этой таблицы **назван** (`lww_rejected`) ⇒ клиент снимает `pending` существующей политикой, без правки клиента.
3. Машина с застрявшей очередью **видна серверу**: снимок уходит даже при упавшем pull, и в снимке есть таблица строк списка деталей.
4. Ветка не тянет миграцию схемы и совместима со старыми клиентами.
