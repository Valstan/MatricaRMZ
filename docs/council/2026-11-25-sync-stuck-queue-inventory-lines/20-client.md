# Ответ Оболочщика (`client`)

> Ответ ведущего по уставу советника ([`docs/advisors/client/CHARTER.md`](../../advisors/client/CHARTER.md)). Отдельные субагенты-с��ветники в этом рантайме недоступны — ответ дан ведущим по контракту устава; это отмечено в покрытии вердикта.

**Вердикт.** Класс на клиенте — из двух частей, и обе делают его **слепым**: **(1) снимок диагностики уходит только после успешного pull'а** ⇒ на планшете с повисшим pull'ом (логи: прогоны 217 с / 603 с / **2320 с**, `pulled:0 pushed:0`) снимок **не уходит никогда** — поэтому ни сервер, ни автолечение очередь не видят; **(2) в снимке нет таблицы `erp_engine_inventory_lines`** ⇒ даже на win32-парке этот класс серверу не виден. Плюс к этому подтверждение приходит, а номера нет ⇒ M52 (`requeueUnconfirmedRows`) возвращает строку в очередь по кругу (чинено PR #2026, **не в 3.146.0**). Уверенность: **высокая** по (1) и (2) — это видно в коде; по потере ответа push'а — **средняя** (нужен снимок машины).

**Путь, где правило живёт сейчас, и не дублируется ли оно.** Снимок — один: `electron-app/src/main/services/sync/diagnosticsReporter.ts` (`buildDiagnosticsSnapshot`, `sendDiagnosticsSnapshot`). Отправка — одна: `electron-app/src/main/services/syncService.ts:6277–6289`. Политика отказов — одна: `sync/skipReasonPolicy.ts`. «Помнить подтверждённое сервером» — одно: `sync/confirmedRows.ts`. **Правило не дублируется** — правки идут в существующие модули, вторых копий не заводим.

**Варианты**

| # | Что | Цена | Риск |
|---|---|---|---|
| A | Снимок уходит **всегда** (даже если pull упал/провис) + в снимок добавлена таблица `erp_engine_inventory_lines` + ошибка отправки **логируется**, а не глотается | 2 файла (`diagnosticsReporter.ts`, `syncService.ts`) + тесты | Низкий: снимок идёт раз в 10 минут и уже шлётся win32-парком; на android это включает наблюдаемость, которой нет |
| B | Только добавить таблицу в снимок | 1 файл | Средний: android-парк всё равно молчит (снимок не уходит при упавшем pull) — главная брешь не закрыта |
| C | Клиент не трогать, чинить только сервер | 0 | Высокий: android остаётся слепым, автолечение по-прежнему не сработает; класс вернётся на следующей машине |

**Чем проверяется за день.** (1) Тест клиента: при упавшем pull вызов `sendDiagnosticsSnapshot` всё равно происходит (сейчас — после pull, при провисании не доходит). (2) Тест клиента: в `buildDiagnosticsSnapshot` есть ключ `erp_engine_inventory_lines` с `pendingCount`/`stuckCount`. (3) Полевая проверка после выката: с android-машины приходит снимок `scope='client'` ⇒ в `diagnostics_snapshots` появляется строка с `client_id LIKE 'android%'`.

**Что заставит передумать.** Если снимок с android не придёт и после правки порядка вызовов (например, `fetchAuthed` на android не проходит авторизацию или указывает другой `apiBaseUrl`) — правка не поможет, и придётся чинить точку отправки на android отдельно. Это проверяется тем же полевым признаком (снимок `scope='client'` от android-машины).
