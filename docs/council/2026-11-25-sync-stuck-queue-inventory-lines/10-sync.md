# Ответ Синхронизатора (`sync`)

> Ответ ведущего по уставу советника ([`docs/advisors/sync/CHARTER.md`](../../advisors/sync/CHARTER.md)). Отдельные субагенты-с��ветники в этом рантайме недоступны — ответ дан ведущим по контракту устава; это отмечено в покрытии вердикта.

**Вердикт.** Это **не** «строка не доехала»: строки доезжают и даже применяются — 1244 журнальные записи на 622 строки это доказывают. Класс двойной: **(1) сервер на неизменённой строке двигает номер и пишет в журнал** ⇒ повторный push бесконечен и журнал пухнет; **(2) отказ по устареванию для этой таблицы не назван** ⇒ клиент не снимает `pending` и шлёт строку снова. Уверенность: **средняя-высокая** (факты журнала и кода сильны; клиентская часть — без снимка машины).

**Дверь записи.** Строка списка деталей идёт через клиентский push (на листе маркер E3 `rowsIn` ⇒ сервер строки из `meta_json` не выводит): `writeSyncChanges` (`backend-api/src/services/sync/syncWriteService.ts`) → `signAndAppendDetailed` (журнал + seq) → `applyPushBatch` (применение к таблице) → `updateSeqAndCollect` (номер + `applied_rows`). **Что её ломает:** повторный push неизменённой строки (`onConflictDoUpdate` с `setWhere updated_at <= excluded.updated_at` ⇒ при равном времени UPDATE проходит ⇒ новый seq ⇒ новая запись журнала) и неназванный отказ (`filterStaleBySeqOrUpdatedAt` без `staleReason` ⇒ причина `conflict`, а клиент снимает `pending` только по `lww_rejected`).

**Варианты**

|---|---|---|---|
| A | Обобщить детектор no-op (`findUnchangedAttributeValueRows` ⇒ общий по таблицам) и добавить в него `erp_engine_inventory_lines`; передавать `staleReason: LWW_REJECTED_REASON` для этой таблицы | 2 файла на сервере + тесты; клиент не трогаем | Низкий: правило «журнал — лог ИЗМЕНЕНИЙ» уже действует для `attribute_values`, мы его расширяем; подтверждение клиенту по-прежнему уходит (`applied_rows`) |

| C | Ничего не делать на сервере, ждать снимка с машины | 0 | Высокий: класс слеп — android не шлёт снимков, а в снимке нет этой таблицы ни на одной платформе |

**Чем проверяется за день.** (1) Тест сервера: повторный push неизменённой строки списка деталей ⇒ **0 новых записей** в `ledger_tx_index` и `last_server_seq` строки **не меняется**, при этом строка **попадает в `applied_rows`** (клиент получает подтверждение). (2) Тест сервера: строка, чья серверная копия новее, ⇒ в `skipped` причина `lww_rejected`. (3) Прод-проверка после выката: `select count(*) from ledger_tx_index where table_name='erp_engine_inventory_lines'` перестаёт расти на неизменённых строках.

**Что заставит передумать.** Если снимок машины покажет, что клиент **не получает** `applied_rows` вовсе (ответ push'а теряется по сети — а логи планшета как раз показывают `Failed to fetch` и прогоны по 38 минут), то no-op фильтр и названный отказ не вытащат класс: нужен другой путь (подтверждение отдельным запросом / повтор с тем же id). Тогда вердикт меняется на «чинить подтверждение», а не «чинить журнал».

**Источники.** `syncWriteService.ts:216–262` (детектор no-op), `syncWriteService.ts:314–339` (фильтр перед журналом), `applyPushBatch.ts:548–658` (отсев по seq/времени), `applyPushBatch.ts:1430` (вызов отсева для строк списка деталей — без `staleReason`), `applyPushBatch.ts:1272–1275` (то же для `operations` — с `LWW_REJECTED_REASON`), `skipReasonPolicy.ts:21–48` (клиентская политика, таблично-независима), прод-разведка 25.11.2026: 1244 записи журнала на 622 строки, 0 `lww_rejected`, 0 `sync_policy_denied` за день.
