# MiniMax-воркер на проде: запуск и эксплуатация

Runbook к сервис-воркеру, который отвечает ИИванычу через MiniMax Code
(промт КАРМАНА `#56`, план `#57`; код — `backend-api/src/minimaxWorker/`,
юнит — `deploy/systemd/matricarmz-minimax-worker.service`).

**Как это устроено (одним абзацем).** Воркер — отдельный сервис на том же боксе,
слушает `127.0.0.1:3010` и говорит с бэкендом по Anthropic-совместимому
`/v1/messages`. Бэкенд ходит к нему тем же SDK, что и в DeepSeek, поэтому
контракт ИИваныча, очередь `ai_chat_requests` и воркер очереди не тронуты —
изменился только транспорт. Аккаунт воркер берёт из пула «Кармана»
(`GET /api/minimax/accounts/available`), поднимает на нём агента MiniMax Code
(`mcode exec`) и отдаёт ответ в Anthropic-совместимом виде. Цепочка звеньев
(D-243): **MiniMax → платный DeepSeek последним** — отказ воркера уводит запрос
на страхователя, а не роняет вопрос оператора.

## Порядок включения (обязательный)

Порядок нельзя менять местами: **пин → юнит → живой прогон → только потом
переключение звена.** Иначе каждый вопрос ИИваныча будет сжигать аккаунт пула
на попытку достучаться до MiniMax и уходить в DeepSeek.

```bash
# 0. свежий dist на боксе (код воркера едет в backend-api/dist)
cd ~/MatricaRMZ && bash scripts/prod-ops/deploy-backend.sh

# 1. пин адресов MiniMax (без него агент на боксе не доходит до MiniMax)
sudo python3 ~/MatricaRMZ/scripts/prod-ops/minimax-dns-pin.py

# 2. юниты: воркер + таймер пина
bash ~/MatricaRMZ/deploy/systemd/install-backend.sh
sudo systemctl enable --now matricarmz-minimax-dns-pin.timer
sudo systemctl start matricarmz-minimax-dns-pin.service

# 3. поднять воркер и убедиться, что он живой
sudo systemctl enable --now matricarmz-minimax-worker.service
curl -fsS http://127.0.0.1:3010/health

# 4. ТОЛЬКО ПОСЛЕ успешного прогона воркера — включить звено
sudo sed -i 's/^MATRICA_AI_PROVIDER=.*/MATRICA_AI_PROVIDER=minimax/' /etc/matricarmz/matricarmz.env
sudo systemctl restart matricarmz-backend-primary.service
sudo systemctl restart matricarmz-backend-secondary.service
```

Шаг 4 меняет значение, а не добавляет вторую строку с тем же ключом, и делается
`sudo sed -i`, потому что файл env принадлежит `root:valstan` (640) — запись
сервисным пользователем упала бы с `Permission denied`.

**Проверить всё это заранее, ничего не меняя на проде:**

```bash
cd ~/MatricaRMZ && bash scripts/prod-ops/deploy-minimax-worker.sh
```

Скрипт по умолчанию — **dry-run**: только проверки и план, ни одного изменения на
машине. Реальные действия — лишь с `--apply`; и даже он не переключает звено
(шаг 4 выше), потому что включать его без живого прогона воркера — сжигать пул.

## Пул пуст: `no_free_accounts` и прочие причины

Пустой пул — это **не поломка**. «Сейчас нельзя» — честный ответ, а не 500:
воркер отвечает `503`, а бэкенд по правилу fail-open уходит на платного
страхователя (DeepSeek). Оператор при этом получает ответ, а не ошибку.

Причины различаются — они видны в ответе воркера и в поле `reason`:

| `reason` | Что значит | Чего ждать |
|---|---|---|
| `pool_empty` | свободных аккаунтов нет (`no_free_accounts`) | сутки учёта комнаты: первый аккаунт — в окне вендорского сброса |
| `pool_no_tokens` | аккаунты свободны, а пары токенов нет (`no_tokens_ready`) | нужен вход владельца в MiniMax; сам не появится |
| `pool_no_handable` | кандидаты были, но все отбракованы (`no_handable_accounts`) | Карман разберётся сам, минуты |
| `karman_unavailable` | Карман не ответил (сеть/сервис) | пауза 15 с и повтор |
| `rate_limited` | превышен лимит запросов (60/мин на токен и IP) | пауза не меньше окна лимита |
| `token_unauthorized` / `token_read_only` | не тот токен / нет права записи | **наша ошибка конфигурации** — чинит владелец, откат на DeepSeek тут спрятал бы поломку |

**Что делать при `no_free_accounts`:** ничего. Это механика пула, а не сбой.
Воркер после отказа встаёт на паузу (для пустого пула — 60 с, с ростом при
повторных отказах; см. `backend-api/src/minimaxWorker/poolBackoff.ts`) и не
дёргает ручку впустую. В журнале видно:

```
minimax worker: пул Кармана не ответил {"reason":"pool_empty","detail":"no_free_accounts","retryInMs":60000}
```

Состояние пула видно и без запроса: `GET /health` → `paused`, `pausedUntilMs`,
`lastFailure`. Если пул пуст долго (сутки и больше) — это сторона «Кармана»:
в служебной комнате `matricarmz-minimax` нет аккаунтов, и ждать надо их
наполнения, а не чинить контур.

**Что делать при отказе аккаунта.** Аккаунт может не сгодиться: очки кончились
или вход протух. Воркер это распознаёт по признакам (`401`, `token expired`,
`invalid_grant`, `insufficient balance` и т.п.), выбрасывает аккаунт (в следующий
запрос уходит `exclude=`, иначе «Карман» отдаст тот же) и берёт следующий —
один повтор запроса. Если и следующий не годится — вопрос уходит на
страхователя, а в журнале видно `аккаунт не годится — беру следующий`.

**Ручка `activations` — только наблюдение.** Мы сообщаем «Карману», какой аккаунт
работал; управление учётом ведёт он. Отказ в ней (например, `404` — «мы его
сегодня не выдавали») **не ломает ответ**: воркер запишет предупреждение
`активация не отмечена` и ответит как обычно. Пустые поля в теле этой ручки не
отправляются вовсе: `null` в `points` превратился бы в `0` (ложное наблюдение
«очков было 0»), а `null` в строке дал бы `400`.

**Ручки `release` у «Кармана» нет** — выдача аккаунта есть погашение. Поэтому
воркер держит **одну аренду**: следующий аккаунт берётся только когда текущий
отказал или его вход скоро истечёт (тогда цепочку продлевает `renew`). Иначе
аккаунты пула сгорали бы за первые минуты (прецедент «Сарафана» 15.11: 15
аккаунтов за две минуты).

## Если что-то пошло не так

| Симптом | Что проверить |
|---|---|
| `/health` не отвечает | `systemctl status matricarmz-minimax-worker.service`; в журнале — ошибка порта или падение при старте |
| `pool: not_configured` | не задан адрес ручек пула: нужен `SECRETS_VAULT_URL` в env (адрес выводится сам) либо `KARMAN_MINIMAX_API_URL` |
| `reason: token_missing` | в комнате `matricarmz` нет ключа `KARMAN_MINIMAX_TOKEN` — положить и перезапустить воркер |
| `reason: token_read_only` | в комнате лежит read-only токен: нужен rw-токен служебной комнаты `matricarmz-minimax` |
| агент не доходит до MiniMax (таймаут 120 с) | пин адресов не на месте: `python3 scripts/prod-ops/minimax-dns-pin.py --check` |
| `agentsQueued` растёт, `agentsActive` = 1 | это штатная защита от OOM: агент один за раз (бокс 1536 МБ, swap запрещён) |
| ИИваныч отвечает, но `answer_source=deepseek` | звено не включено или воркер отказал — смотреть `reason` в ответе воркера и журнал бэкенда |

## Локальная проверка без прода

Весь контур поднимается на заглушке API «Кармана» — без настоящих токенов и без
прода:

```bash
corepack pnpm -F @matricarmz/backend-api minimax:worker-stand
```

Подменяется только внешний бинарь `mcode` (вендорского CLI на машине разработчика
нет) — всё остальное настоящее: клиент пула, профиль, разбор ответа агента,
превращение в `tool_use` и HTTP-слой. Сценарии: успех, пустой пул, отсутствие
пары токенов, отказ аккаунта (берётся следующий), продление цепочки.

## Границы

- **Прод не трогаем без слов владельца.** Установка юнита, переключение звена и
  правки `/etc` — команды владельца, гейт на запись в системные пути их не пускает.
- **Свой пул и свою логику подбора не заводим** — это зона «Кармана» (D-214, D-216).
  Вторая реализация правила разъезжается с первой.
- **Пишущий токен «Кармана» на бокс не кладём** — служебная комната сужает радиус
  поражения (см. [`OPERATIONS.md`](../OPERATIONS.md) §8а).
- **Своих env-файлов не заводим:** новый юнит читает `/etc/matricarmz/matricarmz.env`
  — тот же, что и бэкенд.
- **Роль юнита — `worker`:** иначе поднялся бы второй набор фоновых задач бэкенда
  и очередь ИИваныча разбиралась бы дважды.
