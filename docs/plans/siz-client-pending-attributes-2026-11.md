# План: клиент не отправляет атрибуты карточки сотрудника — сотрудник исчезает из карточек СИЗ (16.11.2026)

**Инцидент.** Оператор СИЗ (`hapik`, компьютер PC63) сообщила: «когда добавила сотрудника, он перестал отображаться в карточках спецодежды». Проверено на проде (БД + журнал синка + диагностические снимки клиентов + логи сервиса).

**Заводская линза:** учёт СИЗ (кадровый контур кладовщика) · затор: не касается (главный затор — начало сборки) · поток: не ломает — обезличивание деталей, ремфонд, `stamped_number` и маршрутный лист не затронуты; правится только приход карточек сотрудников.

## Что установлено (факты с прода)

1. **Оператор:** логин `hapik`, компьютер **PC63**, сегодня на 3.130.0 (обновилась утром).
2. **Сотрудник, которого она добавила** (12.11, 08:28–08:31) — клиент создал сущность EAV `32308884…` и **опубликовал на сервер только строку `entities`**. Атрибуты (ФИО, должность, табельный номер, даты приёма и рождения, размеры) остались в клиентском черновике `card_drafts` (kind=`recovery`), который клиент затем удалил. На сервере у сотрудника **ноль атрибутов**.
3. **Журнал синка (`ledger_tx_index`):** по этому сотруднику — 4 записи `entities` (12.11, 13.11, 16.11) и **ноль** `attribute_values`. Последняя удачная публикация `attribute_values` от её клиента — 11.11 08:24 (правка существующего сотрудника). То есть сломан путь «новый сотрудник», а «правка существующего» ещё работала.
4. **Зеркало СИЗ (`erp_employee_cards`)** берёт сотрудников по ФИО (`loadDirectoryEmployees` пропускает без ФИО). Поэтому по безымянным сотрудникам зеркала нет → **нет карточки СИЗ ни на сервере, ни на клиентах** (клиент строит списки СИЗ из `erp_employee_cards`). Последняя строка зеркала — 11.11 08:03.
5. **Таких сотрудников 6** — все созданы её клиентом (05.11, 09.11, 12.11). Все шесть — без атрибутов на сервере.
6. **Данные всех шести целы** — лежат в `card_drafts.payload_json` на сервере (ФИО, должность, табельный, даты, цех, размеры). Это снимки формы, которые опубликовал сам клиент: данные принадлежат оператору, восстанавливать их можно без догадок.
7. **Клиент PC63 (диагностический снимок, 10:55):** `attribute_values` — **pendingCount 617**, errorCount 0; `entities` — pending 0; по всем остальным клиентам парка pending `attribute_values` = 0. То есть на её машине накопилось 617 строк, которые клиент **не отправляет**.
8. **Сервер такие строки никогда не видел:** в логах сервиса (primary и secondary) за 10–16.11 нет ни одного отказа по `attribute_values` — ни `sync_invalid_row`, ни `sync dependency rows skipped`. Значит, дело в клиенте: пакет с атрибутами до сервера не доходит.
9. **Автолечение не сработало:** сервер видит по PC63 `autoheal_signal` уровня **critical** (driftCount 5, unknownCount 3) и каждые 10 минут шлёт команду починки, но получает `action=skip, reason=daily_budget_exceeded, budget=2` — дневной бюджет исчерпан, клиент остаётся в critical без починки.
10. **Её собственная карточка:** в зеркале 5 строк по ФИО «Хапикова Ирина Сергеевна» (2 из них удалены 08–11.11, 3 живые, одна — с табельным 818). Это отдельная, уже известная проблема дублей сотрудников ([пункт](pending/dubli-sotrudnikov-ostatok-zapret-po-polnomu-klyuchu-shtatka-s-pdo.md)).

## Что сделано

- **Скрипт восстановления** [`backend-api/src/scripts/restoreEmployeesFromDrafts.ts`](../backend-api/src/scripts/restoreEmployeesFromDrafts.ts) — берёт атрибуты сотрудников без атрибутов из их recovery-черновиков и пишет их обычным путём синка (`recordSyncChanges`), чтобы данные уехали всем клиентам. Dry-run по умолчанию; `--apply` — запись; `--mirror` — прогнать зеркало СИЗ после записи. Команда: `pnpm -F @matricarmz/backend-api employees:restore-from-drafts -- --apply --mirror`.
- **Диагностика:** сняты факты по БД, журналу синка, диагностическим снимкам клиентов и логам сервиса (см. «Что установлено»).

## Восстановление на проде (16.11.2026, по решению владельца)

Порядок: сначала данные на сервере, потом клиент — любой ремонт её машины (полный pull, переустановка) сносит неотправленные локальные строки.

1. **Dry-run на проде:** 6 сотрудников, 77 строк атрибутов — у каждого свои данные из его черновика (ФИО, должность, табельный, даты, цех, размеры). Пропущенных нет.
2. **Запись:** `employees:restore-from-drafts -- --apply` → 77 строк `attribute_values` в журнале синка (последний seq 6052676).
3. **Зеркало СИЗ:** сначала dry-run (`создать 6, обновить 0, погасить 0, без изменений 436` — ничего не гасим), затем `--apply` → 6 карточек создано, опубликованы (seq 6052677–6052682), `sync_status=synced`.
4. **Проверка:** атрибуты на сервере — 15+12+11+15+12+12 = 77 по шестерым; «сотрудников без атрибутов» — **0**; живых строк зеркала 435 → 441. Доставка идёт: клиент PC26 уже вытянул seq 6052682, остальные — на ближайшем тике.
5. **Не тронуто:** одна неоднозначность зеркала (табельный номер занят другой карточкой) — была до восстановления, к инциденту не относится.

## Ремонт клиента PC63 (16.11.2026, по решению владельца)

Какая команда нужна, разобрались по коду клиента (`clientAdminService.ts`): `reset_sync_state_and_pull` только сбрасывает курсор и тянет обычным синком — **очередь он не разгребает**. Пересобирает реплику из сервера `force_full_pull_v2` (то же делает `deep_repair`); `reinstall` — команда внешнего watchdog'а, приложение её не исполняет.

1. Команда поставлена штатным серверным механизмом (тот же путь, что у autoheal — `client_settings.sync_request_type`), минуя правило дневного бюджета: `force_full_pull_v2`, request id `f92eee71…`.
2. Клиент взял команду и подтвердил: **ackStatus = ok** в 12:07:09.
3. Снимок клиента после ремонта (12:07:08): `attribute_values` **pendingCount 0** (было 617 → 548 → 0), errorCount 0; `entities` pending 0; локальных строк 53 659 → 52 671 (реплика пересобрана из сервера).
4. Autoheal-сигнал: **critical → observe**, driftCount 5 → 2, driftRatio 0.45 → 0.18, действие — `skip / below_action_threshold` (лечение больше не требуется).
5. Локальных правок, которых не было на сервере, на её машине не осталось — они ушли при пересборке; данные шестерых восстановленных на сервере до этого, так что карточки СИЗ у неё на месте.

**Побочный факт для будущих инцидентов:** клиентский снимок (`diagnostics_snapshots`, scope=`client`) — единственный способ увидеть pending-очередь клиента без доступа к его машине; `audit_log` показывает только действия оператора, а логи клиента лежат на его ПК.

## Что осталось (по шагам)

1. **Причина в клиенте** — почему 617 строк `attribute_values` не уходили: локально не ловится, нужен её клиентский лог (`matricarmz.log`) или воспроизведение на стенде. Ремонт снял симптом (очередь чиста, дрейф не critical), но путь, на котором строки застревали, в коде не найден.
2. **Сторож в программе, чтобы это не повторялось молча:**
   - клиент: строки, которые висят в `pending` дольше N минут, должны быть видны оператору («N документов не отправлено» уже считается — нужен явный признак «застряли»);
   - сервер: `autoheal` при `critical` не должен молча скипаться из-за дневного бюджета — либо бюджет, либо явная отметка «лечение отложено» в диагностике клиентов (сейчас видно только `skip / daily_budget_exceeded`);
   - сервер: команда починки должна быть доступна оператору без ожидания автолечения (сейчас — только через autoheal, который упирается в бюджет).
3. **Связать с пунктом дублей:** у самой оператора 5 строк зеркала на одно ФИО (3 живые) — отдельный открытый пункт, не связан с текущим инцидентом.

## Границы

- Запись на проде — только по решению владельца (восстановление атрибутов шестерых из их черновиков + зеркало СИЗ); никаких других изменений в прод-данных не вносилось.
- Данные сотрудников в доки не попадают (ФИО/логины) — в плане только счётчики и даты.
