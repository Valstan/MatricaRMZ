# План: Платежи по двигателям (карточка двигателя + контракт + слоты + отчёты)

> При выходе из plan mode первым шагом скопировать этот план в `docs/plans/engine-payments-2026-07.md` (PR-flow, видимость между машинами).

## Context

Владелец (бухгалтерский контур) хочет вести оплаты по каждому двигателю: стоимость по контракту, авансы/доавансы, окончательный расчёт — с итогами (оплачено, переплата/недоплата). С первого аванса идёт отсчёт **90 дней** на ремонт; бухгалтер должен видеть «горящие» двигатели (жёлтый/красный фон в контракте, счётчик в списке контрактов) и собирать их в накопительную служебную записку. Деньги часто приходят раньше двигателей → нужны «слоты» в контракте с распределением аванса, при привязке двигателя платежи слота становятся его платежами. Плюс отчёт-матрица платежей по контракту/ДС.

Решения владельца: подсветка гаснет по факту **ремонта двигателя** (не оплаты); срок — **константа 90 дней**.

## Ключевое архитектурное решение

**Единственный источник истины — контрактный EAV-атрибут `contract_payments`** (dataType `json`), слоты внутри него. Карточка двигателя читает/пишет **через контракт** (`contract_id` у двигателя уже есть). Почему не по-двигательный атрибут: требование двусторонней видимости иначе означает двойное хранение одних денег → вилки при sync (два бухгалтера); платежи по пустым слотам всё равно живут только на контракте; «привязка двигателя» = проставить `engineId` в слоте, без миграции данных. Никаких DDL-миграций — чистый EAV, едет существующим sync.

```ts
// shared/src/domain/payments.ts (новый) + payments.test.ts
type PaymentKind = 'contract_price' | 'advance' | 'extra_advance' | 'final';
interface PaymentRow { id: string; date: string /*ISO*/; amountKop: number /*копейки, int*/;
  kind: PaymentKind; note?: string; countdownStart?: boolean /*макс. один на слот*/ }
interface PaymentSlot { id: string; sectionKey: string /*'primary'|'ДС {seq}'*/;
  engineBrandId?: string; engineId?: string /*пусто = слот без двигателя*/;
  contractPriceKop?: number; payments: PaymentRow[] }
interface ContractPayments { version: 1; slots: PaymentSlot[] }
const REPAIR_COUNTDOWN_DAYS = 90;
```

Чистые функции (все под unit-тестами): `parseContractPayments` (толерантный), `slotTotals` (оплачено/дельта/последний платёж/дата старта отсчёта; дефолт старта — самый ранний `advance`, если флаг не стоит), `countdownStatus(slot, today, engineRepaired)` → `none|ok|warning(>45 дн)|danger(≤20 дн осталось или просрочка)`; гасится `engineRepaired`; `syncSlotsWithPlan` (создать слоты по plan-qty секций, привязать двигатели к свободным слотам, слоты с платежами не удалять; отвязка двигателя оставляет платежи на слоте), `distributeAmount` (равномерно по слотам секции, остаток копеек первому), `findSlotForEngine`, `addPayment/updatePayment/removePayment` (иммутабельно), `burningEnginesCount`.

### Этап 6 — массовый перенос двигателей пачкой (промты КАРМАНА #18/#19)

Владелец (08.11.2026): «раскидывать авансы и двигатели пачками — чтобы можно было выделять их галочками и переносить в какую-то ДС списком, скопом, целым блоком, а не прощёлкивать по одному». Разнос авансов по отмеченным слотам закрыт нитью 13.11 (PR #1707); **перенос двигателей пачкой** — эта нить.

- **Домен** `shared/src/domain/payments.ts`: `planBulkEnginePlacement` (чистый расчёт: кто куда сядет, кто сверх плана, у кого цена места разошлась с планом) + `applyBulkEnginePlacement` (запись через `attachEngineToSlot`). Режим «по плану» (целевой раздел пустой): раздел выбирается по строкам плана договора — там, где запланирована марка движка; режим с явным разделом — **строго** в него, fallback в соседний раздел запрещён (как у одиночного переноса).
- **Риск «движок попал не в тот слот» закрыт тремя правилами**: место — только своей марки; занятое место не трогаем; своих мест не хватило — место сверх плана, отдельным счётчиком.
- **UI** (`ContractDetailsPage.tsx`, вкладка «Двигатели»): список ВСЕХ движков контракта с галочками (раньше там был только список «без раздела»), колонки «Раздел» и «Место», панель действий «Разложить по слотам» / «Перенести пачкой» + выбор раздела, **предпросмотр до записи**, итог операции и **откат** к снимку.
- **Запись**: места — одной записью платежей (`mutateContractPayments`, план считается по свежему состоянию), разделы — карточкам движков (`engines:card:save`). Деньги за движком остаются на прежнем месте («деньги без движка»).
- **Аудит факта** — [`../reports/engine-payments-audit-2026-11-18.md`](../reports/engine-payments-audit-2026-11-18.md): 1010 движков без раздела, 53 сироты, 9 посажены не в тот раздел, 34,4 млн ₽ ждут движка.

### Этап 7 — вкладка «Авансы и расчёт» (аудит по цене) — по образцу ведомости владельца

Владелец 18.11.2026 прислал свою ручную ведомость «АУДИТ по цене по ВИ № 1 и ВИ № 2 Технотранс» (Excel) и попросил такую же таблицу в карточке контракта: «чтобы удобно было оператору забивать данные по контракту и по двигателям, подтягивать двигателя, видеть какие уже пришли и делаются, и по ним авансирование рассчитывать».

**Что взято из ведомости и откуда оно в программе:**

| Столбец ведомости | Откуда в программе |
|---|---|
| Модель двигателя | марка движка (`engine_brand_id`) |
| Номер двигателя | `engine_number` карточки (клик ведёт в карточку) |
| Сумма по договору | цена места (`erp_contract_payment_slots.contract_price_kop`), для движка без места — цена плана по марке |
| Аванс 50% | расчётная колонка (процент от цены) + фактически внесённое (`advance` + `extra_advance`) |
| Долг до авансирования | цена − внесённое |
| Номер/дата заключения | раздел договора: основной договор или ДС N (номер и дата подписания) |
| РКМ получены заказчиком | состояние движка «Принято заказчиком» + дата отгрузки |
| Сумма ок-расчёта | платёж вида `final` |
| Итоги по СП/ДС | итоги по разделам и по договору |

**Сделано:** домен `buildEngineFinanceTable` (чистая функция: строки, итоги по разделам и по договору) + вкладка «Авансы и расчёт» в карточке контракта: таблица, галочки, массовый разнос аванса (суммой или процентом — та же форма, что и в списке мест), печатная форма «аудит по цене».

**Что в ведомости есть, а в программе пока нет** (отдельная работа, требует новой сущности): «Цена по заключению ВП без НДС» и «Фиксированная цена с НДС 20%» — это ВТОРАЯ ценовая система (фиксированная цена по «заключению ВП» по каждому двигателю), в программе цена одна — из плана договора; «Примечание» по каждому двигателю (в программе примечание есть только у платежа); ставка НДС в договоре (20/22%) — тоже нет. Вынос их в программу = новая строгая таблица + контракт синка + реплика клиента.

### Этап 8 — НДС и примечание по двигателю (решение владельца 18.11.2026)

Владелец ответил на вопрос по ведомости «Аудит по цене»: **вторую ценовую систему («Цена по заключению ВП без НДС», «Фиксированная цена с НДС 20 %» — своя цена по каждому двигателю) не заводим**. Заводим только НДС и примечание.

**Ставка НДС раздела** — `contract_sections.primary.vatPercent` (%, 20 или 22). Живёт внутри секций, как и срок ремонта: EAV заморожен, а секции едут в зеркало `erp_contracts.sections_json` сами — миграции не нужно. Дополнения наследуют ставку основного договора (`effectiveVatPercent`). Цена по договору считается **с НДС**, поэтому «без НДС» = цена ÷ (1 + ставка/100), а «в т.ч. НДС» — остаток. Ставки нет → обе цифры не показываются вовсе («—», а не ноль: ноль означал бы «НДС нет»).

**Примечание по двигателю** — поле `engine_note` строгой карточки (`erp_engine_cards`), оно уже было в программе (метка «Примечание» в карточке движка, поиск по файлам, история). Не хватало двух вещей: доставить его в список движков (`EngineListItem.engineNote` + чтение в `listEngines`) и показать/править прямо в сводке оплаты.

**Правка примечания в сводке.** Ячейка правится на месте и пишется той же дверью `engines:card:save`. Список движков читает EAV, а он догоняет запись после цикла синка — поэтому введённый текст не затирается «внешним» значением (оператор правит — поле его, до переоткрытия карточки).

## Сквозные предосторожности
- `exactOptionalPropertyTypes`: не присваивать `undefined` опциональным (`engineId`, `note`) — conditional spread.
- Read-modify-write одного крупного атрибута: писать только после пользовательской правки / реального diff syncSlots; перед записью перечитывать.
- Деньги — целые копейки; общий форматтер в shared (согласие UI и отчётов); есть `formatRuMoney` в `utils/dateUtils.ts` — сверить/переиспользовать.
- Отвязка двигателя от секции: платежи остаются на слоте («деньги без двигателя») — описать владельцу в PR.
