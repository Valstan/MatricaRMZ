# Инструменты: сведение двух справочников в один

> Разведка 2026-08-13. **Код не меняется до решения владельца** — это план и обоснование.
> Заземление: SQL по проду (`ssh matricarmz`), чтение кода на `main` @ `1ac710c7`.

## Коротко

Исходная гипотеза («`tool_catalog` дублирует позиции номенклатуры с `itemType='tool'`») **подтвердилась, но
дублирование глубже и хуже**: инструмент размазан по **восьми** структурам, две из них — мёртвые,
две — сироты, а связка между номенклатурой и экземплярным учётом **на проде физически разорвана**.
Побочный результат разведки: раздел **«Учёт инструментов» на проде сейчас нерабочий** — выпадашка выбора
инструмента пуста по двум независимым причинам (см. §4). Это не следствие будущей миграции, это текущее
состояние.

Живых данных — **три экземпляра, три наименования, одно движение**. Стоимость миграции близка к нулю,
и это лучший момент решать: через полгода реального учёта цена вырастет на порядок.

## 1. Что реально лежит в проде

```
entity_types:  tool=3, tool_catalog=3, tool_property=4   (alive)
erp_nomenclature item_type='tool'          = 2
erp_nomenclature item_type='tool_consumable' = 1
directory_tools                             = 2
operations operation_type='tool_movement'   = 1
erp_tool_templates                          = 0
```

Восемь структур, описывающих один и тот же предмет:

| # | Где | Что там на самом деле | Живых | Статус |
|---|---|---|---|---|
| 1 | `erp_nomenclature` `item_type='tool'` | `TL-000197 Шуруповерт`, `TL-000198 Лопата` — **позиции, набитые данными экземпляров** | 2 | ⚠️ смешаны уровни |
| 2 | `directory_tools` | зеркало **экземпляров** из EAV (миграция `0045`), источник `directoryRefId` | 2 | ⚠️ уровень перепутан |
| 3 | EAV `tool` | экземпляры: таб. № 1/2, s/n, подразделение, фото, даты, свойства | 3 | ✅ содержательно |
| 4 | EAV `tool_catalog` | наименования: `Молоток`, `Шуруповерт`, `Лопата` | 3 | 🔴 дубль номенклатуры |
| 5 | EAV `tool_property` | свой справочник свойств: `Радиус`×2, `Высота`, `Длина` | 4 | 🔴 дубль `nomenclature_property` |
| 6 | `nomenclature_template` `default_tool` + 8 `nomenclature_property` | «Инвентарный номер», «Производитель», «Ресурс, ч», «Период поверки»… | 1+8 | ⚠️ смешаны уровни |
| 7 | `erp_tool_templates` | — | 0 | 💀 мёртвая таблица |
| 8 | `erp_nomenclature` `item_type='tool_consumable'` | «Лопата» без кода | 1 | 👻 невидима в UI |

### 1.1. Пересечение по наименованиям — есть, и оно точное

| Наименование | `tool_catalog` | номенклатура `item_type='tool'` | EAV `tool` (экземпляр) |
|---|---|---|---|
| Шуруповерт | ✅ `37125f27` | ✅ `TL-000197` | ✅ s/n `1234567890`, таб. № 1 |
| Лопата | ✅ `bb87ab05` | ✅ `TL-000198` | ✅ s/n `334455`, таб. № 2 |
| Молоток | ✅ `1f5e246b` | ❌ | ❌ |
| Лопата (второй раз) | — | ✅ `item_type='tool_consumable'`, без кода | — |

Два из трёх наименований задублированы буква в букву. «Молоток» живёт только в `tool_catalog` —
в номенклатуре его нет, то есть справочники **уже разъехались** на трёх записях.

### 1.2. Главный перевёртыш: номенклатурная «позиция» — это экземпляр

Ожидалось: `erp_nomenclature item_type='tool'` = каталог наименований, `tool` = экземпляры.
Фактически `spec_json` строки `TL-000197`:

```json
{"templateId":"4df035e8-…","propertyValues":{
  "tool_number":"1", "serial_number":"1234567890",
  "department_id":"65146db0-…", "received_at":"1770584400000",
  "description":"зеленый шуруповерт Бош",
  "tool_catalog_id":"37125f27-…",
  "properties":"[object Object]", "photos":"[object Object]"}}
```

Это **слепок конкретного шуруповёрта**, а не наименования: серийный номер, табельный номер,
подразделение, дата поступления. Цепочка, как это получилось:

```
EAV tool (экземпляр)
   └─ миграция 0045_backfill_directory_from_entities.sql
        WHERE t.code = 'tool'   ← берёт ЭКЗЕМПЛЯРЫ
   └→ directory_tools (id = id экземпляра)
        └─ migrateDirectoriesToNomenclature / nomenclatureUpsert
        └→ erp_nomenclature item_type='tool'   ← экземпляр стал ПОЗИЦИЕЙ
```

То есть уровень «позиция/экземпляр» был потерян не в дизайне, а в конкретной миграции: `0045` зеркалит
в справочник наименований таблицу экземпляров. Настоящий справочник наименований (`tool_catalog`)
в номенклатуру не переносился вовсе.

**Попутная потеря данных:** `properties` и `photos` записаны в `spec_json` строкой `"[object Object]"` —
объект приведён к строке при переносе. Список свойств и фотографии в номенклатурной копии **утрачены**
(в EAV-оригинале они целы: у «Лопаты» — фото `Фото лопаты.jpg` 392 КБ и свойство «Длина = 1,4»).

### 1.3. Сироты

- `2f499c3d` — EAV `tool` «Новый инструмент»: нет `department_id`, нет строки в `directory_tools`,
  нет позиции в номенклатуре. Создан позже `0045` через кнопку «Создать инструмент» на номенклатурной
  странице (`createSourceEntityForDirectoryKind('tool')` заводит EAV-сущность **до** строки номенклатуры,
  и на этой попытке строка не доехала). Не виден **ни в одном** списке.
- «Лопата» с `item_type='tool_consumable'` и пустым кодом: строгий фильтр раздела «Инструменты» её не
  берёт, legacy-fallback включается только при нуле строгих строк (`NomenclatureDirectoryPage.tsx:133-136`),
  а строгих две. Тоже не видна нигде.

## 2. Сверка моделей: кто что умеет

### Есть у экземплярного учёта (`tool`) и **нет** у номенклатуры

| Поле / способность | Комментарий |
|---|---|
| Табельный номер (`tool_number`) | заводской «инвентарник» на конкретной единице |
| Подразделение-владелец (`department_id`) | **несёт права доступа**: не-admin видит только свой цех (`toolsService.ts:191-262`) |
| Дата поступления / снятия / причина снятия | жизненный цикл единицы |
| Фото единицы (`photos`) | у «Лопаты» реально лежит файл |
| Свойства по экземпляру (`properties` JSON → `tool_property`) | «Длина = 1,4» у конкретной лопаты |
| Выдача/возврат сотруднику (`operations` `tool_movement`) | с подтверждением, комментарием, историей |
| Печать карточки в PDF (`exportToolCardPdf`) | отдельная печатная форма |
| Отчёт «где инструмент» (`buildToolsReport`) | на складе / на руках / неизвестно |

### Есть у номенклатуры и **нет** у `tool_catalog`

`tool_catalog` — это **ровно одна EAV-сущность с единственным атрибутом `name`** (проверено по проду:
у типа `tool_catalog` заведён один `attribute_def` — `name`). Больше в ней нет ничего. Номенклатура даёт:

код/артикул, SKU, штрихкод, группа, единица измерения, поставщик и артикул поставщика, min/max остаток,
активность, шаблон свойств, участие в заявках снабжения и складских документах, остатки и движения,
серийные экземпляры (`erp_engine_instances`), места хранения, вкладки карточки «Основное / Свойства по
шаблону / Экземпляры / Склад и движения» (после #558).

**Вывод по §2:** `tool_catalog` не умеет ничего, чего не умеет номенклатурная позиция.
Это чистый дубль на одном поле. А вот экземплярный учёт `tool` — **не** дубль: у него восемь
способностей, которых в номенклатуре нет.

### Чего не хватит, если экземпляры переносить в `erp_engine_instances`

Таблица `erp_engine_instances` тонкая: `serial_number`, `contract_id`, `current_status`,
`warehouse_location_id`. В ней **нет** подразделения-владельца, дат поступления/снятия, фото,
свойств экземпляра, табельного номера и истории выдачи сотруднику. Поэтому «просто перенести
инструменты в существующий механизм экземпляров» — не вариант без доработки (см. §5, вариант C).

### Свойства: три параллельных механизма

| Механизм | Где | Живёт на уровне |
|---|---|---|
| `tool_property` (EAV) | «Справочник свойств» под «Инструментами» | экземпляра |
| `nomenclature_property` + шаблон `default_tool` | «Склад → Номенклатура → Шаблоны» | позиции… **и экземпляра** |
| `spec_json.propertyValues` | строка номенклатуры | смешано |

Шаблон `default_tool` сам смешивает уровни: «Производитель», «Артикул поставщика», «Ресурс, ч»,
«Гарантия, мес», «Условия хранения» — свойства **наименования**; «Инвентарный номер», «Период поверки,
мес», «Последняя поверка» — свойства **конкретной единицы** (у каждого штангенциркуля своя поверка).

## 3. Что видит оператор сегодня

**Меню «Производство → Инструменты»** (`ToolsPage` = `NomenclatureDirectoryPage` + `TOOLS_PRESET`):
список из двух строк — `Шуруповерт`, `Лопата`. Клик открывает **карточку номенклатуры**
(`openNomenclature`). Свойства и фото в ней пустые (`"[object Object]"`). Перехода на карточку
инструмента нет. Рядом кнопка «Справочник свойств» ведёт в EAV-справочник `tool_property`, которым
эта карточка **не пользуется** — им пользуется другая, недостижимая отсюда карточка.

**Меню «Снабжение → Учёт инструментов»** (`SupplyToolMovementsPage`): форма выдачи/возврата.
Выпадашка «Инструмент или товар из номенклатуры» **пуста** (см. §4), в ней подсказка
«перенесите справочники производства в складскую номенклатуру». Единственное существующее движение
(«Лопата», получена, подтверждена) в списке видно, но кнопка «Открыть карточку» не срабатывает.

**Карточка инструмента** (`ToolDetailsPage`, 985 строк — полноценная: свойства, движения, фото,
печать) достижима **только по deep-link** (`kind: 'tool'`) или из глобального поиска. Ни один пункт
меню на неё не ведёт.

Итого оператор видит две несвязанные ветки, ни одна из которых не работает целиком, и справочник
свойств, прицепленный не к той карточке.

## 4. Два живых дефекта, найденных попутно

Оба существуют **уже сейчас**, независимо от того, какой вариант сведения выберет владелец.

**Д1. `directoryRefId` пуст у всех строк-источников.** Фильтр subject'ов требует непустой
`directoryRefId` (`SupplyToolMovementsPage.tsx:38-41`). На проде:

```
directory_kind='tool'  → 2 строки, из них с directory_ref_id: 0
directory_kind='good'  → 84 строки, из них с directory_ref_id: 0
```

Ни один инструмент и ни один товар в выпадашку не попадает. (У деталей ссылки на месте — 561 из 561;
потеря точечная, только tool/good/service.)

**Д2. Название группы не проходит whitelist.** Даже если Д1 починить, фильтр сверяет название группы
со списком `'инструменты' | 'инструмент и оснастка'`, а на проде группа называется
**«Закупка · Инструмент и оснастка»**; `labelNorm` — это только `trim().toLowerCase()`, префикс не
снимается. То же с товарами: группа «Закупка · Товары» против ожидаемого `'товары'`. Whitelist
отстал от переименования групп при сидинге.

Починка Д1+Д2 — ~20 строк и оживляет раздел независимо от миграции. Предлагаю сделать её **первым
шагом в любом варианте**: она же и проверит, что выбранная модель subject'а работает на живых данных.

## 5. Варианты

### Вариант A — свести `tool_catalog` в номенклатуру, `tools.*` оставить экземплярным учётом ⭐

Граница проводится по смыслу: **номенклатура = что это за инструмент, `tool` = вот эта конкретная штука**.

- `tool_catalog` (3 записи) → позиции номенклатуры `item_type='tool'`. «Молоток» заводится новой позицией,
  «Шуруповерт»/«Лопата» сливаются с существующими `TL-000197/198`.
- У EAV `tool` поле `tool_catalog_id` заменяется на `nomenclature_id`; в карточке инструмента
  выпадашка «Наименование» смотрит в номенклатуру.
- Из строк номенклатуры вычищаются экземплярные `propertyValues` (`tool_number`, `serial_number`,
  `department_id`, `received_at`, `tool_catalog_id`) — они остаются только в EAV-экземпляре.
- Шаблон `default_tool` чистится до свойств наименования; «Инвентарный номер», «Период поверки»,
  «Последняя поверка» уезжают в `tool_property` (справочник свойств экземпляра).
- `directory_tools` перезаполняется из **`tool_catalog`**, а не из `tool` (правка логики `0045`),
  и `directoryRefId` наконец проставляется → Д1 закрывается структурно.
- Карточка инструмента получает ссылку «Открыть позицию номенклатуры», карточка номенклатуры —
  вкладку «Экземпляры инструмента» со списком EAV-`tool`. Раздел «Инструменты» в меню начинает вести
  на номенклатуру осознанно (это каталог), а «Учёт инструментов» — на экземпляры.
- Мёртвое сносится: `erp_tool_templates` (0 строк), сирота `2f499c3d`, «Лопата»-`tool_consumable`.

**Плюсы:** одно наименование — одна запись; заявки снабжения, остатки, поставщики, артикулы работают
для инструмента «бесплатно»; экземплярный учёт с его правами по подразделениям и историей выдачи
сохраняется целиком, ничего не переписывается. Миграция — 3 записи.
**Минусы:** остаются две карточки (позиция и экземпляр) — но они про разные вещи, и это честно;
нужна аккуратная развязка шаблона свойств.

### Вариант B — оставить как есть, провести границу в документации

Записать в `docs/WAREHOUSE.md` и `CODEBASE_MAP.md`: `tool_catalog` — справочник наименований
экземплярного учёта, номенклатура `item_type='tool'` — складская позиция; они намеренно разные.

**Плюсы:** нулевой риск, ноль кода.
**Минусы:** документация закрепила бы неправду — сегодня номенклатурные «позиции» набиты данными
экземпляров, а «Молоток» уже разъехался. Пришлось бы сначала всё равно чинить §1.2, то есть половину
варианта A. Дублирование ввода остаётся: заводя инструмент, оператор набивает наименование дважды,
и через год два справочника разойдутся необратимо. Д1/Д2 придётся чинить отдельно.

### Вариант C — полное слияние: экземпляры инструмента в `erp_engine_instances`

Убрать EAV `tool` целиком, инструмент = позиция номенклатуры + серийные экземпляры общего механизма.

**Плюсы:** один механизм экземпляров на весь завод, одна карточка, вкладка «Экземпляры» уже есть.
**Минусы:** `erp_engine_instances` придётся расширять под подразделение-владельца, даты поступления/
снятия, фото, свойства экземпляра, табельный номер и историю выдачи сотруднику — иначе теряются восемь
способностей из §2. Плюс переписывание `toolsService` (1291 строка), `ToolDetailsPage` (985 строк),
модели прав по подразделениям и печатной формы. Большой объём ради трёх записей;
`erp_engine_instances` заточена под двигатели (`contract_id`, `contract_section_number`) и обрастёт
полями, которые двигателям не нужны.

### Рекомендация

**Вариант A.** Он убирает ровно то, что дублируется (справочник наименований на одном поле), не трогает
то, что дублем не является (экземплярный учёт с правами и историей), попутно чинит перепутанные уровни
из §1.2 и структурно закрывает Д1. Вариант C — возможное продолжение через год, когда станет ясно,
нужен ли инструменту общий механизм экземпляров; сейчас он платит рефакторингом двух тысяч строк за
три записи. Вариант B закрепляет расхождение, которое уже началось.

## 6. Риски миграции

| Риск | Оценка | Мера |
|---|---|---|
| Потеря данных при слиянии | **низкая** — 3 наименования, 3 экземпляра, 1 движение | dry-run со сверкой построчно, вывод в тело PR |
| Разрыв ссылки `tool.tool_catalog_id` | средняя — 2 живые ссылки | миграция ставит `nomenclature_id` по точному совпадению имени; несовпавшие — в отчёт, не в тишину |
| Единственное движение осиротеет | низкая — `operations.engine_entity_id` указывает на EAV-`tool` `473899f6`, который остаётся | экземпляры не переносятся → ссылка цела |
| Заявки снабжения / остатки на позициях `tool` | **отсутствует** — проверено: 0 строк в `erp_reg_stock_balance`, `erp_document_lines`, `erp_engine_instances` | — |
| Чистка `propertyValues` затрёт нужное | низкая — там `"[object Object]"` вместо свойств и фото | оригиналы в EAV целы; сверять после переноса |
| Расхождение прав: `tools` в «Производстве», `tool_accounting` в «Снабжении» | средняя | `LEDGER_SECTION_BY_ENTITY_TYPE` намеренно не мапит `tool*` (fail-open, `sectionAccess.ts:306`) — при смене модели решить осознанно, а не по умолчанию |
| Клиенты с несинхронизированной локальной БД | средняя | миграция идёт через ledger как обычная правка мастер-данных; SQL мимо ledger не гнать (`server-script-sync-write-gotchas`) |

**Точка невозврата отсутствует:** пока живых записей три, откат — это ручное пересоздание трёх строк.

## 7. Порядок работ (если владелец выбирает A)

1. **Ф0. Починить Д1+Д2** — отдельный PR, ~20 строк, оживляет «Учёт инструментов» на текущих данных.
   Приёмка: CDP-смоук — выпадашка непуста, «Открыть карточку» открывает номенклатуру.
