## Что просил владелец (промт #21, дословно)

1. «набор норм должен заводиться прямо из карточки СИЗ, без ручной правки приказа — в том числе набор на мыло, которого в приказе сейчас нет»;
2. «Нужна отдельная карточка на мыло: выдаётся отдельно от карточки по спецодежде, по своей норме (мыло выдаём всем стандартно, сверх нормы не выдаём)»;
3. «Проверить, что делает дата возврата в карточке… Там же должен быть процент износа» — **сделано 11.11** (миграция 0126): отметка «получил обратно», дата возврата, процент износа в бланке и в ведомости;
4. «Саму карточку СИЗ с оборотной стороной я пришлю» — **не прислана**: правило пересчёта процента износа не выводим, колонка под него есть и заполняется кладовщиком.

## Как мы это читаем (уточняем у себя, библиотеку не переписываем)

**«Карточка СИЗ»** — личная карточка сотрудника в модуле Кладовщика (`PpeCardDetailsPage`): там видны позиции норм сотрудника, сроки выдачи, история выдач. Значит «завести набор из карточки» = **одно действие в карточке**: собрать набор норм из позиций карточки (номенклатура + количество + срок носки) и сразу назначить его карточке — без правки приказных данных (миграций, сидов приказа).

**«Набор на мыло, которого в приказе нет»** — значит набор нужен **свой набор завода** (в модели уже есть: `source_kind='local'`, экран «Нормы выдачи» → «+ Набор»). Не хватало пути «из карточки» и отдельного вида, в котором мыло не мешается спецодежде.

**«Отдельная карточка на мыло»** — у сотрудника **две открытые карточки выдачи**: по спецодежде и по мылу. Поэтому у карточки и у набора появляется **вид** (`kind`): `workwear` | `soap`. Карточка принимает только наборы своего вида; выдача мыла не смешивается с выдачей спецодежды в одной карточке и в одном журнале.

**«Мыло выдаём всем стандартно»** — набор вида `soap` не привязан к должности и назначается всем карточкам мыла: заводится один раз, действует на всех.

**«Сверх нормы не выдаём»** — правило выдачи, а не текст: остаток по позиции считается в домене, и для вида `soap` сервер отказывает в выдаче сверх остатка. Для спецодежды норма остаётся напоминанием (как сейчас) — запрет владелец просил именно про мыло.

## Заводская линза (три строки)

- **Участок:** склад (СИЗ): номенклатура, выдача, учёт выданного.
- **Кормит ли затор:** не кормит. Главный затор модели — «начало сборки: ручной подбор совместимых деталей из обезличенного фонда»; СИЗ его не касается.
- **Инвариант потока:** не ломает. Обезличивание деталей, партия/экземпляр (`stamped_number`), маршрутный лист и сдельщина против нормо-часов не затрагиваются; вид карточки СИЗ — это разрез учёта выдачи, движение по фонду деталей не меняется.

## Этап 1 — вид СИЗ: карточка спецодежды и карточка мыла (PR 1)

### 1.1. Данные

- Миграция `backend-api/drizzle/0131_ppe_card_kind.sql`:
  - `ppe_norm_sets.kind` (text, not null, default `'workwear'`) — вид набора;
  - `ppe_issue_cards.kind` (text, not null, default `'workwear'`) — вид карточки;
  - уникальный индекс `ppe_issue_cards_employee_open_uq` (employee_id) → `ppe_issue_cards_employee_kind_open_uq` (employee_id, kind): открытая карточка теперь одна **на вид**, а не одна на сотрудника.
- `backend-api/src/database/schema.ts` — те же колонки.
- Строгая таблица, не EAV (EAV заморожен).

### 1.2. Контракт синхронизации (четыре места — забытое = тихая потеря поля)

- `shared/src/sync/dto.ts` — `ppeNormSetRowSchema` += `kind`, `ppeIssueCardRowSchema` += `kind` (мягко-опционально: старые строки без поля остаются валидными).
- `shared/src/sync/registry.ts` — `PPE_NORM_SET_FIELDS` += `{ db: 'kind', dto: 'kind' }`, `PPE_ISSUE_CARD_FIELDS` += то же.
- `backend-api/src/services/sync/ppeSyncPublisherService.ts` — `toPpeNormSetInput` / `toPpeIssueCardInput` += поле (здесь поля перечисляются руками).
- Реплика клиента: `electron-app/src/main/database/schema.ts` (sqlite-таблицы), `electron-app/src/main/database/migrate.ts` (inline `CREATE TABLE` + доводка долгоживущих БД через ALTER), `android-app/src/db/migrate.ts` — **зеркало electron строчки в строчку** (сторож `drizzleChain.test.ts` сверяет `sqlite_master` посимвольно).

### 1.3. Сервер

- `upsertPpeNormSet` — принимает `kind`; приказные наборы остаются `workwear` (вид приказа не переопределяем).
- `openPpeCard(employeeId, kind)` — открытая карточка данного вида; при открытии карточки вида `soap` сервер **сам назначает** ей все живые наборы вида `soap` («мыло выдаём всем стандартно» — одним действием, без обхода каждого сотрудника).
- `getPpeCard({ employeeId, kind })` — карточка нужного вида.
- `assignCardNorms` — гейт: набор назначается только в карточку своего вида.
- `resolveEmployeeNormSetIds(employeeId, kind)` — личные нормы по виду.
- Новый набор вида `soap` — назначается всем открытым карточкам мыла (иначе «всем» пришлось бы назначать вручную).
- `distributeCollective` — коллективная выдача остаётся по спецодежде (вид `workwear`): карточка выбирается по виду, иначе при двух карточках у сотрудника выдача попала бы в случайную.

### 1.4. Клиент

- **«Нормы выдачи»** (`PpeNormsPage`): колонка «Вид», фильтр по виду, вид при создании набора; приказные наборы — только `workwear`.
- **Карточка СИЗ** (`PpeCardDetailsPage`): переключатель вида [Спецодежда | Мыло]; карточка, нормы, сроки и история выдач — по выбранному виду; для вида `soap` — подсказка «норма всем».
- **Список карточек** (`PpeCardsPage`): метка вида у строки сотрудника.
- **Журнал выдачи** (`PpeJournalPage`): фильтр по виду — «выдаётся отдельно… свой журнал».
- IPC: `ppe:cards:open` / `ppe:cards:get` / `ppe:cards:byEmployee` / `ppe:norms:upsert` — принимают `kind`; новый канал `ppe:cards:createNormSet` (набор из карточки) пишет — значит, в список write-гейта разделов (`sectionGate.ts`) и в `ppe.test.ts`.

### 1.5. Набор норм из карточки (одно действие)

- Сервер: `POST /ppe/cards/:id/norm-sets` — { name, kind, lines[], postTitle? }: создаёт набор (`source_kind='card'`) и **назначает его карточке** в том же запросе; для вида `soap` — всем открытым карточкам мыла.
- Клиент: в карточке кнопка «Набор из позиций карточки»: название, вид (задан видом карточки), строки из текущих позиций карточки (номенклатура, количество, срок носки) + «+ Позиция» (например «Мыло» из справочника номенклатуры).
- Должность подставляется из карточки — набор, заведённый из карточки, потом подхватывается автоподбором «Назначить нормы по должности» у других сотрудников.

## Этап 2 — «сверх нормы не выдаём» (PR 2)

- Домен (`shared/src/domain/ppe.ts`): остаток по позиции — `ppeIssueRemainder(norms, entries, now)`: норма за период (срок носки; годовая норма — 12 месяцев) минус выданное за текущий период. Правило фиксируется в домене, а не в тексте (план #26, «Осторожности»).
- Сервер: в `issuePpe` — для вида `soap` отказ при количестве сверх остатка, с внятным текстом («норма исчерпана»); спецодежда не затрагивается.
- Клиент: остаток виден в карточке («осталось по норме») и в форме выдачи; поле количества ограничено остатком.
