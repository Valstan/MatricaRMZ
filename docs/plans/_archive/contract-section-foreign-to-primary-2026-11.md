# Раздел договора: номер договора в поле раздела → «основной договор»

**Заказ владельца (13.11.2026):** «по 8 движкам: перенеси договор в „основной договор“».

**Статус:** в работе. **Дата:** 2026-11-13. **Ника:** привязка двигателей, раздел договора, перенос данных.

Продолжение нитки «колонка „Договор“» (план [`_archive/binding-column-contract-digits-2026-11.md`](_archive/binding-column-contract-digits-2026-11.md)): тогда 55 движков со старым форматом раздела ДС перевели к канону «ДС N», а 8 движков с номером договора в поле раздела оставили как есть — решение владельца по ним ещё не было. Теперь решение есть.

## Что лежит в данных (проверено на проде 12.11.2026, 578 заполненных строк)

| Вид значения `contract_section_number` | Движков | Что это |
|---|---|---|
| «ДС 1»…«ДС 5» | 199 | канон ДС (`isContractAddonToken`) |
| `primary` | 276 | основной договор |
| пусто | 40 | раздела нет |
| «1»–«4» (голые числа) | 55 | легаси импорта: номер ДС без слова «ДС» |
| номер договора (`2325187913551442245231239/739-1/…`) | 8 | мусор импорта: в поле раздела лежит номер договора |

## Решение владельца и его смысл

- Голое число — это номер ДС → «ДС N» (решение 13.11.2026, сделано в прошлой нитке).
- Всё прочее не-ДС — основной договор → `primary` (**это решение**).

Смысл второго пункта: секций у договора ровно две (основной договор и ДС), поэтому у значения, которое не токен ДС, другой секции и быть не могло. Клиент это уже считает так — `canonicalContractSectionKey` переводит любое не-ДС в `primary`. То есть перенос **не меняет смысл привязки**, он приводит запись к тому, что домен и так читает. На экране у этих 8 двигателей ничего не поменяется: до и после в колонке «Договор» один и тот же короткий номер и один зелёный кружок.

## Что делаем

1. **Одно доменное правило разбора** — `planContractSectionToken` (`shared/src/domain/contract.ts`):
   - `empty` — раздела нет (не трогаем);
   - `addon` — канон «ДС N» (приводим регистр/пробел к виду);
   - `primary` — канон основного договора;
   - `bare-number` — голое число → «ДС N»;
   - `foreign` — всё прочее → `primary`.
2. **Перенос** — `contracts:backfill-section-tokens` (`backend-api/src/scripts/backfillContractSectionTokens.ts`): dry-run по умолчанию, `--apply` пишет; отчёт по видам и по каждой строке.
3. **Второй скрипт перестал быть вторым правилом** — `contracts:canonicalize-section-keys` для привязок двигателей зовёт то же `planContractSectionToken`. Прежде он сворачивал голое число «3» в `primary` — то есть сдвинул бы 55 движков с их ДС на основной договор. Слоты платежей там по-прежнему канонизируются `canonicalContractSectionKey` — там ключ секции, а не раздел двигателя.
4. **Сторож** — `backend-api/src/scripts/contractSectionTokens.guard.test.ts`: оба скрипта обязаны звать доменное правило и писать через серверную дверь атрибута.

## Как доезжает до парка (проверено на стенде 13.11.2026)

1. Скрипт пишет EAV через `setEntityAttribute` — это серверная дверь атрибута, прямая правка EAV в SQL обновила бы только сервер (парк читает локальную копию).
2. Триггер `trg_mirror_engine_card_attr` (миграция `0105`) пересобирает строгую карточку `erp_engine_cards` → значение уже там.
3. Издатель `dictionarySyncPublisherService` берёт строки `sync_status != 'synced'` и кладёт их в журнал `ledger_tx_index` → парк забирает журнал обычным pull'ом.
4. На клиенте строгая реплика побеждает EAV по свежести (`mergeStrictCardAttrs`: «посвежее побеждает») → в списке двигателей значение новое.

Замер на стенде: посадили «3» и номер договора → прогон `--apply` → EAV «ДС 3» / «primary», зеркало «ДС 3» / «primary» и `sync_status: synced`, в журнале `erp_engine_cards upsert` с новыми значениями. Стенд возвращён в исходное состояние.

⚠️ Строка `attribute_values` в журнал при этом **не** попадает: путь записи видит, что серверная строка уже равнаpayload'у, и считает изменение пустым. Это не потеря: парк получает значение строгой карточкой.

## Чего НЕ делаем

- Не трогаем «ДС N» и `primary` — они уже канон.
- Не заполняем пустой раздел: раздел заводят руками.
- Не трогаем слоты платежей договоров (это ключи секций, другой разбор).
- Не меняем клиент: на экране у этих 8 двигателей ничего не меняется.
