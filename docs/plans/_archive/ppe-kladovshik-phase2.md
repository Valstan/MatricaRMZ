## 1. Решения

1. **Зима/лето и М/Ж — отдельные наборы норм**, а не один набор с сезоном.
   У набора появляются `gender`/`season` (NULL = для всех/всесезонный); сотруднику
   назначают зимний и летний комплекты двумя строками привязки. Ядро фильтрует
   по полу сотрудника и сезону расчёта. Вопрос из §12 закрыт так — проще версионировать
   и проще объяснять кладовщику («два комплекта» вместо «один набор с условиями»).
2. **Отпуска — строгая таблица `ppe_absences`**, не EAV. Причина: по отпускам идёт
   расчёт (сдвиг сроков), а расчётное EAV — это боль и для sync, и для отчётов.
   Вид отсутствия `kind='vacation'` (задел под больничные/командировки без нового DDL).
3. **Группы — поперечные**, не дублируют подразделения. Подразделение — штатное место;
   группа — «все, кому положен зимний комплект» (может резать цеха поперёк).
   Массовое назначение норм — по группе.
4. **Прошлые выдачи при импорте — записи с `document_id = NULL`.**
   Потребует 0108-ослабления NOT NULL (см. §2). NULL = «доввод истории, документа
   в системе не было». Отчёты NULL переживают (документ не показываем), проводки
   задним числом не делаем — остатки правим документом поступления/инвентаризации.
5. **Импорт разбирает сервер** (exceljs уже в backend-api), клиент шлёт файл и
   показывает preview → apply. Причина: парсер один на всех клиентов (десктоп,
   планшет), preview считается теми же валидаторами, что apply (расхождение
   preview/apply — отдельный гейт-тест).
6. **Коллективная выдача — двухшаговая**: шаг 1 — документ расхода на
   подразделение/МОЛ (шапка `department_id`, без персональных следов); шаг 2 —
   распределение по сотрудникам (персональные `ppe_issue_entries` на тот же документ).
   Самый рискованный пункт фазы — проектируется первым в своём PR (§6, PR-3),
   до кода пишется 20-строчный сценарий в тело PR.
7. **Дежурные нормы — наборы с флагом**, а не отдельная сущность:
   `ppe_norm_sets.is_duty + department_id`, выдача/возврат — коллективным документом
   без персональных следов (возврат = сторно-документ склада, уже есть).

## 2. Схема (миграция `0108_ppe_phase2`, реплика `0034`, паритет в 3 местах)

Аддитивно, строгие таблицы; id — голый uuid, даты — bigint Unix-ms,
`created_at/updated_at NOT NULL`, `sync_status/last_server_seq` под паблишер:

- `ppe_norm_sets`: + `gender text NULL ('M'/'F')`, `season text NULL ('winter'/'summer')`,
  + `is_duty boolean NOT NULL DEFAULT false`, индекс `(post_title, gender, season, valid_from)`.
- `ppe_issue_entries.document_id` → nullable (доввод истории, решение 4).
- `ppe_absences`: `employee_id → erp_employee_cards`, `from_ms/to_ms NOT NULL`,
  `kind NOT NULL DEFAULT 'vacation'`, индекс `(employee_id, from_ms)`.
- `ppe_groups`: `name NOT NULL`; `ppe_group_members`: `(group_id, employee_id)` unique
  среди неудалённых, индекс по `group_id`.
- `ppe_collectives`: шапка коллективной выдачи — `department_id NOT NULL`,
  `warehouse_id NOT NULL`, `document_id NULL` (до проведения), `distributed_at NULL`,
  `created_at/updated_at/deleted_at`, sync-хвост.
- `ppe_collective_lines`: `(collective_id, employee_id, nomenclature_id, qty)` —
  план распределения; факт — персональные `ppe_issue_entries` на тот же документ.
- Sync: 5 таблиц в контракт (tables/registry/dto/ledger/ownership=server/requirement),
  клиентская drizzle-схема, паблишер PR-1 расширить списком таблиц (порядок:
  sets → cards → lines → cardNorms → entries → absences → groups → members → collectives).

## 3. Ядро (`shared/ppe.ts`, pure)

- `resolveEmployeeNorms(lines, { gender?, season? })` — фильтр по условиям
  (NULL в норме = подходит всем). Сигнатура обратно совместима (второй аргумент опционален).
- `shiftByAbsences(nextDueAt, absences)` — сдвиг срока на пересечение с отсутствием
  (календарные дни, UTC). `nextIssueDates` принимает `absences` опционально.
- `resolveGroupNorms(groupMembers, cardNorms)` — нормы сотрудника = личные привязки +
  привязки его групп (дедуп по norm_set_id; конфликт сроков — минимальный, как в MVP).
- Групповой `upcomingIssues` без изменений — работает поверх уже слитых норм.
- Тесты: пересечение отпуска со сроком, зимний/летний фильтр, дедуп групповых норм.
- Открытый вопрос владельцу на PR-1 (не сейчас): правило пересечения норм (§10 MVP)
  остаётся «минимальный срок» и для групповых.

## 4. Сервис и REST (`ppeService`, `routes/ppe.ts`, те же гейты прав)

- Нормы: upsert принимает `gender/season/is_duty`; список фильтрует по ним.
- `ppe_absences`: CRUD (create/list/delete), валидация `from < to`, пересечения
  не запрещаем (сдвиг считается по объединению) — фиксируем в тесте.
- Группы: CRUD + members set/get; `assignCardNorms` принимает `groupIds`
  (разворачивается в личные привязки с пометкой источника? — НЕТ, храним связь
  группа→норма отдельно: `ppe_group_norms (group_id, norm_set_id)`, карточка
  тянет их транзитивно; иначе отзыв нормы у группы не отзовёт её у людей).
  Плюс таблица `ppe_group_norms` в 0108 (упущена выше — входит в PR-0).
- Коллективная: `openCollective`, `distributeCollective` (создаёт stock_issue на
  подразделение + персональные entries; идемпотентна по `collective_id`),
  `closeCollective`. Дежурные: выдача/возврат коллективным документом.
- Импорт: `POST /ppe/import/preview` (xlsx → разбор → совпадения/конфликты),
  `POST /ppe/import/apply` (те же валидаторы, dry-run флаг). Матчинг сотрудников:
  табельный номер → ФИО (нормализация как в `match1cNomenclature`); подразделения/
  должности создаются автоматически (как QS), отчёт о созданном — в ответе apply.
  Ожидаемые колонки ЗУП (документировать в ответе preview при несовпадении шапки):
  Табельный номер, ФИО, Должность, Подразделение, Пол, Дата рождения, Дата приёма,
  Дата увольнения, Отпуск с/по. Прошлые выдачи: лист «Выдачи» (Таб. №, Номенклатура/
  артикул, Размер, Кол-во, Дата) → entries с `document_id=NULL`.
- Импорт никогда не создаёт молча: каждая созданная/сомнительная строка — в preview;
  apply без preview-id отказывается (preview-id живёт 30 минут).

## 5. UI (группа «Кладовщик», те же компоненты)

- Нормы: selects пол/сезон/«дежурная» в редакторе; фильтр по сезону в списке.
- Карточка СИЗ: блок отпусков (CRUD), сроки считаются со сдвигом (подпись «+N дн. отпуск»).
- Новая страница «Группы»: состав + нормы группы (транзитивно видно у людей).
- Коллективная выдача: страница/диалог — шапка (подразделение, склад) → строки
  (сотрудник × позиция × кол-во) → «Провести» → распределение; дежурные — тем же
  путём с флагом (без персональных следов, только шапка + возврат).
- Импорт: страница — загрузка xlsx → таблица preview (создастся/совпало/конфликт) →
  apply с итогом. Ошибка шапки — человеческим списком ожидаемых колонок.
- EAV не трогаем (размеры уже есть).

## 6. Отчёты (7 штук, механизм пресетов; темы warehouse/catalogs)

1. `ppe_request_sheet` — **Заявка**: `upcomingIssues` (горизонт 90 дней, фильтр) ×
   кол-во минус остатки = дефицит; деньги — если у номенклатуры заполнена цена
   (иначе прочерк, не ноль: ноль врёт в бюджет).
2. `ppe_issued` — по выданному (период, сотрудник, позиция; фильтр date_range).
3. `ppe_writeoffs` — по списаниям (движения `stock_writeoff` по workwear-номенклатуре).
4. `ppe_operations` — по складским операциям СИЗ (движения по workwear-позициям).
5. `ppe_recipients` — получившие СИЗ (distinct сотрудников с выдачами за период).
6. `ppe_coverage` — обеспеченность % (сотрудники с карточкой и без просрочки /
   все с карточками; формула — в описание пресета, она и есть контракт).
7. `ppe_annual_need` — среднегодовая потребность (Σ norm.qty × сотрудников / wear_years;
   без живых выдач не врёт — считается из норм, не из истории).
- Фикстура humanLabels: расширить ppe-рядом (набор с полом/сезоном, отпуск,
  коллектив); новые пресеты — в покрытые. Ключи итогов — только из словаря подписей.

## 8. Гейты и риски

- Гейты стандартные (typecheck+test+lint+CI; CDP — PR-6, строкой в теле).
- Риск 1: **типовая ЗУП ≠ их ЗУП.** Образца нет; preview с явным списком ожидаемых
  колонок — граница: несовпадение шапки = понятная ошибка, а не молчаливый мусор.
  Перед PR-2 показать владельцу список колонок (§4) на утверждение.
- Риск 2: **коллективная сломает простоту.** Двухшаговость обязательна (иначе «выдача
  в никуда» без следов); распределение идемпотентно по collective_id (повторный клик
  не двоит).
- Риск 3: **nullable document_id разъедет чужие места.** Поиск `document_id` по коду
  перед PR-0: все чтения entries обязаны держать NULL (join'ы → left, счётчики —
  без предположений). Проверка — grep + тест.
- Риск 4: **групповые нормы vs личные.** Транзитивная модель (решение 3) — отзыв
  у группы отзывает у людей; в карточке групповая норма помечена источником
  («от группы X»), снять её можно только в группе, не в карточке.

## 9. Финальный проход #166 (2026-10-18)

Сквозной взгляд по диффу всей ветки (PR-0…PR-6) после того, как каждый PR порознь был
зелёным — по классу brain [#166](https://github.com/Valstan/brain_matrica): новая граница
(права разделов, склады, подразделения, реплика) обязана держаться по всему периметру,
а по-PR-ное ревью слепо к швам между задачами.

Найдено и закрыто четыре шва (ветка `fix/ppe-phase2-166-seams`):

1. **write-гейт разделов (класс M135).** 12 мутирующих IPC-каналов фазы 2 (отпуска,
   группы, состав и нормы групп, коллективные, дежурные, импорт) не попали в
   `WRITE_CHANNELS` (`electron-app/src/main/ipc/sectionGate.ts`): наблюдатель раздела
   «Склад» правил данные фазы мимо гейта, тогда как фаза 1 была закрыта. Список
   дополнен, и появился сторож `sectionGateWriteChannels.guard.test.ts`: он читает
   регистрацию каналов и держит шов в обе стороны — мутирующий канал обязан быть в
   write-списке, чтение в нём стоять не должно, а канал без HTTP-метода (ходит в
   локальную реплику) не имеет права писать в базу сам.
2. **Имена сотрудников в отчётах СИЗ.** `loadPpeSnapshot` брал ФИО только из строгой
   `erp_employee_cards` (её наполняет импорт ЗУП), а карточку в UI заводят по
   EAV-справочнику клиента — у такого сотрудника в колонке «Сотрудник» стоял прочерк.
   Вторым источником стали EAV-сущности типа `employee`: `full_name`, иначе собранное
   из `last_name`/`first_name`/`middle_name`.
3. **Конфликтная строка импорта не отменяет файл.** Apply отклонял весь файл, если хоть
   одна строка конфликтна («данные изменились после preview»): выгрузку ЗУП с одной
   незнакомой позицией нельзя было применить вовсе. Теперь apply пропускает ровно
   конфликтные строки (`ppeImportConflictLines`), считает их в отчёте
   (`employees.conflict` / `absences.conflict` / `entries.conflict`), а диалог
   подтверждения и итог называют оператору, что именно не импортировано.
4. **Сторож NUL-байтов и каталог смоука.** `sourcesAreText.guard.test.ts` обходил
   `.verifier-electron` (артефакты CDP-прогонов, каталог в `.gitignore`) и краснел на
   UTF-16-файле прошлого прогона — локальный `-r test` падал не по делу.

Проверено живьём: CDP-смоук `.claude/skills/verifier-electron/scripts/cdp-ppe-phase2.mjs`
— **30/30** (шаг [10] переписан под новое поведение импорта). Гейты: `-r typecheck`,
`typecheck:test`, `lint`, `-r test` — зелёные. Найденные при прогоне грабли стенда
(миграции ветки надо накатывать до клиента; драйвер не запускать во время первичного
синка) записаны в `docs/machines/PC79.md`.
