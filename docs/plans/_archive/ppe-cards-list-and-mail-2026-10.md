# Карточки СИЗ: список сотрудников, вкладка карточки, почта — 2026-10

> Запрос владельца (20.10.2026, после выпуска моста сотрудников v3.83.0):
> «Карточки СИЗ» — это не пикер, а **список сотрудников**, как список двигателей: видно,
> у кого карточка заполнена и что человеку выдано, есть фильтры по параметрам карточки,
> печать/Word/Excel. Клик по сотруднику открывает его карточку **в отдельной вкладке**.
> Плюс модуль **отправки по почте** рядом с каждой кнопкой печати/Word/Excel в программе.

Три приращения, каждое — свой PR. Порядок: A (быстро, снимает открытый вопрос владельца),
B (главная работа), C (почта).

## A. Уволенные — серые и недоступные для выбора

Решение владельца 20.10: **показывать серыми и недоступными для выбора** (не скрывать —
история выдач на уволенном должна читаться).

- `SearchSelectOption.disabled` — общий флаг компонента: строка серая, клик и Enter по ней
  не выбирают, стрелки её перепрыгивают.
- Пикеры СИЗ (`PpeCardsPage`, `PpeGroupsPage`, `PpeCollectivePage`) передают
  `disabled: isActive === false` и подсказку «уволен».
- Список сотрудников (приращение B) показывает уволенных отдельной серой строкой и ступенью
  фильтра «Уволен: да/нет».

«Показывать фазу 2 кладовщику» — не код: разделы `ppe_*` уже висят на доступе «Склад»
(`sectionAccess.ts`, `warehouse`), а роль `storekeeper` сеет `warehouse: editor`. Показ
включается выдачей доступа людям склада на проде (админка → «Доступы по разделам»),
это действие владельца, отмечено в `PENDING_FOLLOWUPS`.

## B. Список карточек СИЗ + вкладка карточки

### Экран списка (`PpeCardsPage` → список, образец `StockDocumentsPage`)

Строка = сотрудник из реплики `erp_employee_cards` (408 на проде), данные карточки
подмешиваются сервером одним запросом. Колонки (не перегружая):

| Колонка | Зачем |
|---|---|
| ФИО | кто |
| Табельный | ключ к EAV-карточке и к ЗУП |
| Карточка | нет / открыта / закрыта |
| Заполнено, % | 5 признаков: одежда, обувь, рост, нормы, выдачи (по 20 %) |
| Одежда · Обувь | размеры из EAV — кладовщику нужны на выдаче |
| Норм | сколько наборов (личные + группы) |
| Выдач | сколько позиций в истории |
| Последняя выдача | когда в последний раз что-то получил |
| Следующая | ближайший срок (мин. по позициям) |
| Состояние | просрочено / скоро выдавать / в сроке / не выдавалось / нет норм |
| Уволен | серым, чтобы не путать с действующими |

Фильтры-ступени (`shared/src/domain/ppeEmployeeListFacets.ts`, поверх общего `listFacets`):
состояние карточки, состояние выдачи, размер одежды, размер обуви, рост, уволен.
Поиск — ФИО и табельный. Сортировка по колонкам, набор/порядок/ширины колонок —
`useColumnLayout` (как в остальных списках).

Печать, Word, Excel — `ListPrintDialog` + `ListExportButtons` (та же модель колонок, что
на экране), плюс кнопка «Почта» (приращение C).

Клик по строке → `props.onOpen(employeeId)` → вкладка `ppe_card` (id вкладки уже
зарезервирован в `uiSections.ts` как detail-вкладка `ppe_cards`).

### Вкладка карточки (`PpeCardDetailsPage`, отдельный файл)

Текущий UI карточки из `PpeCardsPage` переезжает целиком: нормы, сроки следующих выдач,
отпуска, выдача, история. Сверху — кнопки «Печать», «В Word», «Почта»; печать и Word
собираются из **одной** модели секций (как накладная склада), чтобы лист и файл не разъезжались.

### Сервер

`GET /ppe/cards/overview` (право `erp.dictionary.view`, как у остальных чтений СИЗ):
- сотрудники — `erp_employee_cards` (живые, `deleted_at is null`);
- размеры — EAV `entity`+`attribute_values` по кодам `PPE_SIZE_ATTRIBUTE_CODES`;
- карточки/нормы/выдачи — `ppe_issue_cards`, `ppe_card_norms`, `ppe_issue_entries`;
- группы — `ppe_group_members` + `ppe_group_norms`;
- сроки — **shared** `resolveEmployeeNorms` + `nextIssueDates` (+ `ppe_absences`), чтобы
  «пора выдавать» в списке и в карточке считались одним калькулятором.

Батч-чтение (по всем сотрудникам сразу), а не N+1: 408 сотрудников × 5 запросов на каждое
открытие списка — это чужая нагрузка на прод.

IPC: `ppe:cards:overview` (тонкая обёртка `httpAuthed`, как остальные двери модуля).

## C. Почта

Транспорт — без собственного почтового сервера (его нет и заводить его в этом приращении
не требуется): **диалог письма в программе** + системный почтовый клиент через `mailto:` +
буфер обмена + готовый файл вложения во временной папке.

- main: `mail:draft` — собирает вложение (`.docx`/`.xlsx`) во временную папку
  `%TEMP%\matrica-mail\`, возвращает путь и имя; открывает `mailto:` с темой и текстом
  (текст короткий — сводка + строка отбора, полные данные в файле). `mail:reveal` —
  «Показать файл в папке».
- renderer: `MailSendButton` + диалог compose: Кому, Тема, Текст (предзаполнены), список
  вложений, кнопки «Скопировать текст», «Открыть почту», «Показать файл».
- Точки подключения: `ListExportButtons` (сразу все списки программы) и карточки, где уже
  есть `exports.card` — наряд, накладная склада, табель, дефектовка, карточка СИЗ.

Ограничение честно показывается оператору: `mailto:` не умеет вложения — файл лежит рядом,
его прикрепляют в почтовом клиенте одним движением («Показать файл в папке»). Свой SMTP
(с паролем на каждой машине) — отдельное решение владельца, если этот путь окажется неудобен.

## Заводская линза

- **Участок:** снабжение СИЗ (склад), поток двигателя не трогает.
- **Затор:** не кормит — это не производственный этап.
- **Инвариант потока:** не ломается; читаем те же строгие таблицы, что и отчёты СИЗ,
  выдач не добавляем (выдача остаётся прежней дверью `ppe:cards:issue`).
