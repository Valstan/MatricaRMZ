# «Кладовщик» видит сотрудников из базы Матрицы — мост EAV-справочник → `erp_employee_cards`

> Статус: **сделано на стенде, ждёт мержа и прогона на проде** (2026-10-20). Заведён по
> жалобе владельца: в пикере сотрудников «Карточек СИЗ» ничего не подставляется при
> наборе фамилии — «кладовщик к базе не подключён».

## 1. Диагноз (измерено вживую 2026-10-20)

Прод (read-only probe, `erp_*`/EAV):

| что | прод | стенд PC79 |
|---|---|---|
| `erp_employee_cards` живых | **0** | **0** |
| EAV-сотрудников (`entity_types.code='employee'`) | **408** | 2 |
| `ppe_issue_cards` / `ppe_issue_entries` | 0 / 0 | 0 / 0 |
| `ppe_norm_sets` | **0** | 0 |

Причина не в пикере, а в двери модуля: субъект «Кладовщика» — строгая
`erp_employee_cards`, а заполняет её **только импорт 1С:ЗУП** (`ppeImportService`).
Справочник же сотрудников завода живёт в EAV (`employee`): 390 из 408 имеют
табельный номер, у всех есть ФИО, у 407 — `employment_status` (`working`/`fired`).
Импорт ЗУП на проде ни разу не запускался → карточек 0 → пикеры пусты, карточку
СИЗ открыть не на кого, отчёты СИЗ пустые. Модуль выпущен (v3.73/3.79), но
**на живых данных не работал ни разу**.

Шов был виден и раньше: финальный проход #166 (п.2) уже чинил ФИО в отчётах
вторым источником (EAV), но пикер оставили на `erp_employee_cards` сознательно —
«строгая дверь знает только эти id». Плата за это — пустой модуль.

## 2. Решение

**Зеркало справочника в строгую таблицу, на сервере** (не клиентский union):
EAV-сотрудник → строка `erp_employee_cards`, дальше существующим путём
(`ppeSyncPublisherService` → журнал → реплика клиента). Тогда один источник у
пикеров, отчётов, групп и коллективных выдач, и ничего не надо чинить в UI.

Правила:

1. **Ключ связи — новая колонка `erp_employee_cards.entity_id`** (uuid, NULL,
   unique среди неудалённых). Только на сервере: в зеркальный DTO не входит
   (клиенту достаточно card id), `checkReplicaStrictness` проверяет колонки
   клиента, а не сервера — паритет не трогается.
2. **Матчинг:** сначала по `entity_id`, иначе по табельному номеру
   (нормализация: trim + снятие ведущих нулей, `00675` = `675`), иначе — новая
   строка с `id = entity_id`. Так импорт ЗУП, приехавший позже, найдёт ту же
   строку по `personnel_no` (у него этот матчинг уже есть) и обновит её, а не
   заведёт дубль.
3. **Поля:** `full_name` ← `full_name` (иначе `last_name`+`first_name`+`middle_name`),
   `personnel_no` ← `personnel_number`, `role_code` ← `role` (должность — тот же
   атрибут, что читает `employeeAuthService`), `is_active` ← `employment_status ≠ 'fired'`.
   `attrs_json` не трогаем (там данные импорта ЗУП: пол/даты).
4. **Идемпотентность:** запись только при реальном расхождении полей; иначе —
   ни `pending`, ни записи (иначе каждый тик плодил бы журнальные строки).
5. **Удалённый/слитый сотрудник** (`entities.deleted_at`, `merged_into`) →
   мягкое удаление карточки (`deleted_at`), история выдач остаётся.
6. **Онбординг живой:** тик 5 минут на primary + проход на старте + `kick` из
   дверей модуля. Плюс CLI-скрипт `ppe:mirror-employees` (dry-run по умолчанию)
   для разового бэкфилла на проде и для отчёта числами.
7. **Дверь не отказывает новому сотруднику:** вместо `employeeExistsStrict`
   (4 call-site: `openPpeCard`, `createPpeAbsence`, `setPpeGroupMembers`,
   `openCollective`) — `ensurePpeEmployeeCard`: карточка есть → ок; нет, но
   EAV-сущность есть → зеркалим её точечно и продолжаем. Иначе прежняя ошибка.

Не делаем: клиентский union пикеров (два источника правды в UI), перенос
`ppe_*` на EAV-идентификаторы (переписывание схемы ради того же результата),
автоматический импорт ЗУП (образца выгрузки по-прежнему нет).

## 3. Заводская линза

**Участок:** склад спецодежды/СИЗ — выдача кладовщиком в цеху; данные о людях
приходят из справочника сотрудников, который заполняет отдел кадров.
**Затор:** не касается — главный затор (начало сборки, ручной подбор из
обезличенного фонда) этим не двигается; это учётный контур, не комплектование.
**Поток:** не ломает — обезличивание деталей, ремфонд и `stamped_number` не
затрагиваются; выдача по-прежнему идёт складским документом (`stock_issue`) с
автором, подпись/ответственный сохраняются; `erp_document_headers.author_id`
начинает получать живых авторов вместо пустоты.

## 4. Разбивка (один PR)

- миграция `0113_ppe_employee_cards_entity_link.sql` + журнал + `schema.ts` + guard-тест;
- `ppeEmployeeMirror.ts`: чистый планировщик расхождений (`planEmployeeMirror`,
  тестируется без БД) + запись + точечный `ensurePpeEmployeeCard`;
- `ppeService`: 4 call-site через `ensurePpeEmployeeCard`;
- `index.ts`: `startPpeEmployeeMirror()` рядом с публикатором зеркала;
- CLI `scripts/mirrorPpeEmployees.ts` + `package.json` (`ppe:mirror-employees[:apply]`);
- тесты: планировщик (матчинг по табельному/entity, идемпотентность, fired,
  удалённый), guard миграции, `ppeService` — отказ только для несуществующей сущности.

## 5. Приёмка

1. Гейты: `build shared+ledger` → `-r typecheck` → `typecheck:test` → `lint` → `-r test` → CI.
2. Стенд PC79: после прогона зеркала пикер «Карточек СИЗ» показывает сотрудников
   стенда по фамилии; карточка открывается; выдача проводится.
3. Прод: `ppe:mirror-employees` (dry-run → `--apply`), ожидаем ~408 строк;
   `/ppe/employees` в реплике клиента. **Проверка на проде — чтением:**
   `cdp-ppe-employees-directory.mjs verify --readonly` + `PPE_EMPLOYEE_QUERY=<фамилия>`
   (реплика, подстановка фамилии, поиск карточки). `cdp-ppe-phase2.mjs` на проде не
   гонять — он заводит синтетическую номенклатуру, карточки и настоящие складские документы.
4. Живой аудит всех разделов «Кладовщика» на стенде с тестовыми данными
   (карточки, нормы, склад СИЗ, группы, коллективная, импорт, 11 отчётов) —
   результат строкой в теле PR и найденные дефекты — отдельными задачами.

## 7. Что показал живой прогон (стенд PC79, 2026-10-20)

Мост проверен на настоящем пути: сотрудники заведены штатным IPC карточки
сотрудника (`create` + `setAttr`), зеркало прогнано CLI, клиент получил строки
обычным путём публикатора.

| проверка | драйвер | итог |
|---|---|---|
| справочник → реплика СИЗ → пикер подставляет фамилию → карточка открывается | `cdp-ppe-employees-directory.mjs verify` | 7/7 |
| весь модуль (импорт, карточка, норма, отпуск, выдача, группа, коллективная, отчёты, подсказка размеров) | `cdp-ppe-phase2.mjs` | 35/35 |
| оставшиеся разделы GUI (нормы, группы, коллективная, склад СИЗ, оба источника людей в пикере) | `cdp-ppe-sections.mjs` | 13/13 |

**Найденный и исправленный по ходу дефект (не связан с мостом по коду, но мешал
жалобе):** вкладки живут в keep-alive, поэтому список сотрудников снимался один
раз при открытии. Импортированные (или приехавшие зеркалом) люди не появлялись в
пикере до перезапуска клиента — то же самое «набираю фамилию, а никого нет», уже
на живом человеке. Три проверки смоука падали именно на этом. Теперь «Карточки
СИЗ», «Группы» и «Коллективная выдача» подписаны на `useLiveDataRefresh`
(импульс при показе вкладки, после синка и раз в 60 с).

**Тестовые данные стенда** (синтетика, реальных людей нет): сотрудники
«СМОК Директория Один/Два/Три» (табельные 91991–91993, из справочника),
импортные «СМОК Тестов …» (90991–90993), номенклатура `SMK-*` категории
`workwear` с размерным рядом 44/46, набор норм «СМОК Нормы летние (смоук)»,
бригада «СМОК Бригада (смоук)». Смоук `cdp-ppe-phase2.mjs` теперь сам заводит
донора номенклатуры (группа + единица + шаблон), если стенд голый — раньше он
падал на пустой базе ровно там, где модуль и надо проверять.
