# Нитка: журнал заливает шумом — телеметрия интерфейса и повторные пуши (26.11.2026)

**Основание.** Решение владельца 26.11.2026 по итогам разбора тревоги «очередь застряла» на PC20:
шум журнала — отдельная нитка + проверка no-op на проде. Разбор — [`docs/pending/trevoga-ochered-zastryla-otchet-po-ustarevshey-probe.md`](../pending/trevoga-ochered-zastryla-otchet-po-ustarevshey-probe.md).

**Зачем нитка.** Журнал синхронизации — лог ИЗМЕНЕНИЙ: он будит парк на pull, и каждая лишняя запись
в нём стоит всему парку. Между тем в него попадает не только изменение данных.

**Глобальная линза:** готовый модуль — правило «журнал — лог ИЗМЕНЕНИЙ» уже есть
(`backend-api/src/services/sync/syncWriteService.ts`: `UNCHANGED_RULES` + `findUnchangedRows` +
`noopIdsByTable`) · дубль: нет · действие: **доработать существующий модуль** (расширить реестр
таблиц), а не заводить второй детектор.

## Что показала проверка no-op на проде (read-only, 26.11.2026)

Замер по журналу (`ledger_tx_index`), повторы считаны **по правилу самого сервера** — содержимое строки
без служебных полей (`sync_status`, `last_server_seq`, `created_at` — они меняются сами по себе).

1. **Правило работает для строк списка деталей.** После выката 3.147.0 повторов с одинаковым
   содержимым в `erp_engine_inventory_lines` **ноль** (до выката — строки уходили по 13 раз каждая:
   15 строк × 13 записей за 4 дня). Значит, инцидент 25.11 («журнал пух от повторного push
   неизменённой строки») на проде закрыт.
2. **Остался другой шум — `entity_types`.** После 3.147.0 три строки типа сущности ушли в журнал
   по 2–6 раз с **одинаковым** содержимым: правило no-op покрывает только `attribute_values` и
   `erp_engine_inventory_lines`, а типы сущностей клиент регистрирует у себя повторно
   (`ensureAttributeDefs` при первом открытии раздела).
3. **Журнал на 93 % состоит из телеметрии интерфейса.** После 3.147.0 в `audit_log` ушло 71 запись,
   из них **66 — `ui.*`** (телеметрия: визит вкладки, открытие карточки) и 5 — бизнес-строки.
   За 4 дня по всему парку `audit_log` дал 1 405 записей, из них 1 202 (86 %) — телеметрия.
   Телеметрия нужна серверу (по ней считается статистика активности), но **в журнале она не нужна**:
   она не изменение данных, а сигнал о том, что оператор что-то открыл.
4. **Прочие таблицы повторяются с разным содержимым** — это обычные правки (`entities` — 8,65
   записи на строку за 4 дня, `erp_production_programs` — 9,6). Отдельного разбора не требует.

## Гипотезы (что проверить в нитке)

1. **Телеметрия `ui.*` не должна попадать в журнал.** Она нужна серверу как строка `audit_log`
   (статистика активности), но не как запись журнала: журнал будит парк. Гипотеза: такие строки
   можно принимать на сервере (таблица `audit_log`) **без** записи в журнал — как это уже сделано
   для `user_presence` (строка пишется сервером, в журнал не идёт).
2. **Правило no-op стоит расширить на `entity_types`** (и, возможно, на `entities`): повторная
   регистрация типа сущности — не изменение.
3. **Порог «что считать изменением»** — общий реестр полей (уже есть в `syncWriteService.ts`),
   а не список таблиц: тогда новая таблица не попадёт в шум молча.
