# Модуль «Кладовщик» (учёт спецодежды/СИЗ) — MVP, план

> Статус: план обсуждён и одобрен владельцем 2026-10-11. Скоуп: фаза 1 (MVP).
> Решения владельца: размер = отдельная позиция номенклатуры; без коллективной выдачи; без импорта Excel/1С.
> Режим: Plan mode, реализация — другой сессией/агентом. Файл плана — только этот.

## 1. Цель и не-цели

Цель: учёт СИЗ на существующей складской платформе — карточки сотрудников, нормы выдачи,
склад спецодежды, персональная выдача, 4 базовых отчёта. Ориентир идей (не копия): QS Workwear.

Не-цели MVP (фаза 2+): условия норм (пол/сезон), учёт отпусков, коллективная/дежурная выдача,
импорт Excel/1С, группы сотрудников, заявка на спецодежду, прогноз запасов, экспорт прогноза,
остальные 7 отчётов, б/у-собственники, МВЗ, постаматы/стирка/мобильное приложение.

## 2. Ключевые проектные решения

1. **Размер = позиция номенклатуры.** `erp_nomenclature`, `category='workwear'`,
   связь размера с базовой моделью через существующий `parent_nomenclature_id`
   (механизм после 0096, один уровень). Склад, документы, регистры ничего нового не узнают.
2. **Нормы версионируются.** Новая редакция нормы = новая строка `ppe_norm_sets`
   (`valid_from/valid_to`), история выдач не переписывается.
3. **Выдача только через складской документ.** Каждая запись выдачи ссылается на
   `erp_document_headers(id)` типа `stock_issue`. Аудит целый, проводка существующая.
4. **Данные — строгие таблицы, EAV-freeze соблюдён.** Единственный EAV-хвост —
   фактические размеры сотрудника в карточке `employee` через `ensureAttributeDefs`
   (миграций не требует).
5. **Ядро расчёта одно.** `shared/src/domain/ppe.ts` (pure): слияние норм, даты следующих
   выдач, выборка «кому выдавать в ближайшие N дней». Отчёты и UI считают через него.
6. **Привязка к сотрудникам — `erp_employee_cards.id`** (строгая таблица, свой uuid-корень;
   `erp_document_headers.authorId` уже ссылается на неё — образец связи).

## 3. Схема БД

### 3.1. Сервер PG — миграция `0107_ppe_workwear.sql` (+ запись в `drizzle/meta/_journal.json`: idx 106, tag `0107_ppe_workwear`)

Конвенции: `id: uuid().primaryKey()` без default (id генерирует приложение);
даты — `bigint Unix-ms`; обязательные `created_at/updated_at bigint NOT NULL`;
индексы по образцу `erp_document_headers` (`schema.ts:1387–1410`).

- `ppe_norm_sets`: `id`, `name text NOT NULL` (напр. «Слесарь РМЦ, основная»),
  `post_title text` (должность), `department_id uuid NULL`,
  `valid_from bigint NOT NULL`, `valid_to bigint NULL`,
  `created_at/updated_at`. Индексы: `(post_title, valid_from)`, `department_id WHERE NOT NULL`.
- `ppe_norm_lines`: `id`, `norm_set_id uuid NOT NULL → ppe_norm_sets`,
  `nomenclature_id uuid NOT NULL → erp_nomenclature` (конкретный размер!),
  `qty integer NOT NULL`, `wear_months integer NOT NULL` (срок носки),
  `created_at/updated_at`. Уникальный `(norm_set_id, nomenclature_id)`.
- `ppe_issue_cards`: `id`, `employee_id uuid NOT NULL → erp_employee_cards`,
  `opened_at bigint NOT NULL`, `closed_at bigint NULL`,
  `created_at/updated_at`. Уникальный `(employee_id) WHERE closed_at IS NULL`
  (одна открытая карточка на сотрудника).
- `ppe_card_norms`: `id`, `card_id uuid NOT NULL → ppe_issue_cards`,
  `norm_set_id uuid NOT NULL → ppe_norm_sets`, `assigned_at bigint NOT NULL`,
  `created_at/updated_at`. Уникальный `(card_id, norm_set_id)`.
  (Несколько норм на сотрудника суммируются ядром расчёта.)
- `ppe_issue_entries`: `id`, `card_id uuid NOT NULL → ppe_issue_cards`,
  `nomenclature_id uuid NOT NULL`, `qty integer NOT NULL`,
  `issued_at bigint NOT NULL`, `document_id uuid NOT NULL → erp_document_headers`
  (документ `stock_issue`), `created_at/updated_at`.
  Индексы: `(card_id, issued_at)`, `(nomenclature_id, issued_at)`.

### 3.2. Клиент SQLite — реплика `electron-app/drizzle/0033_ppe_replica.sql`

Образец — `0032_erp_engine_cards_replica.sql`: nullability ровно как на сервере
(иначе `checkReplicaStrictness` уронит pull), даты — `integer`, флаги —
`integer NOT NULL DEFAULT 0`, хвост `created_at/updated_at integer NOT NULL,
last_server_seq/deleted_at integer, sync_status text DEFAULT 'synced' NOT NULL`.
Дублировать схему в 3 местах (иначе расхождение паритетных тестов):
1. `electron-app/src/main/database/migrate.ts` → `ensureClientSchemaParity()`
   (`CREATE TABLE IF NOT EXISTS` + индексы);
2. `android-app/src/db/migrate.ts` (async-порт того же);
3. покрыть `electron-app/src/main/database/migrate.test.ts`.

### 3.3. Sync-регистрация (`shared/src/sync/`)

- `tables.ts`: добавить `PpeNormSets/PpeNormLines/PpeIssueCards/PpeCardNorms/PpeIssueEntries`.
- `registry.ts`: 5 записей по образцу `erpEngineCards` (строки 750–757):
  `syncName/ledgerName/schema(zod в dto)/fields(+withBase)/conflictTarget:['id']`,
  `dependsOn`: lines→sets, card_norms→cards+sets, entries→cards.
- Нормы и карточки — pull-only справочники через `writeSyncChanges`
  (прецедент `0102` + `warehouseLocationsSyncPublisherService`).
  Выдачи едут существующими складскими документами — нового sync не надо.

## 4. Бэкенд (`backend-api/`)

- `services/ppeService.ts`: CRUD норм (набор+строки), карточки (открыть/назначить нормы/закрыть),
  выдача = `createWarehouseDocument({docType:'stock_issue', ...})` + строка `ppe_issue_entries`
  в одной транзакции; серверный write ERP — доменной функцией + `signAndAppendDetailed`
  (прямой PG-upsert, НЕ `writeSyncChanges` для строк — см. GOTCHAS applyPushBatch/erp_*).
- `routes/ppe.ts` (или расширение `warehouse.ts`): permissions по образцу склада —
  `ErpRegistersView` (остатки/реестры), `ErpDocumentsView/Edit/Post` (документы),
  идемпотентность через `clientOperationId` + `x-client-id` (образец `warehouse.ts:997–1003`).
- zod-схемы в `shared/src/sync/erpDto.ts` рядом с существующими.

## 5. Ядро расчёта (`shared/src/domain/ppe.ts` + `ppe.test.ts`)

- `resolveEmployeeNorms(cardNorms, normLines)` — слияние нескольких норм (сумма qty по номенклатуре,
  минимальный срок носки при пересечении).
- `nextIssueDates(mergedNorms, issueEntries)` — дата следующей выдачи по позиции
  (последняя выдача + `wear_months`); просрочка = дата < сегодня.
- `upcomingIssues(..., horizonDays)` — «кому и что выдавать в ближайшие N дней»
  (зародыш прогноза и заявки; детерминировано из тех же данных, что отчёты).

## 6. Клиент (Electron)

- Раздел меню: `shared/src/domain/uiSections.ts` — новые `TabId`
  (`ppe_cards`, `ppe_norms`, `ppe_stock`, `ppe_reports`), `MENU_TAB_LABELS`,
  группа (решить при реализации: отдельная `kladovshik` или внутри `warehouse`;
  рекомендация — отдельная группа «Кладовщик»), `PARENT_TAB` для карточек,
  ключи в `sectionAccess.ts`.
- Страницы: личная карточка СИЗ (нормы, размеры из EAV `employee`, история выдач,
  даты следующих + кнопка «Выдать» → `warehouse:documents:create` с `docType:'stock_issue'`
  через preload IPC, образец `preload/index.ts:816`); редактор норм; склад СИЗ
  (фильтр `category='workwear'` поверх существующих остатков).
- Интерфейс склада правим только в точках касания, не редизайним модуль целиком.
- Фактические размеры сотрудника: `ensureAttributeDefs('employee', [...])`
  (коды новые, напр. `ppe_size_clothes/ppe_size_shoes/ppe_height`; образец —
  `fieldOrder.ts:37–71`, регистрация рядом с существующими атрибутами сотрудника).

## 7. Отчёты MVP (4 из 11)

Новые `ReportPresetId` в `shared/src/domain/reports.ts` + билдеры в
`electron-app/src/main/services/reports/presets/` + `case` в `dispatch.ts` + тема в
`REPORT_PRESET_THEMES`, фильтры/колонки по образцу `parts_demand` (строки 566–586):
1. `ppe_summary_sheet` — сводная ведомость;
2. `ppe_by_size` — список по размерам (группировка по базовой модели → размеры);
3. `ppe_unissued` — справка по невыданному (ядро `nextIssueDates`, просрочка);
4. `ppe_stock_list` — складская ведомость (остатки `category='workwear'`).

Остальные 7 (выданное, списания, заявка, операции, получившие СИЗ, обеспеченность,
среднегодовая потребность) + экспорт прогноза — фаза 2+.

## 11. Ворота фаз (когда планировать дальше)

Переход на следующую фазу — только явным словом владельца, не автоматически.
Сигнал готовности фазы 1: все PR из §8 смержены в `main`, нитка записана в
`docs/COMPLETED.md`, MVP показан кладовщику. Тогда — новая сессия планирующим
агентом: «спланируй фазу N Кладовщика, база — этот файл + §12».

- **Ворота 1→2.** MVP в main + список правок от кладовщика разобран
  (что — баги в фазу 1, что — скоуп фазы 2). Без этого фазу 2 не планируем:
  иначе спроектируем поверх непроверенных предположений.
- **Ворота 2→3.** Фаза 2 в main + есть месяц живых выдач (ядро `ppe.ts` и отчёты
  сверены с реальностью). Прогноз фазы 3 строится только на проверенных данных —
  прогнозировать по непроверенным значит врать уверенно.

### Фаза 2 (кандидаты, порядок уточнить с владельцем)

1. **Условия норм (пол/сезон).** Набросок: `ppe_norm_sets` + колонки
   `gender ('M'/'F'/NULL=все)`, `season ('winter'/'summer'/NULL=всесезон)` —
   аддитивная миграция, ядро `resolveEmployeeNorms` фильтрует по атрибутам
   сотрудника (пол уже есть в карточке; сезон — параметр расчёта, не данные).
   Вопрос тогда: зимний/летний комплекты — разные строки норм или один набор с сезоном.
2. **Отпуска в расчёте.** Данные об отпусках сотрудника сейчас нигде не живут —
   понадобится либо EAV-атрибуты, либо малая строгая таблица; ядро сдвигает
   `nextIssueDates` на длительность отпуска. Вопрос: откуда берутся отпуска
   (ручной ввод / импорт из 1С — связать с п.5).
3. **Коллективная выдача (через МОЛ).** Владелец 11.10.2026: «пока не надо».
   Перед планированием перепроверить — если МОЛ не появился, пропустить.
   Набросок: документ `stock_issue` с `department_id` вместо карточки + распределение
   по сотрудникам вторым шагом; карточка дежурных норм — отдельно.
4. **Импорт Excel/1С.** Сотрудники, нормы, прошлые выдачи (даты старых выдач нужны
   ядру для корректных `nextIssueDates` с первого дня). Клиентский парсинг
   (прецедент отчётов `preset1cXml`), запись через существующие IPC/REST.
   Вопрос: формат выгрузки 1С:ЗУП — запросить образец у владельца до планирования.
5. **Группы сотрудников.** Справочник групп + привязка (массовое назначение норм
   по группе вместо поодиночке). Зависит от п.4 (группы могут приехать из 1С).
6. **Остальные отчёты + заявка:** выданное, списания, складские операции,
   получившие СИЗ, обеспеченность, заявка на спецодежду (заявка = `upcomingIssues`
   с горизонтом + остатки; денежная оценка — цены из номенклатуры, если заполнены).

### Фаза 3 (только после живых данных, см. ворота 2→3)

1. **Прогноз запасов/потребности** — расширение ядра `ppe.ts`: потребность
   (нормы × сроки × горизонт) минус остатки = дефицит вплоть до дня и сотрудника;
   средний расход по позиции + дата исчерпания (идея из QS: «средний расход запасов»).
2. **Экспорт прогноза** (для бюджета) — CSV/Excel из отчёта-прогноза.
3. **Среднегодовая потребность** — отдельный отчёт (в QS это базовая редакция,
   у нас — только сюда: без живых выдач цифра фиктивная).
4. **Дежурные нормы** — отдельная карточка на подразделение (не на сотрудника),
   выдача/возврат без списания.
5. **Б/у-собственники и износ** — аналитика склада (состояние экземпляра);
   конфликт с решением «размер = номенклатура»: б/у тех же размеров плодит позиции,
   при планировании решить — отдельный `owner`/флаг на документе vs позиции.
   Это самый спорный пункт, не проектировать наспех.

### 10. Риски и открытые точки (решить при реализации)

- Группа меню: отдельная «Кладовщик» vs внутри «Склад» (рекомендация — отдельная).
- Пересечение норм: правило «минимальный срок носки» — подтвердить с владельцем на PR-2.
- `parent_nomenclature_id` — один уровень; вложенность «модель → вид → размер» не влезет,
  при нужды глубины — отдельный вопрос.
- Дежурные нормы и возврат — только фаза 2+, в MVP возврата нет (ошибочная выдача
  правится сторно-документом склада).
