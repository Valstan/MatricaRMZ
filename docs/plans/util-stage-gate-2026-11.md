# Утиль: ремонт не начинаем, пока деталь не отремонтирована (промт КАРМАНА #170)

**Дата:** 2026-11-26 · **Решение владельца:** зачитка 26.11.2026 · **Статус:** реализовано по коду (PR **#2119** слит `88cbdae3`), ждёт приёмки глазами владельца

## Задача

Утильный двигатель (красная строка в списке) не должен получать этап ремонта: пока утильная
деталь не отремонтирована, ремонтный цикл не начинается. Блокировка должна стоять **в общей
воронке записи этапа**, а не на одном экране, и считать конфликт **по текущему заезду**, а не
по всей истории. Все решения по утилю остаются в истории двигателя.

## Что сделано

### 1. Правило — в домене, одно на все места

`shared/src/domain/engineScrapStageGate.ts`:

| Что | Где |
|---|---|
| Список этапов ремонта, которые держит гейт | `SCRAP_GATE_REPAIR_STAGE_CODES` (`parts_repair`, `ukladka`, `faza`, `sborka`, `obkatka`, `otk`) |
| Решение «заводить / показать окно / подсказка» | `evaluateScrapStageGate` |
| Текущий заезд | `isScrapInCurrentTrip` + `currentVisitStartAt` (`engineCurrentPass.ts`) |
| Согласованность «утиль ↔ этап» | `isScrapStageStateConsistent`, `findScrapStageInconsistencies` |
| Причины снятия утиля | `SCRAP_RESOLVE_REASONS` (`Ремонт` / `Закупка` / `Иное`) |
| Главные детали (критерий утиля) | `scrapCriterion.ts`: `SCRAP_MAIN_PART_NAME_PARTS` (`картер`, `головка`, `блок`), `isMainScrapCriterionName` |

Граница «ремонтный этап» — **явный список**, а не «по рангу»: линейку этапов владелец
переставляет (drag&drop в «Карте этапов»), и гейт не должен молча переехать вместе с ней.
Приёмка, разборка, отгрузка и приёмка заказчиком гейтом не держатся: утильный движок с
завода тоже уезжает.

### 2. Блокировка — в воронке записи этапа

`electron-app/src/main/services/repairStageService.ts` → `saveRepairStageRow`: гейт
(`resolveScrapStageGate`) спрашивается ВНУТРИ функции общей записи, до записи строки.
`ensureRepairStageRow` (автоматы мастеров: обкатка, сборка) идёт через тот же путь, поэтому
останавливается тоже. Ничего не пишется: в истории ремонта этапа не остаётся.

Прежнее правило «укладка и выше снимает метки утиля» у утильного двигателя больше не
срабатывает: до гейта дело не доходит — ремонтный этап там не заводится. Снятие утиля
остаётся явным действием «Деталь отремонтирована» (с причиной и автором, следом в истории).
Порог оставлен для двигателей, которых гейт утильными не признал (например, только
legacy-метка `is_scrap`), и для уехавших с завода — прежнее поведение там не менялось.

Состояние двигателя собирает `electron-app/src/main/services/engineScrapStageGateService.ts`:
флаги статуса карточки и их даты (EAV), утильные детали последнего акта дефектовки, след
снятия утиля из истории. Модуль намеренно не тянет `engineService` (тот тянет
`repairStageService` — статический цикл импортов сломал бы инициализацию).

### 3. Окно с двумя действиями

`electron-app/src/renderer/src/ui/components/ScrapStageBlockDialog.tsx` (+ хост
`ScrapStageBlockHost.tsx`, общий доступ `utils/scrapStageGate.ts`):

* названа утильная деталь и двигатель;
* **«Деталь отремонтирована»** — снимает утиль, пишет след, возвращает деталь в ремонтный
  фонд, после чего запись этапа повторяется;
* **«Отмена (не была отремонтирована)»** — этап не создаётся, следов записи нет;
* спрашивается **причина** снятия утиля (без неё след неполон).

Окно одно на приложение: экранов, которые заводят этап, много (карточка, список, ПП,
массовое добавление), а правило одно. Все четыре экрана обрабатывают отказ гейта.

### 4. Снятие утиля — существующий механизм, а не второй

`electron-app/src/main/services/engineScrapResolveService.ts` + IPC `engines:scrap:resolve`:

1. **след в истории ремонта** — `scrapResolved {outcome, partLabel, reason, atMs}`, автор
   записи — `performedBy`;
2. **утиль снимается** — те же глобальные флаги, что снимает воронка (`clearEngineScrapFlag`),
   плюс сам след гасит утиль по детали (по моменту события, не по времени записи);
3. **деталь возвращается в ремонтный фонд** — существующей дверью `warehouse:repairFund:intake`;
4. **причина обязательна** — без неё действие отказывает.

Тот же след и та же причина добавлены в действие «Вывод из утиля» в карточке двигателя —
решения по утилю не должны расходиться по двум экранам.

### 5. Текущий заезд

Текущий заезд — по общему правилу (`engineCurrentPass.ts`): последняя приёмка на завод
(`arrival` / `arrival_reclamation`) отделяет заезды. Утиль прошлого заезда текущую работу не
держит: движок вернулся (рекламация, повторный заезд) и ремонтируется заново. Этапы
прошлых заездов расхождением не считаются.

### 6. Проверка согласованности

`findScrapStageInconsistencies` (домен) + IPC `engines:scrap:consistency`: перечень
двигателей, у которых в текущем заезде есть И этап ремонта, И статус утиль. Новых
расхождений программа не заводит (гейт в воронке), старые — видны проверкой.

## Решения, закрытые по умолчанию (за владельцем подтверждение)

1. **Блокирует только утиль.** Неглавная утильная деталь (маслонасос) этапу не мешает —
   оператору показывается подсказка «В дефектовке есть утильная деталь». Так и просил
   промт; блокировка по ЛЮБОЙ утильной детали — альтернатива, решение за владельцем.
2. **Главные детали — картер, головка, блок** (зачитка владельца 26.11.2026). Набор
   критериев по умолчанию расширен с одних картеров; флаг наполнения версионирован
   (`SCRAP_CRITERION_SEED_VERSION = '2'`), чтобы новый состав дошёл до парка. Наполнение
   трогает только те детали, по которым владелец ЕЩЁ НЕ высказался: снятую метку оно не
   возвращает (иначе расширение состава возвращало бы снятое обратно).
3. **Причина снятия утиля спрашивается и в окне гейта, и в карточке** — «Ремонт / Закупка /
   Иное» + свободный текст в примечании.
4. **Утиль прошлого заезда не держит текущий ремонт** (иначе движок, вернувшийся по
   рекламации, нельзя было бы отремонтировать заново).

## Открыто за владельцем

* **Главные детали:** список зафиксирован по словам владельца (картер, головка, блок), но
  точный перечень он не помнит — состав набора открыт, дополняется галкой на карточке
  детали. Проверить на боевых актах: не должны ли «головка»/«блок» быть критерием.
* **Возврат детали из локации «утиль» в ремонтный фонд:** действие зовёт существующий занос
  в ремфонд; обратное складское движение (сторно прихода по дефектовке) делается
  перепроведением акта дефектовки — отдельная задача.
* **Живая приёмка глазами владельца** (окно, оба исхода, подсказка по неглавной детали) и
  **перебор расхождений на боевых данных** (`engines:scrap:consistency`).

## Сторожи

* `shared/src/domain/engineScrapStageGate.test.ts` — 18 проверок домена (блокировка,
  подсказка, текущий заезд, согласованность, перебор расхождений);
* `electron-app/src/main/services/repairStageScrapGate.test.ts` — 6 проверок воронки на
  живой фикстуре (этап не создан, этап создан, утиль прошлого заезда, подсказка, снятие
  утиля открывает этап);
* `electron-app/src/main/services/engineScrapResolveService.test.ts` — 4 проверки снятия
  утиля (след + причина + автор, причина обязательна, возврат в ремфонд, отказ склада не
  отменяет снятие);
* `electron-app/src/main/services/repairStageFunnel.guard.test.ts` — **сторож места**:
  гейт обязан стоять в `saveRepairStageRow`, автоматы идти через тот же путь, все экраны
  обрабатывать отказ, окно — с двумя кнопками и причиной. Сторож проверяет именно ВЫЗОВ
  гейта (`resolveScrapStageGate(`) и его порядок — гейт до записи строки; упоминание в
  типе (`typeof resolveScrapStageGate`) его не спасает. Проверено временной правкой:
  с убранным вызовом гейта краснеют обе проверки этого блока.

## Заводская линза

`Заводская линза: дефектовка → карточка двигателя · затор: не кормит (главный затор — ручной подбор деталей из фонда при начале сборки; фича его не двигает) · поток: не ломает — детали по-прежнему обезличиваются в общую кучу, партия и stamped_number не затрагиваются`
