# Веб-админка и карточка сотрудника: пользователи, доступы, поле «Цех»

**Основание:** промты КАРМАНА (раздел `MatricaRMZ`) **#76** (задача владельца) + **#77**
(план). Нитка — 23.11.2026, PR **#1955**, **#1960**, **#1962**.

План из библиотеки — задание владельца, а не готовое решение: он разобран на три
самостоятельные части, у каждой свой источник правды и свой гейт.

## 1. Поиск по пользователям в веб-админке (PR #1955)

**Заказ:** «во вкладке "Админ" неудобно искать пользователя: чтобы найти нужного,
приходится вручную прокручивать весь список».

- Все места, где выбирают пользователя, переведены на общий `SearchSelect`
  (готовый компонент с подсказками и подсветкой совпадений): «Выбрать пользователя»,
  «Слить с существующим…», «делегирует (пользователь)».
- Список ожидающих одобрения тоже ищется — по ФИО или логину, с пустым состоянием.
- Поиск ищет и по фамилии с именем, и по логину (логин уходит в строку поиска).
- Сторож: `backend-api/src/tests/adminUsersSearch.guard.test.ts`.

**Чего не сделано:** серверного `GET /admin/users?q=` нет — список и так приходит
целиком, пагинации нет; это отдельное решение, если данных станет много.

## 2. Вкладка «Доступ» — один источник правды (PR #1960)

**Заказ:** «пользователю, у которого роль "администратор", показывается роль
"наблюдатель". Логин вижу, а пароль сменить не могу — есть только кнопка "Создать
учётную запись", а учётная запись уже есть».

Три источника в одной карточке сведены к одному:

1. **Роль** в зеркале доступов бралась из EAV-атрибута `system_role`, который после
   cutover 0103 заморожен (триггеры зеркала снесены) ⇒ у администратора «Наблюдатель».
   Теперь роль — из `permissions-view` (`normalizeRole`), то есть из строгой таблицы
   `users`.
2. **Состояние учётной записи**: любой отказ сервера приравнивался к «записи нет», и
   форма «Создать учётную запись» появлялась поверх существующей. Теперь состояний
   четыре: `loading` | `account` | `none` | `error`; при `error` — причина и «Обновить».
3. **404** читается как «записи нет» (и по русской строке сервера, и по английской).

**Что НЕ менялось:** `employeeService.ts` — развилка «реплика налита или нет» уже
сделана правильно (EAV-путь только когда реплики нет вовсе; форму держит сторож
`sectionAccessDelta.guard.test.ts`). Форма создания записи: роль «Наблюдатель» там
видимое значение в списке, а не молчаливое.

**Что осталось за владельцем:** в его карточке роль может ещё показываться «Наблюдатель»
из-за старой сборки клиента — парк обновляется релизом; после обновления проверяем.

## 3. Ошибка «Error invoking remote method 'workshop'» (PR #1962)

**Диагноз (по коду 23.11.2026):** на текущем коде дефект **не воспроизводится** — хендлер
`workshops:list` есть (`main/ipc/register/workshops.ts`), подключён безусловно, окно
создаётся позже регистрации, гейт раздела канал не режет. Значит ошибка пришла из
установленной у владельца сборки без этого хендлера (старый клиент) — правкой кода
лечится не она, а обновлением клиента (парк обновляется релизом).

Что сделано, чтобы класс не повторился:

- **Сторож инвентаризации IPC-каналов** (`main/ipc/ipcChannelInventory.guard.test.ts`):
  все `ipcRenderer.invoke('X')` из preload против всех `ipcMain.handle('X')` из main;
  расхождение — падение теста. Сейчас: 561 канал preload, 562 хендлера main, единственное
  расхождение — `files:uploadBlob` (его обслуживает Android-мост), и он в белом списке,
  который не может разрастись молча. Тот же метод, что в `docs/gotchas/M42.md`.
- **Поле «Цех» показывает состояние словами**, а не сырым текстом IPC: «Справочник цехов
  пуст» / «Список цехов не загрузился — обновите карточку». Отдельно: «у подразделения нет
  цехов» — не причина, справочник цехов общий.
