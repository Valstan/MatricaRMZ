# Производственная программа: порядок, перетаскивание, две нумерации, отметки

**Промт КАРМАНА:** #48 (задание) + #49 (план владельца от 19.11.2026).

## Цель

В списке производственной программы:

- двигатели и группы (договоры со своими списками двигателей) **перетаскиваются вверх-вниз**;
- нумерация — **две**: общая по программе и своя внутри каждого договора, пересчитываемая автоматически при любом перетаскивании;
- отремонтированные двигатели помечаются **своим фоном**;
- оператор может помечать отдельные двигатели **своим цветом** («особое внимание», обмен данными с другими операторами).

## Что уже есть (прочитано в репозитории)

- **Печатная модель уже умеет группировать по договорам и сквозной «№ п/п»** — `shared/src/domain/productionProgram.ts:757` (`buildProductionProgramPrintModel`): группы идут **в порядке строк**, «№ п/п» сквозной, подсветка — по факту из карточки двигателя.
- **Подсветка строки по факту из карточки** — `productionProgramRowHighlight` (`:386`): `ready` | `shipped` | `none`.
- **Ручная пометка строки — прецедент есть**: розовая пометка утиля `engineScrapRowStyle` (`pages/EnginesPage.tsx:1217`), синий выбор накладывается поверх (`:1218`).
- **Состояния строк плана — не статусы движков и не этапы ремонта** (`ProductionProgramState`, `productionProgram.ts:116`): смешивать нельзя.
- Группировка строк по договору в UI есть (`ProductionProgramPage.tsx`, мемо `groups`).

## Ключевая находка при сверке с кодом: экран и печать расходятся в порядке групп

Печатная модель собирает группы **в порядке строк** (порядок первого появления), а экран сортирует группы **по названию договора** (`groups` → `.sort((a, b) => a.label.localeCompare(b.label, 'ru'))`). Значит сегодня «порядок в программе» на экране и на бумаге — разный, и перетаскивание невозможно проверить «по тому, что напечатано».

Лечение: **источник порядка один** — плоский массив строк (позиция = `orderNo`). Экран строит группы по порядку строк, как печать. Сортировку по названию убираем: порядок групп теперь ручной (перетаскиванием).

## Разбивка на PR

Нитра шире одного PR: часть — чисто клиентская (порядок, перетаскивание, нумерации, подсветка), часть — новая колонка в строгой таблице с миграцией и контрактом синхронизации.

- **PR A — порядок и нумерации** (этот план): перетаскивание строк и групп, две нумерации на экране, подсветка по стадии ремонта, печать с номером в группе. Без новых колонок и миграций.
- **PR B — ручная отметка оператора**: колонка `operator_note` в `erp_production_program_rows` + миграция + **три хранилища** (сервер, реплика Electron, Android) + контракт синхронизации (DTO, реестр, зеркало).

## Шаги (PR A)

1. **Домен — нумерация по позиции.** `productionProgramNumbering(rows)`: для каждой строки `{ global, inContract }`. Обе считаются **по позиции**, а не по сохранённому числу, — иначе после перестановки цифры разъедутся. Своя нумерация внутри договора **отдельным полем не хранится**.
2. **Домен — перестановки.** `productionProgramMoveRowWithinGroup(rows, rowId, targetContractKey, targetIndex)` — двигатель меняет место **в пределах договора**; `productionProgramMoveGroup(rows, groupKey, targetGroupIndex)` — группа (договор со своим блоком) меняет место **внутри программы** и уносит блок целиком. Обе — чистые функции над плоским массивом строк; после них пересчитываются номера и уходит тот же `saveRows`.
3. **Домен — тон строки.** `productionProgramRowTone(engine, operatorNote)`: факт из карточки (`productionProgramRowHighlight`) даёт свой фон (готов/отгружен), отметка оператора — свой. Правило живёт **в домене**, а не в компоненте страницы: иначе подсветка разойдётся с карточкой (тот же запрет, что у `productionProgramEngineHint`).
4. **Экран.** Группы — в порядке строк (как в печати); колонка «№ п/п» (общая) + «№ в договоре»; drag&drop строк и групп; фон строки по тону.
5. **Печать — по образцу, без изменений.** Форма «ПП Цех № 1» — документ с фиксированными семью колонками и ширинами (сторож `productionProgramPrintHtml.test.ts`: «семь колонок заданной ширины, в сумме — печатная полоса 271 мм»). Вторую нумерацию в печать **не добавляем**: сломали бы образец. На экране обе нумерации, на бумаге — сквозная, как есть.
6. **Порядок по выполнению.** Отдельным решением владельца: по умолчанию автосортировка **не** переставляет строки без его воли (иначе «перетащил — а оно вернулось»). Вычисляемый порядок по факту из карточки (`productionProgramRowHighlight`) — как **подсказка** (значок/тон), а не как тихая перестановка.

## Осторожности

- **Одна дверь записи строк.** После перетаскивания — тот же `saveRows`, никакого второго пути.
- **Номера пересчитываются на клиенте по текущему порядку** (`orderNo = i + 1`) — иначе упрётся в частичный уникальный индекс `erp_production_program_rows_order_uq`.
- **Отметка не влияет на порядок** и **не затирается** при пересохранении программы.
- **Не смешивать** состояние строки плана (`ProductionProgramState`), статус движка и этап ремонта — три разные вещи, каждая со своим полем.
- **Персист выделения и перетаскивания** — как у списка движков (`useListSelection`, персист в `sessionStorage`): после перезапуска клиента выделение может сброситься, и это не должно выглядеть как потеря правки.
- **Право на перетаскивание** — `production_program.edit` (то же, что на правку строки).

## Что показал смоук (20.11.2026)

cdp-production-program-order.mjs — **7/7 PASS** на живом клиенте: обе нумерации на экране, перетаскивание двигателя внутри договора меняет порядок, цифры едут за строками, новый порядок записан на сервер (проверено чтением с сервера), план и фикстуры сняты.

Смоук нашёл две вещи, обе исправлены:

1. **Обрыв связи глотался молча.** Запись шла без try/catch: при недоступном сервере исключение из моста уходило в никуда, и оператор видел только «Правка не сохранена» — без строки об ошибке («смотрите ошибку выше», а ошибки выше нет). Теперь обрыв связи показывается текстом.
2. **Экран и печать показывали разный порядок групп** (см. «Ключевая находка» выше) — убрана сортировка групп по названию договора.
