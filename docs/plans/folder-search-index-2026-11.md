# Поиск по папкам: причина медленного обхода, карта индекса и фоновая индексация

> Первоисточник — промт КАРМАНА **#180** (зачитка владельца, 27.11.2026): «поиск по папкам идёт медленно — на второй папке обход ползёт по одной папке»: найти и назвать причину числами, построить индекс дерева папки в фоне отдельным процессом и показать прогресс индексирования.
>
> План из библиотеки — **задание владельца, а не готовое решение** (`AGENTS.md` §«Промты проекта из КАРМАНА»): он сверён с нашим кодом и уточнён ниже.

**Статус:** код готов 27.11.2026 (ветка `feat/folder-search-tree-index-2026-11`). **Дата:** 2026-11-27. **Нить:** поиск по файлам → поиск по папкам → карта индекса дерева.

## Заводская линза (три строки)

- **Участок:** приёмка и дефектовка — оператор находит папку с фотографиями двигателя по номеру в её названии.
- **Кормит ли затор:** не кормит. Главный затор модели — «начало сборки: ручной подбор совместимых деталей из обезличенного фонда»; модуль ищет фото по номеру двигателя, а не детали в фонде. Косвенно помогает приёмке: находит «что известно про этот движок» в бумажном виде быстрее.
- **Инвариант потока:** не ломает. Модуль читает папки и **ничего в них не пишет** — карта индекса лежит в машинно-локальном хранилище клиента, не рядом с папкой оператора. Записи в карточку двигателя не касается.

## Глобальная линза (три строки)

- **Модуль-кандидат:** прогресс индексации папок.
- **Дубль:** нет — `shared/src/domain/searchProgress.ts` (`searchProgress.ts` в реестре глобальных модулей) про **поиск**, а не про фоновое индексирование; индексация идёт отдельным процессом вне канала поиска. Общий прогресс поиска не тронут.
- **Действие:** новый модуль нужен (фоновая индексация — отдельная жизнь со своим сторожем и своим каналом), дублировать общий прогресс поиска нельзя.

## Что уже есть (сверено с кодом, а не по памяти)

- **Скан папок** — `electron-app/src/main/services/fileSearchFolderService.ts`: обход дерева выбранных папок с потолками (`MAX_FOLDER_DEPTH` 3, `MAX_SCANNED_FOLDERS` 5000, `MAX_SCANNED_FILES` 20 000, `MAX_FOLDER_MATCHES` 200, `MAX_IMAGES_PER_MATCH` 200), потолок ожидания на одну папку (`FOLDER_READ_TIMEOUT_MS` 30 с).
- **Общий прогресс поиска с отменой** — `electron-app/src/main/services/searchProgress.ts`: один канал `search:progress` на всю программу, одна полоса, троттлинг, честная отмена с частичным результатом (промт #166). **Его не трогаем.**
- **Отдельные процессы клиента** — движок синка (`workers/syncWorker.ts`) и процесс чтений (`workers/dataWorker.ts`), оба на `utilityProcess` с прокси-сервисами в main (`services/syncProxy.ts`, `services/dataProxy.ts`).
- **Домен папок** — `shared/src/domain/fileSearchFolders.ts`; типы IPC — `shared/src/ipc/types.ts`; мост — `electron-app/src/preload/index.ts`; страница — `electron-app/src/renderer/src/ui/pages/FileSearchPage.tsx`.
- **Журнал клиента** — `electron-app/src/main/utils/logger.ts` (`matricarmz.log` в `userData`), туда же пишут воркеры синка и чтений.

## Разбор причины (промт #180, п.1) — числами

Полный отчёт с числами: [`docs/evidence/folder-search-180/README.md`](../evidence/folder-search-180/README.md). Инструмент замера: [`scripts/folder-scan-benchmark.mjs`](../../scripts/folder-scan-benchmark.mjs).

**Версия «переполнен индекс» отвергнута:** индекса в программе не было. До правки в `fileSearchFolderService.ts` нет ни кэша, ни карты — каждый поиск начинал полный обход заново (`:452` `await walk(source.path, '', 0)`).

Причина — три вещи, измеренные по отдельности:

| Что | До | Стало |
|---|---|---|
| Обход папок | строго по одной (`await walk(child)`) | 4 папки одновременно (`FOLDER_WALK_CONCURRENCY`) |
| Метаданные | отдельный запрос на **каждый** файл (`:428`) | только для картинок результата, одним проходом |
| Индекс | не было | карта дерева, строится в фоне, поиск идёт по ней |

Замер (локальный SSD, `C:\Windows\System32`: 1 198 папок, 18 564 файла): было 3 112 мс, стало 81 мс — **×38**. Метаданные занимали **90 %** времени обхода. На сетевой папке запрос метаданных — это сетевой круг, поэтому разрыв ещё больше.

## Решения (развилки промта, закрытые по умолчанию)

1. **Где хранить карту индекса.** По умолчанию — **машинно-локальное хранилище клиента** (`<userData>/folder-index/<id>.json`). Причины: модуль «Поиск по папкам» только читает (сторож `FileSearchPage.guard.test.ts` проверяет, что модуль ничего не пишет), а на сетевой папке прав на запись может не быть. Минус очевиден: карта не переживёт переустановку и не попадёт на другую машину. → владельцу.
2. **Правило устаревания карты.** По умолчанию: карта протухает, если папка менялась позже индекса (**идём по диску** — иначе оператор не найдёт свежий файл), и сверху «карте не старше суток» (`FILE_SEARCH_FOLDER_INDEX_MAX_AGE_MS`): правка файла в глубине времени изменения корня не меняет. → владельцу.
3. **Строить ли карту автоматически.** По умолчанию — **да, при добавлении папки**, в фоне. Плюс кнопка «Построить индекс» для перестроения. Промт отмечал, что построение карты стоит как один полный обход и выигрыш появляется со второго поиска — поэтому оставили и кнопку. → владельцу.
4. **Куда «сообщить разработчику», что индексация не завершилась.** По умолчанию — **в журнал клиента** (`matricarmz.log`, запись «индексирование папки не завершилось») **и** предупреждение в интерфейсе на экране поиска по папкам. Отдельного канала разработчику в программе нет. → владельцу.
5. **Потолок индексации и приоритет.** По умолчанию: потолок 15 минут на папку (`FOLDER_INDEX_TIMEOUT_MS`), после него процесс останавливается; пауза между чтениями папок 30 мс (`FOLDER_INDEX_RATE_LIMIT_MS`) — сеть и диск не выбираются целиком. Режим «тише» при полной загрузке — не делали. → владельцу.

## Что сделано (27.11.2026)

- **Домен карты** (`shared/src/domain/fileSearchFolderIndex.ts`): `FileSearchFolderIndexEntry` (путь, имя, тип, размер, дата, «картинка ли»), `FileSearchFolderIndex`, `isFolderIndexFresh` (правило устаревания), `FolderIndexProgress` (состояние для полосы).
- **Одно правило совпадений для диска и для карты** (`shared/src/domain/fileSearchFolders.ts`): `FileSearchFolderMatchCollector`. Раньше совпадения считались прямо в обходе, и «поиск по индексу» был бы вторым правилом со своим результатом; теперь обход диска и карта индекса подставляют записи в ОДИН сборщик. Находки по-прежнему считаются **во время** обхода — счётчик «найдено» в полосе не расходится с результатом.
- **Скан папок** (`fileSearchFolderService.ts`): обход с ограниченным параллелизмом (`FOLDER_WALK_CONCURRENCY = 4`), без лишних запросов метаданных (`fillImageSizes` — размер только для картинок результата, параллелизм 8), путь «по карте» через `FolderIndexLookup` (`load` + `requestBuild`).
- **Сборщик карты** (`services/folderIndexBuilder.ts`): обход дерева с паузой между папками, метаданные файлов, карта в порядке «родитель → дети».
- **Процесс индексации** (`workers/folderIndexWorker.ts` + `folderIndexWorkerProtocol.ts`): отдельный `utilityProcess`, порт сообщений, отмена.
- **Сервис карт** (`services/folderIndexService.ts`): очередь заданий, запись карты на диск, **сторож** (15 мин → процесс останавливается, в журнал идёт «индексирование папки не завершилось»), состояния для окна.
- **IPC** (`ipc/register/fileSearch.ts`): `fileSearch:folderIndex:status`, `fileSearch:folderIndex:build`, событие `fileSearch:folderIndex:progress`; при добавлении папки карта ставится в очередь сразу.
- **Экран** (`FileSearchPage.tsx`): колонка «Индекс» в списке папок, полоса индексации (идёт / сколько просмотрено), предупреждение при зависании, кнопка «Построить индекс».

## Границы (что сознательно не входит)

- **Запись в папки оператора** — по-прежнему нет ни одной: карта лежит в хранилище клиента.
- **Индексация всего диска** — только явно выбранные оператором папки.
- **Поиск по PDF и OCR** — не входит.
- **Полоса индексации — не полоса поиска.** Общая полоса поиска (`search:progress`) не тронута: индексация фоновая, и её прогресс живёт отдельным каналом.
- **Смоук на живом стенде** — не гонялся (гейт по диалогу Electron на этой машине); приёмка сделана юнит-тестами и замером инструмента.
