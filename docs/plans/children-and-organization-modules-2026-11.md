**Заказ владельца (#30, дословно-смысл):** разработать организационный модуль — для отдела организационного, который организует праздники, вручает подарки, призы, грамоты, проводит соревнования; весь учёт этих документов и соревнований — с использованием модуля сотрудников (ФИО подставляются, взаимосвязи работают). Уволен → его дети «серенькие»: не участвуют ни в отборах, ни в фильтрах, уходят из напоминалок. Организационный модуль — каркас, детский — целиком; дальше правки по замечаниям оператора.

## Шаг 0. Разбор практики (постулат 42: факты о внешнем мире — из веба)

### Модель A — «зависимый член семьи» (SAP SuccessFactors Employee Central, Oracle HCM/PeopleSoft, BambooHR)

- Ребёнок — **отдельная персональная запись** (dependent person), связанная с сотрудником **типом связи** (`personRelationshipType`: ребёнок / супруг / иное), а не атрибут карточки сотрудника.
- **Минимальный набор полей** (BambooHR, Benefits Enrollment): имя, фамилия, дата рождения, пол, связь с сотрудником. Без них запись не попадает ни в льготы, ни в выдачу — «незаполненная зависимая запись» отсекается.
- Дополнительно у мировых систем: дата начала/окончания связи, признак «получатель выплат», признак «сопровождающий иждивенец» (SAP), признак инвалидности и «студент» — для детей старше 19 (SAP IT0021).
- Льготы, выдачи и отборы привязаны к **записи о ребёнке**, а не к сотруднику.

### Модель B — «карточка ребёнка в семейном справочнике завода» (наша, по смыслу = A, но в нашей архитектуре)

- Ребёнок — карточка в **строгой таблице** (EAV под заморозкой — AGENTS.md §EAV), ссылка на сотрудника (EAV-сущность) по id.
- Статус ребёнка **не хранится**: «серенький» выводится из `EmploymentStatusCode` родителя — одно правило, без ручного флага (иначе разъедется).
- Признаки отбора (СВО, лечение) — **атрибуты карточки**, не отдельные сущности.
- Подарки/награды — **журнал выдачи**: что, кому (сотруднику или ребёнку), когда, вид (подарок / приз / грамота / деньги), мотив (мероприятие).
- Отбор под мероприятие — **фасет**, а не сохранённый список; решение оператора (приглашён / не приглашён и почему) — хранится.

### Модель C — «дети — набор атрибутов сотрудника»

- Дети — JSON-массив в карточке сотрудника; подарки — отдельные записи.
- Плюс: почти ноль работы с контрактом синка.
- Минус: у ребёнка **нет своих фильтров и отчётов** (владелец прямо просил «полный учёт по всем возможным фильтрам — по детям и по работникам»); история подарков раздувает карточку сотрудника; хранение в EAV, который под заморозкой.

### Решение по моделям

**Берём B.** C отбрасываем по трём причинам: EAV-мороз, нет собственных отчётов и фильтров, раздувание карточки сотрудника. A — прямой прототип B: из неё берём **набор полей** (ФИО / дата рождения / пол / связь с родителем) и правило **«запись без обязательных полей неполна»**.

### Что берём из практики

1. **Обязательный набор** (BambooHR): ФИО, дата рождения, пол, связь с родителем — без них карточка ребёнка не считается заполненной (в нашем случае — не проходит бой и не попадает в отборы).
2. **Напоминание с опережением**: Calamari — «за 14 дней», Greetigo — «за день и утром в день», Frappe HR — ежедневная задача по совпадению дня и месяца.
3. **Напоминание — только по активным** (Frappe HR: reminder уходит Active-сотрудникам). Наше правило «серенькие уходят из напоминалок» совпадает с мировой практикой, а не расходится с ней.
4. **ПДн детей**: SHRM — возраст и год рождения не разглашаются публично, дата рождения — фактор кражи личности. Отсюда: ДР/возраст не выгружаются в отчёты по умолчанию и не показываются в публичных списках без запроса (пункт «Осторожности» плана #31).
5. **Подарок — документ с датой выдачи, мотивом и табличной частью «кому что»** (1С:ЗУП, документ «Приз, подарок»: месяц, дата выдачи, флаг «подарок/приз», табличная часть, печатная форма Т-11 — приказ о поощрении). Наш журнал выдачи повторяет форму, но мотивом служит **мероприятие** (праздник / соревнование / день рождения), а не формулировка приказа.
6. **Отбор под мероприятие — зафиксированное решение по каждому** (BambooHR enrollment: сначала состав, потом решение по каждому лицу), а не пересчёт состава каждый раз.

### Что отбрасываем

- НДФЛ, страховые взносы, 6-НДФЛ, договоры дарения, код дохода 2720 — это бухгалтерия 1С; наш модуль организационного, а не расчёт зарплаты.
- Бенефиты, страховые планы, coverage, пенсионные выплаты, бенефициары для страхования — чужой контур.
- Год рождения и возраст в публичных выгрузках и на всеобщих экранах.

## Шаг 2. Развилки (за владельца)

1. **Модель ребёнка:** отдельная карточка (решено: модель B) или набор атрибутов сотрудника.
2. **Куда повесить раздел:** отдельный пункт меню или вкладка в модуле сотрудников.
3. **Правило «сереньких»:** только уволенные или ещё и декрет / лечение (в коде сегодня только `working` / `fired`).

### Решения владельца (15.11.2026)

1. **Отдельная карточка ребёнка** — своя сущность `erp_employee_children`, свои фильтры и свои отчёты.
2. **Два раздела:** «Дети» и «Организационное», оба в группе «Персонал и доступ». Доступ — свой раздел «Дети и организационное» (данные детей — персональные, в общий кадровый контур не пускаем).
3. **«Серенькие» = уволенные + декрет + лечение.** Значит, статус занятости расширен: `EmploymentStatusCode` получил `decret` и `sick_leave` (`shared/src/domain/employees.ts`), правило одно — `isSilverParentStatus`.

## Шаг 3. Модель данных

Три строгие таблицы (EAV-мороз — новые фичи не добавляют EAV-атрибутов):

| Таблица | Что | Ключевые поля |
|---|---|---|
| `erp_employee_children` | Карточка ребёнка | `id`, `employee_id` (id сотрудника), `full_name`, `birth_date` (мс), `gender`, `tags_json`, `note`, служебные поля синка |
| `erp_org_events` | Мероприятие (праздник, соревнование, день рождения) | `id`, `title`, `kind`, `event_date` (мс), `description`, `status`, служебные поля синка |
| `erp_gift_records` | Журнал выдачи подарков/наград/грамот | `id`, `event_id`, `recipient_kind` (`employee`/`child`), `recipient_employee_id`, `recipient_child_id`, `gift_kind`, `title`, `place` (место/ранг), `given_at`, `note`, служебные поля синка |

Правила:

- **Возраст считается** от даты рождения, в коде нет захардкоженного возраста.
- **«Серенький» выводится** из статуса родителя; ручного флага на ребёнке нет.
- **Отбор — фасет**, а не сохранённый список; решение оператора хранится.
- **Дубли не заводятся**: получатель подарка — ссылка на сотрудника или ребёнка, а не свободный текст с ФИО.
- Персональные данные детей (ДР, возраст, здоровье) — в карточке; в отчёты по умолчанию не выгружаются.

## Шаг 5. Организационный модуль — каркас

Мероприятия (список + карточка), журнал выдачи подарков/наград/грамот, получатели из модуля сотрудников, связь «дети сотрудника — получатели подарков». Каркас = можно создать, записать и увидеть; наполняет оператор.

## Стражи (тесты, закрывающие правила)

1. Уволенный сотрудник → его дети **не попадают** ни в один отбор, ни в одну напоминалку (один тест на правило, покрывающий все экраны).
2. Возраст ребёнка **считается** от даты рождения — смена ДР меняет возраст везде.
3. Фильтры по детям — **тот же** `FacetDescriptor`, не своя копия (сторож на импорт движка).
4. Напоминание о ДР приходит **только** детям активных сотрудников.
5. Новая сущность **переживает синх** (клиент видит тех же детей, что сервер).
6. Получатель подарка — **ссылка**, а не свободный текст (дубли не заводятся).
