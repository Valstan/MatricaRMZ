## Цель

Единый модуль печатных форм: шаблоны живут в БД (не в localStorage), привязаны к объектам (карточка СИЗ, карточка двигателя, наряд, списки), данные объекта подставляются в форму по шаблону, пункты формы можно отключать перед печатью, шаблон правится прямо из окна печати и применяется «на лету», из шаблона создаются документы (служебная записка, заявление на отпуск), документ можно передать другому оператору и принять в программе.

## Решение по контуру данных — отклонение от плана #5 (Шаг 1)

**План #5 предлагал** новую таблицу `print_templates` в **sync-контракте** (запись в `SYNC_TABLE_OWNERSHIP`, дверь в `WRITE_DOORS.md`, клиентский sqlite-дубль, `SyncTableName`, ветки в `syncService.ts` и `errorRecovery.ts`) — это ~15 файлов.

**Делаем так:** обе новые таблицы — **серверные, вне sync-контракта, клиент ходит по REST** (прецедент — «Приказ о ценах на услуги», и ровно так же уже устроены шаблоны печати СИЗ: `ppe:printTemplates:list` → REST).

Почему так — по фактам, а не по вкусу:

- **Реальный путь печати сегодня — REST.** Форма читает шаблон по сети в момент печати (`PpeCardDetailsPage.tsx:660`). Копия в реплике синка этой форме не нужна и не используется.
- **Синк-контракт тянет за собой 15 файлов** и риск регрессий в контуре, который daily-работает (журнал, выдача, зеркала) — ради копии, которую печать не читает.
- **Целостность данных (ст. 1 Конституции) и «не ломать работающую структуру» (ст. 3)** — дешевле держать шаблоны на сервере как источник правды, чем расширять контур доставки в этой нити.

**Чем платим:** печать шаблона требует связи с сервером. Офлайн (сервер недоступен) печать деградирует до «без шаблона» — все пункты печатаются (как сегодня при недоступном сервере). Это **не регрессия**: так же ведёт себя печать СИЗ сегодня. Офлайн-режим шаблонов — **отдельный пункт** в [`PENDING_FOLLOWUPS`](../PENDING_FOLLOWUPS.md) с готовым рецептом (добавить таблицы в sync-контракт по образцу `ppe_print_templates`).

`ppe_print_templates` **не переименовываем и не удаляем** (её имя живёт в sync-контракте). Старую таблицу оставляем до выпила; данные переносим в новую миграцией.

### PR 3 — Сквозное редактирование + пилот на карточке СИЗ

- Универсальный диалог печати: список шаблонов объекта → выбор → предпросмотр; кнопка **«Править форму»** → редактор → «сохранить» → печать перерисовывается сразу (перечитанный шаблон, без перезагрузки данных).
- Пилот: печать личной карточки СИЗ переводится на общий механизм (`print_templates`, entity_key `ppe_card`); старый путь `ppe_print_templates` остаётся **фолбэком**, если новых шаблонов нет (не ломаем 22/22 смоук от 16.11).

### PR 4 — Модуль документов + приёмка между операторами

- Раздел «Документы»: список (мои / входящие / отправленные), создание по виду документа (служебная записка, заявление на отпуск) → форма заполнения → печать с отключением пунктов галочками.
- Состояния: `draft → sent → accepted | rejected`. Приёмка — явное действие получателя; «отправил документ» = серверная запись, получатель видит входящие у себя.
- Экспорт: Word/Excel — через существующий слой (`listExportSpec.ts` / `window.matrica.exports.card`).

## Заводская линза (три строки)

- **Участок:** печатные формы — сквозной слой документов: наряды, акты, карточки СИЗ, складские документы, ПП; новая сущность — документы и их приёмка.
- **Кормит ли затор:** главный затор — **начало сборки** (ручной подбор деталей из обезличенного фонда). Печатные формы его не кормят. Снимают **вторичную боль**: бумажная передача между операторами (записки, заявления) и ручная перенабивка форм — то, что сегодня ходит тетрадками.
- **Не ломает ли инвариант потока:** поток ремонта не меняется — печать и документы его не трогают; версионирование снимка печати (акты) сохраняется. **Риск:** подписи по должности/цеху — персональные данные → доступ только через существующие `signatureAccess.ts` / `permissions.ts`, узкое право `employees.position.edit` не расширяем.

## Осторожности

- **Обратная совместимость печати.** Печать — ежедневная операция операторов. 4 формы наряда (`woPrintModel.ts` + `woPrintTemplates.ts`) и печать списков (`ListPrintDialog.tsx`) не трогаем; пилот идёт на карточке СИЗ, где новый механизм **перекрывается** старым, а не заменяет его.
- **Персональные данные.** Подписи, состав бригады, должности и подразделения — доступ через существующие `signatureAccess.ts`/`permissions.ts`. Узкое право `employees.position.edit` не расширяем.
- **Шаблоны перестают быть локальными.** После переезда пресеты поедут за оператором — изменение поведения, а не только кода (учесть в релизе).
- **Картинки в шабблоне** — data URI внутри `layout_json`. Ограничение размера (валидация на двери + в редакторе), иначе шаблон станет тяжёлым для всех клиентов.
- **Печать не требует правок контура доставки**, но клиентский релиз (Electron) нужен: без обновления клиента новых форм не появится.
- **Канон репозитория.** План — файл в `docs/plans/` (он и есть), `docs/SESSION_HANDOFF.md` обновляется в каждом PR нитки, работа — PR-only flow, фича на 3+ PR → финальный сквозной проход по всей ветке.

## Что не трогаем

- `ppe_print_templates` — не переименовываем, не удаляем (имя живёт в sync-контракте).
- `ledgerAuthz.ts` / `WRITE_DOORS.md` — гейт не обходим: новые таблицы **вне** sync-контракта, записи о владении не требуются (прецедент — «Приказ о ценах на услуги»).
- `permissions.ts` / `signatureAccess.ts` — узкие права не расширяем.
- Существующие 4 формы наряда и печать списков — не ломаем.
- Прод-контур (`deploy/`, релизный процесс) — не трогаем.
