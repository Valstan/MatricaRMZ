# Производственная программа: переверстка модуля, печатной формы и рекламаций 🗓 since:2026-11-10

**Заказ владельца (10.11.2026), два больших задания в одном:**

1. **Экран ПП.** Рабочая область модуля — на всю ширину программы; окно делится на две части: слева плашки производственных программ (выбор по названию и дате), справа — настройка открытой программы. Починить синхронизацию (двигатель при добавлении на время пропадает). Починить период (не выбирается, три поля дат наползают на название). Порядок полей: название → цех → период → статус → строка выбора договоров и двигателей. Внедрить ПОИСК в выпадашки договоров и двигателей (как в списках). Выбор двигателя по номеру — с подтягиванием заказчика и номера договора, и всё это должно жить в связке с карточкой двигателя. Сортировка и группировка по договорам; в колонке «Организация» — заказчик и ТРИ ЦИФРЫ номера договора (до слэша, как уже считает `shortContractSuffix`). Цвета статуса (черновик/утверждён). План следит за выполнением по статусам двигателей, на плашке — счётчики.
2. **Печатная форма.** Кнопка «Печать» сначала открывает ПРЕВЬЮ (сейчас сразу выскакивает окно принтера, и форму печати нельзя поправить). В превью — галочки у подписей (убрать ненужную подпись из печати) и регулировка размеров шрифтов (шапка, список, подписи). Подписи — вертикально, в два столбца.

Плюс (в том же заказе): **рекламаций может быть несколько** — со своей очередностью (1-я, 2-я, 3-я), даты прихода/ухода не должны пересекаться, «основное» — это первый заезд, рекламация — второй и т.д.; рекламации видны в истории двигателя. И **баг**: при удалении производственной программы пишет «программа не найдена».

Продолжение нитки: [`proizvodstvennaya-programma-2026-11.md`](proizvodstvennaya-programma-2026-11.md) (модуль слит в `main` PR #1638, выкатан v3.113.0).

## Найденные причины (разведка 10.11.2026)

**1. «Двигатель пропадает, потом возвращается» — это не синх как таковой, а смена id строк плана.**

- Клиент шлёт строки плана с черновыми id (`draft-<время>-<n>`, `ProductionProgramPage.tsx`), сервер их не знает и **заводит новые uuid** (`productionProgramService.ts` → `replaceProductionProgramRows`: `id = row.id && existingById.has(...) ? row.id : randomUUID()`).
- Клиент после сохранения НЕ перечитывает строки — до прихода pull'а в экране живут черновые id. Следующее сохранение снова присылает черновой id → сервер снова создаёт строку с новым uuid, а прежнюю снимает мягко.
- В журнале это пара «удалить старую строку + вставить новую». Клиент применяет их по очереди: между «удалением» и «вставкой» строка исчезает — **ровно то, что видит владелец**; потом возвращается «в целости и сохранности».
- Второй симптом того же: у сервера есть уникальный индекс `erp_production_program_rows_order_uq (program_id, order_no) WHERE deleted_at IS NULL`, а вставка новой строки идёт **до** снятия старых → повторное сохранение падает на конфликте номера п/п.

**2. Таблицы ПП не заведены в зеркала синхронизации.**

- `erp_production_programs` / `erp_production_program_rows` отсутствуют в `SERVER_MIRROR_TABLES` (`applyPushBatch.ts`) и в `PG_SYNC_TABLES` (`pgSyncTables.ts`).
- Отсюда: (а) `sync_status='pending'` никогда не снимается → публикатор зеркала переотправляет одни и те же строки **каждый тик (60 с)** — журнал пухнет; (б) `stampRowSeq` не ставит `last_server_seq` → инкрементальный pull по этим таблицам не отдаёт строку (работает только ветка журнала); (в) **холодный снапшот новой машины (`/state/snapshot`) по этим таблицам пуст** — на новом компьютере программы не появятся никогда.

**3. «Программа не найдена» при удалении.**

- Удаление на сервере идёт мягко (`deleted_at`), а журнал доезжает до клиента только через публикатор (до 60 с) и pull.
- Клиент после успешного удаления делает `reload()` по **локальной реплике**, где программа ещё жива → она остаётся в списке; повторный клик «Удалить» → сервер: «программа не найдена».
- Плюс: удаление не идемпотентно — второй запрос с тем же id даёт ошибку вместо успеха.

**4. Ширина экрана.** Карточка ПП — обычный `.ui-content-block`, а его ширина ограничена переменной `--ui-content-block-max-width: min(95vw, 1200px)` (`global.css`). Отсюда «рабочая область модуля не на всю ширину программы».

**5. Печать.** `openProductionProgramPrint` открывает окно и сразу зовёт `w.print()` → оператор видит окно принтера и не может поправить форму. Подписи лежат одной горизонтальной строкой (8 подписей — половина листа).

**6. Рекламация одна.** Рекламация живёт набором EAV-атрибутов карточки (`reclamation_flag`, `reclamation_accepted_date`, `reclamation_shipped_date`, … — `EngineDetailsPage.tsx`), без номера очереди и без проверки порядка дат.

## Решения

1. **Строки плана получают постоянный id.** Клиент шлёт `crypto.randomUUID()`; сервер принимает клиентский id, если это валидный uuid и он не занят другой программой. Строка не пересоздаётся → нет пары «удалить+вставить» → движок не пропадает. Порядок в серверной двери: сначала мягко снять пропавшие строки, потом вставить новые (уникальный индекс по № п/п не конфликтует).
2. **Таблицы ПП заводим в зеркала.** `PG_SYNC_TABLES` (штамп `last_server_seq` + холодный снапшот) и `SERVER_MIRROR_TABLES` (снятие `pending`). Класс гонки — тот же, что закрыт для СИЗ и умолчаний подписей.
3. **Удаление идемпотентно и видно сразу.** Сервер на «уже снятой» программе отвечает успехом; клиент убирает программу из списка сразу после ответа и показывает, что ждёт подтверждения синком.
4. **Период — вид + календарь.** Выпадашка вида периода (две недели / месяц / свои даты) + календарь выбора дат (`Input type=date` с пикером проекта). Порядок полей шапки — как у владельца: **название → цех → период → статус**.
5. **Поиск в выпадашках — через `SearchSelect`** (тот же механизм, что в списках): договор (заказчик/номер) и двигатель (марка/номер).
6. **Выбор двигателя по номеру подтягивает заказчика и договор** из живой карточки (`EngineListItem.customerName/contractName`), а строка плана показывает их из карточки, а не из снимка. Договор в строке — ссылка, а не копия текста: снимок `group_label` остаётся для печати, но текст «Организация» печатается/показывается из карточки.
7. **Колонка «Организация» — заказчик + `*NNN`** (три цифры до слэша, `shortContractSuffix`). Без слэша — номер договора как есть.
8. **Цвета статуса:** черновик — бледно-серый (нейтральный), утверждён — зелёный. Плашка показывает также счётчики выполнения.
9. **Превью печати — промежуточный этап.** «Печать» открывает окно с формой и кнопкой «Печать»; в окне — галочки подписей и кегли (шапка/список/подписи). Настройки живут в состоянии окна (и `localStorage` по id программы), в саму программу не пишутся: это вид печати, а не данные плана.
10. **Подписи — вертикально в два столбца** (должность сверху, линия подписи снизу), как в Word-форме.
11. **Рекламации — строгая таблица `erp_engine_reclamations`** (EAV-заморозка: новые атрибуты не заводим): двигатель, номер очереди, даты приёма и отправки, описание дефекта, характер, акт, комментарий. Порядок и гейт — в домене.
12. **Гейт дат рекламаций:** основной цикл — заезд №1; рекламация №1 — заезд №2 и т.д. Дата прихода следующего заезда не может быть раньше даты отправки предыдущего; дата отгрузки из вкладки «Основное» не может быть позже прихода рекламации.
13. **История двигателя** показывает рекламации по порядку заездов (1-й — основной, дальше — рекламации).

## Заводская линза

`Заводская линза: планирование производства (ПП) и учёт рекламаций · затор: не касается (ПП не разбирает детали и не трогает начало сборки — главный затор по модели) · поток: не ломает — заезды двигателя появляются в истории как этапы (основной → рекламация №1 → №2), инвариант «приход до отгрузки, заезды по порядку» проверяется гейтом, а не молчанием.`

## Этапы (каждый — отдельный PR, правило «один PR — одна задача»)

### Этап 1. Синхронизация и удаление программы  ✅ (PR #1662)
- Постоянные id строк плана (клиент — uuid, сервер — принимает клиентский id).
- Порядок в `replaceProductionProgramRows`: снять пропавшие → вставить/обновить.
- Таблицы ПП в `PG_SYNC_TABLES` и `SERVER_MIRROR_TABLES` (штамп seq, снятие `pending`, холодный снапшот).
- Удаление идемпотентно; клиент убирает программу из списка сразу.
- Тесты: идемпотентность удаления, стабильность id, регистрация таблиц в зеркалах.

### Этап 2. Экран: две части на всю ширину  ✅ (PR #1663)
- Полная ширина (`--ui-content-block-max-width: 100%` на корне страницы).
- Слева — плашки программ (название, период, цех, статус-цвет), справа — редактор.
- Порядок полей: название → цех → период (вид + календарь) → статус → добор строк.
- Поиск в выпадашках договоров и двигателей.
- Выбор двигателя по номеру с подтягиванием заказчика и договора.
- Группировка строк по договорам; «Организация» = заказчик + `*NNN`.

### Этап 3. План следит за выполнением  ✅ (PR #1664)
- Домен: статус выполнения строки (готов к отгрузке / отгружен / в работе / не начат) и «в срок / просрочен» по плановой дате.
- На плашке программы: собрано / не собрано / в срок / просрочено.

### Этап 4. Печатная форма: превью, галочки, кегли  ✅ (PR #1665)
- Промежуточный этап «Печать» → окно превью с кнопкой «Печать».
- Галочки подписей (подпись убирается из печати).
- Кегли: шапка / список / подписи — плюс-минус.
- Подписи вертикально в два столбца.

### Этап 5. Рекламации по очереди  ✅ (PR #1666)
- Строгая таблица `erp_engine_reclamations` (миграция `0125`): одна строка — один заезд по
  рекламации (`queue_no` = порядок 1, 2, 3 …), даты приёма и отправки, описание и характер
  дефекта, акт, комментарий. EAV под заморожкой — новых атрибутов нет.
- Контракт синхронизации: `SyncTableName.ErpEngineReclamations` (таблицы/dto/registry),
  `LedgerTableName`, владение `server`, зеркала в `PG_SYNC_TABLES` / `pullChangesSince` /
  `SERVER_MIRROR_TABLES`, домен синка — `engines`.
- Серверная дверь: `engineReclamationService` (список + полная замена очереди) и REST
  `/engine-reclamations`; публикатор зеркала `engineReclamationSyncPublisherService`.
- Реплика клиента: таблица в electron и android (текст CREATE — буквально, сторож паритета),
  ветка применения pull, IPC `engineReclamations:list/save`.
- Домен (`shared/src/domain/engineReclamations.ts`): гейт дат заездов (основной цикл — заезд
  №1, рекламация №1 — заезд №2; приём не может быть раньше отгрузки предыдущего заезда),
  порядок очереди, заезды для истории, строки истории рекламации.
- Вкладка «Рекламация» карточки: **слева очередь (1-я, 2-я, 3-я …), справа — выбранная
  рекламация**; своя кнопка «Сохранить очередь» (как «Сохранить платежи»); гейт дат
  проверяется на клиенте и на сервере.
- История двигателя: блок «Заезды двигателя» — основной цикл и рекламации по порядку.
- Перенос старых данных: `engine-reclamations:backfill` (dry-run по умолчанию, `--apply`)
  переносит существующие EAV-рекламации в очередь №1.
- EAV-атрибуты остаются **зеркалом текущей (последней) рекламации**: по ним читают синяя
  метка в списке двигателей и источник правды по датам (`resolveEngineTruthDates`).
