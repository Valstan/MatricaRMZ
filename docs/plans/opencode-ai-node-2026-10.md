# ИИ-узел: авто-подъём сессий + ИИваныч через встроенный opencode (D10)

Дизайн D10 (план `client-stability-and-ai-2026-10.md`). Статус: слайс 1 в работе,
слайсы 2–3 — следующими PR.

## Что уже есть (main)

- Нативный узел: per-user каталог, serve только на loopback `:3080`, старт/стоп
  с клиентом, статус в разделе (#1320); релей `/opencode/*` через `:38080`
  стримом без буферизации (#1322).
- ИИваныч сегодня: очередь `aiChat` → sync → серверный воркер `callLlmWithTools`
  (DeepSeek, batch) → ответ целиком → поллинг 15 с/5 с. Стрима в окне нет.

## Решение 1: изоляция данных вместо общей базы (проверено живьём 14.10.2026)

Десктопный CLI 2.0.28 и наш узел v1.19.0 делили
`%USERPROFILE%\.local\share\opencode`: новый CLI смигрировал базу на
`session_v2`-only, наш serve упал «Database is not empty and has no session
table», а файл держал живой инструмент владельца — вариант 3 (.bak + рестарт)
неприменим без остановки его работы. Проверка: `XDG_DATA_HOME=<отдельный
каталог>` + `serve --port 13080` → здоровый serve, свежая база 250 КБ,
десктоп ничего не заметил. Конфиг (`opencode.jsonc`, auth) при этом читается
общий — split ровно там, где надо: общее — конфиг, своё — база.

Слайс 1: менеджер поднимает serve с `XDG_DATA_HOME=<install>/data`
(не-Windows — `<userData>/opencode-node-data`).

## Решение 2: вотчер вместо «упал до перезапуска»

`proc.on('exit')` только обнулял `child`: упавший serve лежал мёртвым до
перезапуска клиента. Слайс 1: тихий интервал 15 с — health dead →
немедленный переподъём; consecutive-ошибки спауна — бэкофф 15 с → 5 мин,
сброс при успехе. Ручной стоп (`stopOpencodeNode`, before-quit) вотчер гасит.

## Решение 3: транспорт — напрямую из main, не релеем

Релей `:38080` — для LAN-пиров и требует включённой раздачи. Агентские вызовы
своего узла main ходит напрямую `http://127.0.0.1:3080` (node fetch): нет
зависимости от тумблера, нет лишних хопов. Релей не трогаем.

## Карта API serve v1.19.0 (снята с живого бинаря 14.10.2026)

`GET /api/session` (список) · `POST /api/session {id?,agent?,model?,location?}` ·
`GET /api/session/active` · `GET|DELETE /api/session/:id` · `POST
/api/session/:id/{fork,agent,model,rename,move,prompt,command,skill,synthetic,shell}`
· `GET /event` (SSE, проверен `server.connected`) · `GET /global/health`.
Промпт: `POST /api/session/:id/prompt {id?,text,files?,agents?,metadata?,delivery?,resume?}`.
Открыто на слайс 2: семантика DELETE (вернул 200, строка осталась в списке);
какой `agent`/`model` — дефолт serve (бесплатная облачная модель раздачи,
решение владельца) или явный; `delivery`/`resume` — по чтению клиента из бандла.

## Слайсы

1. **Изоляция + вотчер** (этот PR): `XDG_DATA_HOME`, интервал переподъёма,
   бэкофф, тесты, живой смоук (убить serve → health вернулся).
2. **Клиент сессий**: `opencodeSessionClient` (create/prompt/abort/delete),
   персист sessionId (userData-файл, валидация при старте), фоновая агентская
   сессия переживает рестарт serve.
3. **Стрим в ИИваныча**: вопрос → prompt → SSE `/event` → прогрессивный рендер
   окна; DeepSeek — запасной контур при мёртвом узле (триггер и пометка
   «ответ узла» — лимиты не публикуются, данные могут идти в обучение).

## Открытое (не блокер слайса 2)

- Auth на релее спрошен у brain (ack-письмо мандата) — без ответа; агентские
  вызовы идут напрямую, не релеем, поэтому не блокер.
- Лёгкий token для serve — вопрос brain без ответа; аналогично.
- `DELETE /api/session/:id` в v1.19.0 — no-op (200, строка остаётся в списке,
  и с `?directory=` тоже): наш remove чистит только свой persisted id —
  best-effort, как и задумано. Мусор копится в изолированной базе узла.
- Директория агентской сессии по умолчанию — CWD процесса serve (у dev-стенда
  вышло `...\\electron-app`): слайс 3 должен передавать явный
  `location: {directory}` (песочница/проект), иначе агент действует из
  непонятного места. Каталог обязан существовать заранее: иначе GET сессии
  падает 500 (`realPath ... ENOENT`, найдено живьём 14.10.2026).
- Промпт с живым прогоном модели — приёмка слайса 3 (здесь только формы,
  модель не дёргалась).
