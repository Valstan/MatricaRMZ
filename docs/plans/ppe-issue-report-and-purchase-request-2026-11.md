## Заводская линза (три строки)

- **Участок:** склад СИЗ: номенклатура спецодежды, остатки, выдача, учёт выданного.
- **Кормит ли затор:** не кормит. Главный затор модели — «начало сборки: ручной подбор совместимых деталей из обезличенного фонда»; СИЗ его не касается.
- **Инвариант потока:** не ломает. Обезличивание деталей, партия/экземпляр (`stamped_number`), маршрутный лист и сдельщина против нормо-часов не затрагиваются; новая номенклатура спецодежды помечена `category='workwear'` и в фонд деталей не попадает.

## Задание владельца (промт #23, своими словами)

> По отчёту СИЗ: сейчас он показывает «выдано 15 человек, остальным не выдано» — одной нормой.
> Нужно, чтобы по каждому сотруднику было видно, что именно выдано, а что нет (например, ботинок не хватило — значит «не выдана»), и чтобы это доходило до отчёта «что кончилось» для закупки: сейчас непонятно, что конкретно заказывать.

## Что уже есть (сверено с кодом, а не по памяти)

- **Журнал выдачи** (`electron-app/src/renderer/src/ui/pages/PpeJournalPage.tsx`) — по каждому сотруднику и позиции: дата выдачи, позиция, размер, выдано, кол-во на год, срок носки, дата возврата, износ. Факты выдачи есть.
- **Справка «Невыданное за период»** (`shared/src/domain/ppeAcceptance.ts`, `buildUndeliveredReport`) — по (сотрудник, позиция): норма, выдано, невыдано, срок. Данные по нехватке тоже есть.
- **Заявка на СИЗ** (`ppe_request_sheet`, `electron-app/src/main/services/reports/presets/ppe.ts:441`) — уже считается по номенклатуре и печатается.
- **Склад СИЗ** — отдельная локация `workwear`, остатки грузятся отчётом 1С как корректировка (план [`siz-stock-and-issue-card-2026-11.md`](siz-stock-and-issue-card-2026-11.md)).

## Разрыв (что реально не сделано)

1. **Заявка не видит главный сценарий владельца.** Потребность считается через `upcomingIssues` (`shared/src/domain/ppe.ts:279`), который берёт только позиции **со сроком в горизонте 90 дней**. Позиция, которую **никогда не выдавали** (`neverIssued`, `nextDueAt = null`), в заявку не попадает вообще. Именно это и есть «ботинок не хватило → не выдана»: нехватка не доходит до закупки.
2. **Заявка не по размерам.** Ключ строки — `nomenclatureId` базовой позиции; размерная пара (база → размер) не собирается, хотя размерный ряд есть и в нормах (`СИЗ-018` + `СИЗ-018-44 …, р. 44`), и на складе.
3. **В заявке нет величины «выдано».** Потребность, остаток и дефицит есть, а «сколько уже обеспечено» — нет: видно число, не видно, из чего оно получилось.
4. **Нет ведомости по людям.** Ни один отчёт не даёт «одна фамилия + набор выданного + что не выдано». `ppe_coverage` даёт по сотруднику счётчики («обеспечен / не обеспечен») — это как раз тот отчёт, где «15 человек обеспечены, остальным не выдано» одной нормой.
5. **Различения «не выдано» vs «выдано частично» нет.** В данных есть `issuedQty` и `normQty`, но признак «норма не выдана целиком» и «выдана частично» нигде не назван.

## Решение (что делаем)

### Домен — `shared/src/domain/ppeIssueCoverage.ts` (новый)

Чистые функции, те же правила для экрана, отчёта и печати:

- `ppeShortage(item)` — **нехватка по позиции и её причина**: `never_issued` (не выдано) · `partial` (выдано частично) · `overdue` (пора перевыдать) · `returned` (сдано). Правила:
  - `neverIssued` → не хватает всей нормы;
  - `returned` → не хватает всей нормы (вещи у сотрудника нет);
  - `overdue` → не хватает всей нормы (старая вещь кончилась, нужна новая);
  - выдано за год меньше нормы → не хватает `норма − выдано` (**частичная** выдача);
  - иначе не хватки нет.
- `buildPpeEmployeeIssueRows(...)` — **ведомость по сотрудникам**: строка = сотрудник; «выдано» — перечень позиций с размерами и количеством, «не выдано» — перечень позиций с причиной и количеством; состояние — обеспечен / не обеспечен / нет норм.
- `buildPpeRequestPositions(...)` — **заявка по позициям и размерам**: строки по паре (позиция, размер): потребность (нехватка), выдано, остаток склада, к закупке, цена, сумма.

### Клиентский сервис — `electron-app/src/main/services/ppeIssueCoverageService.ts` (новый)

Сборка из клиентской реплики (тем же путём, что журнал): номенклатура с размерным деревом, карточки сотрудников, нормы (по базам), журнал выдач (по размерным детям), размеры сотрудника из EAV (`PPE_SIZE_ATTRIBUTE_CODES`), остатки склада `workwear`, цены из EAV `price`.

### Отчёты

- **Новый пресет** `ppe_issue_by_person` — «Ведомость по выдаче СИЗ»: одна строка на сотрудника.
- **Переработан** `ppe_request_sheet` — «Заявка на СИЗ»: потребность → остаток → к закупке, с разбивкой по размерам и колонкой «выдано».

## Формула заявки (и почему такая)

`к закупке = потребность (нехватка) − остаток на складе`

- **Потребность в отчёте — уже за вычетом выданного** (это и есть нехватка): не выдано ни разу, выдано частично, подошёл срок, сдано.
- **Выданное показано отдельной колонкой и дважды не вычитается.** Выдача списывает склад (`ppeService.issuePpe` → документ `stock_issue` проводится сразу), поэтому «выданное» и «остаток» — непересекающиеся величины: выданное уже не лежит на складе.
- **Остаток, которого мы не знаем, не вычитается.** Где позиции нормы на складе нет, остаток — прочерк, а не ноль: иначе заявка сказала бы «склад пуст» там, где он просто в другом слое номенклатур.

## Границы (что НЕ делаем в этой нитке)

1. **Мост «приказная норма ↔ торговая позиция завода»** — не в этой нитке: это промт **#20/#25** (отдельная пара, ждёт принципа владельца). Пока моста нет, остатки торговых позиций (отчёт 1С) и потребность приказных (`СИЗ-xxx`) лежат в разных слоях, поэтому «На складе» для приказной позиции — прочерк. Это видно в отчёте, а не спрятано.
2. **Мыло и карточка смывающих средств** — промт **#21/#26**, отдельная нить.
3. **Своя номенклатура на позицию набора** — промт **#20/#25**.
