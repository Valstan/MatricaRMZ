# Синхронизация СИЗ: клиент ронял pull у всего парка (вид карточки в реплике)

> Нить по инциденту 20.11.2026: у всех клиентов парка падала синхронизация ошибкой
> `UNIQUE constraint failed: ppe_issue_cards.employee_id, ppe_issue_cards.kind`.

**Статус:** код готов, ждёт выката (клиентский релиз + бэкенд). **Дата:** 2026-11-20.
**Ника:** СИЗ, кладовщик. **Симптом пришёл из:** лога клиентов (6+ машин, разные пользователи).

## Что случилось

С 20.11.2026 ~12:11 клиенты парка падают на синхронизации одинаковой ошибкой:

```
sync failed: SqliteError: UNIQUE constraint failed: ppe_issue_cards.employee_id, ppe_issue_cards.kind
  at upsertPulledRowsInChunks ... at applyPulledChanges ... at pullOnce ... at runSync
```

Ошибка не в данных и не в сети: она в разборе pull'а клиента.

## Диагноз (по коду и по прод-данным)

1. **Прод (read-only).** Открытых карточек по мылу ровно одна, и она у того же сотрудника, у которого открыта карточка по спецодежде. Серверный индекс по паре `(employee_id, kind)` (частичный, `WHERE closed_at IS NULL AND deleted_at IS NULL`) держит инвариант: 0 нарушений. Сервер отдаёт **законную** пару строк.
2. **Журнал.** Карточка по мылу опубликована 20.11 в 12:11 (`ppe_issue_cards`, seq 6087898) — ровно тогда, когда пошли первые падения. Карточка по спецодежде того же сотрудника опубликована сильно раньше (seq 2335012), то есть **у клиента она уже была**.
3. **Клиент.** Вид карточки (`kind`) вошёл в таблицу миграцией 0131. План нити СИЗ перечислил четыре места, где поле надо продублировать (dto, реестр, издатель, схема реплики) — и все четыре обновили. **Пятое место — разбор pull в `applyPulledChanges` — забыли.** Клиент вставлял карточку без `kind`, SQLite брал дефолт колонки (`'workwear'`), и карточка по мылу вставала в реплику как ещё одна карточка по спецодежде → уникальный индекс открытой карточки → **падал весь батч pull**. Две строки останавливали синхронизацию завода.

## Заводская линза (три строки)

- **Участок:** склад (СИЗ): учёт выдачи СИЗ, карточки сотрудника.
- **Кормит ли затор:** не кормит. Главный затор модели — «начало сборки: ручной подбор совместимых деталей из обезличенного фонда»; СИЗ его не касается. Но чинит он кое-что важное: **синхронизация парка**, без которой оператор видит устаревшие данные.
- **Инвариант потока:** не ломает. Движение по фонду деталей, обезличивание, маршрутный лист и сдельщина не затрагиваются. Инвариант модуля СИЗ — «одна открытая карточка на вид» — сохраняется: серверский индекс и клиентский частичный индекс совпадают по паре `(employee_id, kind)`.

## Что сделано

### Клиент (`electron-app/src/main/services/syncService.ts`)

- `kind` для `ppe_issue_cards` и `ppe_norm_sets` — и в объекте строки, и в conflict-set (без conflict-set поле вставилось бы один раз и больше не обновилось бы).
- Догружены поля того же класса: `trade_name` / `certificate` (приказные строки), `returned_at` / `returned_by` / `wear_percent` (возврат СИЗ).
- Три поля набора норм (`occupation_id`, `source_kind`, `source_label`) добавлены в conflict-set — раньше они не обновлялись.
- **Четыре таблицы, которые приезжали в pull и молча терялись**, теперь применяются в реплику: профессии приказа (`ppe_occupation_ref`), приказные строки (`ppe_norm_line_specs`), личные карточки СИЗ (`ppe_employee_cards`), шаблоны печатных форм (`ppe_print_templates`). Клиентский код эти таблицы читает — выгрузка для 1С (имя позиции, подразделение, должность) и запасной шаблон печати личной карточки; реплика была пустой.

### Сервер (`backend-api/src/services/sync/ppeSyncPublisherService.ts`)

- Порядок публикации карточек: закрытые и удалённые раньше открытых. Без этого «закрыли карточку и открыли новую» в одном проходе давали клиенту промежуточное состояние, в котором открытая карточка вставлялась при ещё живой старой (класс [M72](../gotchas/M72.md)).

### Сторожи и гейты

- `electron-app/src/main/services/sync/pullColumnCoverage.guard.test.ts` — каждая колонка реплики обязана заполняться из payload, обновляться в conflict-set и быть в контракте реестра.
- `electron-app/src/main/services/sync/pullApplyGroups.guard.test.ts` — каждая собранная группа обязана применяться в реплику (обратная сторона того же класса).
- `electron-app/src/main/services/sync/ppeIssueCardsReplica.guard.test.ts` — реплика на настоящей SQLite принимает карточку по мылу рядом с карточкой по спецодежде.
- `android-app/src/core/runSyncPpeReplica.smoke.test.ts` — **сквозной** гейт: настоящий `runSync` клиента против фейкового сервера с двумя открытыми карточками. Без правки падает ровно той же строкой, что в логе парка.
- Оба сторожа и сквозной гейт **проверены контролем**: снятие правки даёт красный тест.

## Почему парк recovers сам

Курсор pull'а у клиента не уехал за упавший батч (`applyPulledChanges` кинул ошибку до записи курсора), поэтому строки приедут снова. С обновлённым клиентом карточка по мылу встанет со своим видом, и синхронизация продолжится. Переустановка и сброс реплик не нужны.

## Что не сделано / что дальше

- Релиз клиента и выкат бэкенда — отдельный осознанный шаг (см. SESSION_HANDOFF).
- Сторож покрывает таблицы реплики клиента. Для Android-порта код синхронизации общий (`android-app` импортирует `electron-app/src/main/services/syncService.ts`), поэтому правка покрывает и планшетный парок.
