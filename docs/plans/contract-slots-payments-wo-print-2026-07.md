# План: слоты контракта как единый список, адресный аванс, контроль марки, печатные формы нарядов

**Статус:** черновик, ждёт «поехали» владельца.
**Дата:** 2026-07-31. Источник — устная постановка владельца (сессия 31.07).

## Context

Три независимых блока из одной постановки. Первые два — надстройка над уже отгруженной
подсистемой платежей ([`engine-payments-2026-07.md`](_archive/engine-payments-2026-07.md),
PR #401–#408, v2026.729.1041); третий — про печать нарядов, к платежам отношения не имеет.

**Что уже есть и переиспользуется** (важно: ничего из этого не пишется заново):

- Слот `PaymentSlot {id, sectionKey, engineBrandId?, engineId?, contractPriceKop?, payments[]}`
  внутри контрактного EAV-атрибута `contract_payments` — `shared/src/domain/payments.ts:27-55`.
  Отдельной таблицы платежей нет и не заводим: EAV едет существующим sync без DDL.
- `syncSlotsWithPlan` (payments.ts:234-304) — разворачивает план `contract_sections` в слоты,
  привязывает двигатели, чистит лишние пустые.
- `distributeAmount` (payments.ts:311-342) — равномерное разнесение суммы по слотам секции.
- Вкладка «Платежи» карточки двигателя — `components/EnginePaymentsTab.tsx`; читает и пишет
  слот **через контракт**, своей копии денег у двигателя нет.
- Колонки «Оплачено ₽ / Последний платёж / Отсчёт ремонта» + подсветка 90 дней в таблице
  двигателей секции; колонка «Горящие» в списке контрактов; два отчёта по платежам.
- Чекбоксы на строках двигателей (для служебной записки) — `ContractDetailsPage.tsx:903-934`.

**Чего нет** (и это ровно постановка владельца): адресности разнесения, единого списка,
контроля марки при привязке, отдельных печатных форм по типу наряда.

## Блок A — три списка в карточке контракта сводятся в один

### Как сейчас

В карточке контракта двигатели и слоты разложены по **трём** таблицам:

| # | Таблица | Файл | Что показывает |
|---|---|---|---|
| 1 | «Двигатели» (внутри секции) | `ContractDetailsPage.tsx:880-986` | двигатели с `contract_section_number === токен секции`, с платёжными колонками |
| 2 | «Платежи по слотам» | `ContractDetailsPage.tsx:990-1088` | **только пустые** слоты (`emptySlots`) |
| 3 | «Прикрепленные двигатели» | `ContractDetailsPage.tsx:2054-2155` | весь `relatedEngines`, 3 колонки, без платежей |

Занятый слот и занявший его двигатель физически рендерятся в **разных** таблицах — это и есть
«два разных списка», на которые указал владелец. Плюс двигатель с `contract_id`, но **без**
`contract_section_number` не попадает ни в один слот никогда (фильтр `ContractDetailsPage.tsx:1569-1570`),
а кнопка «Добавить двигатель» общего блока (`attachEngineToContract`, 1500-1518) создаёт ровно
такое состояние — пишет только `contract_id`.

### Как будет

Одна таблица на секцию. **Строка = слот.** Порядок — по марке, внутри марки: занятые (по номеру
двигателя), затем пустые.

```
[✓] │ № │ Марка (план) │ Двигатель │ Статус │ Стоимость ₽ │ Платёж 1 │ Платёж 2 │ … │ Оплачено ₽ │ Отсчёт
```

- **Платёж N** — динамические колонки, число = максимум платежей среди слотов секции.
  В ячейке две строки: сумма и дата (`100 000 ₽` / `14.07.2026`). Таблица уже в
  `overflow-x: auto` (`DataTable`), горизонтальная прокрутка бесплатна.
- Пустой слот: ячейка «Двигатель» — пикер «привязать» (см. блок C, фильтр по марке слота).
- Занятый слот: номер двигателя, клик открывает карточку.
- **Платежи редактируются на любой строке**, не только на пустых слотах — закрывает пункт 3
  открытого хвоста `PENDING_FOLLOWUPS §Платежи по двигателям` («редактирование платежей пустых
  слотов прямо в контракте»).
- Таблицы 2 и 3 **удаляются**. Вместо таблицы 3 — блок-предупреждение «Двигатели без секции (N)»,
  показывается **только когда список непуст**, с кнопкой «Разложить по слотам» (блок C).

### Устойчивый идентификатор строки

Сейчас номер слота в UI — `№{idx+1}` от индекса отфильтрованного массива
(`ContractDetailsPage.tsx:1041`), то есть при любой пересортировке он «прыгает».
В новой таблице ключ строки — `slot.id` (uuid), а видимый «№» считается внутри группы марки
и служит только для чтения глазами.

## Блок B — аванс разносится на **выбранные** двигатели

### Как сейчас

`distributeAmount(cp, sectionKey, amountKop, kind, date, newId, slotCount?)` берёт слоты секции
**в порядке массива** и режет `slice(0, slotCount)` (payments.ts:320-321). Форма спрашивает
«На слотов (из N)» — то есть «первые N», без выбора конкретных марок и двигателей.
Для контракта с двумя марками (10 шт. марки A + 10 шт. марки B) разнести аванс только по марке A
сегодня **невозможно**.

### Как будет

**Домен.** Новая чистая функция рядом с существующей (старую не ломаем — её зовёт текущая форма):

```ts
export function distributeAmountToSlots(
  cp: ContractPayments,
  slotIds: readonly string[],
  amountKop: number,
  kind: PaymentKind,
  date: string,
  newId: () => string,
  note?: string,
): ContractPayments
```

Правила — те же, что у `distributeAmount`, чтобы поведение не разъехалось:
`per = floor(amount / N)`, остаток копеек — **первому** слоту из `slotIds` в порядке их
следования в `cp.slots`; `countdownStart: true` ставится, если у слота стартового платежа ещё
нет и `kind ∈ {advance, extra_advance}`. Дополнительно — прогон `normalizeCountdownFlags`
(которого `distributeAmount` сегодня не делает, payments.ts:331): чинит уже испорченный слот,
а не только не портит чистый.

**UI.** Одно состояние выделения на секцию, **ключ — `slot.id`** (не `engineId`: пустые слоты
тоже надо уметь выбирать — деньги часто приходят раньше двигателей).

- Колонка-чекбокс слева, шапка — «выбрать все в секции».
- Внутри группы марки — строка-заголовок марки с чекбоксом «вся марка» (это главный сценарий
  владельца: «на 10 двигателей определённой марки такой-то авансовый платёж»).
- Панель над таблицей: `Отмечено: N` · `[Разнести аванс]` · `[Служебная записка]`.
- Модалка разнесения: сумма ₽, дата, вид платежа, примечание; под полями — живой расчёт
  «по 100 000 ₽ на 10 позиций, остаток 0 ₽ первой».

**Существующее выделение «в служебную записку» переезжает на это же состояние** — один
столбец чекбоксов, два действия. Сегодня их два разных (`memoSelection` по `engineId`).

### Двусторонняя видимость

Отдельной работы не требует и уже работает: платёж лежит в слоте, вкладка «Платежи» карточки
двигателя читает **тот же** слот по `engineId`. Разнесённый в контракте аванс появляется в
карточке двигателя сам. Обратно — тоже.

### ⚠️ Обязательный к починке стык: потеря чужой записи

Прежде чем добавлять групповое разнесение, чиним существующий lost-update — иначе новая фича
бьёт ровно в него:

- `ContractDetailsPage.saveContractPayments` (1541-1548) пишет **весь** `contract_payments` из
  React-стейта **без пере-чтения** контракта. План подсистемы это требовал (`engine-payments-2026-07.md:53`),
  в карточке контракта требование не выполнено.
- `EnginePaymentsTab.save` (188-249) контракт пере-читает, но **свой** слот заменяет черновиком
  целиком (215-217): аванс, разнесённый в контракте после того, как вкладка была открыта,
  затирается при нажатии «Сохранить платежи».

**Решение:** один хелпер на оба пути —
`mutateContractPayments(contractId, mutator: (cp) => ContractPayments)`: читает контракт,
парсит, применяет мутатор, пишет. Все мутации платежей (разнесение, правка строки, удаление,
привязка слота) идут только через него. Кладём в
`electron-app/src/renderer/src/ui/utils/contractPaymentsStore.ts`.

## Блок C — двигатель попадает в слот **своей** марки

### Как сейчас

Контроля марки нет **нигде**:

1. `syncSlotsWithPlan` шаг 3 (payments.ts:284-287): `pool = brandMatched.length > 0 ? brandMatched : free`
   — если свободного слота своей марки нет, двигатель **молча** ложится в слот чужой марки.
2. Пикер двигателя в секции (`ContractDetailsPage.tsx:966-977`) отдаёт **все** двигатели системы,
   без фильтра по марке.
3. `engineService.setEngineAttribute` (main, 907-1005) валидирует только дубли номера — марку и
   контракт не сверяет.
4. `syncSlotsWithPlan` вызывается **ровно из одного места** — эффекта карточки контракта
   (`ContractDetailsPage.tsx:1580`). Двигатель, привязанный из **своей** карточки, слот получит
   только когда кто-то откроет карточку контракта.

### Как будет

**C1. Инвариант домена: марка слота = марка двигателя.** В `syncSlotsWithPlan` убираем падение
в `free`: если свободного слота своей марки нет — заводим слот **сверх плана с маркой двигателя**
(механизм уже есть, payments.ts:288-296, просто сейчас до него не доходит). Двигатель больше
никогда не занимает чужое плановое место.

**C2. Привязка из карточки двигателя — автоматическая, с показом результата.**
Новая чистая функция:

```ts
export function planSlotForEngine(
  cp: ContractPayments,
  sections: ContractSections,
  engine: { engineId: string; engineBrandId?: string },
  preferredSectionKey?: string,
): { sectionKey: string; slotId?: string; mode: 'free-slot' | 'new-slot' | 'over-plan' }
```

Порядок выбора: (1) свободный слот своей марки в предпочтённой секции; (2) свободный слот своей
марки в любой секции — primary, затем ДС по порядку; (3) секция, где марка **запланирована**, но
свободных мест нет → слот сверх плана; (4) марка вообще не запланирована → слот сверх плана в
предпочтённой/primary секции.

В `EngineDetailsPage.saveAllAndClose` (879-990) после записи `contract_id`: если контракт задан —
дёрнуть `planSlotForEngine` через `mutateContractPayments`, проставить слоту `engineId`, а
двигателю — `contract_section_number` выбранной секции (сегодня оператор выбирает ДС руками и
может оставить пусто → двигатель не получит слот никогда).

**Что видит оператор:** ничего лишнего в обычном случае — двигатель просто встаёт на своё место.
Плашка появляется только в режимах `over-plan`:
«⚠️ В контракте нет свободного места под марку «В-84». Двигатель добавлен сверх плана — проверьте
план контракта или марку в карточке.» Это соответствует правилу проекта «auto-fix только там, где
действие однозначно правильное» (memory `data-integrity-over-convenience`): постановка в свободный
слот своей марки однозначна, «сверх плана» — нет, поэтому о нём говорим вслух.

**C3. Привязка из карточки контракта — гейт на пикере.** Пикер слота по умолчанию показывает
**только двигатели марки этого слота**; переключатель «показать все марки» — на месте. Если через
него выбран двигатель чужой марки, открывается блокирующий диалог (`useConfirm.pickChoice`,
`ConfirmContext.tsx:134-145`) с тремя выходами:

1. «Поставить в свободный слот марки «X»» (показывается, только если такой слот есть);
2. «Создать слот под марку «X»» (сверх плана);
3. «Отмена» + ссылка «Открыть карточку двигателя» (если ошиблись там, а не в контракте).

Молча положить двигатель в слот чужой марки нельзя ни одним путём.

**C4. Побочная починка `sectionKey`.** `EnginePaymentsTab.tsx:223` при отсутствии слота создаёт
его с `sectionKey: props.sectionKey || fallbackToken || 'primary'`. Литерал `'primary'` **не
совпадёт ни с одним** слотом из карточки контракта: там токен первичной секции — это **номер
контракта** (`ContractDetailsPage.tsx:1499-1501`). Фолбэк на `'primary'` убираем.

> ⚠️ **Известная мина, в этот план не входит.** Токен первичной секции — редактируемый номер
> контракта. Правка номера осиротит все `slot.sectionKey` и все `engine.contract_section_number`.
> Чинится либо стабильным идентификатором секции, либо перепиской токенов при смене номера.
> Отдельной строкой в `PENDING_FOLLOWUPS` — трогать в этом плане слишком широко.

## Блок D — своя печатная форма на каждый тип наряда

### Как сейчас

Одна функция на все типы: `buildPrintModel(current, settings)` —
`WorkOrderDetailsPage.tsx:1590-1853`, объявлена **внутри компонента**, замыкается на 7 внешних
значений (`engines`, `employees`, `parts`, `workshops`, `warehouseLocations`,
`engineContractInfo`, `appliedHiddenFields`). Единственная развилка по типу — булев
`isAssembly` (1609), управляющий шестью точками. `Repair`/`Regular`/`Manufacturing` печатаются
**идентично**, с `isAssembly = false`. Юнит-тестов у печати нет.

Что владелец назвал лишним и почему это сегодня не убрать:

- **«Утверждаю»** — `WorkOrderDetailsPage.tsx:1773-1774`, секция добавляется **безусловно** (1845).
  Флага скрытия в `WorkOrderPrintSettings` нет. Список утверждающих зашит константой из двух
  директоров (`WORK_ORDER_APPROVERS`, `workOrder.ts:275-278`).
- **«Работу сдал» / «Работу принял (ОТК)» / «Работу принял»** и
  **«Наряд выдал» / «Согласовано (ОТК)» / «Принял в работу»** — это `defaultCaptions` блоков
  `completion` и `issue` (`workOrderSignatures.ts:95, 101`), одинаковых для всех типов.
  Удалить их в карточке нельзя: `setSignatureSlots` (1553-1560) при пустом списке выбрасывает
  запись блока, а `resolveWorkOrderSignatureSlots` (121-128) в её отсутствие подставляет
  `defaultCaptions` обратно. Нетронутый наряд **всегда** печатает 6 ролей.

### Как будет

**D1. Вынести печать из компонента** (это основной объём работ, а не вёрстка). Новый модуль
`electron-app/src/renderer/src/ui/utils/woPrint/`:

- `deps.ts` — тип `WoPrintDeps` со всеми семью зависимостями явными параметрами;
- `assembly.ts` — `buildAssemblyPrintModel` — **побайтово текущее поведение** для сборки;
- `simple.ts` — `buildSimplePrintModel` — новая форма;
- `index.ts` — `buildWorkOrderPrintModel(payload, settings, deps)` с развилкой по `workOrderKind`.

Оба потребителя (`printWorkOrderCard` 1855-1857 и `WorkOrderPrintDialog` 3565-3599) зовут ровно
одну функцию — менять `printPreview.ts`, диалог и IPC не придётся. После выноса печать
становится тестируемой; первым тестом закрепляем сборочную форму, чтобы разделение её не
задело.

**D2. Кто получает простую форму.** `Regular`, `Repair`, `Manufacturing` → `buildSimplePrintModel`.
`Assembly` → без изменений. (Изготовление по составу ближе к обычному наряду бригады, чем к
сборке двигателя, — поэтому в ту же группу.)

**D3. Состав простой формы** — по образу заполняемого наряда:

| Секция | Содержимое |
|---|---|
| `title` | Заголовок наряда + № наряда |
| `meta` | Дата · Приступить · Срок · Цех · № двигателя · Марка · Заказчик/контракт |
| `works` | № · № двигателя · № детали · Вид работ · Ед. · Кол-во · Цена · Сумма; футер «Итого» |
| `crew` | Сотрудник · КТУ · Начислено · **Подпись** (линия под роспись на каждого) |
| `signatures` | Специалист по нормированию · Специалист по кадрам · ОТК · Мастер цеха |

- Секции `director` (**«Утверждаю»**) в простой форме **нет**.
- «Подпись каждого члена бригады» — пятая колонка таблицы бригады. Отдельных слотов на бригаду
  не заводим: их число заранее неизвестно, а колонка растёт вместе с составом сама.
- «№ детали»: в модели строки серийного/чертёжного номера **нет**; берём `partArticle`
  (артикул) с фолбэком на `productNumber` («№ изделия»). Если Рамзии нужен именно чертёжный
  номер — это новое поле `WorkOrderWorkLine` + правка `normalizeWorkOrderLine`
  (`workOrder.ts:68`, иначе поле молча срежется), **вопрос владельцу**.
- «№ двигателя» в шапку: код для этого уже есть (`distinctTrimmed` / `headerEngineNumber`,
  1620-1630), сейчас включён только для сборки — включаем и здесь, когда двигатель во всех
  строках один.

**D4. Подписи по типу наряда.** `getWorkOrderSignatureBlocks(kind)` уже принимает `kind` —
ломать сигнатуру не надо, меняем только содержимое:

- `Assembly` — как сейчас (`issue` + `completion` с прежними `defaultCaptions`);
- остальные типы — новый блок `norming`: `['Специалист по нормированию', 'Специалист по кадрам',
  'ОТК', 'Мастер цеха']`, `dateLineLabel: 'Дата выполнения'`; блоки `issue`/`completion`
  **возвращаются с пустыми `defaultCaptions`** — то есть печатаются, только если оператор сам
  их заполнил. Так уже подписанные наряды не осиротеют, а нетронутые перестанут тащить
  «сдал/принял».
- Заодно чиним расхождение кода с собственным комментарием (1712-1716): блок без слотов
  сейчас всё равно печатается, потому что `signaturesHtml` формируется безусловно (1734-1750)
  и условие `...(signaturesHtml ? … : [])` (1850) всегда истинно.
- Автоподстановку сотрудника по должности **не делаем**: это подписи от руки. Готовые группы
  поиска (`findEmployeeByPositionGroups`, `workOrderSignatures.ts:188-197`) остаются для
  зарплатной ведомости.

**D5. Флаг «Утверждаю».** Добавляем `hideApprover?: boolean` в `WorkOrderPrintSettings` +
чекбокс в `WorkOrderPrintDialog`. Простая форма грифа не строит в принципе; флаг нужен, чтобы
владелец мог убрать гриф и со **сборочной** формы, не трогая код.

### Чего в этом блоке НЕ делаем

- `appliedHiddenFields` — эфемерный `useState` (`WorkOrderDetailsPage.tsx:418`), не сохраняется
  в payload и не восстанавливается при открытии карточки: скрытые шаблоном «Цена»/«Сумма»
  возвращаются после переоткрытия. Отдельный дефект → `PENDING_FOLLOWUPS`.
- `matrica:woPrintDefaults` живёт в `localStorage` (per-машина, не синкается) — для «формы
  Рамзии, одинаковой у всех» это не годится, но перенос в бэкенд-стор уже висит отдельным
  пунктом в `PENDING_FOLLOWUPS §Шаблоны/умолчания печати наряда`. Новая форма от него не зависит.

## Решения, принятые без владельца

Технические развилки решены здесь, чтобы не тормозить работу (правило проекта: на технические
open-questions решение принимает агент и фиксирует его в плане).

1. **Изготовление (`Manufacturing`) идёт в простую форму** вместе с обычным и ремонтным.
   По составу это наряд бригады на услуги, а не сборка двигателя по BOM; держать его на
   сборочном шаблоне не за что. Если окажется, что у него своя специфика — развилка уже
   будет в `index.ts`, добавить третий билдер дёшево.
2. **Двигатели без секции раскладываются автоматически** при открытии карточки контракта, тем
   же `planSlotForEngine`, — но только в режимах `free-slot` / `new-slot` (однозначно правильное
   действие). Режим `over-plan` автоматически не применяется: такие двигатели остаются в блоке
   «Двигатели без секции» и ждут кнопки, потому что «сверх плана» — это либо ошибка марки в
   карточке двигателя, либо недобитый план контракта, и молча решать за оператора нельзя.
3. **«№ детали» — артикул (`partArticle`) с фолбэком на «№ изделия» (`productNumber`)**, без
   нового поля. Чертёжный номер в модели строки наряда отсутствует вовсе; заводить поле ради
   догадки не будем — см. вопрос ниже.

## Открытый вопрос владельцу

**«№ детали» в наряде Рамзии** — устраивает артикул из справочника номенклатуры, или ей нужен
именно чертёжный номер детали? Во втором случае это новое опциональное поле `WorkOrderWorkLine`
+ правка `normalizeWorkOrderLine` (`shared/src/domain/workOrder.ts:68` — иначе поле молча
срежется при первом же сохранении) + колонка в редакторе строк наряда. Работы примерно на
полдня, делается отдельным PR и первую форму не блокирует.
