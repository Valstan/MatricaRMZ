# Импорт СИЗ из Excel (ЗУП/1С): поиск шапки не должен быть строже чтения

> **Основание:** промты КАРМАНА **#78** (текст владельца, 23.11) и **#79** (план из библиотеки).
> План из библиотеки — **задание владельца, а не готовое решение** (`AGENTS.md` §«Промты и планы
> проекта из КАРМАНА»): он сверен с нашим кодом 23.11.2026 и уточнён ниже. Каждое уточнение
> помечено — чем решено и почему.

**Задача владельца:** настоящая выгрузка ЗУП/1С распознаётся, импорт доходит до «Применить»;
если файл нераспознаваем — понятная ошибка (что нашли и какой колонки не хватает).

**Заводская линза:** склад СИЗ / выдача СИЗ (кладовщик) · затор: не касается (главный затор —
начало сборки) · поток: не ломает — выдача и остатки не меняются, правится только разбор файла.

## Что уже есть (факты с путями, проверено 23.11.2026)

1. **Импорт серверный.** `backend-api/src/routes/ppe.ts:765` — `POST /ppe/import/preview`,
   тело `{filename, contentBase64}`; применение — `applyPpeImportPreview`. UI:
   `electron-app/src/renderer/src/ui/pages/PpeImportPage.tsx` («Проверить файл» → «Применить»,
   preview живёт 30 минут — `PPE_IMPORT_PREVIEW_TTL_MS`, `ppeImportService.ts:58`).
2. **Разбор книги** — `backend-api/src/services/ppeImportService.ts`, `parsePpeImportWorkbook` (`:192`).
3. **⚠️ Главный дефект: поиск шапки строже, чем чтение.** Поиск — `findHeaderRow` (`:164-182`)
   требует **точных** нормализованных заголовков: `EMPLOYEE_REQUIRED = ['табельный номер','фио']`
   (`:47`), `ISSUE_REQUIRED = ['таб. №','дата']` (`:48`), `ISSUE_NOM_REQUIRED = ['номенклатура','артикул']`
   (`:49`). Чтение же идёт через **алиасы** `pick()` (`:184-190`): `PERSONNEL_ALIASES` (`:51`),
   `FIO_ALIASES` (`:52`), `NOM_NAME_ALIASES` (`:53`), `ARTICLE_ALIASES` (`:54`), количество
   (`:275`), даты приёма/увольнения (`:243-244`). **Алиасы применяются только при чтении, но не при
   поиске шапки** ⇒ файл, который прочитался бы, не опознаётся. Это и есть механизм ошибки.
4. **⚠️ Косвенное доказательство дефекта — UI и сервер ждали разного.** Клиент печатает подсказку
   «лист выдач — **Таб. №, Номенклатура/артикул**, Размер, Кол-во, Дата»
   (`PpeImportPage.tsx:61`), а сервер требовал **две отдельные** колонки «Номенклатура» + «Артикул»
   ⇒ обещание клиента и приёмка сервера разошлись. Владельцу обещали объединённую колонку и не дали.
5. **Объединённой колонки сервер не понимает и при чтении:** `pick(cols, NOM_NAME_ALIASES)` /
   `ARTICLE_ALIASES` не найдут «номенклатура/артикул» ⇒ строки выдач пришли бы с пустыми
   номенклатурой и артикулом.
6. **Шапка ищется только в первых 10 строках:** `maxRow = Math.min(ws.rowCount, 10)` (`:169`) ⇒
   выгрузка 1С с заголовком отчёта/периодом/фильтром выше шапки не опознаётся.
7. **Ошибка не сообщает, что нашли** (`:227-231`) — перечислены только ожидаемые колонки.
8. **Тесты разбора** — `backend-api/src/tests/ppeImport.test.ts`.

## Уточнения плана #79 (чем отличаемся от библиотеки)

1. **Объединённую колонку НЕ разбираем своим правилом — отдаём значение домену.**
   План предлагает разбирать ячейку на артикул и наименование («артикул — короткий код»). Это
   вредно: у СИЗ много названий с числом в конце («Костюм рабочий 46») ⇒ «короткий код» отрежет
   размер и приклеит его как артикул, а артикул в матчинге — первый ярус ⇒ можно сопоставить
   строку с **чужой** позицией. В домене уже есть канон: `match1cNomenclature`
   (`shared/src/domain/import1cStock.ts:75`) — ярусы «артикул → имя → имя+артикул», причём
   компакт-нормализация (`normalizeLookupCompact`, `lookupNormalize.ts:15`) снимает скобки,
   слэши и дефисы. Значит «Ботинки рабочие (BT-9)», «Ботинки рабочие BT-9» и «BT-9 Ботинки рабочие»
   совпадают с программной позицией «Ботинки рабочие / BT-9» **без своего разбора**.
   Решение: значение объединённой колонки идёт в `nomName` целиком; дополнительно — одна
   попытка «это чистый артикул» (см. п. 2).
2. **Одна попытка «ячейка = артикул».** Если объединённая ячейка содержит только код
   («BT-9»), домен по имени её не возьмёт (нет ни яруса «имя», ни «имя+артикул»). Поэтому матчинг
   строки выдачи идёт **общим помощником** в двух прочтениях: сначала как имя, затем как артикул.
   Помощник обязателен и в preview, и в apply — иначе правила снова разъедутся (тот же класс
   дефекта, что и «поиск строже чтения»).
3. **Окно поиска шапки — 25 строк** (план #79 п.7) — согласен: у выгрузок 1С сверху бывают
   «Выгрузка ЗУП», период, фильтр, объединённый заголовок.
4. **«Код» как артикул — только на листе выдач** (план #79, «Осторожности»): концепт «артикул»
   с алиасом «код» опрашивается только при поиске шапки выдач; на листе сотрудников его нет,
   поэтому «код сотрудника» артикулом не станет.
5. **Ошибка — по листам и по найденному** (план #79 п.8): «Листы книги: …; на листе «…» (стр. N)
   нашли: …; не нашли: Табельный номер (искали: табельный номер, таб. №, таб.номер, табельный №)».
   Ожидаемые колонки остаются в подсказке клиента (`PpeImportPage.tsx:266`) — второй раз в тексте
   ошибки они не нужны.
6. **Понятие «концепт колонки» — единственный источник** для поиска и чтения (план #79 п.1).
   Никаких вторых списков.

## Шаги (один PR — одна задача)

1. `ppeImportService.ts`: таблица **концептов колонок** (заголовок → алиасы). Поиск шапки и чтение
   колонок берут её и только её.
2. `findHeaderRow` → поиск по концептам, окно **25 строк**, отдельный детектор объединённой
   колонки «Номенклатура/артикул».
3. Чтение листа выдач: объединённая колонка → `nomName` (+ признак `nomCombined`).
4. Общий помощник матчинга строки выдачи (два прочтения объединённой ячейки) — в preview и apply.
5. Понятная ошибка: листы книги, нашли/не нашли с перечнем искавшихся заголовков.
6. Юниты в `backend-api/src/tests/ppeImport.test.ts`:
   - книга с алиасами («Таб. №», «Ф.И.О.», «Наименование», «Код», «Количество», «Дата приема») —
     опознаётся;
   - объединённая «Номенклатура/артикул» — лист выдач опознаётся, значение матчится с позицией
     программы; вариант «только артикул» — тоже;
   - шапка на 12-й строке — опознаётся;
   - две отдельные колонки «Номенклатура»/«Артикул» — работают как раньше (регрессия);
   - на заведомо чужом файле — ошибка называет, что нашли и чего не хватает.

## Осторожности

- **Даты** уже разбираются `parseImportDateCell` (`:89`) — не переписывать.
- **Табельный номер** — `personnelKey` (`:123`) снимает ведущие нули; не менять, иначе разъедутся
  с `importEmployeesCsv`.
- **Импорт пишет только по «Применить»**, preview — read-only, TTL 30 минут (`:58`). Это часть
  договора, не менять.
- **Валидацию сотрудников и применение не трогать** (`validatePpeImport`, снапшот,
  `applyPpeImportPreview`) — меняем только разбор шапки и текст ошибки.
- **Права на импорт** прежние: `requirePermission(PermissionCode.ErpDictionaryEdit)`.
- **Прод и реальные данные не трогать без слов владельца.**

## Что НЕ трогаем

- `ppeStockImportService.ts` и его тесты — другой импорт (остатки склада).
- `applyPpeImportPreview` / `validatePpeImport` — логика данных и сверки (кроме вызова общего
  помощника матчинга).
- Клиентский UI — текст ошибки сервера он выводит как есть.
- Другие импорты Excel в программе (персонал, ЗУП).
