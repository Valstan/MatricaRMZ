# План: программа застревает на старой версии — отложенное обновление глушит новое

**Задача владельца (21.11.2026):** «и у меня стоит 136 версия и не обновляется на следующие».

## Что нашли (живая машина парка, PC79)

Разбор шёл по данным самой машины, а не по коду:

- Установленный клиент — **3.136.0** (`MatricaRMZ.exe`, FileVersion 3.136.0).
- В `AppData\Roaming\@matricarmz\electron-app\matricarmz-updater.log`:
  ```
  [2026-11-20T19:46:03Z] pending-update saved version=3.137.0 … size=144377064
  [2026-11-20T19:46:04Z] update downloaded, waiting for operator: version=3.137.0
  [2026-11-20T20:36:38Z] pending-update saved version=3.137.0 …
  [2026-11-20T20:41:04Z] pending-update saved version=3.137.0 …
  [2026-11-20T21:01:05Z] pending-update saved version=3.137.0 …
  ```
  Обновление **3.137.0 скачано** (инсталлятор 144 377 064 Б лежит в
  `MatricaRMZ-Updates\matrica_rmz_update.exe`, `pending-update.json` на месте) и сутки
  ждёт нажатия «Перезапуск».
- Про **3.138.0** клиент не знает вообще: сервер отдаёт 3.138.0 с 00:37, а в логе
  апдейтера после 00:01 (21:01Z) — ни строки. Синхронизация при этом чистая
  (`sync.run.done ok=1`), машина работает.

## Причина (в коде)

`electron-app/src/main/services/updateService.ts`, фоновый тик `tick()`:

```ts
if (pending?.version && compareSemver(pending.version, current) > 0) {
  setUpdateState({ state: 'downloaded', … });
  return;                       // ← сервер про новую версию больше НЕ спрашивается
}
```

Пока на диске лежит отложенное обновление, клиент **перестаёт искать более новую
версию**. Отложенное 3.137.0 закрывает обзор на 3.138.0, а снимается оно только
нажатием «Перезапуск» — то есть по сути нажатием, которого не случилось.

Вторая половина проблемы — **незаметность**. Готовность обновления сообщалась
одноразовой всплывающей плашкой («Вышло обновление … нажмите ‹Перезапуск›»), которая
гаснет за 20 секунд; кнопка «Перезапуск» в шапке выглядела ровно как обычная. Оператор,
не смотревший на экран в тот момент, не узнавал о готовом обновлении вообще.

По данным парка то же самое: `client_settings.last_version` — максимум 3.136.0 (7 машин),
до 3.137.0 не дошёл никто.

## Решение

1. **Правило — в домен** (`shared/src/domain/updateFlow.ts`, `chooseUpdateFlow`):
   отложенное обновление **не имеет права глушить более новое**.
   - `offer-pending` — отложенное новее установленного и ничем не заменено → предлагаем;
   - `discard-pending` — отложенное устарело (сервер знает более новую) или уже не нужно → выкидываем;
   - `download-newer` — отложенного нет, сервер отдаёт более новое → качаем;
   - `none` — обновлений нет.
   Сравнение версий — эпохо-зависимое (`compareAppVersion`): клиент со старой
   нумерацией не должен считать 3.138.0 откатом назад.
2. **Тик спрашивает сервер ДО решения о судьбе отложенного** (`updateService.ts`):
   сервер отдаёт `latest-meta` один раз, его же переиспользует каскад скачивания.
   Серверной правки не нужно: глушение было локальным.
3. **Готовность обновления видна постоянно**: кнопка «Перезапуск» в шапке получает
   точку и отдельный вид (`data-update-ready`, `v3-restart-btn--ready`), подсказка
   называет версию.
4. **Напоминание повторяется**, пока обновление не поставили (раз в 30 минут) — раньше
   плашка была одна на версию.

Правило владельца «перезагружать программу только тогда, когда это действительно
требуется» соблюдено: **ничего не перезагружается само**. Меняется только заметность
и то, что клиент не перестаёт следить за новыми версиями.

## Что не трогаем

- Само правило «перезагрузжать только по требованию» — решение владельца от 08.11.2026.
- Механику применения отложенного при старте (`applyPendingUpdateIfAny`) — она работает:
  при перезапуске программы отложенное уходит само, если сервер не знает более нового.
- Схема версий, дельта-скачивание, LAN-раздача, Яндекс-зеркало — не в этой правке.
