## Два трека

Работа идёт двумя параллельными треками. Трек A (v4) не ждёт трека B: Ф0/Ф1 строятся рядом, мост Ф2 подключается к базе только когда трек B дойдёт до этапа 6.

```
Трек A (Matrica4):  Ф0 контракт ──► Ф1 отчёты ──────────► Ф2 мост ──► Ф3+ переезд доменов
Трек B (v3, здесь): этап 0 ──► 1 марки ──► 2 договоры ──► 3 auth ──► 4 двигатели ──► 5 хвосты ──► 6 EAV из синка
                                                                                        (Ф2 требует ≥ этапа 6)
```

## Трек A — Matrica4 (новый репозиторий)

### Ф0 — контракт (kickoff-сессия)

Скелет монорепы по эскизу концепта:

- `core/contract/` — **единственный файл-API ядра** для модулей (аналог `vscode.d.ts`) + типы манифеста. Правила: стабильное не ломается никогда, только аддитивные расширения; эксперименты в `proposed_*`-неймспейсе.
- `core/kernel/` — загрузчик модулей по манифестам, **safe mode** (модуль упал при старте → следующий запуск поднимает ядро без виновника), шина событий in-process (интерфейс допускает замену на брокер без правки модулей), health-статус модулей.
- Манифест модуля: имя, версия, зависимости, min-версия ядра (**без** верхней границы — грабли until-build JetBrains), декларативные вклады (меню/страницы/отчёты/таблицы/задачи). Манифест декларирует и таблицы модуля — задел под расширяемый синк.
- **Границы держит CI, не дисциплина:** линтер границ (модуль импортирует только contract, не внутренности ядра/соседей) + мини-verifier (манифест валиден, вклады существуют).
- Модуль-образец `modules/sample/` — прогон контракта: манифест, вклад, событие, health.
- Никакой горячей выгрузки: обновление модуля = рестарт.

### Предохранители смешения поколений (владелец 2026-08-17, все три обязательны)

1. **Отсутствие двери:** в Matrica4 до стадии клиентских релизов физически нет релизных workflow/скриптов клиентов.
2. **Гейт в AGENTS.md обоих репо** (вписать на Ф0, до первой строки кода): агент v4 на просьбу про релиз/деплой клиентов отвечает «это делается из MatricaRMZ»; агент v3 симметрично — «стройка ядра v4 — в Matrica4».
3. **Диспетчер обновлений — единственные ворота к операторам** (уже так: парк получает только то, чему диспетчер выписал план).

### Ф1 — пилот: модуль отчётов (решение владельца 2026-08-18)

Движок v3 уже распилен на слои (format/context/options/presets/dispatch/render, `electron-app/src/main/services/reports/`), 36 пресетов по 6 доменам. Пилот переносит движок в `modules/reports/` v4 и лечит боль №4 («отчёты заперты в Electron main»): исполнение становится доступно вебу, планшету и ИИванычу. Открытый вопрос концепта №4 (где исполняются отчёты: сервер / локальная реплика / оба с одним кодом) решается здесь.

### Главные факты разведки

- В репо **два разных «EAV→erp»**: (1) мёртвый прототип-слой `/erp/*` весны 2026 (`erp_part_templates`, `erp_tool_*`, `erp_reg_contract_settlement`, `erp_reg_employee_access`, generic `routes/erp.ts` — пуст по данным, частично протух: `postErpDocument` оперирует осью `part_card_id`, удалённой миграцией 0060) — кандидат на **снос**, не на дожим; (2) реальный конвейер `EAV → directory_* → erp_nomenclature` + складской контур — **добит** (последние дыры закрыты 2026-08-13).
- **Чисто EAV осталось ядро бизнес-данных:** договоры (включая платежи одним JSON-атрибутом `contract_payments`), карточки двигателей (фазы, резервы, рекламации, гейты номеров), сотрудники со **всей аутентификацией** (login/password_hash/system_role/section_access как attribute_values), контрагенты, экземпляры инструмента, warehouse-справочники (`nomenclature_group`, `unit`, `stock_write_off_reason`), category/ui_screen. **Долг растёт:** фичи 2026-08 (резервы, рекламации, гейты номеров #612/#613) строятся поверх EAV.
- **Гибрид (правда в EAV, строгое — зеркало):** марки двигателей (`directory_engine_brands` — id-тождественное lazy-зеркало; FK из строгих таблиц идут прямо в EAV: `erp_engine_assembly_bom_brand_links.engine_brand_id → entities.id`, `erp_nomenclature.group_id/unit_id/default_brand_id → entities.id`), услуги (карточка EAV + `directory_services`; цены строгие).
- **`MATRICA_ERP_STRICT_MODE` декоративен:** единственная точка — `adminMasterdata.ts:36`, гейтит 8 админ-роутов; sync (`applyPushBatch`) и сервисные EAV-писатели не гейтятся. Вместо глобального флага — по-доменные гейты записи по мере cutover.
- **Дефект «читаем пустоту»:** склад (`warehouseService.ts:899-902`), `getContractSections` и AI `getContracts` читают `erp_counterparties`/`erp_contracts`/`erp_employee_cards`, которые на проде пусты — эти пути либо мертвы, либо молча отдают пустые списки. Разобрать в этапе 0.
- **Sync-хребет — EAV:** 4 EAV-таблицы синкаются двунаправленно с ID-remap; erp_* — pull-only. Пока марки/группы/единицы в EAV, `entities` физически нельзя вывести из синка (dependsOn + FK). Попутный дрейф: `routes/ledger.ts` `PG_SYNC_TABLES` не содержит `ErpEngineInstances`, а `pullChangesSince.ts:77-79` содержит.
- **`erpLegacyCleanup.ts` опасен:** его запуск сегодня снёс бы живые EAV-договоры/сотрудников/инструмент. `migrateEavToErp.ts` не годен как основа переезда (randomUUID → чужие id, attrs_json-свалка, без auth-полей).

### Ответ на вопрос D-031 п.3 (auth: дожимать в v3 или v4-auth отдельно)

**Дожимать в v3, включая auth.** Auth — FK-ядро `entities` (~15 таблиц ссылаются user_id → entities.id): «v4 подключается к базе без EAV» недостижимо, пока сотрудники живут в entities, а пережить переход умеют только v3-клиенты (офлайн section-gate, штатная смена набора синк-таблиц, рычаг 426). Отдельный v4-auth = два авторизационных контура на одной базе на весь переход + двойная миграция. Цена в v3 умеренная (L, не XL): EAV-доступ изолирован в одном сервисе, password_hash не синкается, refresh-токены/права уже не-EAV, id сохраняемы. Дилемма снимается тем, что **схема** строгой auth-таблицы проектируется как v4-канон.

## Сверка состояния трека B — 2026-08-27

Полная разведка кода (workflow `track-b-state-survey`, 5 читателей, ключевые факты перепроверены построчно вручную). Итог: **B0 ✅, B1 ✅ (серверная половина), B2 ⏳ (~40%), B3–B6 не начаты**; после релиза v3.3.0 (19.08) коммитов трека B нет — месяц ушёл на другие нитки.

### Ключевая развилка, найденная сверкой: узел офлайн-записи

Синк-контракт — закрытый набор 20 таблиц; **все 7 `erp_*` в нём pull-only**, push-обвязка (`applyPushBatch`) существует для 4 EAV + 8 app-таблиц (`operations`, `chat_*`, `notes`, …) — прецедент push для строгих таблиц есть, но ни одной `erp_*` среди них. Все домены, которые операторы правят офлайн (договоры, платежи, двигатели, инструмент, рекламация), пишут через EAV-синк. Поэтому «cutover CRUD» любого домена — это не один флип на сервере (он потребовал бы обратного зеркалирования strict→EAV с риском триггерных петель), а **единый трёхшаговый механизм на домен**:

1. **Pull строгих таблиц клиентам** (реплика в ОБЕИХ клиентских цепочках миграций — drizzle и clientSchemaMigrations, ловушка холодного старта) + флип клиентских читателей;
2. **Флип записи**: серверный API-вызов (для редких/админских операций) или push-хендлер по образцу app-таблиц (для массовых офлайн-правок);
3. Закрытие EAV-домена (гейт записи), старые клиенты — рычаг 426.

Механизм строится **один раз** и закрывает разом: B2-cutover + платежи, B4, B5(a/b), перенос рекламации. До него эти пункты не трогать.

## B3: схема `users` — v4-канон (синтез 2026-08-28, направлено brain)

Спроектирована панелью из трёх независимых проектов (minimal / full-surface / v4-forward) + два судьи по критериям brain; полные материалы — workflow `users-schema-design`. Оба судьи отвергли full-surface (person-строки с nullable login растворяют инварианты; HR-зеркала в каноне = второй источник правды). Синтез = модель аккаунтов из minimal + структурные ходы из v4-forward + обязательные правки судей. Письмо-канон: [`mailbox/to-brain/2026-08-28-users-schema-canon-b3.md`](../../mailbox/to-brain/2026-08-28-users-schema-canon-b3.md).

### Решения синтеза

1. **`users` = таблица АККАУНТОВ** (строка ⟺ логин; `login NOT NULL`, CHECK нормализации, частичный UNIQUE среди живых). Сотрудник без доступа — HR-карточка (EAV до 3b), не строка users. `id = entities.id` (LOCKED, FK-стена не двигается); FK на `entities` сознательно нет (приём 0083/0084 — канон не зависит от EAV).
2. **Секрет отделён структурно:** `user_credentials` (user_id PK→users, password_hash NOT NULL CHECK непустой, created/updated_at) — server-only, отсутствует в sync-контракте. «password_hash не синкается» — свойство конструкции, не кода-фильтра (`pullReadFilter.ts` остаётся страховкой EAV-хвоста до B6).
3. **Доступы по разделам — junction, не JSON:** `user_section_access` (id uuid PK — синк ключует uuid row_id; user_id→users; section_id→`access_sections`; level CHECK viewer/editor; UNIQUE(user_id, section_id); soft-delete — снятие раздела доезжает pull-синком) + каталог-якорь `access_sections` (id text PK; мета — titleRu/menuTabs — остаётся в shared-коде, новый раздел = INSERT, не миграция). Семантика «нет живых строк = не засеян → fail-open» сохранена (инцидент 2026-07-10, симметрия клиент↔сервер).
4. **`system_role`:** NOT NULL **без DEFAULT** (оба пути создания называют роль явно, ошибка — громкая), CHECK по закрытому каталогу **12 ролей** (`SYSTEM_ROLE_CATALOG`; 2026-08-28, до R1, добавлен `storekeeper` «Кладовщик» — складские документы + номенклатура + заявки; без него у кладовщиков не было роли и admins раздавали легаси-`user`, письмо-амендмент brain'у 2026-08-28). `'merged'` (`adminUsers.ts:404`) в каталог не входит: бэкфилл нормализует в `'employee'` (= сегодняшняя семантика чтения `normalizeRole`), на cutover merge-flow переходит на soft-delete строки users. `login='valstan' → 'superadmin'` — явно в `rebuild_user` (зеркало `normalizeRole:256`).
5. **`access_enabled boolean NOT NULL DEFAULT false`** — fail-closed в самой схеме.
6. **Жизненный цикл:** `deleted_at` = «аккаунт отозван», логин освобождается (частичный UNIQUE). `delete_requested_at/by` — 2 колонки в users (v4-free), `delete_requested_by` — настоящий FK→users; CHECK асимметричный (инициатор без даты невозможен, дата без инициатора терпима — легаси-бэкфилл); `delete_requested_by_username` **умирает** (денормализованная копия ради EAV-join'а).
7. **`user_settings`** (server-only, НЕ синкается, НЕ канон): дом изгнанных serverOnly-EAV — `ui_settings`/`ui_profile` (jsonb + CHECK jsonb_typeof='object'), `logging_enabled/logging_mode`. В канонную users их класть нельзя: каждый PATCH профиля дёргал бы pull строки users на весь парк.
8. **`chat_display_name`/`telegram_login`/`max_login` остаются EAV до 3b** — профильные атрибуты доставки, не auth (позиция minimal, судья-1 требовал явной классификации — вот она).
9. **Sync-транспорт** (`sync_status text NOT NULL DEFAULT 'synced'`, `last_server_seq bigint` + индекс) — на обеих синкаемых таблицах (`users`, `user_section_access`), помечен «не канон, умирает с протоколом v3» (оба судьи: без них `pullChangesSince` физически не работает).
10. **Триггерное зеркало на переход:** `rebuild_user` / `rebuild_user_sections` + триггеры на `entities`/`attribute_values` (образец 0084), бэкфилл включая soft-deleted (0083: «каждой ссылке нужна строка»). **Триггеры сносятся атомарно с флипом записи** (R4), не «на B6» — вооружённый триггер поверх прямых записей затирает канон из замороженного EAV (оба судьи).

  Разрыв `lastServerSeq=null`, который план велел «проверить и не наступить», оказался **структурным**, а не угловым: `updateSeqAndCollect` в `applyPushBatch` — единственное место, где строке проставляется seq, а `users`/`user_section_access` пишут PL/pgSQL-триггеры, минуя путь записи приложения. Инкрементальный pull страницует по seq → таблица без seq не приезжает никогда. Холодный снапшот при промахе PG-карты падает в фолбэк на in-memory ledger-state, пустой для триггерных таблиц → клиент получил бы ноль строк, а офлайн-гейт закрыл бы доступ всем. Плюс `applyPushBatch` молча игнорирует таблицу без обработчика, хотя ledger-seq выдаётся ДО его вызова — ledger и PG разошлись бы беззвучно.

  **Развилка (решение владельца):**
  1. **Сначала R4, потом R3.** Cutover переводит запись на приложение, триггеры сносятся — seq начинает проставляться сам. Но R4 в чистом виде ломает то, что ещё читает EAV (`listEmployeesAuth`, клиентский офлайн-гейт), то есть зависимость круговая.
  2. **Шаг публикации.** Триггер остаётся строителем содержимого строки, а приложение сразу после EAV-записи публикует затронутую строку `users` через `writeSyncChanges` — так она получает seq. Разрывает круг без cutover'а, но добавляет обязанность «не забыть опубликовать» каждому писателю.
  3. **Дуальная запись** на переход — то, чего план избегал триггерами.

  Отдельно: клиентских цепочек миграций **три**, а не две — план не учитывал `android-app/src/db/migrate.ts`.
- **R4 (cutover):** запись auth-кодов в EAV закрывается гейтом, триггеры сносятся в том же релизе; merge-flow → soft-delete; парк-аудит версий → рычаг 426 при необходимости.
