## 2. Цифры прода (13.09, read-only)

- Номенклатур в BOM — 952, из них **935 без артикула** (`sku` пуст). В справочнике «Прокладка» заведена **60 раз** под разными id, «Кольцо уплотнительное» — 38, «Кольцо» — 28, «Пружина» — 17.

## 3. Диагноз: «слот» — не поле, а три сложенных механизма

1. **Глобальное дерево типов** задаёт, какой тип под каким может стоять. `carter` в дереве **отсутствует вовсе** — картеру в структуре места нет, хотя тип есть в перечислении.
2. **Ключ узла скелета выводится из типа** (`buildEngineBomSkeletonBlockLines`, `warehouse.ts:1050-1107`): в блоке варианта не более одного узла каждого типа. Два картера или верхний/нижний с разными детьми схлопываются в один ключ.
3. **Тип строки — не выбор оператора, а свойство карточки номенклатуры**: при сохранении сервер переписывает `component_type` по карточке (`warehouseBomService.ts:503-576`), а карточка BOM запрещает связь «родитель → ребёнок», которой нет в схеме (`EngineAssemblyBomDetailsPage.tsx:301-304`).

Сложение: строка типа «поршень» цепляется под что угодно, куда схема пускает поршень; тип берётся не из позиции, а из номенклатуры; позиции «картер» в дереве нет. Отсюда «в картер попадает поршень». При 76 % «Прочее» дерево держит форму, но не содержание: **тип — это класс детали, а не слот спецификации.** Вывод для макета: дерево типов — в справочную роль (подписи разделов, сортировка, легенда печати), не в структурную.

## 4. Что ещё вскрыл аудит (только фиксация; чинить — отдельными PR по OK владельца)

- **«Основной BOM марки» — два конфликтующих механизма.** Флаг связки `is_default_for_brand` (никем не выставлен) и заголовочный `is_default` (у всех `true`, ставится сервером). Прогноз при нескольких BOM марки берёт «самый свежий по `updated_at`» и пишет предупреждение (`warehouseForecastService.ts:585-607`); планирование сборочного наряда при двух BOM отдаёт `bom_conflict` — оператор выбирает руками. **Марка В-84 сейчас именно в этом состоянии** из-за пустого дубля.
- **Дедуп деталей** сверяет выжившую строку по `(bom_id, номенклатура)`, без `variant_group` и `component_type` (`directoryPartsDedupeService.ts:616-647`), а уникальный индекс — с ними. Слияние может снести законную строку варианта или оставить дубль.
- **Печать без общего кода:** «Печать всех BOM» — `buildAllBomsPrintHtml` локально в `EngineAssemblyBomPage.tsx:62`, N последовательных IPC-вызовов; печать одного BOM — отдельный код в карточке. Функции «скопировать BOM» нет.
- **Отчёт «Комплектование двигателя»** онлайн группирует по `positionKey ?? variantGroup`, офлайн (по реплике) — только по `variantGroup` с `isDefaultOption=false` (`reports/presets/engines.ts:970,1036`). Пока `position_key` пуст, расхождение не видно.
- `variant_group` и `position_key` читаются потребителями вразнобой: дефектовка — только `variantGroup`, наряд — `positionKey`, отчёт — `positionKey ?? variantGroup`.

## 6. Предложения — по каждому пожеланию

### 6.1. Упрощённая карточка (макет)

Принцип: **одна таблица, тип — заголовок раздела, а не поле строки; варианты — вкладки; дерево и схема — под «Расширенно».**

```
┌ BOM В-84 · марки: В-84, В-84М, … (9) · [Привязать марки] · [Печать ▾] ─────────────────┐
│ [Базовый комплект] [Вариант 1] [Вариант 2] [+ вариант]                                 │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│ ГИЛЬЗА ────────────────────────────────────────────────────────────────── 2 позиции      │
│  Гильза 303-07-22 150,11-150,18                      12 шт   норма 40 %   [примеч.]      │
│  Гильза 303-07-22 150,19-150,26                      —  шт   запасной вариант позиции ↑  │
│ ПОРШЕНЬ ───────────────────────────────────────────────────────────────── 1 позиция      │
│  Поршень К 3305-05-24-04 149,56-149,60               12 шт   норма 60 %                  │
│ ПРОЧЕЕ ───────────────────────────────────────────────────────────────── 214 позиций     │
│  Прокладка                                            6 шт                               │
│  …                                                                                       │
│ [+ строка]                                           поиск по названию/артикулу ______   │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│ ▸ Расширенно: дерево связей (родитель строки), схема типов, профиль исполнения           │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

- Раздел = `component_type` из карточки номенклатуры; **менять тип — в карточке детали**, в BOM тип не редактируется (это уже так на сервере, UI лишь перестаёт делать вид, что иначе).
- Баннер «не хватает типа X по схеме» — снять как обязательный (валидации на сервере уже нет с v1.21.3).
- `lineKey`/`parentLineKey` — **не удалять** (прогноз выбрасывает строки с битым родителем), но убрать с первого экрана.
- Взаимозаменяемый вариант позиции — вторая строка под основной с пометкой «запасной», без отдельных «карточек позиций». Это и есть `position_key`, только без UI-церемонии.
- Что не меняется: модель, upsert, materialHash. Этап — чисто UI.

### 6.2. Шаблон на группу марок

- **Вариант A (рекомендую):** модель не трогать. Один BOM уже висит на N марках (В-84 — на 9). Добавить в карточку BOM действие «Привязать ко всем маркам группы …» (выбор группы → в `engineBrandIds` добавляются её марки) и обратную подсказку в карточке группы: «BOM этих марок: …». Стоимость — день, потребители не задеты.
- **Вариант B:** ссылка BOM→группа с резолвом «марка → её группа → BOM». Трогает девять точек фильтра по `engine_brand_id` (прогноз ×2, планирование, отчёт, реплика, HTTP-клиент, опции отчётов) и инвариант «один основной BOM на марку». Не сейчас; вернуться, если после A владелец увидит, что связки расходятся.
- Трейд-офф A: при добавлении марки в группу BOM за ней **не** пойдёт сам — нужно повторить действие. Приемлемо при 23 марках.

### 6.3. Печать

- **«На один лист»:** отдельная компактная форма — свёрнуто по позициям (запасные варианты не печатаются), без дерева и легенды, альбомная, при >60 строк — две колонки, кегль 8–9. Для В-84 (558 строк) один лист физически невозможен — печатать «сколько влезет + продолжение», честно показать это в предпросмотре.
- **«Несколько для сверки»:** мультивыбор в списке BOM → одна печать. Уже есть `buildAllBomsPrintHtml` — вынести в общий модуль вместе с одиночной печатью (сейчас два разных кода), добавить серверную точку `GET /warehouse/assembly-bom/print?ids=` вместо N+1 IPC. Раскладка сверки — колонки по BOM, строки по номенклатуре, пустая ячейка = «нет в этой спецификации».

### 6.4. Обобщённая позиция («масляный насос один на все»)

Что уже есть и почему не подходит как есть:

| Механизм | Что даёт | Почему мало |
|---|---|---|
| `position_key` в BOM | Одна позиция, варианты, один основной, подстановка по остатку в прогнозе | Область — один BOM; в справочнике деталь остаётся размноженной |
| `group_id` номенклатуры | Свёрнутые группы со счётчиками в `NomenclaturePage` | Папка каталога (одна «Детали» на всё), не идентичность |
| `component_type` | Группировка в пикере (`buildGroupedNomenclatureOptions`) | 7 классов — не уровень «масляный насос» |
| `sourceGroupId` связи деталь↔марка | «Одна деталь применима ко многим маркам» | Применимость, не идентичность: три артикульных насоса не схлопнет |
| Безартикульная строка с пустым `code` | Уже легальна и уникальность её не запрещает (`warehouseService.ts:822-826`) | Родителя из неё никто не делает: импорт **поглощает** её первым артикулом (`importBasePartsList.ts:218-242`) |

**Рекомендация:** аддитивная колонка `erp_nomenclature.parent_nomenclature_id` (nullable, FK на себя, один уровень).
- Родитель — безартикульная строка («Масляный насос»), варианты — строки с артикулом и `parent_nomenclature_id`.
- BOM ссылается **на родителя**; прогноз раскрывает родителя в варианты тем же `collapsePositionsToDefaultOption` (основной = по остатку). Наряд и выдача работают по конкретному варианту, как сейчас.
- Переключатель «свёрнуто / развёрнуто» в списках номенклатуры и остатков — по образцу свёрнутых групп `NomenclaturePage.tsx:761-816`.
- Обязательные следствия, без них фича вредна: **свод остатков по родителю** (`erp_reg_stock_balance` ключ — номенклатура×локация, агрегата нет); правило для `part_id` листа деталей (родитель или вариант); правка импорта, чтобы безартикульная строка оставалась родителем; сверка с решением brain 12.06 «идентичность детали = (имя, артикул)» — родитель это не нарушает, он добавляет уровень над парой.
- Заведение родителей: 60 «Прокладок» и 38 «Колец уплотнительных» — это разные детали с одним именем, **их нельзя объединять по имени скриптом**; родителей заводит оператор, скрипт лишь предлагает кандидатов (одинаковое имя + разный артикул).
