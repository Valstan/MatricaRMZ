# План: импорт остатков склада из 1С

**Status:** MVP ГОТОВ (2026-07-27, этапы 0–4 ✅) — ждёт приёмки владельцем. Остался этап 5 (автозабор из 1С, исследование).

## ⚠️ Ревизия семантики после первого боевого импорта (2026-07-28)

Первый боевой импорт (607 строк) вскрыл две проблемы; обе закрыты:

1. **Матчинг был мёртв** (0/607): диалог ждал поле `article`, которого API не отдаёт (артикул — в `code`/`sku`); имена структурно разные (в программе имя обобщённое + артикул отдельно, в 1С артикул внутри имени). → `match1cNomenclature` (shared): ярусы артикул → имя → склейка «имя+артикул»/«артикул+имя».
2. **«Дельта против прошлого импорта» дважды списывала расход нарядов** (наряд 100→90, потом файл 1С тоже 90 → −10 → 80). → семантика заменена на **ревизию против текущего остатка программы** (`revise1cAgainstBalances`): файл — абсолютная истина для позиций, известных слою 1С; чисто программные остатки (нет ни в файле, ни в прошлом снапшоте — напр. детали от разборки) не затрагиваются; пропавшие из отчёта обнуляются по текущему остатку. Запаздывание файла на 1–2 дня даёт ограниченную ошибку, самокорректируемую следующим импортом (прошлый `diff1cSnapshot` копил её навсегда).

Плюс закрыт хвост «заведение ненайденных»: чекбокс (default on) заводит новые позиции по правилу владельца — **имя без артикула, артикул отдельным полем** (`canonical1cNomenclature` срезает артикул из имени, дедуп новых — по артикулу), ед.изм. маппится на справочник по названию. Внутренний номер детали в импорте не участвует (в 1С не фиксируется, набивается при дефектовке).

## ✅ Реализация (2026-07-27)

- **Домен** (`shared/src/domain/import1cStock.ts` + тесты): парсер TSV-отчёта (группы-склады, числа «30 165,000», хвостовая запятая), `diff1cSnapshot` — ревизия слоя 1С (дельты против прошлого импорта, пропавшие обнуляются, дробные округляются до целых — складской учёт целочисленный).
- **UI** — кнопка «📥 Импорт из 1С» на странице Склад → Документы (`Stock1cImportDialog.tsx`): выбор файла → выбор блока-склада из файла + склада программы (дефолт — «Основной») → превью (сопоставлено/не найдено/дельты/прошлый импорт) → «Провести импорт».
- **Проводка** — документ «Инвентаризация» (`stock_inventory`) со строками `adjustmentQty` (существующая механика inventory_surplus/shortage); в header-payload — метка `source: 1c_stock_import` + полный снапшот (`importSnapshot`) для следующего диффа. Живой учёт программы не затрагивается.
- **Матчинг** — артикул → имя, оба compact-нормализованные (дефисы/пробелы не важны); неоднозначные и ненайденные строки не проводятся, показываются в превью.
- **Живой e2e-смоук** (`.verifier-electron/_1c-import-smoke.mjs`, реальный файл через `DOM.setFileInputFiles`): первый импорт → повторный (дельта 0, кнопка выключена) → импорт другого блока (пропавшая позиция **обнулилась**, новые легли плюсом), документ posted с меткой и снапшотом.
- Дев-грабля: dev-БД отставала от миграций (`erp_stock_reservations` отсутствовала) — вылечено `db:migrate` на dev.

**Хвосты:** ненайденную номенклатуру можно будет заводить/привязывать прямо из превью (сейчас — пропуск); `.xlsx`-парсер вторым форматом; блоки цехов файла можно маппить на цеховые склады программы (сейчас оператор выбирает пару файл-блок → склад вручную).
**Заказ владельца:** 2026-07-27.

## ✅ Решение по формату (2026-07-27, этап 0 закрыт)

- **Основной формат — `.txt`** (в 1С: Сохранить как → Текстовый файл): TSV, UTF-8 BOM, CRLF. Отчёт «Остатки и доступность товаров» (УТ-семейство).
- Структура образца: 2 строки заголовка отчёта + параметры/отбор + 2 строки шапки таблицы; далее **группы-склады** (строка без ведущего таба: «Основной склад», «склад стройматериалов», «Склад цех №3»), под ними строки данных с ведущим табом: `Артикул \t Номенклатура,Характеристика \t Ед.изм. \t В наличии \t Отгружается \t В резерве \t Доступно \t Доступно(Всего) \t К обеспечению \t Дефицит \t Излишек`; терминатор — строка «Итого». 732 строки данных в образце.
- Числа: запятая — десятичный разделитель, пробел — разряды («30 165,000»). Артикул часто пуст. Название заканчивается запятой (пустая характеристика).
- **`.mxl` отклонён** — бинарный MOXCEL, вне 1С надёжно не парсится.
- `.xlsx` — второй парсер, добавить позже (тот же нормализатор).
- Бонус: в файле все склады — UI импорта может маппить группы файла на склады программы (дефолт — «Основной склад» → общезаводской).

## Context

Экспорты из МатрицыРМЗ уже есть; импортов из 1С ещё не было. Первый импорт — **отчёт 1С об остатках на складе**, планируется гонять **ежедневно**.

## Требования владельца

1. Проанализировать два присланных формата, выбрать самый надёжный для машинного импорта — но **в идеале научить программу есть любой формат выгрузки 1С** (владельцу без разницы, чем приносить).
2. Импорт — в клиенте (Электрон), модуль «Импорт из 1С».
3. **Выбор склада** при импорте; по умолчанию — **основной/общезаводской склад** (не привязанный к цеху).
4. Семантика — **ревизия**: после импорта остатки «как в файле».
5. **НО: не трогать номенклатуру/движения, внесённые другими путями** (наряды, ремонт → склад). Импорт не должен «затирать» живой учёт программы.
6. Проблема нулей: отчёт 1С выгружает **только позиции с ненулевым остатком** — как узнают «ноль» позиции, бывшие в прошлом импорте и пропавшие из нового?
7. Идея на будущее: утилита/плагин, который сам подключается к 1С (логин/пароль, read-only) и забирает остатки автоматически.

## Ключевое проектное решение (предлагается)

**Слой «остатки 1С» с признаком происхождения.** Каждый импорт помечает создаваемые строки/движения `source = '1c-import'` (+ id сессии импорта, дата, склад). Тогда:

- **Ревизия внутри слоя:** новый импорт — это полный снапшот слоя 1С по выбранному складу. Позиция была в прошлом импорте, а в новом отсутствует → **обнуляется автоматически** (в пределах слоя 1С). Это прямой ответ на вопрос п.6 — «другой отчёт 1С» не нужен, достаточно правила «отсутствие в снапшоте = ноль».
- **Живой учёт не трогаем:** остатки, рождённые нарядами/документами программы, лежат вне слоя 1С и импортом не корректируются. На складе показываем сумму слоёв (и при необходимости разрез «из 1С / из программы»).
- Технически: отдельный тип складского документа «Импорт остатков 1С (ревизия)» — сторнирует прошлый снапшот слоя и проводит новый. Прозрачно в истории, откатываемо.

## Формат файла

До получения образцов — заготовка парсеров под типовые выгрузки 1С:
- `.xlsx` / `.xls` (табличный отчёт с шапкой, группировками, итогами) — вероятный основной;
- `.mxl` (табличный документ 1С) — если пришлют, конвертация неудобна, попросим сохранить как xlsx;
- `.txt/.csv` (разделители, cp1251!) — простой запасной.

**Решение о «рекомендованном» формате — после анализа образцов.** Цель-максимум: автоопределение формата по содержимому, единый нормализатор → `[{ name, article?, unit, qty }]`.

Матчинг номенклатуры: по артикулу, затем по нормализованному названию (учесть compact-нормализацию дефисов/пробелов, как в PR #363); нераспознанные строки — в отчёт-превью импорта, оператор решает (создать новую номенклатуру / привязать вручную / пропустить).

## Этапы

### Этап 0 — получить образцы (блокер)
- Владелец передаёт оба файла; анализ структуры, выбор основного формата, фикс правил парсинга в этом плане.

### Этап 1 — доменная модель слоя 1С
- `shared`: типы сессии импорта, правило снапшот-ревизии (pure-логика + тесты).
- Схема: пометка происхождения на складских движениях (проверить, что есть в `warehouseService` — возможно, хватит существующих полей документа).

### Этап 2 — парсер(ы) + превью
- Нормализатор форматов, автоопределение; юнит-тесты на реальных образцах.
- UI: страница «Импорт из 1С» — выбор файла, выбор склада (дефолт — основной), превью (сматчено / не найдено / будет обнулено), кнопка «Провести».

### Этап 3 — проведение и отображение
- Документ «Ревизия по данным 1С»: сторно прошлого снапшота + новые остатки; журнал импортов.
- Остатки на складе отражают импорт; проверить отчёты/прогноз сборки.

### Этап 4 — смоук и приёмка
- CDP-смоук импорта на dev-стенде; приёмка владельцем на реальном файле.

### Этап 5 (отдельная нитка, исследование) — автозабор из 1С
- Варианты: OData/HTTP-сервисы 1С (штатный REST, read-only пользователь), COM-коннектор (Windows, локальная сеть), внешняя обработка/расширение 1С, выгружающее по расписанию в файл/на endpoint МатрицыРМЗ.
- Зависит от версии/конфигурации 1С на заводе и доступности её сервера из сети — **собрать вводные у владельца** (какая 1С: 8.x? УТ/БП/УНФ? файловая или серверная? есть ли у ИТ доступ включить OData?).
- Реализация — только после устойчивой работы ручного импорта.
