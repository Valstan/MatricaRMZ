> Составлено адверсариальным картированием (4 линзы, 28 агентов, блокеры перепроверены по коду).
> Цель документа — чтобы следующая сессия не картировала заново. Ссылка из

## ⛔ Главное: R3 в нынешнем виде не выполним, пока зеркало держат триггеры

Разрыв `lastServerSeq = null`, о котором план велел «проверить и не наступить», оказался не углом, а **структурным блокером**.

- `updateSeqAndCollect` (`applyPushBatch.ts:501-530`) — **единственное место во всём бэкенде**, где строке проставляется `last_server_seq`.
- Строки `users` / `user_section_access` пишут PL/pgSQL-триггеры `rebuild_user` / `rebuild_user_sections` (0086). Они физически не проходят через путь записи приложения, поэтому seq у всех 36 аккаунтов и 191 живой строки доступов — `NULL`.
- Инкрементальный pull страницует по seq. Таблица без seq не приезжает **никогда**.
- Холодный снапшот (`routes/ledger.ts`) при промахе PG-карты падает в фолбэк на in-memory ledger-state, а он для триггерных таблиц **пуст**. Клиент на холодном старте получил бы ноль строк, офлайн-гейт `employeeService` увидел бы пустую реплику — и закрыл бы доступ всем.
- `applyPushBatch` **молча игнорирует** таблицу без блока-обработчика, при том что `writeSyncChanges` выдаёт ledger-seq ДО его вызова. Значит таблица в контракте без хендлера = ledger и PG расходятся беззвучно, обнаружится только на DR-replay.

**Следствие:** сначала нужен путь записи через приложение (или явная публикация строки после триггера), и только потом контракт. См. развилку в основном плане.
