## Сделано 09.11.2026

### 1. Отдельное право `employees.dedupe`

Разбор дублей — операторская работа, но она требовала права вести кадровую карточку целиком. Теперь у неё своё узкое право:

- `shared/src/domain/permissions.ts` — код `employees.dedupe`, строка в каталоге прав («Обработка дублей сотрудников»), роль `storekeeper` его получает. Кадровое право `employees.create` кладовщику по-прежнему **не** выдаётся.
- Серверные маршруты дублей (`backend-api/src/routes/adminMasterdata.ts`) больше не под `requireAdmin` — под право `employees.dedupe` **или** `employees.create` (кадровик работает, как и раньше).
- Клиентские IPC-двери (`electron-app/src/main/ipc/register/employees.ts`) — так же.

### 2. Удаление карточки-дубля = СЛИЯНИЕ, а не стирание

«Очистить карточку» ≠ «слить»: при стирании остались бы сироты — наряды, закупки, чат. Поэтому удаление карточки-дубля идёт через слияние:

- Новая серверная операция `removeDuplicateEmployee` (`employeeDedupeService.ts`) и маршрут `POST /admin/masterdata/employees/dedupe/remove`.
- Сервер сам находит настоящую карточку (тот же человек: совпал табельный номер либо должность при незаполненном номере) и сливает в неё: ссылки перевешиваются, карточка гасится с меткой «слит в другую» и уходит из списка и из реплики клиента.
- Клиентская кнопка «удалить» (`employees:delete`) сначала спрашивает сервер «это дубль?»; если да — слияние и карточка гаснет сразу (режим `merged`), если нет — прежний путь (запрос администратору).
- **Внятные отказы вместо запроса:** спорный случай (разные табельные) и «у карточки есть вход, а у найденной — нет» возвращают объяснение, а не заявку в админку. Жалоба владельца была именно на это: «запрос уходит, а карточка остаётся» — и запросы эти копились.

### 3. Блокер слияния — расхождение ЗНАЧЕНИЙ, а не «меньше заполненных полей»

Счёт «заполнено полей 15 против 10» — подсказка, какую карточку взять основной, а не запрет: пустое поле значит «не заполнено», а не «по-разному».

- Новое отношение карточек: `same` (один человек) / `disputed` (один человек, значения расходятся — решает оператор) / `different` (разные люди — сливать нельзя).
- Правило: табельные равны — один человек; должности разные — разные люди (блокер с внятным отказом); должность одна, а табельные разные — спорный случай (слияние идёт, расхождение попадает в отчёт); данных нет — разными людьми не объявляем.
- Отчёт о слиянии теперь несёт `conflicts` (табельный номер, должность, дата приёма, ДР) — диалог показывает их оператору: чьи значения останутся.

## Шаг 2 — запрет создания дубля по полному ключу (сделано 09.11)

**Почему прежний гейт не мог проверить полный ключ.** Он жил в `employees:setAttr` и
сравнивал ОДИН атрибут за раз: ФИО пишется первым, табельный номер и даты — позже.
Проверить ключ «ФИО + табельный номер + должность + дата приёма + ДР» по одному
атрибуту физически нечем: половины ключа ещё нет. Запись шла и по одному полю, так
что карточка могла остаться наполовину заведённой.

**Что сделано:**

- **Правило ключа — одно на обе половины** ([`shared/src/domain/employeeCardKey.ts`](../../shared/src/domain/employeeCardKey.ts)): нормализация (регистр, «ё», пробелы, «00675» = «675», даты разных писателей в один календарный день) и сравнение ключей. Сервер и клиент считают по одному правилу — разойтись не могут.
- **Шкала связи:** `different` (разные люди) → `disputed` (человек один, значения разошлись — или совпало только ФИО) → `exact` (совпал полный ключ) → `personnel` (совпал табельный номер).
- **Единая дверь записи** ([`electron-app/src/main/services/employeeCardWrite.ts`](../../electron-app/src/main/services/employeeCardWrite.ts), `saveEmployeeCardGated`): принимает карточку ЦЕЛИКОМ, считает ключ из всех полей разом, спрашивает сервер и пишет **только после** того, как гейт пропустил. `employees:setAttr` и `employees:card:save` — оба входа идут через неё (два гейта разошлись бы — класс brain G363).
- **Проверка — на сервере** (`findEmployeeDuplicatesByKey`, маршрут `/admin/masterdata/employees/dedupe/key-check`): там полный срез сотрудников, локальная реплика отстаёт. Правило сравнения — общее с клиентом.
- **«ДО» и «ПОСЛЕ»:** блокируется только связь, которую запись **сама** создала. Дубль, пришедший из импорта ЗУП, поправить можно — иначе его нельзя было бы ни исправить, ни слить.
- **Три уровня отказа для оператора:** табельный номер занят — отказ без обхода (номер идентифицирует человека); совпал полный ключ — обход только с **обоснованием** (пишется в журнал критических событий на сервере, `employee_duplicate_overridden`); совпало только ФИО — достаточно подтверждения (однофамильцы бывают).
- **Даты приёма и ДР** приезжают на клиент только владельцу карточки (`pullReadFilter`: HR-чувствительные поля для операторов — своя запись), поэтому ключ считается на сервере, а не в реплике.
- **Третий вход — админ-справочник — тоже через эту дверь.** `admin:entities:setAttr` умеет писать любую сущность, в том числе сотрудника, а право `masterdata.edit` есть у ролей, которые кадровую карточку не ведут (технолог). Без общего гейта запрет дублей обходился бы этим путём (класс brain G363): теперь запись карточки сотрудника из админ-справочника идёт через `saveEmployeeCardGated`, а проверку ключа на сервере получают все, кто пишет карточку (`employees.create` / `employees.position.edit` / `employees.dedupe` / `masterdata.edit`) — иначе сервер отвечал бы 403, клиент счёл бы это «сервера нет» и гейт молча выключался.
- **Календарный день считается в зоне Europe/Moscow, а не фиксированным смещением +03:00.** Разные писатели отдают один день разными миллисекундами (клиент пишет локальную полночь машины, серверный импорт — полночь по UTC), и фиксированное смещение сводило их к одному дню только для дат после 2014 года: в Москве до 2014-го было декретное время (UTC+4 летом), и день рождения 1985 года съезжал на сутки назад — ключ переставал совпадать сам с собой, и дубли по ПДО (главный сценарий гейта) проходили мимо. Найдено CDP-смоуком на живом клиенте.

## Что осталось (шаг 5 плана владельца)

- **Шаг 5 — штатка с ПДО.** Источник дат приёма и дней рождения пришлёт владелец. Импорт должен **дополнять** существующие карточки, а не плодить новые (иначе получим ровно тот класс дублей, который чиним), и не обходить запрет дублей из шага 2. Даты приёма и ДР — персональные данные: в отчёты они не выгружаются.
- **Живая приёмка на парке** (человек): удаление дубля из карточки, слияние тройки, внятный отказ для двух разных людей.

## Правила (из плана владельца, держим)

- Сливать только **реальные** дубли: одинаковое ФИО + совпадение по табельному номеру либо по имени и структурному подразделению + должность. Однофамильцы — не дубли.
- Спорные случаи (разные табельные у одного человека) решает оператор — выбором основной карточки; расхождение показываем, а не прячем.
- Удаление карточки необратимо для привязок → слияние **перевешивает** ссылки (`employeeReferenceRepoint`), а не просто удаляет.
- «4 миллиона запросов с компьютера» — симптом неработающего удаления, а не повод вводить rate-limit.
