# План: глобальный поиск — группировка выдачи по месту совпадения (промт КАРМАНА #137)

> Задание владельца (зачитка 25.11.2026, раздел промтов КАРМАНА `MatricaRMZ`, промт **#137**):
> поиск отдаёт «всё, что нашлось», и непонятно, где именно совпало. Нужно, чтобы выдача
> группировалась по полю совпадения («по номеру двигателя — 3», «по номеру контракта — 7»)
> и шла в порядке, который указал владелец.

**Статус:** реализовано кодом (см. «Что сделано»). Промт отправлен в архив КАРМАНА после мержа.

## Линзы (ритуал — три строки в план)

Глобальная линза: поиск — `electron-app/src/renderer/src/ui/utils/search.ts` (подготовка записи)
+ `shared/src/domain/tieredSearch.ts` (общий тир-матчер) · дубль: нет — в реестре глобальных
модулей (`docs/GLOBAL_MODULES.md`) поиска не было, «реестра полей по видам сущностей» в проекте
не существовало (ближайшее — `FacetDescriptor` в `shared/src/domain/listFacets.ts`, но это
фильтры, а не атрибуция совпадения) · действие: **доработать существующее ядро** —
подготовка полей добавлена в общий домен `shared/src/domain/searchFields.ts`, второй матчер
и второй движок не заводились.

Заводская линза: участок — поиск по программе, не производственный поток · кормит ли затор —
нет, затор не меняется · не ломает ли инвариант потока — нет, поиск только читает.

Совет специалистов **не созывался**: это исполнение уже принятого владельцем решения с
готовым планом (промт из КАРМАНА), а не новая граница/сущность/миграция/права
(`docs/council/PROTOCOL.md` §3). Открытые вопросы промта закрыты решениями ниже и вынесены
владельцу явно.

## Что сделано

1. **Домен** — `shared/src/domain/searchFields.ts` (новый):
   - `SEARCH_FIELDS` — реестр полей по видам сущностей (`GlobalSearchKind` → список полей:
     id, подпись, ключи строки). Порядок полей = порядок групп в выдаче;
   - `prepareSearchFields` — подготовка полей строки один раз на набор строк (не на ввод);
   - `matchPreparedSearchFields` — какие поля совпали: **тот же тир-матчер и тот же режим**
     («точный» / «≈ Похожие»), что и в списках, ⇒ объяснение не может противоречить выдаче;
   - `groupRowsBySearchField` — группировка строк по полю с заголовками и приоритетом.
2. **Ядро поиска** — `electron-app/src/renderer/src/ui/utils/search.ts`:
   `prepareRecordSearch(..., { kind })` готовит поля строки; `filterPreparedRecords`
   возвращает `fieldMatches` (id строки → совпавшие поля). Что нашлось — не изменилось:
   поиск по склеенной записи остался как был.
3. **Палитра Ctrl+K** — `GlobalSearchOverlay.tsx`: внутри группы по виду сущности появились
   подгруппы по месту совпадения («по номеру двигателя — 3»). Подгруппы появляются только
   там, где поле известно; серверный (L3) и карточный (L2.5) слои поля не знают — там вид
   остался плоским, как был.
4. **Списки** — `useListDeepFilter` отдаёт `fieldMatches`; общий бейдж
   `SearchMatchBadge` («по номеру двигателя») показан у найденной строки в списке двигателей.

## Решения (владелец не ответил — закрыто по умолчанию, вынесено в PENDING)

- **Строка совпала по двум полям** → показывается в группе **первого** по приоритету поля
  («номер двигателя»), а не в обеих: выдача не двоится.
- **Поле вне реестра** (например, совпадение в примечании) → группа «совпадение в записи»:
  молчать о неизвестном поле нельзя.
- **Вложенность, а не замена оси**: группа по виду сущности осталась, поле — подгруппа
  внутри. Так группировка «Двигатели / Контракты / Номенклатура» не ломается.
- **Строка без известного поля** (серверный/карточный слой) остаётся в плоском виде группы.

## Границы

- Поле совпадения знают только **клиентские** слои (L1 — строки страницы, L2 — справочники
  в памяти). Серверный поиск (L3, номенклатура и складские документы) и глубокий поиск по
  содержимому карточек (L2.5) ищут по всему подряд ⇒ поле они не отдают. Учить им поле —
  отдельная работа на бокенде (в промте это названо открытым вопросом).
- Реестр полей ведётся руками ⇒ рядом стоит сторож `searchFields.guard.test.ts`: каждое
  поле двигателя должно реально быть в `EngineListItem`, иначе группа молча пустая.
- Бейдж поля совпадения показан в списке двигателей; остальные списки (`WorkSheetsPage`,
  отчёты) получают то же самое из `useListDeepFilter`, но бейдж в них не отрисован — хвост
  в `docs/pending/`.
