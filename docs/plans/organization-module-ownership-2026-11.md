# Организационный отдел и «Дети»: хозяин — один, остальные смотрят (задание владельца 21.11.2026)

**Задание владельца (21.11.2026, чат):** организационный отдел — модуль, хозяином которого является оператор — **хозяин модуля** (владелец назвал его в переписке; логин в репозитории не хранится); список «Дети» тоже под ним — он видит и может редактировать, создавать и удалять в них документы, данные и карточки. Суперадмин `valstan` имеет наивысшие права в программе на всё. Остальные операторы **видят** документы и карточки организационного отдела, но **не могут редактировать** (создавать и удалять — тоже нет). Список детей не видят **никто, кроме суперадмина и хозяина модуля**. Данные о детях не видит никто, кроме суперадмина и хозяина модуля.

**Статус:** в работе · 2026-11-21 · машина PC79
**Заводская линза:** организационный отдел (праздники, подарки, карточки детей) · затор: **не касается** — модуль не в производственном потоке (затор по модели — начало сборки) · поток: **не ломает** — права и видимость, данные и поток не трогаются.

## Что есть сейчас (21.11.2026)

- **Один раздел на оба модуля:** `organization` с `menuTabs: ['children', 'organization']`, `restrictedAssign: true` (назначает только суперадмин). Якоря раздела в `access_sections` на проде не было — раздел был невыдаваемым (починено в нити ПП 21.11).
- **Права:** `children.view` и `organization.view` — **в базе оператора**, то есть есть у всех, кто работает в программе; `children.edit` и `organization.edit` — только поимённо (никто не выдан).
- **IPC-гейта по разделам для этих каналов нет вовсе** — каналы `children:*` и `organization:*` идут мимо гейта разделов; единственный барьер сегодня — право `*.view` в капсах клиента (плитка в меню) и `*.edit` на серверной двери.
- **Данные о детях едут в реплику всем:** `erp_employee_children` публикуется издателем зеркала в журнал синка, а pull фильтруется только по правам на EAV и по таблице `audit_log` — строки детей приезжают в локальную БД каждой машины.

## Решение

1. **Два раздела вместо одного.**
   - `organization` — организационный отдел (мероприятия, журнал выдачи): `menuTabs: ['organization']`, раздел **обычный** (не restricted) → засевается ролью, новичок видит модуль сразу; уровень засева — **viewer** для всех (admin и легаси `user` тоже: править модуль может только хозяин модуля).
   - `children` — список детей и карточки детей: `menuTabs: ['children']`, **restricted** (назначает только суперадмин).
2. **Права.**
   - `children.view` **убирается из базы оператора** и зажимается до суперадмина в `defaultPermissionsForRole` (admin и легаси `user` его не получают) → ни плитка «Дети», ни данные не видны никому, кроме суперадмина и хозяина модуля (хозяину — персональным override'ом).
   - `organization.view` остаётся в базе оператора (видят все).
   - `children.edit` и `organization.edit` — персональные override'ы хозяину модуля (суперадмин получает всё по роли).
3. **IPC-гейт по разделам:** `children:*` → раздел `children`, `organization:*` → раздел `organization`. Наблюдатель раздела читает, писать может editor (те же мутирующие каналы — в write-списке гейта). Каналов детей/организации в гейте до сих пор не было — это и есть дырка, из-за которой «данные о детях» читались мимо разделов.
4. **Данные о детях не едут в реплику тем, кому нельзя.** В pull-фильтре строка таблицы `erp_employee_children` отбрасывается для тех, у кого нет права `children.view` (суперадмин и хозяин модуля — получают). Это то же отношение к персональным данным, что уже есть в фильтре для `birth_date`/`hire_date` у сотрудников.
5. **Карта разделов в ledger:** таблица `erp_employee_children` принадлежит разделу `children`, а не `organization`.
6. **Скрипт выдачи** — `grantOrganizationModuleAccess`: якоря разделов (все разделы каталога), права `children.view`/`children.edit`/`organization.edit` — хозяину модуля, раздел `organization` — всем живым аккаунтам с заданным membership (viewer, хозяину editor), раздел `children` — только хозяину модуля (editor). Логины — аргументом (D-041).

## Шаги

1. Каталог разделов: новый `children`, `organization` без `children` в menuTabs и без `restrictedAssign`, сид `organization` → viewer всем ролям.
2. Права: `children.view` из базы оператора; кламп `children.view` до суперадмина.
3. IPC-гейт: префиксы `children:` / `organization:` + мутирующие каналы в write-списке.
4. Pull-фильтр: строки детей — только для тех, у кого есть `children.view`.
5. Карта разделов в ledger: `erp_employee_children` → `children`.
6. Скрипт выдачи + npm-точки.
7. Сторожи: роль не даёт права на детей; админ/легаси `user` не получают `children.view`; разделы разведены; IPC-каналы гейтятся своими разделами; сид `organization` → viewer.
8. Выкат: сначала выдать права и разделы (скрипт), потом катнуть код — иначе раздел «Дети» окажется у Васи, а право ещё нет (или наоборот).
9. Приёмка на проде: пересчёт эффективных прав по всем живым аккаунтам; раздел `organization` — у всех, `children` — только у двоих; REST `GET /children` без права → 403; `GET /organization` у наблюдателя → 200, `POST` → 403.

## Приёмка на живом проде

- Пересчёт эффективных прав: `organization.view` — у всех, кто работает в программе; `organization.edit` — только у круга; `children.view`/`children.edit` — только у суперадмина и хозяина модуля.
- Разделы: `organization` — у всех живых аккаунтов с membership (viewer, у хозяина модуля editor), `children` — только у хозяина модуля (editor) и по обходу суперадмина.
- REST: `GET /organization/events` у наблюдателя — 200, `POST /organization/events` — 403; `GET /children` у наблюдателя — 403, у хозяина модуля — 200.
- Плитки: «Дети» — только у суперадмина и хозяина модуля; «Организационный отдел» — у всех, кнопки правки — только у хозяина модуля.

## Что НЕ трогаем

- Данные и бизнес-логика модулей (`childrenService`, `organizationService`) — права и видимость.
- Мероприятия и журнал выдачи: они по-прежнему видны всем (только чтение) — задача не про их данные.
- Раздел «Персонал», права сотрудников, их карточки — задача про детский и организационный модули.
- Права смежных модулей (СИЗ, ПП, этапы работ).

## Осторожности

- **Три слоя, а не один:** право (`user_permissions` поверх роли) → раздел (плитка в меню + IPC-гейт данных) → клиентская капа. Пропущенный слой даёт «право есть, а плитки нет» (или наоборот: «плитки нет, а данные отдаёт» — как с каналами детей/организации, которых в гейте не было вовсе).
- **Уже синхронизированные машины сохранят строки детей в локальной БД.** Pull-фильтр не умеет отзывать строки: строка, переставшая приходить, у клиента остаётся. Новые машины строки детей не получат вовсе; на старых они лежат до полной перезаливки реплики. Через программу они не видны (IPC-гейт раздела), но в файле БД — лежат.
- **Снятие `children.view` из базы оператора — обратная совместимость:** у кого-то может быть личный override `children.view = true` с прошлых выдач; скрипт выдачи их перезаписывает (allowed=false), иначе раздел «Дети» остался бы открыт кому-то лишнему.
- **Суперадмин обходит разделы по роли** — он видит и ведёт оба модуля по умолчанию, без строк в membership (как и ПП).
