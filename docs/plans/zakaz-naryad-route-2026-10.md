# Заказ-наряд — маршрут по цехам внутри существующих нарядов (2026-10-22)

**Статус:** план согласован владельцем в объёме (ответы 22.10: маршрут внутри существующих нарядов, шаг передачи фиксируют обе стороны, список причин неисполнения принят). Реализация — PR-0…PR-6 ниже.

**Заводская линза.** Участок — движение работы/детали между цехами (заявка → комплектация → работа в цеху → контроль → сдача). Затор (начало сборки, подбор деталей из обезличенного фонда) **кормится косвенно**: маршрут показывает, в каком цеху работа стоит и что уже готово, то есть сокращает ручной поиск «что есть и где». Инвариант потока не ломается: наряд остаётся строкой `operations` с `meta_json`, движение — `repair_history_entry`, ремфонд — существующий регистр + поэкземплярный учёт; новых EAV-атрибутов нет (EAV-freeze).

## 1. Что просил владелец и что из этого следует

| Просьба | Как решаем |
|---|---|
| «Заказ-наряд» на основе существующих нарядов | **Отдельной сущности не заводим.** Модуль = существующая `operations` с `operation_type='work_order'`, внутри которой живёт маршрут. Новый пункт меню не нужен: список нарядов уже есть, его и расширяем |
| Движение по заводу/цехам, «где сейчас» | Маршрут = упорядоченные **шаги с цехом**. «Где сейчас» — производное: первый шаг, который не выполнен. Копии «текущего цеха» в шапке нет — нечему расходиться |
| Передачу фиксируют **обе стороны** | У шага две отметки: **отправил** (цех-владелец шага) и **принял** (цех следующего шага). Пока приёмки нет — шаг «в пути» |
| Завершение цехом-заказчиком: исполнен / не исполнен с причиной | Финал маршрута — шаг «Сдача» у цеха-заказчика. Итог пишется в payload наряда (`completion`) и уходит в ленту двигателя. Проводка по складу — существующее закрытие наряда |
| Детали из ремфонда | Строки шага «Комплектация» со ссылкой на ремфонд; списание — существующий (сегодня не вызываемый) `releaseRepairFundForWorkOrder` |
| Изготовленные новые детали — обратно в ремфонд | Приход из строк наряда при закрытии: новый путь `intakeRepairFundFromWorkOrder` (образец — `intakeRepairFundFromEngine`), экземпляры — существующий `repair_fund_instance` |
| Подписи внизу карточки | Существующий механизм `payload.signatureBlocks` + два новых слота: «Сдал цех-исполнитель», «Принял цех-заказчик» |
| Список с фильтром по типам нарядов | Фильтр типа переезжает из рендерера в main-фильтр `listWorkOrders`; в список добавляются колонки «Где сейчас», «Шаг», «Дней в шаге» |
| Названия шагов и структура — на наше усмотрение | Реестр из пяти видов шагов, см. §3 |

## 2. Домен (shared, без БД и синка)

Новое поле payload — `route` (payload version 5, `shared/src/domain/workOrderRoute.ts`). Хранение в `meta_json` не требует ни миграции, ни новой sync-таблицы: `recalcPayload` новые ключи сохраняет (`workOrderService.ts:333-346`), нормализация — своим whitelist'ом (иначе поле доедет, но не будет проверено, `workOrder.ts:541-626`).

```ts
type WorkOrderRouteStepKind = 'order' | 'picking' | 'work' | 'control' | 'handover';
type WorkOrderRouteStepState = 'planned' | 'sent' | 'accepted' | 'done' | 'declined';

interface WorkOrderRouteStep {
  id: string;                     // uuid шага
  kind: WorkOrderRouteStepKind;
  shopId: string;                 // directory_workshops.id
  shopName: string;               // снимок имени: справочник цехов в реплику не едет
  title?: string;                 // «расточить гильзы» — словами цеха
  state: WorkOrderRouteStepState;
  sent?: { at: string; by: string };      // отправил (цех предыдущего шага)
  accepted?: { at: string; by: string };  // принял (этот цех)
  done?: { at: string; by: string };
  declined?: { at: string; by: string; reason: WorkOrderDeclineReason; note?: string };
  lines?: WorkOrderRouteLine[];   // требования шага (детали/материалы)
}

interface WorkOrderRouteLine {
  id: string;
  name: string;
  qty: number;
  source: 'repair_fund' | 'manufacture' | 'stock';
  nomenclatureId?: string;
  repairFundInstanceIds?: string[];  // ссылки на экземпляры, не копии
}
```

Правила (в домене, юнит-тестами):

- порядок шагов задаёт маршрут; шаг можно выполнить, только если предыдущий `done`;
- `accepted` без `sent` невозможен (и наоборот: `sent` без `accepted` = «в пути», это законное состояние);
- `declined` — только с причиной из реестра; отказ возвращает работу на предыдущий шаг (он снова `done`, следующий `planned`);
- текущий шаг: первый не-`done`; если все `done` — «готов к сдаче»;
- маршрут валиден, если последний шаг `kind='handover'` и его `shopId` = цех-заказчик наряда.

Причины неисполнения (реестр в `shared`, коды + подписи — чтобы изменение формулировки не ломало старые записи): `no_material` (нет материала), `no_worker` (нет исполнителя), `machine_busy` (станок занят), `defect` (брак при изготовлении), `waiting_customer` (ждём заказчика), `other` (другое — с обязательной припиской).

## 3. Пять видов шагов

Названы по заводскому разговору (`docs/zavod/FACTORY_MODEL.md` §3): приёмка → комплектовка → ремонт/изготовление → контроль → сдача.

1. **Заявка** (`order`) — цех-заказчик ставит заказ: что нужно, сколько, откуда берём (ремфонд / изготовить / со склада).
2. **Комплектация** (`picking`) — цех-исполнитель или склад подтверждает наличие: строки требований, что взято из ремфонда, чего нет.
3. **Работа в цеху** (`work`) — ремонт или изготовление; здесь же обычные строки работ и расценки наряда (сдельщина не меняется).
4. **Контроль** (`control`) — ОТК или сам заказчик проверяет; брак — `declined` с причиной `defect` и возвратом на шаг 3.
5. **Сдача** (`handover`) — цех-заказчик принимает и завершает: **исполнен** или **не исполнен** с причиной, две подписи.

Маршрут не обязан содержать все пять: минимальный — `order → work → handover` (когда комплектация не нужна).

## 4. Лента движения: одна строка, две отметки

Каждая смена состояния шага дополнительно пишется в `operations` типа `repair_history_entry` (`entryType: 'transfer'`, форма меты — `engineRepairHistory.ts:83-133`), чтобы «где сейчас» на двигателях, таймлайн и отчёт «Сейчас на заводе» работали без нового механизма. Мета расширяется полями `fromShopId`, `toShopId`, `sent{at,by}`, `accepted{at,by}`, `reason` — **обе стороны в одной строке ленты**, чтобы не удваивать события.

Симметрия парсера и билдера обязательна: новые ключи добавляются и в `parseRepairHistoryMeta`, и в `buildRepairHistoryMeta` (`engineRepairHistory.ts:333-399`) — иначе неизвестный ключ молча срежется.

## 5. Экраны

- **Карточка наряда, вкладка «Маршрут»** (новая, рядом с «Подписями»): вертикальная лента шагов, у каждого — цех, что делают, состояние, кто отправил/принял/выполнил и когда, кнопки «Отправить», «Принять», «Выполнить», «Отклонить с причиной». Текущий шаг подсвечен; «Где сейчас: цех 3, работа» — строка над лентой.
- **Список нарядов**: колонки «Где сейчас», «Шаг», «Дней в шаге»; фильтр по типу — в main (сейчас фильтруется только в рендерере, `WorkOrdersPage.tsx:213`); выгрузка и печать получают те же колонки общим механизмом (`listPrintColumns`).
- **Печать**: секция «Маршрут» (шаги, цеха, даты, кто принял) и «Не исполнено: причина» в модели печати наряда.

## 6. Права

Шаги маршрута правятся `work_orders.edit` (мастер цеха), приёмка — тоже: отправитель и принимающий равны в правах, различаются только отметкой. Закрытие с итогом — `work_orders.close`. Новых прав не заводим: маршрут — часть наряда, а не отдельный документ. Серверный backstop (`ledgerAuthz`, `operations.edit` для строк `operations`) не меняется.

## 7. Ремфонд

- **Списание**: строки `source='repair_fund'` при завершении списываются с локации `repair_fund` существующим `releaseRepairFundForWorkOrder` (`repairFundService.ts:330`, сегодня без вызовов) — включаем в закрытие, clamp по остатку оставляем (лучше списать меньше и сказать, чем уйти в минус).
- **Возврат изготовленного**: строки `source='manufacture'` при завершении приходуются в `repair_fund` (`intakeRepairFundFromWorkOrder` по образцу `intakeRepairFundFromEngine`, идемпотентно по номеру наряда). Экземпляры — `repair_fund_instance` с провенансом на двигатель; новых таблиц нет.
- Ветку ремонта в закрытии не трогаем (`production_release` в склад цеха) — она уже отгружена и принята.

## 9. Риски и как их снимаем

- **Payload растёт**: маршрут со строками — это десятки килобайт на наряд. Мера — строки требований без вложенных объектов, ссылки на экземпляры вместо копий; на 5000 нарядов в разборе списка маршрут не парсим (как сейчас: список читает только сводные поля).
- **Две правды (payload и лента)**: расходиться могут только добавлением события без шага. Мера — единственная функция перехода шага пишет и шаг, и ленту в одной транзакции локальной записи; сторож в тестах проверяет, что второго писателя нет.
- **Серверные SQL-агрегаты** (`workshopStatsService`) читают `meta_json` напрямую: для «Где сейчас» по цехам на сервер нужно поле в JSON, а не только в payload — `route.currentShopId` пишем в `meta_json` рядом с payload при каждом переходе (одно поле, не копия маршрута).
- **`operations` на PG без индексов по двигателю/типу**: выборки «где сейчас» на сервере пойдут сканом. Мера — не заводить серверных списков по маршруту до появления нужды; фильтр в списке идёт по `meta_json->>'workOrderKind'` через существующий `q`/`month`-путь.
