## Почему скрипт переписан, а не просто дописан

Прежняя версия `contracts:resync-slots` писала в EAV-атрибут `contract_payments`. После cutover платежей (план `contract-payments-strict-2026-10`) запись в EAV закрыта, а зеркала strict→EAV нет намеренно. При этом триггер зеркала EAV→strict (`trg_mirror_contract_payments_attr`, миграция 0104) делает **полную замену по контракту**: любая запись в EAV снёсла бы строки, созданные парком после cutover (двигатели, привязки, новые платежи). Перепись на strict — пункт плана `contract-payments-strict-2026-10` (шаг 5, «перепись resyncContractSlots на strict»).

**Новый скрипт:** [`backend-api/src/scripts/resyncContractSlots.ts`](../../backend-api/src/scripts/resyncContractSlots.ts) (+ тесты [`resyncContractSlots.test.ts`](../../backend-api/src/scripts/resyncContractSlots.test.ts)).

| Что | Как |
|---|---|
| Источник правды | строгие `erp_contract_payment_slots` / `erp_contract_payments`; EAV не пишется |
| План договора | EAV `contract_sections` (его же читает карточка), fallback — зеркало `erp_contracts.sections_json` |
| Привязки двигателей | строгая `erp_engine_cards` (`contract_id`, `contract_section_number`, `engine_brand_id`) |
| Раздел двигателя | канон `planContractSectionToken` (решение владельца 13.11.2026) |
| Правило раскладки | домен `syncSlotsWithPlan` — тот же, что зовёт карточка (правда одна) |
| Запись | `writeSyncChanges` (журнал + seq) — парк видит обычным pull |
| Отчёт | кто получил место / кто переехал / кто отвязан / кто без раздела / сколько пустых мест осталось |
| Откат | снимок (JSON) перед записью; `--rollback <файл>` возвращает прежнее состояние и гасит созданные места |
| Гейт | dry-run по умолчанию; на проде запись — по слову владельца (гейт #025) |

### Решения, которые приняты осознанно

1. **Пустые места не удаляются.** Полная сверка их убирает (−798 по прод-аудиту), но удаление места гасит строку, которая ещё есть в EAV-зеркале, и `payments:parity` начинает кричать о «потере» там, где ничего не потеряно. Скрипт их считает и печатает; чистка — отдельный шаг с отдельным решением владельца.
2. **Деньги не пишутся вообще.** Строки платежей скрипт не трогает; сумма по контракту до и после обязана совпасть — не совпала, запись не выполняется (guard «суммы сходятся» из плана #19).
3. **Раздел не выдумывается.** Двигатель без раздела мест не получает — иначе аванс ляжет не в тот ДС. Такие двигатели идут в отчёте отдельной строкой (решение за владельцем — «разделы у 1010 движков»).
4. **Двигатель без раздела, но сидящий в месте, — отвязывается** правилом домена (карточка делает ровно то же). Место и деньги остаются на месте; в отчёте это отдельная цифра.
5. **Контракты — объединение EAV и strict.** Контракт, созданный парком после cutover, не должен молча выпасть из обработки; движки, ссылающиеся на несуществующий контракт, попадают в отчёт («не обработаны»), а не в никуда.
6. **Раздел двигателя читается каноном `planContractSectionToken`** (решение владельца 13.11.2026): «ДС {seq}» — токен ДС, голое число («3») — тоже номер ДС, всё прочее не-ДС — основной договор, пусто — «раздела нет». Старое чтение сворачивало голое число в «primary» и сдвигало движок с его ДС на основной договор. **Находка (21.11.2026):** карточка контракта (`ContractDetailsPage`) читает раздел по старому правилу — на живых данных расхождения нет (голых чисел в базе 0: 443 `primary`, 237 `ДС N`, 974 пустых), но при появлении голого номера карточка увезёт движок с его ДС. Это отдельная правка UI, в эту нить не входит.
