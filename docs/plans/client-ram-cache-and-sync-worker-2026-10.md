# Клиент: БД в RAM, синк в отдельном процессе, обновления по таблицам

**Статус:** PR-1 выкачен в 3.93.0; PR-2 — в PR (движок в `utilityProcess`); PR-3…4 по плану.
**Дата:** 2026-10-29
**Автор решения:** владелец (идея «три части: UI в RAM, сброс на диск, синк с сервером»)
**Рабочая копия:** этот файл.

## Решения владельца (2026-10-29)

1. **Durability:** все страницы БД живут в оперативной памяти, диск остаётся точкой правды. RAM-only как единственная копия данных — **отклонено** (потеря незасинканной работы оператора при сбое питания/падении процесса недопустима).
2. **Область:** только десктоп. Планшетного разделения процессов не будет.
3. **Репозиторий:** всё реализуется в MatricaRMZ (v3), без разделения разработки по репозиториям. Это **осознанное решение владельца** вопреки гейту «строительство ядра v4 — в Matrica4» (`AGENTS.md` §Два поколения): v4 унаследует реализацию как образец.
4. **Память:** не режем. Потолок кэша страниц — 512 МБ, но это *лимит*, а не выделение: SQLite занимает страницы по мере обращения. `temp_store = MEMORY`. Фактический RSS виден в диагностике.

## Заводская линза (три строки)

- **Участок:** платформа клиента — все участки, включая этапы ремонта, наряды, склад.
- **Кормит ли затор:** напрямую нет. Сокращает простой оператора в момент ввода; движение двигателя по этапам не меняется.
- **Инвариант потока:** не ломается. Доменные правила, гейты дублей, субординация дат и статусы не трогаются.

## Контекст: что найдено в коде (факты, не впечатления)

| Факт | Где |
|---|---|
| Локальная БД — одна `matricarmz.sqlite`, SQLCipher, WAL | `electron-app/src/main/database/db.ts` |
| Драйвер `better-sqlite3` **синхронный**: каждый запрос блокирует поток | там же |
| БД живёт **в главном процессе Electron** — том же, что окно, IPC, обновления, трей | `electron-app/src/main/index.ts` |
| `cache_size`, `temp_store`, `busy_timeout` **не заданы вовсе** → кэш по умолчанию **2 МБ** на шифрованную базу | grep по `electron-app`: совпадений нет |
| Синк уже событийный: `/state/wait` (~25 с окно), сторож своих правок 1 с, страховочный тик 60 с | `services/syncManager.ts` |
| Применение pull: страницы по 2000 строк, JSON.parse + расшифровка + upsert — **в главном процессе** | `services/syncService.ts:4908–4979` |
| 25 страниц подписаны на **общий** пульс (15 с) и на «sync done» — каждая целиком перечитывает свой список | `ui/services/liveDataService.ts`, `hooks/useLiveDataRefresh.ts` |
| `syncService` импортирует `app` из Electron (userData, getVersion, relaunch) и переиспользуется планшетом через инъекции | `syncService.ts:25,340,443,4321,4342,4474`; `android-app/src/core/syncWiring.ts` |

**Вывод:** тормозит не частота синка (она уже секундная), а два свойства: (а) тяжёлое применение pull идёт в потоке окна и IPC; (б) любое изменение дёргает весь экран, а не затронутый кусок. Оба лечатся без RAM-базы как единственной копии.

## Целевая архитектура (desktop)

```
renderer (UI)
   │ IPC
main — окно, IPC, обновления, трей. Pull не применяет, диск на синке не ждёт.
   │ MessagePort
sync-процесс (utilityProcess, своё соединение SQLite)
   ├─ сеть: /ledger/state/wait, pull, push
   ├─ разбор: JSON + расшифровка полей
   ├─ применение pull короткими транзакциями
   └─ сторожа: pending 1 с, страховочный тик 60 с
```

SQLite остаётся на диске (SQLCipher + WAL), но настроен так, что всё прочитанное — в RAM. «Сбрасыватель» RAM→диск — WAL, а не наш код.

## Этапы

### PR-1. БД живёт в RAM (отдельный релиз)

**Цель:** проверить гипотезу «всё в RAM» одним прагмой и получить числа «до/после».

**Замеры (2026-10-29, стендовый объём: 12 000 двигателей, 240 000 значений атрибутов, SQLCipher):**

| Операция | Кэш 2 МБ (сегодня) | Кэш 512 МБ | Вывод |
|---|---|---|---|
| Чтение 240k строк (`SELECT … all()`) | 160.6 мс | 158.0 мс | ≈2% — кэш **не** про чтения: время уходит на материализацию строк в JS |
| Тот же запрос на plaintext-базе | 155.2 мс | 161.8 мс | расшифровка — не узкое место |
| Список с `LIMIT 50` (то, что видит оператор) | 2.2 мс | 2.1 мс | без изменений |
| **Upsert 2000 строк (2 индекса) — применение pull** | **56.1 мс** (max 205.3) | **9.2 мс** (max 15.3) | **6× быстрее, пики в 13× ниже** |

Отсюда честная формулировка эффекта PR-1: кэш страниц убирает перечитывание и перерасшифровку b-tree при **записи** pull, то есть именно те секундные пики, на которых замирает окно. Обещать «списки в разы быстрее» нельзя — это ложь, которую замер опроверг. Замирания от чтений лечатся не кэшем, а выносом работы из главного потока (PR-2/PR-4).

- `openSqlite` / `openSqliteReadonly` (`database/db.ts`):
  - `PRAGMA cache_size = -524288` (512 МБ, KiB; лимит, не выделение);
  - `PRAGMA temp_store = MEMORY` (сортировки, DISTINCT, отчёты);
  - `PRAGMA busy_timeout = 5000` (готовим почву под второе соединение);
  - `PRAGMA optimize` на старте (дешёво; `ANALYZE` — только если `sqlite_stat1` пуст);
  - `synchronous` **не трогаем** (остаётся FULL: durability — заявленное требование).
- Замер: `perf_hooks.monitorEventLoopDelay({ resolution: 20 })` в главном процессе — модуль [`services/eventLoopLag.ts`](../electron-app/src/main/services/eventLoopLag.ts). Гистограмма включается на старте (`index.ts`, до открытия базы), окно замера сбрасывается на каждом прогоне синка (`SyncManager.runNow`), фоновая сводка раз в минуту пишет warn (`loop-lag`) только если p99 ≥ 50 мс, метаданные несут `loopP50Ms/loopP99Ms/loopMaxMs/rssMb`. Плюс уже существующие `logPerfWarn`/`perfTrace` и фазы `engine:list`.
- Тесты: `openSqlite.test.ts` — прагмы применены и на writable (включая `optimize`/первый `analyze` и отказ от повторного `ANALYZE`, когда планы уже есть), и на read-only (без записи статистики); `eventLoopLag.test.ts` — жизненный цикл монитора, порог срабатывания, состав метаданных и отсутствие ложных сводок.
- Приёмка: p99 главного потока во время pull заметно ниже базовой линии; отчёт «до/после» в теле PR; на стенде список двигателей открывается не медленнее, чем до.

### PR-2. Движок синка в utilityProcess

**Цель:** применение pull перестаёт останавливать окно и IPC.

- Новый вход сборки: `electron-app/electron.vite.config.ts`, `main.build.rollupOptions.input = { index, syncWorker }`, выход `dist/main/syncWorker.js`.
- `electron-app/src/main/workers/syncWorker.ts`: открывает своё соединение SQLite (ключ — **только сообщением**, не в argv), поднимает `SyncManager` целиком.
- `SyncManager` переезжает в воркер без изменения семантики очереди (`runOnce` во время идущего синка ждёт и запускает свежий — поведение M134 сохраняется).
- `main` получает `SyncProxy` с тем же API: `runOnce`, `getStatus`, `setApiBaseUrl`, `startAuto`, `stopAuto`, события `progress` → `sync:progress` рендереру.
- Замена Electron-зависимостей в `syncService.ts` на инъекцию `host` (`userData`, `appVersion`, `relaunch` → сообщение в main, `log sink` → main пишет в общий файл). Тот же приём, которым уже сделан android-порт; `android-app/src/core/syncWiring.ts` не меняется.
- Супервизор в main: падение воркера → рестарт с backoff 1→30 с, статус `error`, синк не задваивается.
- Контention: `busy_timeout`, короткие транзакции применения (500–2000 строк), повтор при `SQLITE_BUSY`; порядок правок оператора не меняется.
- Флаг отката `MATRICA_SYNC_WORKER=0` — синк возвращается в main без выпуска нового кода.
- Тесты: протокол сообщений (`syncWorkerProtocol.test.ts`), семантика прокси (`SyncProxy` — очередь, статус, ошибки), сторож `syncService` без Electron-импорта на уровне модуля, сторож перезапуска воркера.
- Смоук (`verifier-electron`): большой pull на 50 000 строк в dev-PG; проверить — окно не замирает, `sync:status` отвечает, прогресс идёт, правка уезжает, ключ не в командной строке.

**Риск, который меряем в этом же PR:** не «остывает» ли кэш главного процесса от записи второго соединения. Если остывает — PR-4 поднимается в приоритете.

**Что выяснилось по ходу (важнее, чем план предполагал).** В `utilityProcess` из Electron доступны только `net` и `systemPreferences` — `app`, `safeStorage`, `dialog` там нет вовсе (проверено вживую на Electron 43). При этом выход сборки — ESM, и статический импорт имени, которого у модуля нет, роняет процесс **при загрузке**: `SyntaxError: The requested module 'electron' does not provide an export named 'app'`. Отсюда три следствия, которые пришлось сделать в PR-2, а не «потом»:

- платформенное движок берёт только через провайдеры: `syncHost` (путь, версия, лог, перезапуск), `syncSession` (сессия расшифровывается там, где живёт ключ ОС), `sync/e2eKeySource` (кольцо E2E-ключей). Провайдеры ставятся явно — `installElectronSyncHost` на десктопе, `wireSyncForAndroid` на планшете; «импорта по умолчанию» нет намеренно, иначе воркер тянул бы `safeStorage` в свой граф и падал на линковке.
- сборка воркера — **второй вход** `main`-сборки, а путь к файлу воркера main передаёт явно: `import.meta.url` внутри чанка указывает на `dist/main/chunks/`, а не на `dist/main/`.
- при включённом E2E движок остаётся в главном процессе (ключи строк читаются через `safeStorage`); на проде E2E выключен, так что это страховка, а не повседневный путь. Второй ручной откат — `MATRICA_SYNC_WORKER=0`.

**Проверено живьём (spike, Electron 43):** собранный `dist/main/syncWorker.js` поднимается `utilityProcess.fork`, чанки линкуются, `require('electron')` из воркера работает (`net.fetch` → 200), хост и провайдер сессии устанавливаются, `init` доходит до открытия базы. Дальше на этой машине путь не пройден: локальный `better-sqlite3-multiple-ciphers` собран под Node-ABI 137, а Electron 43 требует 148 (`C:\BuildTools` с MSVC сейчас нет) — поэтому CDP-смоук в PR честно помечен «не гнался», а не выдан за пройденный.

### PR-3. Изменения по таблицам, а не «весь экран»

**Цель:** убрать вторую болезнь — 25 страниц, одновременно перечитывающих списки.

- `applyPulledChanges` возвращает `changedTables: Record<string, number>` (таблица → сколько строк).
- `SyncManager` склеивает изменения за прогон и отдаёт **одно** событие `sync:changed { tables, pulled }`.
- `shared/src/domain/syncTableDomains.ts` — карта «таблица контракта → домены UI» (`engines`, `workOrders`, `workSheets`, `warehouse`, `supply`, `directories`, `chat`, `ppe`, `files`, `users`). Сторож: у каждой таблицы контракта есть домен (класс `pullApplyCoverage`).
- Renderer: `useLiveDataRefresh` принимает домены; `liveDataService` фильтрует `sync_done` по ним. `interval`/`focus` — по-прежнему всем.
- Скрытые вкладки (keep-alive) не перечитываются; при показе — один догоняющий проход через существующий `shownSeq`.
- `App.tsx`: убрать общий перегон двигателей на любой pull; оставить точечный (`syncPulledEngineTables`).
- Приёмка: счётчик «страница перечиталась, хотя её таблиц не касались» = 0; складской pull не дёргает список двигателей.

### PR-4. Тяжёлые чтения (только по замеру, отдельным решением)

Условие входа: после PR-1…3 p99 главного потока > 50 мс или тёплое открытие списка > 150 мс.

Варианты по возрастанию цены:
1. индексы/запросы/фазы сборки (дешевле всего);
2. тяжёлые пути чтения (двигатели, отчёты, поиск) — в data-процесс с read-only соединением;
3. весь сервисный слой БД — в data-процесс, main становится брокером.

При выборе 2/3 учесть дублирование кэшей: крупный кэш остаётся у владельца БД, у остальных — маленький.

## Порядок выпуска (решение агента)

1. **PR-1 — отдельным релизом.** Даёт владельцу почувствовать разницу быстро, а нам — числа, от которых зависит PR-4. Если PR-1 один снимает почти всю боль, PR-2 не гоним в спешке.
2. **PR-2 + PR-3 — одной серией и одним релизом.** По отдельности каждая половина не даёт заявленного эффекта: без PR-3 синк в воркере всё равно дёргает весь экран.
3. **PR-4 — только после чисел**, отдельным решением и, при необходимости, отдельным планом-дополнением.

## Метрики приёмки

| Метрика | Порог | Как мерим |
|---|---|---|
| Пауза главного потока p99 во время pull 50k строк | < 50 мс | `monitorEventLoopDelay` + лог синка |
| Тёплое открытие списка двигателей | ≤ 150 мс | существующие фазы `engine:list` |
| Свежесть чужой правки | ≤ 2 с (не хуже сегодняшнего) | `sync:status.lastSyncAt`, лог |
| Лишние перечитывания страниц после pull | 0 | счётчик в живом смоуке |
| RSS клиента после часа работы | без OOM на 8 ГБ; число в диагностике | `process.getProcessMemoryInfo`, отчёт |

## Риски и закрытие

| Риск | Закрытие |
|---|---|
| Два писателя в один файл → `SQLITE_BUSY` | короткие транзакции, `busy_timeout`, повтор, лог отказов |
| Кэш главного процесса остывает от записи воркера | замер в PR-2; при подтверждении — PR-4 раньше |
| Ключ шифрования утекает через argv/лог | только `postMessage`, в логи не пишем, сторож в тестах |
| Падение воркера = синк молча умер | супервизор + статус `error` + видимая плашка |
| Антивирус ругается на новый процесс | это тот же подписанный `MatricaRMZ.exe` (Electron Helper), новых файлов нет |
| Планшет ломается об общий `syncService` | инъекция `host` вместо `app`; android-проводка не меняется; guard-тест |
| `temp_store=MEMORY` раздувает память на огромных отчётах | RSS в диагностике; при аномалии — точечный `PRAGMA temp_store=FILE` на тяжёлых отчётах |
| Локальные флейки тестов на PC79 | гейт = CI; локальный красный вне зоны правки перепроверять одиночным прогоном |

## Что не делаем

- RAM-база как единственная копия (потеря работы оператора).
- Свой сбрасыватель RAM→диск (это WAL).
- Переписывание синка на Go/C++/Rust (узкое место — не язык; второй контракт на 30 таблиц, authz, E2E и ремапы id).
- Разделение процессов на планшете (другой стек, Capacitor).
- Полный переезд БД в отдельный процесс сразу (риск для работающего парка; делаем по замеру).
