# Журнал действий: конкретный объект и ссылка; «Удалённое за 3 дня» (промт КАРМАНА #169)

**Задача:** [промт КАРМАНА #169](https://github.com/Valstan/MatricaRMZ) от 26.11.2026 — «Журнал действий и история удалённых объектов».
**Ветка:** `feat/audit-object-links-deleted-history-2026-11-26`
**Статус:** в работе (26.11.2026)

## Что просили

1. Журнал ловит больше **конкретных** действий (сегодня часть строк остаётся «Выполнил действие» / раздел «Прочее»).
2. Строка журнала **называет объект**: «Открыл карточку двигателя «Д-100»», а не «Открыл объект, категория прочее».
3. У строки с объектом — **ссылка на объект**; у удалённого объекта ссылки нет, и в строке сказано, что объект удалён.
4. Подписи считаются **на показе** (прошлое не переигрывается); журнал в клиенте и в веб-админке — один и тот же.
5. Собрать **удалённое за последние три дня** из мягко удалённых записей.
6. **Отдельная вкладка** «Удалённое за 3 дня».
7. У каждой записи **три кнопки**: «Посмотреть» (без восстановления), «Восстановить», «Удалить окончательно» (с подтверждением).
8. До восстановления видно **путь возврата**: «Двигатели → Д-100».
9. Ровно **три дня**: старше — не показываем и удаляем окончательно; правило видно в интерфейсе.
10. Не задеть **черновики** и **корзину ярлыков**.

## Что нашлось в коде (факты с файлами)

- **Подпись строки** — `shared/src/labels/auditAction.ts`: `describeAuditAction(row)`. Читает `action`, `actionText`, `section`, `documentLabel`, `actionType`. Общий модуль на клиент и веб-админку — копий нет.
- **Источник строк**: серверная таблица `audit_log` (`backend-api/src/database/schema.ts:120`: `actor`, `action`, `entityId`, `tableName`, `payloadJson`, `createdAt`) → проекция `statistics_audit_events` (`schema.ts:439`), наполняется **один раз** при инжесте (`backend-api/src/services/statisticsAuditService.ts:173` `ingestAuditBatch`) — поэтому подпись обязана считаться на показе.
- **Раздел строки** считается на сервере: `statisticsAuditService.ts:76` `sectionOf(action)` — знает префиксы `app.session.`, `auth.`, `ui.supply_request.`, `supply_request.`, `ui.engine.`, `engine.`, `part.`, `tool.`, `employee.`, `masterdata.`, `admin:`, `sync.`, `files.`; всё остальное → **«Прочее»**.
- **Имя объекта** (`docLabel`, `statisticsAuditService.ts:136`) знает только `requestNumber`, `engineNumber`, `name` (для деталей), `docNo` — у большинства строк имени нет.
- **Ссылка в журнале уже есть** на клиенте: `electron-app/src/renderer/src/ui/pages/SuperadminAuditPage.tsx:172` `getDeepLinkPayload` + `window.matrica.app.navigateDeepLink`; сервер отдаёт `entityId` (`statisticsAuditService.ts:564` `listAuditStatistics` — `entityId` берётся джойном из `audit_log`). Но ссылка рисуется **только если есть `documentLabel`** — то есть почти никогда.
- **Клиент пишет журнал**: `electron-app/src/renderer/src/ui/utils/uiUsageLog.ts` (`ui.visit`, `ui.card_open`, `ui.report_open`, `ui.report_build`) и карточки (`EngineDetailsPage.tsx:1642`, `SupplyRequestDetailsPage.tsx:875` → `window.matrica.audit.add`). Локальная таблица `audit_log` (`electron-app/src/main/database/schema.ts:111`) едет на сервер через синк.
- **Удаление мягкое**: `deletedAt` в серверной и клиентской схеме; серверный образец — `backend-api/src/services/adminMasterdataService.ts:1560` `softDeleteEntity` (метка + `insertChangeLog`). «Воскрешение» tombstone значения атрибута уже есть там же (`:1471`, флаг `reviving`).
- **Права**: `shared/src/domain/permissions.ts` (коды прав), серверная проверка — `backend-api/src/auth/permissions.ts` (`defaultPermissionsForRole`), право журнала `audit.view` выдаётся поимённо (суперадмин по умолчанию).
- **Синк-ограничение (важно!)**: `backend-api/src/services/sync/applyPushBatch.ts:593` — «seq-less undelete» отклоняется, если у сервера есть tombstone с известным seq ⇒ **восстановление из клиента может быть отбито сервером**. Значит, восстановление — **серверная операция** (сервер снимает метку и пишет журнал изменений → разойдётся по всем машинам).

## Решения (по умолчанию; развилки владельца — в PENDING)

| Развилка промта | Решение по умолчанию | Почему |
|---|---|---|
| «Три дня» — хранение или окно показа | **И то, и другое**: показываем записи с `deletedAt` за последние 3 дня; записи старше 3 дней **удаляем окончательно** при следующем заходе в список | критерий приёмки требует и «не показываются», и «удаляются окончательно» |
| Что попадает в историю удалений | **Виды, где в программе есть мягкое удаление и есть имя**: двигатели, договоры, контрагенты, файлы + EAV (заявки, наряды, записи справочника, сотрудники). **Не покрыты:** детали (`directory_parts`), инструменты (`directory_tools`), документы склада (`erp_document_headers`), карточки СИЗ (`erp_employee_cards`) — для них у клиента нет готового payload-конвертера в журнал изменений, а второй конвертер заводить нельзя (глобальная линза). Решение — за владельцем (PENDING) | промт просит «по всем типам объектов»; реестр видов — в `shared/src/domain/deletedObjects.ts`, список не закрытых — в `docs/pending/` |
| Кто может восстанавливать | **Новое право `deleted.restore`**, по умолчанию только суперадмин (как `audit.view` — поимённо) | восстановление меняет данные; решение владельца записано в PENDING |
| Восстановление может быть неполным | **Честно предупреждаем** в подтверждении: объект вернётся, связи могут остаться битыми | риск промта назван до реализации |
| «Удалить окончательно» — след в журнале | **След остаётся**: строка в `audit_log` («Удалил окончательно <объект>»), из списка удалённого запись исчезает | журнал действий — не место для тихой потери |
| Клиент без сервера | **Список пустой с честной причиной** («нужен сервер — восстановление и список собирает сервер»); локальные черновики и корзина ярлыков не тронуты | восстановление — серверная операция (см. `applyPushBatch`) |
| Синхронизация восстановления | Сервер снимает метку **через журнал изменений** (`insertChangeLog`) → разходится по всем машинам; клиентский путь восстановления не заводим | иначе сервер отобьёт undelete |

## Линзы

```
Глобальная линза: auditObject (новый домен-модуль) · дубль: есть (sectionOf/docLabel в statisticsAuditService, getDeepLinkPayload в SuperadminAuditPage, entityLabel в changes.ts) · действие: вынести общее правило в shared/src/domain/auditObject.ts и перевести на него существующие места (правка существующего кода, не второй копией)
Заводская линза: фича не трогает производственный поток (наряды, этапы, склад) — только чтение истории и восстановление удалённого; инвариант потока не ломается, движения двигателя не меняются; затор не кормит
```

## План работ

1. **Общее правило** `shared/src/domain/auditObject.ts`: раздел по коду действия, имя объекта по payload, вид объекта (kind) по коду/таблице — одно место на клиент, сервер и веб-админку.
2. **Подпись** `shared/src/labels/auditAction.ts`: называет объект, говорит «объект удалён», не печатает «Выполнил действие».
3. **Сервер**: `sectionOf`/`docLabel` переводятся на общее правило → в проекции появляются раздел и имя объекта для всех типов.
4. **Клиент**: строка журнала показывает объект и **кнопку «Открыть»**; удалённый объект — без кнопки и с пометкой «объект удалён» (проверка по локальной реплике).
5. **Реестр удалённого** `shared/src/domain/deletedObjects.ts`: виды объектов, путь возврата «Двигатели → Д-100», правило «три дня».
6. **Сервер** `deletedObjectsService.ts` + маршрут `/admin/deleted`: список за 3 дня, восстановление, окончательное удаление, уборка старых; право `deleted.restore`.
7. **Клиент**: IPC + вкладка «Удалённое за 3 дня» + страница с тремя кнопками и путём возврата.
8. **Тесты и гейты**: `shared`, `electron-app`, `backend-api` — зелёные; правило в `AGENTS.md`; доки (карта, PENDING, handoff, COMPLETED).

## Границы нитки

- Не трогаем: черновики карточек (`cardDrafts`), корзину ярлыков на верстаке, движение двигателя по этапам, релизный контур.
- Серверные операции — только под правами; прод не трогаем (выкат — отдельным осознанным шагом).
