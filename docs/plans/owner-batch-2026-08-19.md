## 1. Снять fallback-ключ `matricarmz-prod-deploy-2026-05-22` с прода 🟢 S

**Что.** Удалить строку из `~/.ssh/authorized_keys` прода. Останутся два ключа: `…@RMZ4VAL-2026-06-02` (вторая машина) и `…@PC40-2026-08-17` (действующий ключ PC40).

**Почему сейчас.** Ключ оставляли страховкой на время ротации 17.08 с плановой датой снятия 24.08. PC40 весь день 19.08 ходил на прод новым ключом — страховка отработала вхолостую и дальше только расширяет поверхность доступа. Brain просил снять раньше срока, если новый ключ уверенно работает; владелец подтвердил.

**Шаги.**
1. Сверка перед правкой: `ssh-keygen -lf ~/.ssh/authorized_keys` — убедиться, что отпечаток `/gWxd…` (PC40, действующий) на месте.
2. Бэкап `authorized_keys.bak-before-fallback-drop` рядом (как делали 17.08 при снятии осиротевшего).
3. Удалить строку с комментарием `matricarmz-prod-deploy-2026-05-22`.
4. **Проверка доступа в том же окне, до разрыва сессии:** новым соединением `ssh matricarmz "echo ok"`. Если не отвечает — вернуть из бэкапа старой сессией, которая ещё жива.
5. Обновить `PROJECT_STATE.md` (история SSH) и память `ssh_prod_key_rotation`.

**Риск.** Отрезать себе доступ. Снимается тем, что удаление идёт **не** последним действием живой сессии: проверочный вход делается, пока прежняя сессия открыта и может откатить.

**Гейт.** Живой вход новым соединением после правки.

## 2. Зашифровать второй артефакт бэкапа (`.sqlite`) 🟡 M

**Что.** `backup:nightly` кладёт рядом с шифрованным дампом `YYYY-MM-DD.sqlite` (~152 МБ) — срез EAV (`entities`, `attribute_values`, `operations`, `audit_log`), фактически та же база предприятия, **открытым текстом**. Закрыть той же логикой, что дамп, не сломав фичу клиента.

**Почему не сделали вместе с дампом.** Этот файл читает живая фича «просмотр бэкапа»: `GET /backups/nightly/:date/url` отдаёт **прямую ссылку на Яндекс**, клиент качает её `net.fetch` и открывает как SQLite. Асимметричный ключ здесь не годится — расшифровать должен уметь сервер, иначе фича умрёт.

**Решение.** Симметричный ключ на сервере + расшифровывающий стрим-эндпойнт; `/url` начинает отдавать ссылку на него. Модель угроз при этом честная: утечка **одного `YANDEX_DISK_TOKEN`** перестаёт давать открытый текст; компрометация самого сервера — нет, и не должна.

**Парк обновлять не нужно** — клиент качает тот URL, который ему дали. Это и определило выбор схемы.

**Шаги.**
1. **Формат.** `MRMZSNAP` v1 — **кадрированный** AES-256-GCM: файл режется на кадры по 4 МБ, у каждого свой тег. Иначе поточная расшифровка не может проверить целостность до конца файла: прокси уже отдал бы клиенту непроверенные байты, и подмена дала бы битую SQLite вместо честной ошибки. Читать 152 МБ в память на VPS с 4 ГБ и двумя инстансами — нельзя.
2. **Ключ.** `BACKUP_SNAPSHOT_KEY` (base64 32 байта) в прод-`.env`. Как и у дампа — **без открытого фолбэка**: нет ключа → выгрузка снимка не выполняется.
3. **Запись.** `nightlyBackup.ts`: снимок шифруется перед `uploadFileStream`, имя `YYYY-MM-DD.sqlite.enc`. Ротация уже матчит `.enc` (сделано в #622).
4. **Чтение.** `routes/backups.ts`:
   - список парсит и `.sqlite`, и `.sqlite.enc`;
   - `GET /nightly/:date/url` — для `.enc` отдаёт ссылку на свой эндпойнт, для легаси-`.sqlite` по-прежнему прямую яндексовую (переходный период);
   - новый `GET /nightly/:date/download?t=<токен>` — стримит расшифрованное. Клиент качает **без auth-заголовков**, поэтому доступ по короткоживущему подписанному токену (HMAC на `MATRICA_JWT_SECRET`, срок минуты, привязан к дате снимка), а не по сессии.
5. **Тесты.** Round-trip кадрированного формата, отказ на подменённом байте в середине файла (проверка ловится на своём кадре, а не в конце), отказ на просроченном/чужом токене.
6. **Раскатка.** Прод: ключ в `.env` → build → ручной прогон `backup:nightly` → проверка живым клиентом (открыть бэкап за сегодня).

**Старые открытые снимки — не трогаем** (решение владельца 19.08): 10 файлов уйдут сами ротацией за 10 дней. Просмотр бэкапов за прошлые даты продолжает работать без перерыва; цена — открытые копии лежат на Яндексе ещё эти 10 дней.

**Гейты.** typecheck + lint + backend-тесты; живая проверка «просмотр бэкапа» в клиенте на шифрованном снимке.

**Риск.** Сломать «просмотр бэкапа» у парка. Снимается тем, что легаси-путь остаётся рабочим и переключение идёт по факту наличия `.enc`.

## 3. Справочники: общий механизм колонок + печать 🟡 M

**Что.** `NomenclatureDirectoryPage` (детали, инструмент, товары, марки двигателей, услуги) — настройка колонок есть **только** в ветке услуг; остальные виды рисуют жёстко зашитый `<thead>` (Код, Наименование, SKU, [Прикреплено деталей у марок], Дата изменения) и парный жёсткий набор `<td>`. Из-за этого в #626 печать туда не подключалась: кнопка в одном справочнике из пяти — хуже, чем её отсутствие.

**Решение владельца 19.08: переводить все виды каталога сразу**, включая марки двигателей — чтобы поведение справочников не расходилось.

**Шаги.**
1. Описать колонки массивом для не-сервисных видов (как уже сделано для услуг), с `printValue`/`printSkip` там, где текст из разметки получается плохим.
2. `useColumnLayout` с **раздельным `layoutId` на вид**: `list:nomenclature:<directoryKind>:columns`. Общая раскладка на все справочники слепила бы детали с марками — у них разный смысл колонок.
3. Единый рендер шапки и ячеек для всех видов — развилка `directoryKind === 'service'` в `renderTableHeader`/`renderRowCells` уходит; остаётся только состав колонок.
4. `ColumnSettingsButton` + кнопка «Печать списка» + `ListPrintDialog` — как на семи списках из #626.
5. `colCount` считать от видимых колонок + филлер (сейчас считается формулой по виду каталога).

**Гейты.** typecheck + lint + CDP-смоук: открыть «Детали», скрыть колонку → число `<th>` равно числу `<td>`; печать берёт видимые колонки.

**Побочная выгода.** Снимается развилка, из-за которой ветка услуг и остальные виды расходились в поведении, и остаётся один путь вместо двух.
