# План: MiniMax-воркер на проде «Матрицы РМЗ» для ИИваныча (промт КАРМАНА #56)

**Источник:** промт `#56` (задача) + `#57` (план) в разделе библиотеки промтов КАРМАНА `MatricaRMZ`;
задание пришло из Управляющего (meta-репо `brain_matrica`, область `p-brain2`) 22.11.2026.
**Решения владельца от 21.11 (приняты, не переигрываются):** воркер живёт **на боксе Матрицы РМЗ**;
доступ к комнате Кармана — **сервисным грантом на запись**, пишущий токен на бокс **не кладём**;
цепочка звеньев — **MiniMax на проде → платный DeepSeek последним** (fail-open, D-243);
контракт воркера — **Anthropic-совместимый `/v1/messages`**.

**Что сделано в этой нитке (код):** воркер целиком + транспорт бэкенда + юнит systemd.
**Что осталось за владельцем:** выдача токена пула в комнате, установка юнита на проде,
замер RAM, DNS-пин MiniMax, приёмка на живом вопросе.

---

## 1. Что за контур и почему он такой

У аккаунтов Кармана **нет пригодного публичного API** — вендор отвечает `401` + `2062 no active token plan
subscription` (ADR-0017 «Сарафана»). Очки чекина тратятся только в сценариях MiniMax Code. Значит воркер —
**не прокси к API**, а реализация семантики агента-CLI: он берёт аккаунт из пула Кармана, собирает профиль
CLI, запускает `mcode exec` и отдаёт ответ в Anthropic-совместимом виде.

Контракт ИИваныча при этом **не меняется**: очередь `ai_chat_requests`, воркер `startAiChatDirectWorker`,
4 мета-инструмента и строгий `tool_use`-JSON остаются как были. Правка — только в транспорте
(`llmProvider.ts`): бэкенд ходит в воркер тем же SDK, что и в DeepSeek.

**Цепочка звеньев (D-243):** `MiniMax на проде` → `платный DeepSeek` (страхователь, fail-open).
Отказ воркера (пул пуст, воркер лежит, агент не ответил) уводит запрос на DeepSeek и пишется в журнал —
молчаливого отката нет. `400/401/403` от воркера — **не** повод уходить: это наша ошибка или нет доступа,
и откат спрятал бы поломку.

## 2. Факты, на которых стоит код (сверено 22.11.2026)

### Карман — три ручки, и только три

| Ручка | Что делает | Отказ |
|---|---|---|
| `GET {base}/accounts/available` | выдача аккаунта: `{account:{id,email,activation_index,points_next,…}, tier, reason, access_token, expires_at_ms}` | `200` + `account:null` + `reason` (`no_free_accounts` / `no_handable_accounts`) — честная пустота, **не 404** |
| `POST {base}/renew` `{account_id}` | продлить цепочку токенов (access живёт ~12 ч) | `409` — аккаунт за другой комнатой или цепочка оборвана; `404` — нет в пуле |
| `POST {base}/activations` `{account_id\|email, points?, activation_index?}` | **наблюдение**: сколько очков было на токене | — |

Авторизация — `Authorization: Bearer skm_…` **токен комнаты с правом записи**; read-only → `403`,
недействительный → `401`, превышение лимита → `429`. Пометка потребителя — заголовки
`X-MiniMax-Project` / `X-MiniMax-Area` (аудит Кармана). **Ручки `release` нет: выдача = погашение.**
Свой пул и свою логику подбора не заводим — это зона Кармана (D-214, D-216).

### «Сарафан» — рабочий прецедент (клоны читались read-only)

- Токен-стор профиля: `<area>/data/auth/prod/en/mcode-public/auth.json`; ключ записи выводится из
  **абсолютного пути** каталога данных (`sha256(path + '\0' + 'mcode-public')` → base64url без padding),
  префикс `com.minimax.mcode.oauth.prod.en`. Рантайм отвергает запись без `refreshToken`, `generation`,
  `loginEpoch` — потому refresh Карман не отдаёт, пишется честная заглушка.
- Запуск агента: `mcode exec --permission off --output-format json --output-last-message <file>
  --system-prompt-file <file> --max-steps N --mode standard --timeout <sec> --model minimax/MiniMax-M3.1-Flash
  --file <payload> "<задание>"`. **`--output-schema` у MiniMax не работает** — формат задаёт промпт.
- Окружение: `MCODE_CONFIG_DIR` / `MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR`; прокси из окружения убираются
  (ломают вход, G536); `NODE_OPTIONS=--dns-result-order=ipv4first --max-old-space-size=320` (на боксе
  1536 МБ без потолка ядро снимает крупнейший процесс).
- Ответ приходит JSON-объектом в stdout (последняя JSON-строка): `status`, `output`, `usage`.

## 3. Что сделано

### Воркер — `backend-api/src/minimaxWorker/`

| Файл | Что |
|---|---|
| `config.ts` | env-конфиг; адрес ручек пула — `KARMAN_MINIMAX_API_URL` либо вывод из `SECRETS_VAULT_URL`; токен — из env либо **из комнаты Кармана** (ключ `KARMAN_MINIMAX_TOKEN`) |
| `karmanPool.ts` | клиент трёх ручек; **причины отказа разные**: `pool_empty` / `karman_unavailable` / `token_read_only` / `token_unauthorized` / `rate_limited` |
| `agentProfile.ts` | материализация профиля: токен-стор (ключ из пути), `config/`, `profile.json` |
| `minimaxAgent.ts` | сборка команды и окружения CLI, запуск, разбор ответа (`status`/`output`/`usage`) |
| `agentPrompt.ts` | запрос `/v1/messages` → промпт агента: правила Ииваныча + каталог инструментов + **контракт ответа** (строгий JSON) |
| `toolUseShaper.ts` | **главный кусок**: свободный текст агента → блоки `text`/`tool_use`; неизвестный инструмент отбрасывается, форма ответа видна в журнале |
| `server.ts` | `POST /v1/messages` (Anthropic-совместимый ответ) + `GET /health`; честные отказы: `503 pool_empty`, `503 token_missing`, `502` (агент не ответил) |
| `index.ts` | вход сервиса; фоновые джобы бэкенда **не поднимает** |

Тесты: `toolUseShaper.test.ts` (11), `karmanPool.test.ts` (10), `agentProfile.test.ts` (4),
`minimaxAgent.test.ts` (8), `server.test.ts` (8) — **41/41 зелёные**.

### Транспорт бэкенда

- `services/ai/llmProvider.ts`: провайдер `minimax` (`MATRICA_AI_PROVIDER=minimax`) → локальный воркер
  `http://127.0.0.1:3010`; **fail-open на DeepSeek** при отказе воркера (свой клиент-кэш, переключение
  липкое на весь агентный цикл); имя модели на проводе — `minimax-m3.1-flash`;
  `tool_choice` принуждением больше не используется (у воркера этого параметра нет).
- `services/ai/common.ts`: **одна строка** белого списка — `minimax-m3.1-flash` (без неё env-фильтр
  молча свёл бы запрос на flash, и воркер не позвали бы вовсе).
- `services/ai/aiChatAnswerService.ts`: `answerSource` теперь `engine | deepseek` — видно, какое звено
  ответило (колонка `answer_source` в БД это уже допускала, клиент это уже умеет показывать).

### Выкат

- `deploy/systemd/matricarmz-minimax-worker.service` — шаблон: `MATRICA_INSTANCE_ROLE=worker`
  (иначе поднялся бы второй набор фоновых задач и очередь ИИваныча разбиралась бы дважды),
  `EnvironmentFile=/etc/matricarmz/matricarmz.env`, порт только на `127.0.0.1`.
- `deploy/systemd/install-backend.sh` — юнит ставится тем же скриптом (плейсхолдеры только оттуда).

**nginx не нужен:** ходит к воркеру только бэкенд на том же боксе, наружу воркер не выставляется.

## 4. Что осталось за владельцем (прод без слов владельца не трогаем)

1. **Токен пула в комнате.** В комнате `matricarmz` положить ключ **`KARMAN_MINIMAX_TOKEN`** — токен комнаты
   Кармана **с правом записи** (`skm_…`). Рантайм читает комнату сам (`services/karmanVaultClient.ts`,
   кэш 5 минут) — переписывать `/etc/matricarmz/matricarmz.env` **не нужно**, и пишущий токен на бокс
   не кладём (в env остаётся только read-only `SECRETS_TOKEN`). Это и есть сервисный грант.
2. **Установить юнит на проде** (после выката кода с этим PR):
   `bash deploy/systemd/install-backend.sh` → `sudo systemctl enable --now matricarmz-minimax-worker.service`.
3. **MiniMax Code на боксе:** CLI (`MINIMAX_CLI`), каталог профилей `MINIMAX_ACCOUNTS_DIR`
   (по умолчанию `/opt/minimax-accounts`) и **DNS-пин MiniMax** (ADR-0017).
4. **Замер RAM:** контейнер 1536 МБ, swap запрещён; у Сарафана `mcode exec` — пик 381 МБ по node-процессам,
   потолок кучи `--max-old-space-size=320` вынесен в конфиг воркера.
5. **Включить звено:** `MATRICA_AI_PROVIDER=minimax` в `/etc/matricarmz/matricarmz.env` + рестарт primary.
   Пока переменная не задана, поведение прежнее — DeepSeek напрямую.
6. **Приёмка на живом вопросе:** вопрос оператора → ответ ИИваныча; в журнале воркера — какой аккаунт
   взят; в `answer_source` — `engine`; при пустом пуле — честный отказ и уход на DeepSeek (`deepseek`).

## 5. Осторожности (из плана #57, подтверждены кодом)

- **Пишущий токен Кармана — блокер**, и он снимается только действием владельца в комнате.
- **Свой пул не заводим** — вторая реализация правила разъезжается с первой (прецедент 09.11).
- **Выдача = погашение**: ручки release нет; аккаунт, на котором кончились очки, уходит в `exclude=`.
- **Один аккаунт — один потребитель**: `accounts_usage` уникален по `(account_id, used_on)`.
- **Второй набор фоновых задач**: юнит воркера обязательно `MATRICA_INSTANCE_ROLE=worker`.
- **Два env-файла на проде разошлись** (`/etc/matricarmz/matricarmz.env` против `backend-api/.env`) — новый
  юнит читает тот, что у него в `EnvironmentFile`.
- **Формат ответа хрупкий**: у MiniMax нет нативной схемы, поэтому слой `toolUseShaper` — условие
  работоспособности, а не украшение; каждое замечание разбора пишется в журнал воркера.
- **Anthropic SDK шлёт ключ как `X-Api-Key`, а не `Authorization: Bearer`** (последнее — только при
  `authToken`). Воркер принимает оба заголовка: иначе бэкенд, ходящий тем же SDK, получил бы `401` —
  а это по правилу fail-open **не** повод уйти на страхователя, то есть поломка была бы глухой.
  Ретраи SDK у воркера отключены (`maxRetries: 0`): отказ пула обрабатывает наш fail-open, иначе
  ожидание ушло бы в три попытки.
