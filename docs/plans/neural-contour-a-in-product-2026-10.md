# Контур A в продукте: серверный Ииваныч считает локальным движком прода (opencode)

> **Тип:** plan · **Статус:** done (прод 22.10; открыто вне плана: баланс DeepSeek и пилот на машине парка) · **Создан:** 2026-10-21 · **Отдельная нитка** (вне 3.85–3.87)
> Решение владельца 21.10: серверное звено цепочки Ииваныча — **opencode с прода**, а не DeepSeek.

## Зачем

Сегодня серверный Ииваныч отвечает через DeepSeek API (`backend-api/src/services/ai/llmProvider.ts`,
решение D-024). На проде стоит движок opencode (контур A: `opencode-web.service`, v2.0.32,
`127.0.0.1:49374`, HTTP Basic), но **продукт им не пользуется** — он существует как эксперимент
контура A. Владелец хочет, чтобы серверное звено считало нашим движком.

## Что мешает «просто переключить»

1. **Другой API.** Движок отдаёт session-API (`POST /api/session`, `POST /api/session/<id>/prompt`,
   `GET /api/session/<id>/message`), а не chat-completions. Текущий `llmProvider` к нему не подходит.
2. **Латентность.** Замер 20.10: реальный ответ free-модели — **96 с**. Держать HTTP-запрос
   клиента столько нельзя (nginx/прокси и сам оператор этого не переживут) → нужен
   **асинхронный путь**: бэкенд ставит задачу и опрашивает движок, клиент опрашивает бэкенд.
3. **Один IP на весь парк.** Free-тир считает лимиты по IP → очередь и честный признак «ждём
   лимит», иначе все машины одновременно получат `limit`.
4. **Инструменты.** Сейчас серверный Ииваныч ходит в PG своими `llmTools` (read-only SQL).
   Движку инструменты отдаются через MCP (как в контуре B — `aiMcpProxy.ts`), и это надо
   повторить на сервере, с тем же принципом «пишущий запрос отбивает сама БД».
5. **Сессии не персонализированы.** Движок общий: он не знает, кто спрашивает. Права/видимость
   полей остаются на стороне бэкенда — движку передаём уже отфильтрованный доступ.

## Предлагаемая схема

- Бэкенд — клиент session-API движка (Basic, токен из `/etc/opencode-web/anon.env`; в репо
  и в клиентских сборках токена нет).
- Задача Ииваныча ставится в очередь (одна на пользователя, общая на движок), состояние —
  `queued / running / done / limit / error`; клиент опрашивает свой статус.
- Инструменты — MCP-сервер на бэкенде с теми же правилами видимости, что у `llmTools`
  (таблица/поле → право), пишущие запросы отбивает СУБД.
- Лимит free-тира (`limit`, exit 2) — не ошибка: `queued` с признаком «ждём лимит», клиент
  показывает «сервер занят, попробую этот компьютер» → локальное звено.
- **Цепочка не меняется:** локальный движок → прод-opencode → DeepSeek (аварийно, если движок
  недоступен/лимит). DeepSeek остаётся последним звеном, пока владелец не решит иначе.
- Обновление движка на проде — **вручную по чек-листу** (после рестарта: health, пробный
  ответ модели, `systemctl is-active`, `/health` бэкенда).

## Код (сделано 21.10, PR «контур A в продукте»)

- `backend-api/src/services/ai/serverEngine.ts` — клиент session-API прода: выбор free-модели
  (`GET /api/model`, кэш 10 мин, env-оверрайд), сессия с deny-списком (`shell`, `bash`, `edit`,
  `write`, `read`, `glob`, `grep`, `webfetch`, `websearch`, …), промпт, опрос `/message` до `idle`,
  типизированные исходы `ok | limit | timeout | error | unavailable`, пауза после сбоя
  (лимит — 10 мин, прочее — 2 мин), чтобы следующие вопросы не платили минутами за мёртвое звено.
- `backend-api/src/services/ai/serverEngineTools.ts` — loopback-мост (127.0.0.1:49390,
  токен из `AI_SERVER_ENGINE_TOOLS_TOKEN`): `GET /tools` — каталог в форме MCP, `POST /tool` —
  исполнение тех же инструментов, что у DeepSeek, с правами спросившего сотрудника. Активный
  контекст один (`withEngineTask`), вне задачи инструменты отбиваются.
- `backend-api/src/services/ai/iivanychTools.ts` — три «продуктовых» инструмента
  (`escalate_to_admin`, `attach_table`, `save_learning_note`) вынесены из `aiChatAnswerService`,
  чтобы их видели оба пути ответа: у движка иначе не было бы эскалации.
- `backend-api/src/services/ai/aiChatAnswerService.ts` — `answerOne`: движок первым, DeepSeek
  последним; очередь больше не глохнет без ключа DeepSeek (движок сам себе звено).
- `scripts/prod-ops/install-engine-mcp.sh` + `scripts/prod-ops/engine-mcp/matrica-engine-mcp.cjs` —
  установка MCP-прокси движку (конфиг в `/home/opencode/.config/opencode/opencode.json`) и проверка,
  что `/api/mcp` видит сервер `matrica`.
- Тесты: `serverEngine.test.ts` (ok/limit/timeout/недоступен/перебор моделей + deny-права сессии),
  `serverEngineTools.test.ts` (нет токена → 401, каталог = инструменты DeepSeek + три наших,
  вне задачи — отказ, две задачи разом — ошибка).

### Сверено на живом движке прода (21.10)

- `POST /api/session` принимает `id/parentID/title/agent/model/location/metadata/permissions`;
  полей `mcp`/`tools` **нет** — инструменты задаются только конфигом движка.
- `/api/session/<id>/wait` → 404; готовность — сообщение `type: 'idle'` в `GET …/message`.
- `POST /api/session/<id>/prompt` ждёт `{ text }`; авторизация — HTTP Basic `opencode:<токен>`.
- `/api/config` → `[{"type":"directory","path":"/home/opencode/.config/opencode"}]`; каталог пуст,
  `/api/mcp` пуст — инструментов у движка не было до установки моста.
- Токен движка: `/etc/opencode-web/anon.env` (600 root, каталог не читается пользователем `valstan`),
  поэтому копия токена живёт в `/etc/matricarmz/matricarmz.env` (там же env бэкенда).

### Приёмка на проде 21.10 (вечер): что выяснилось живьём

- **MCP-мост работает от края до края.** Движок сам зовёт инструменты: в сообщениях сессии видны
  `matrica.query_nomenclature`, `matrica.get_engine_brands`, `matrica.escalate_to_admin` (движок
  оборачивает MCP-инструменты в свой `execute`-песочник, вызов идёт в прокси → мост → база).
- **Запрет файловых инструментов в правах сессии убивает free-тир:** `read/glob/grep/list` в
  `permissions` → `403 provider.auth` «free tier can only be used from within OpenCode» за 2 с.
  Список запретов сокращён до 12 действий; сторож в тесте держит это от «улучшений» (GOTCHAS M164).
- **Ошибку движка надо читать с любого сообщения:** `idle` с ошибкой приходит раньше `assistant`,
  из-за чего в лог попадало бесполезное «движок вернул failed». Исправлено (`failureOf`).
- **Пауза по балансу DeepSeek больше не крутит очередь вхолостую:** при включённом движке тик
  продолжается только если движок реально доступен (не в паузе) — иначе 402 летел каждые 2 с.
- **Баланс DeepSeek на проде — 402 `Insufficient Balance`** (на 21.10, до деплоя тоже). То есть
  последнее звено цепочки сейчас мертво: пока движок отвечает, оператор ответ получает; упал
  движок — ответа нет вовсе. Это вопрос к владельцу (пополнить ключ), а не к коду.
- Установка MCP движку проверяется не одним запросом: `/api/mcp` наполняется через несколько секунд
  после рестарта (движок подключает серверы лениво) — `install-engine-mcp.sh` теперь ждёт до 60 с.

### Приёмка контура A — пройдена 21.10 (после фикса free-тира)

Вопрос «сколько двигателей сейчас в работе?» прошёл весь серверный путь трижды (48–80 с):

- ответ по данным базы: **150** двигателей; тот же счёт прямой SQL-проверкой
  (`status_repair_started and not status_repaired and not status_customer_sent`) — **150**;
- инструменты вызваны: примеры в ответе — реальные карточки (`erp_engine_cards`), ссылка
  `[report:engines]` на отчёт;
- DeepSeek в это время мёртв (`/user/balance` → `is_available: false`, баланс `0.00`), значит
  ответить мог **только** движок — фолбэка в цепочке не было;
- в журнале бэкенда нет ни одной строки `server engine failed, falling back to deepseek` и ни
  одного 402 — то есть движок не падал;
- движок в это время писал свой WAL (`opencode.db-wal` менялся каждые 1–5 с) — сессия шла.

Уроки приёмки (в GOTCHAS M165):

- **в проде `logInfo` не пишется в журнал** (`MATRICA_LOG_MODE=prod` пропускает только warn/error),
  поэтому `ai chat direct: answered` в `journalctl` не видно **никогда**. Судить об успехе — по
  отсутствию ERROR и по активности движка, а не по отсутствию строки «answered»;
- копия `opencode.db` **без `-wal`** показывает устаревшее состояние (сессии живут в WAL до
  чекпоинта) — по ней нельзя заключать «движок не работал»; смотреть mtime `-wal`;
- строки приёмки, вставленные в `ai_chat_requests` напрямую, **уедут клиентам** (при закрытии
  `writeAiChatRow` присваивает `last_server_seq`): это видимый в окне Ииваныча технический диалог.
  Удаление — на прод-БД, только с подтверждения владельца.

**22.10 — метка источника ответа принята на проде.** Миграция `0114` применена (`db:migrate`,
колонка `answer_source text`), вопрос через серверный путь → строка `answered` с
`answer_source = engine`, `last_server_seq` присвоен (уехала клиентам). Ответ занял **160 с** —
free-тир отвечает неровно, и прежний потолок движка (150 с) обрывал почти готовый ответ;
потолок поднят до **240 с** (`AI_SERVER_ENGINE_TIMEOUT_MS`, дефолт в `serverEngine.ts`).

## Риски и границы

- **Скорость:** free-модель на проде медленная (96 с). Если окажется, что это не разово —
  честно вернуть DeepSeek первым серверным звеном (решение владельца, не наше).
- **Нагрузка:** движок ест ~340 МБ RSS; на проде живут два backend-инстанса, память бокса
  ограничена — очередь должна быть одна на движок, а не по инстансу.
- **Приватность:** запросы уходят бесплатным моделям (могут обучаться) — владелец это принял
  19.10; в UI серверного ответа оставляем ту же оговорку, что в локальном контуре.
