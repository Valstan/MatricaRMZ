# Производственная программа (ПП) — модуль плана производства на две недели / месяц 🗓 since:2026-11-09

**Заказ владельца (09.11.2026):** модуль-раздел создания и учёта выполнения производственных программ на основе Word-формы цеха №1. Выбирать контракты, подбирать из них двигатели для первоочередного ремонта, подсказывать, какие двигатели взять (а какие ещё не приехали на завод или уже уехали), вести состояния строк, печатать форму аккуратно (шрифт не меньше 14), разделять военные и гражданские контракты, ставить состояния вручную, подписи брать из документа, а если такой должности нет — подставлять название.

## Образец (Word-форма)

Снят с файла «ПП Цех _1 с 01.11 по 15.11.2026.docx»:

- шапка: «УТВЕРЖДАЮ / Директор _____________ И.А. Тихомиров», заголовок «ПРОИЗВОДСТВЕННАЯ ПРОГРАММА (ЦЕХ № 1)», период «Ноябрь 2026 г. (01.11-15.11)»;
- таблица, 7 колонок: «№ п/п | Организация | Марка и номер двигателя | Состояние | Отгрузка | Факторы, влияющие на выполнение плана | Примечание»;
- строки сгруппированы по договорам (строка-шапка группы: организация + номер договора);
- состояния строк: **Восстановление**, **Ремонтопригодный**, **Капитальный ремонт** — таких значений в программе нет, это поля плана, ставятся вручную;
- подписи: Коммерческий директор (Беркута А.А.), Технический директор (В.И. Гурьянов), Зам. директора по основному производству (А.А. Габдуллин), Начальник цеха №1 (И.К. ## Решения (приняты 09.11.2026)

1. **Две таблицы, не EAV.** EAV под заморозкой (с 18.08.2026) — новые атрибуты карточек не заводим.
   - `erp_production_programs`: период (начало/конец), цех, заголовок, статус (`draft`/`approved`), `signature_slots` (jsonb: должность + ФИО + привязанный сотрудник), служебные поля синка.
   - `erp_production_program_rows`: программа, № п/п, договор, строка-шапка группы, снимок вида договора, двигатель, марка, номер, **состояние** (`restoration`/`repairable`/`capital_repair`), плановая отгрузка, факторы, примечание, служебные поля синка.
   - Отдельной таблицы групп нет: группа = (договор, строка-шапка), UI группирует по договору.
2. **Состояния — только поля плана.** В статусы двигателей они не пишутся: «Капитальный ремонт» по гражданским, «Восстановление»/«Ремонтопригоден» по военным (у владельца: «Военные договоры это восстановление (если утиль) и ремонтопригоден»).
3. **Подсветка печати:** основная — «готов к отгрузке» (прошёл обкатку и ОТК, но не отгружен): за этим следят. Отгруженные строки — грифом «Отгружен» без заливки, иначе весь план «позеленеет» и подсветка перестанет что-то значить. (Владелец спросил, что лучше — выбрано первое.)
4. **Подписи — строки подписей модуля, а не карточки сотрудников.** Вносить этих людей в кадровый реестр нельзя: это засоряет реестр сотрудников и попадает под гейт дублей по полному ключу (запрет 09.11.2026). Поведение: сначала ищем сотрудника по должности (как `findEmployeeByPositionGroups`), нашёлся — печатаем ФИО из карточки; не нашёлся — печатаем ФИО из образца. Проверено в базе: в дев-базе должностей-подписантов ПП нет (4 сотрудника, справочник должностей пуст) — значит, режим «ФИО из документа» будет рабочим уже сейчас.
5. **Колонка «Отгрузка»** — плановая дата вручную; факт отгрузки подтягивается из карточки двигателя (для подсказок и подсветки).

## Заводская линза

`Заводская линза: планирование производства (ПП) · затор: не касается (ПП не разбирает детали и не трогает начало сборки — а это главный затор по модели) · поток: не ломает — обезличивание деталей и ремфонд как общая «куча», партия/экземпляр (stamped_number) и маршрутный лист не затрагиваются.`
