# M234 — Проверки не запускаются на PR в конфликте: «no checks reported» — это не «CI считает» и не «форс-пуш сломал»

**Область:** PR-flow с GitHub Actions (`gh pr checks`, `gh pr merge`) в репо, где одновременно
работают несколько линий и `main` уезжает между открытием PR и мержем.

- **Симптом:** `gh pr checks <num>` печатает **«no checks reported on the '<ветка>' branch»**
  (либо пустоту) — проверок нет, красных нет, жёлтых нет. `gh run list --branch <ветка>`
  показывает прогоны **старого** коммита (по push'у до ребейза) и **ни одного** — по текущему
  SHA. `gh api repos/…/actions/runs?head_sha=<SHA>` → `total_count: 0`.
- **Корень:** совпало с тем, что PR **в конфликте с `main`** (`gh pr view --json mergeable` →
  `CONFLICTING`, `mergeStateStatus: DIRTY`): пока ветка не переведена на свежий `origin/main`,
  check-suite для нового коммита не создаётся, и `pull_request`-событие до workflow не доходит.
  Отличительный признак: в `gh api repos/…/commits/<SHA>/check-suites` видны только
  сторонние приложения (Travis, Cursor, Render, Claude) — **Actions-сьютов нет вовсе**.
  Связь с конфликтом замечена по совпадению (отдельной проверки платформы не делалось), но
  воспроизводится однозначно: после ребейза проверки появляются сразу.
- **Диагностика:** (1) `gh pr view <num> --json mergeable,mergeStateStatus` — `CONFLICTING`
  ⇒ дело не в CI; (2) `gh api repos/…/actions/runs?head_sha=<SHA>` — ноль прогонов по текущему
  SHA ⇒ workflow не триггерились; (3) `gh api repos/…/commits/<SHA>/check-suites` — Actions
  отсутствует, сторонние приложения на месте.
- **Лечение:** `git fetch origin && git rebase origin/main` → разрешить конфликт вручную →
  `git push --force-with-lease` → проверки появляются сразу (событие `synchronize`).
  Пока PR в конфликте, гейт **не проверять**: он не красный, потому что его не на чём было
  считать — «нет проверок» ≠ «проверки зелёные».
- **Понятки:** 2026-11-26, полоса 1 (машина **PC79**), промт КАРМАНА #143. PR **#2059**
  (доводка правила бота) попал в конфликт после мержа соседних полос — #2055, #2057, #2058,
  и все три тронули `docs/SESSION_HANDOFF.md`. `gh pr checks` дважды ответил «no checks
  reported», и это сначала выглядело как «Actions не триггерится на форс-пуш»; на деле
  конфликт был снят ребейзом — и проверки пошли сразу. Побочно вскрылось второе правило:
  **локальный прогон гейта относится к состоянию кода на момент прогона** — тип-ошибка,
  внесённая ПОСЛЕ прогона `typecheck`, всплыла только на CI.
- **Правило на будущее:** пустой ответ `gh pr checks` — это не «ждём» и не «CI сломан», а
  **вопрос к состоянию PR**. Первым делом `mergeable`: в конфликте — ребейз на свежий
  `origin/main`, и только потом гейт. И гейт, прогнанный локально, перестаёт быть гейтом
  для кода, который правили после него.
