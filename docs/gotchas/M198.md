# M198 — Мигратор drizzle пропускает запись, у которой метка `when` в журнале старее последней применённой

**Область:** миграции БД (`backend-api/drizzle/meta/_journal.json`), `db:migrate`

- **Симптом:** миграция добавлена (файл `.sql` есть, запись в `_journal.json` есть),
  `db:migrate` отрапортовывает `[backend-api] migrations applied` — **но на базе нет ни
  таблицы, ни столбца, ни строки справочника**. На стенде это выглядело как «миграция
  0128 не применилась, хотя все отчёты зелёные». Проверено 11.11.2026 на миграции
  `0128_repair_stage_arrival_reclamation.sql`.

- **Корень:** мигратор drizzle **не сверяет содержимое**, а идёт по полю `when` в
  `meta/_journal.json`: применяются записи, у которых `when` **больше** метки
  последней применённой миграции (`drizzle.__drizzle_migrations.created_at`). Метка
  новой миграции, взятая «по системным часам в момент её создания», может оказаться
  **раньше** метки уже применённой миграции — например, когда релизную миграцию
  (`0127`, метка на 18:00) добавили раньше, а новую (`0128`) создали в тот же день, но
  по часам машины раньше 18:00. Тогда мигратор тихо считает её уже применённой и
  **ничего не делает** — без ошибки и без внятного предупреждения.

- **Диагностика:** (1) сравнить, что просит журнал, с тем, что лежит в базе:

  ```sql
  select id, created_at from drizzle.__drizzle_migrations order by created_at desc limit 3;
  ```

  (2) посмотреть метки последних записей `_journal.json`: если `when` новой записи
  **не больше** метки последней применённой — вот и причина; (3) убедиться, что
  сама миграция действительно не применена: `\d <таблица>` / `select … from
  repair_stage_templates where code = '<код>'`.

- **Лечение:** ставить метку новой миграции **строго за** меткой последней применённой
  (не «сейчас по часам», а «последняя + 1»):

  ```bash
  node -e "const fs=require('fs');const p='backend-api/drizzle/meta/_journal.json';
    const j=JSON.parse(fs.readFileSync(p,'utf8'));const last=j.entries[j.entries.length-1];
    j.entries.push({idx:last.idx+1,version:'7',when:last.when+1000,tag:'<тег>',breakpoints:true});
    fs.writeFileSync(p,JSON.stringify(j,null,2)+'\n','utf8');"
  ```

  Миграция, **изменённая после применения**, в журнале не переигрывается — поэтому
  «починить» уже применённую миграцию нельзя: нужна новая.

- **Проверка после выката:** не только «`db:migrate` отрапортовал», а **факт на
  базе**: строка справочника/столбец/таблица существует и заполнен ожидаемым
  числом строк. Это же относится к переносам данных: `stages:backfill-reclamations`
  (26 строк) — отчёт переноса читается вручную, а не по «applied».
