# M197 — Express 4: отклонённый промис async-обработчика вешает запрос навсегда (не 500, а тишина)

**Область:** серверные двери (Express 4), любой async-обработчик маршрута

- **Симптом:** оператор жмёт «Сохранить очередь рекламаций» — «ничего не сохраняется».
  В логах сервера нет ни ошибки, ни 500: запрос уходит, ответа нет никогда, клиент
  отваливается по своему таймауту. В базе при этом строки появляются — но не те, что
  ожидали. Проверено на стенде 11.11.2026: `PUT /engine-reclamations/:id` с очередью,
  у которой уже есть строка №1, **висел** 40+ секунд вместо ответа 400.

- **Корень:** Express 4 **не ловит отклонённый промис** async-обработчика. Обработчик
  `async (req, res) => { … throw … }` не передаёт ошибку в `next(err)`, потому что
  Express 4 вообще не ждёт промис из обработчика: ошибка уходит в «никуда», а ответ
  клиенту не отправляется **никогда**. Это не «500 при ошибке», это «висящий запрос» —
  и выглядит как «программа не работает», а не как «запись не прошла».
  Второй слой: упавшая операция может быть частью составной — запись в очередь
  прошла, а падение случилось на шаг позже (уникальный индекс, FK, валидатор), и
  клиент видит «ничего не сохранилось», хотя часть данных записана.

- **Диагностика:** (1) отличить «виснет» от «падает»: клиентский таймаут без
  ответа + пустой лог сервера = этот случай; (2) найти запрос в логах доступа: он
  есть, а ответа нет; (3) воспроизвести локально: `curl --max-time 40 -X PUT …` —
  соединение закрывается по таймауту без ответа; (4) посмотреть в базе, что записано
  частично: строки, созданные до падения, остаются (у нас так остались три строки
  очереди с одним `queue_no`).

- **Лечение:** (1) **каждый async-обработчик обернуть** в обёртку, которая переводит
  отказ в `next(err)` — иначе Express отвечает 500 с текстом, а не тишиной:

  ```ts
  const wrap = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
  ```

  Либо один раз обернуть слои маршрутизатора (`router.stack`), чтобы не искать
  непойманные async-обработчики по всему проекту (у нас это сделано в
  `backend-api/src/utils/asyncForward.ts` + вызов в `app.ts`); (2) поймать падение
  **внутри** составной операции и откатить/не применять частичные изменения:
  ошибка на шаге «вставить строку» не должна оставлять документ в промежуточном
  состоянии; (3) клиент не должен считать «таймаут» = «не сохранилось»: он должен
  различать «сервер не ответил» и «сервер ответил ошибкой» — и говорить оператору
  прямо, что запись могла не сохраниться.

- **Связано с [M197](M197.md) и память проекта:** `docs/PENDING_FOLLOWUPS.md` не
  содержит пункта об этом — ловушка выглядит как «рекламация не работает», а на
  самом деле это общий класс Express 4. **Обходной путь для владельца парка:** если
  оператор говорит «нажал, а не сохранилось», первым делом спросить, висел ли
  запрос — и искать в базе частично записанные строки, а не перезаписывать их.
