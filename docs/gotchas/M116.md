# M116 — «уходит в error, чтобы выйти из вечного цикла» не работает: строку воскрешает соседняя функция

**Область:** sync / dead-letter

- **Симптом:** сервер сутками пишет `sync dependency rows skipped` про ОДНИ И ТЕ ЖЕ строки одного клиента, каждые 40 секунд. На клиенте — ни ошибки на экране, ни записи в диагностике. Работа оператора (у нас — четыре листа деталей двигателя за 20.08–31.08) не доезжает до сервера и не видна нигде, кроме чужого счётчика.
- **Корень:** лечение было написано (`planDependencyRequeue` → `markPendingError`), но двадцатью строками ниже в том же файле `recoverErroredRows` возвращает в `pending` любую `error`-строку, которая **проходит по схеме**. А сломана не схема — сломано отсутствие родителя. Цикл замыкается: push → skip → error → recover → push.
- **Почему держалось:** обе функции по отдельности правильны и обе покрыты смыслом («не терять строки из-за разовой невалидности» против «не гонять безнадёжные вечно»). Тест был на первую, вторая её отменяла — и ни один гейт не спрашивает «а не отменяет ли соседний код это лечение».
- **Побочный эффект, дороже самого цикла:** журнал пишется ДО применения (`syncWriteService`: `signAndAppendDetailed` → `applyPushBatch`), поэтому в журнал ложится КАЖДАЯ отвергнутая попытка. 29 таких строк дали 65 069 записей — 5,6% журнала (861 МБ), +6 000 записей в сутки от одного клиента.
- **Диагностика:** `journalctl -u matricarmz-backend-primary --since '24 hours ago' | grep 'sync dependency rows skipped'` → свернуть по `table|dependency|user` и сравнить **сумму `missing`** с числом различных `row_ids`. Если различных единицы, а сумма тысячи — это цикл, а не потеря данных. Проверка «строка вообще доезжала?»: `select count(*) from ledger_tx_index where row_id=…` против наличия строки в проекции.
- **Лечение:** карантин (`electron-app/src/main/services/sync/blockedRows.ts`) — состояние, из которого `recoverErroredRows` не воскрешает; выход один — зависимость появилась локально либо строка перестала быть `error`. Плюс доклад на сервер один раз на строку (`client.sync.blocked_rows`), чтобы застрявшая работа была видна на своей машине, а не только по чужому симптому.
- **Поймано:** 2026-09-08 разбором ночного алерта. Родня: M103 (отсутствие улики — не улика), M52 (строка `synced` без подтверждения сервера).
