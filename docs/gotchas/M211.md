# M211 — строки, вставленные миграцией, до парка не доезжают: `sync_status = 'synced'` снимает их с публикации

**Область:** синхронизация / зеркало клиента / миграции-сиды

- **Симптом:** в программе всё верно — интерфейс кладовщика показывает приказные нормы, добавленные миграцией, — а **напечатанный бланк выдачи** на клиенте парка выходит без этих строк. В журнале синхронизации строк нет. Всё выглядит как «клиент не обновился».
- **Корень:** миграция вставляет строки с `sync_status = 'synced'` (так написаны все сид-миграции приказа о СИЗ: 0118–0122). Публикатор зеркала СИЗ (`backend-api/src/services/sync/ppeSyncPublisherService.ts`) выбирает строки условием `sync_status <> 'synced'` — признак «не опубликовано» несёт сама строка. Миграция идёт **мимо пути записи синхронизации** (`writeSyncChanges`), поэтому её строки не получают номера журнала и в журнал не попадают НИКОГДА.
- **Как выглядит масштаб:** на проде (17.11.2026) в журнале лежало 220 строк приказа из 241, 49 наборов норм из 63 и 333 позиции номенклатуры СИЗ из 424. То есть **все строки миграций 0119–0121** (4 новые профессии, 13 заводских норм, 48 позиций номенклатуры) до парка не доехали, хотя в интерфейсе они были видны.
- **Почему это долго не замечали:** интерфейс кладовщика читает приказ **по серверу** (REST `/ppe/*`), а печать бланка и отчёты — **по локальной реплике клиента**. Данные расходились только в одном месте — в том, из которого делают бумажку.
- **Лечение:** скрипт `backend-api/src/scripts/publishPpeSeedToMirror.ts` (`pnpm -F @matricarmz/backend-api ppe:publish-seed -- --apply`) публикует в журнал то, что уже есть в базе: номенклатуру СИЗ → профессии → приказные строки → наборы норм → строки наборов, в порядке зависимостей (клиент применяет строки по номеру журнала, и строка набора должна прийти после своей номенклатуры). Удалённые строки уходят тумбстоунами (`op = 'delete'`), поэтому в реплике их тоже не остаётся.
- **Общая форма:** **сид-миграция — это запись в базу, а не запись в журнал синхронизации.** Если таблица зеркалится, строки сида надо доставить до журнала отдельно, иначе реплика клиента молча останется неполной. Проверка «сколько строк таблицы есть в журнале» — дешёвый тест на этот класс расхождения.
- **Поймано:** 2026-11-18, при сверке сида приказа о СИЗ с официальной ЕТН (миграция 0122): строки приказа из миграций 0119–0121 не доезжали до парка, и миграция 0122 усугубила бы это. Скрипт публикации и проверка журнала — в PR #1788.
