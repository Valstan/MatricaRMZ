# M104 — блок в цепочке ledger ≠ состоявшаяся транзакция: «блок-призрак» после обрыва в `appendBlock`

**Область:** ledger / целостность

- **Симптом:** пересборка состояния из блоков (`ledger:rebuild-state`) даёт `DATA_DIVERGENCE` по `attribute_values`: 767 строк есть только в цепочке, 190 — в цепочке новее, чем в `state.json`. Все — из одного блока `386592` (13.08.2026 13:51 UTC, seq 1360011…1361010, 1000 транзакций массового push'а). В PG этих строк нет, в `ledger_tx_index` ровно этот диапазон seq отсутствует (по корзинам 1000: …1000, **588, 412**, 1000…), в проекции их тоже нет.
- **Корень:** порядок в `appendBlock` (`ledger/src/store.ts`): файл блока → `saveIndex` → `loadState`/`applyTxs`/`saveState` → и только потом, уже вне ledger'а, применение пакета в PG (`syncWriteService.ts`, шаг 2) и `ledger_tx_index` (шаг 3). Обрыв процесса между записью блока и `saveState` (тут — M79: `JSON.stringify` проекции на 194 МБ при массовом push'е) оставляет блок и продвинутый индекс, а транзакции не применяются **нигде**. Клиент получает ошибку и повторяет push уже с новыми seq — цепочка хранит и провалившуюся попытку, и удачную.
- **Чем опасно:** любая «пересборка из цепочки» или «доказательство по цепочке» воскресит транзакции, которые рабочее хранилище не принимало. Цепочка — **не надмножество истины**, а журнал попыток. Сверять пересборку надо с PG, а не только с проекцией; «блок есть» — ещё не «данные были».
- **Как ловится:** `ledger_tx_index` по корзинам seq — провал ровно в один блок; `last_server_seq` строк PG по тому же диапазону — тот же провал; проекция по `per-block` сверке — тот же блок. Три независимых свидетеля на один диапазон.
- **Родня:** зеркальный случай — записи в PG **мимо** ledger'а (скрипты миграций пишут прямо в таблицы: 1147 `operations` за 05.2026 с `last_server_seq IS NULL`, мягкие удаления при старом seq). Обе дыры смотрят в разные стороны, и ни одна не видна из самой цепочки.
- **Поймано:** 2026-09-04 вторым, полным прогоном `rebuild-state` на проде. Разбор — `PENDING_FOLLOWUPS.md` §«Второй прогон rebuild-state».
- **Закрыто (вариант А, 05.09.2026):** все 1000 `row_id` блока сверены с PG (767 нет, 190 старше блока, 43 обновлены клиентом позже другими seq; ни у одной `updated_at` не равен метке блока). Блок записан в `KNOWN_GHOST_BLOCKS` (`rebuildLedgerStatePlan.ts`) — пересборка его читает, называет и **не применяет**. Сам `rebuild-state` больше не судит о данных (вердикт только о читаемости цепочки); сверка «цепочка ↔ PG» по открытому тексту — `resnapshot-state --chain-rebuilt`.
