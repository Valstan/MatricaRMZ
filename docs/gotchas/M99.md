# M99 — таблица выглядит пустой/мёртвой в `pg_stat_user_tables`, а в ней десятки тысяч строк

**Область:** БД / прод-аудит

- **Симптом:** обзорный запрос `select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc` на проде показывает `attribute_values` 489 строк (реально 45 116), `directory_parts` 0 (реально 1201), `change_log` 0 (реально 162 670) при размере таблицы 60 МБ. Вывод «таблица мёртвая, читатель висит на пустоте» строится на песке.
- **Корень:** `n_live_tup` — **оценка**, которую обновляют autovacuum/ANALYZE. После массовых правок (миграции EAV→строгие таблицы, бэкфиллы) она расходится с фактом на порядки и живёт так, пока не придёт autoanalyze. Размер (`pg_total_relation_size`) при этом честный — отсюда и характерная примета: «0 строк в таблице на 60 МБ».
- **Диагностика:** приметой служит расхождение размера и счётчика. Настоящие счётчики по всем таблицам разом:
  ```sql
  select c.relname,
         (xpath('/row/cnt/text()', query_to_xml(format('select count(*) as cnt from %I.%I', n.nspname, c.relname), false, true, '')))[1]::text::bigint as rows,
         pg_size_pretty(pg_total_relation_size(c.oid)) as sz
  from pg_class c join pg_namespace n on n.oid = c.relnamespace
  where n.nspname = 'public' and c.relkind = 'r'
  order by 2 desc;
  ```
  (Через `pg_stat_user_tables` тот же запрос падает на `__drizzle_migrations` — её нет в `public`.)
- **Лечение:** в аудитах «что живо, что мертво» брать `count(*)`; `n_live_tup` годится только для прикидки порядка **свежепроанализированной** таблицы.
- **Урок шире случая:** оценка, названная как факт (`n_live_tup` = «live tuples»), читается как факт. Прежде чем строить на числе вывод «источник мёртв», спроси, кто и когда его посчитал.
- **Поймано:** 2026-09-03, первый прогон проверки перекосов (пункт 14 владельца): по статистике половина `directory_*` выглядела пустой — при том, что нитка parts на них и стоит.
