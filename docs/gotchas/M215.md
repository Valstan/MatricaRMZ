# M215 — SAST-гейт цепляется к cleartext-HTTP в смоук-скриптах; `nosemgrep` работает только в той же строке

**Область:** CI · SAST (semgrep) · смоук-скрипты `.claude/skills/verifier-electron/scripts/`

- **Симптом:** PR уходит в CI зелёным по всем джобам, кроме `SAST (semgrep)`: `1 Code Finding`, `typescript.react.security.react-insecure-request.react-insecure-request` — «Unencrypted request over HTTP detected», строка в `.mjs`-скрипте смоука. Гейт блокирующий на PR (`--baseline-commit`), на `main` — полный скан, неблокирующий.
- **Корень:** правило из `p/react` ловит `fetch`/`axios` с URL по `http://`. Смоук-скрипты ходят по loopback (`http://127.0.0.1:<порт>`) — это стенд, а не браузерный код приложения, но правило смотрит только на схему, а не на адрес.
- **Лечение:** точечный `// nosemgrep: typescript.react.security.react-insecure-request.react-insecure-request` **в конце той же строки**, где вызов (как в `App.tsx`, `ChatPanel.tsx`, `backend-api/src/database/db.ts` — см. [M57](M57.md)). Комментарий **над** строкой не работает: semgrep глушит только находку на строке с директивой. Рядом — короткое объяснение, почему cleartext здесь уместен.
- **Почему это молчало:** локальные гейты (тесты, lint, typecheck) про такой файл ничего не говорят — скрипты смоуков не входят в typecheck/lint-контур. Ловится только на CI, и только на PR.
- **Диагностика (быстро, без прогона CI):** semgrep ставится в отдельный venv вне репо — `python -m venv %TEMP%\semgrep-venv; %TEMP%\semgrep-venv\Scripts\python.exe -m pip install semgrep`, затем прогон с теми же конфигами, что и в `.github/workflows/sast-semgrep.yml`:
  `semgrep scan --config p/security-audit --config p/secrets --config p/nodejs --config p/react --config p/typescript --severity ERROR --severity WARNING --exclude dist --exclude node_modules --exclude '*.test.ts' --metrics off --no-git-ignore --json <файл>`.
  Проверить все файлы PR разом: `git diff --name-only origin/main...HEAD`.
- **Правило (главное):** новый смоук-скрипт с сетевыми вызовами к стенду проверяется **локальным semgrep до пуша**, а не после красного CI. Прочие `fetch` по `http://127.0.0.1` в старых скриптах — в базовой линии гейта и не мешают; блокирует именно **новый** файл.
- **Замечено:** 19.11.2026, PR #1809 (смоук по узкому праву на размеры сотрудника). Правило сработало на одной строке из трёх одинаковых по форме вызовов — почему именно на одной, semgrep не объясняет; глушить надо все `http://`-вызовы нового файла, иначе следующая версия semgrep выстрелит по другой строке.
