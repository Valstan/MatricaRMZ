# M227 — «очередь застряла», а сервер всё отвергает молча: подтверждённая строка возвращается в очередь по кругу

**Область:** клиент (`electron-app/src/main/services/syncService.ts`) + сервер (`backend-api/src/services/sync/applyPushBatch.ts`), любая таблица реплики, где серверная копия совпадает с присланной (no-op)

- **Симптом:** алерт «🚨 Матрица РМЗ: очередь отправки на сервер застряла» повторяется каждые 10–30 минут с ОДНИМ И ТЕМ ЖЕ числом строк и одной и той же «самой старой» меткой времени; строки висят сутками. При этом: сервер их **не отклоняет** (в журналах обоих инстансов ни отказа по правам, ни LWW, ни dependency-скипа), **данные на сервере уже есть** (те же значения и та же `updated_at`), а курсор pull'а стоит на голове журнала — клиент полностью синхронизирован. Инцидент PC63 (17–25.11.2026): 4 строки `attribute_values` в карточке сотрудника «Викулов Александр Анатольевич», `errorCount` = 0, алерт шёл неделю.
- **Корень:** две поломки, обе про «строка ушла, но клиент её не отпустил».
  1. **Сервер (до 25.11.2026):** отброс строки по LWW на уровне ПАРЫ (`entity_id` + `attribute_def_id`) шёл **молча** — строка выпадала из батча, в `skipped` не попадала, клиент о ней не узнавал. Отказ по ID-уровню в это же место назывался (`lww_rejected`), а отброс по паре — нет.
  2. **Клиент (всегда):** `markAllSynced` ставит подтверждённой строке только `sync_status='synced'`, **не проставляя `last_server_seq`**. Номер строки приходит с pull'ом — но сервер для no-op строки номер **не меняет** (журнал — лог изменений, содержимое не изменилось ⇒ записи нет), а pull отдаёт только строки **новее курсора** ⇒ номер не приходит никогда. Самолечение `requeueUnconfirmedRows` (M52, «отправлено, но сервером не подтверждено») считает такую строку неподтверждённой и **возвращает в `pending`** — по кругу, без конца.
- **Почему молча:** обе поломки не оставляют следов ни в журнале сервера (строка не «отклонена», а просто не применена), ни в журнале клиента (ошибки нет — сервер ответил «ок»). Ошибку показывает только счётчик застрявших строк; данные при этом верные.
- **Диагностика:** 1) снимок диагностики клиента (`diagnostics_snapshots`, `scope='client'`): `pendingCount` по таблице и `oldestPendingAt`; 2) сервер: та же пара `(entity_id, attribute_def_id)` — есть ли строка и с каким `updated_at`/`last_server_seq`; 3) журналы обоих инстансов: **нет** отказов ⇒ дело не в правах и не в конфликте, а в подтверждении; 4) `last_server_seq` серверной строки **ниже курсора клиента** ⇒ pull её не привезёт ⇒ подтверждения не будет.
- **Лечение:** (1) сервер — отброс по паре называть `lww_rejected` (`applyPushBatch.ts`), тогда клиент снимает `pending` по этой причине; (2) клиент — помнить строки, подтверждённые сервером (ответ `applied_rows`), и не возвращать их в очередь в `requeueUnconfirmedRows`; (3) разовая починка боевой машины — команда `force_full_pull_v2`: полная пересборка реплики привозит строки с номерами, и очередь снимается сама (на PC63: 4 → 0 за 9 минут, реплика после пересборки совпала с сервером по всем типам).
- **Поймано:** 2026-11-25, разбор машины PC63 (оператор-кладовщик, 4 строки `attribute_values` неделю). Сторож: `backend-api/src/tests/syncSkipLogging.guard.test.ts` (отброс по LWW назван), юнит `electron-app/src/main/services/sync/confirmedRows.test.ts` (подтверждение сервера не отменяется).
- **Правило на будущее:** **«сервер молча не применил» и «клиент не отпустил» — разные поломки, и обе выглядят как «очередь застряла».** Симптом один (число строк в pending), а лечатся по-разному: первая — назвать отказ, вторая — не возвращать подтверждённое в очередь. Проверять обе.
