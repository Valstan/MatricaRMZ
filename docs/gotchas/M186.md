# M186 — новая серверная таблица: данные на сервере есть, клиент их не видит — а издатель тем временем дублирует их каждый тик

**Область:** [M186](#m186--новая-серверная-таблица-данные-на-сервере-есть-клиент-их-не-видит--а-издатель-тем-временем-дублирует-их-каждый-тик)

- **Симптом (две половины одного шва):** (1) на сервере строки новой таблицы лежат, а клиент их не видит — ни ошибки, ни лога; (2) журнал синхронизации (`ledger_tx_index`) пухнет: одна и та же строка даёт по одной записи **каждые 60 секунд**. 03.11.2026 на проде: 111 записей журнала на одну строку `ppe_employee_cards` за полтора часа, при этом `sync_status='pending'` и `last_server_seq IS NULL` — то есть строка и не опубликована, и не проштампована.
- **Корень:** серверная таблица-зеркало должна стоять в **трёх** местах сразу, и пропуск любого из них даёт свою поломку:
  1. `SERVER_MIRROR_TABLES` (`backend-api/src/services/sync/applyPushBatch.ts`) — обработчик, который снимает `sync_status='pending'` и штампует `last_server_seq`. Без него издатель (`ppeSyncPublisherService`) шлёт строку в журнал каждый тик заново — **журнал пухнет**, клиент получает дубли;
  2. `PG_SYNC_TABLES` (`pgSyncTables.ts`) — полный снимок для холодной реплики. Без него свежая машина остаётся без модуля целиком;
  3. `pullChangesSince.ts` — инкрементальный pull (`last_server_seq > since`). Без него живой клиент строки не получает **никогда**.
  Штамп и снятие `pending` — одна операция: номер журнала не должен лежать на чужом содержимом, поэтому снимать `pending` можно только той же транзакцией, что записала строку.
- **Почему не поймали раньше:** каждый PR серии был зелёный. В PR #1554 четыре таблицы приказа о СИЗ внесли в две карты pull (2 и 3) и забыли в первом (1) — а сторож `mirrorTables.guard.test.ts` проверял только направление «зеркало → обе карты pull». Обратное направление — «издатель публикует таблицу, а её нет в зеркалах» — не проверял никто, поэтому пропуск проходил молча.
- **Лечение случившегося:** (1) внести таблицы в `SERVER_MIRROR_TABLES`; (2) строки, уже лежащие в PG без номера, — проштамповать через журнал: `corepack pnpm -F @matricarmz/backend-api sync:restamp -- --tables=<table>` (dry-run) → `sync:restamp:apply -- --tables=<table>`; (3) строки, залитые в таблицу мимо журнала, — перевести в `pending` отдельной миграцией, иначе издатель их не подхватит.
- **Чтобы не повторилось:** `backend-api/src/services/sync/mirrorTables.guard.test.ts` — сторож на **обе** стороны шва: каждая таблица зеркала есть в обеих картах pull, и каждая таблица, которую публикует издатель СИЗ, — зеркало. Проверен «на зуб»: с убранной из `SERVER_MIRROR_TABLES` `PpeOccupationRef` тест краснеет с внятным сообщением.
- **Порядок выката (AGENTS.md §Release process):** сначала код с обработчиком зеркала, **потом** миграция, переводящая строки в `pending`, **потом** отдельный шаг публикации для таблиц без своего издателя (`sync:restamp`). Обратный порядок (миграция → код) даёт окно, в которое издатель наполняет журнал дублями.
- **Сторожа:** `backend-api/src/services/sync/mirrorTables.guard.test.ts` (4), `backend-api/src/services/sync/syncTableAppliers.guard.test.ts` (3).
- **Пул:** [M179](M179.md) — «новая таблица контракта: клиент выбросил строки незнакомой таблицы и всё равно сдвинул курсор» (там клиент не знал таблицу; здесь сервер не отдавал её и не штамповал).
