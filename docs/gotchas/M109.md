# M109 — колбэк готовности ждёт все подсистемы, и один сломанный сокет прячет успех остальных

**Область:** прод / раздача обновлений

- **Симптом:** при каждом старте primary в логе `[WARN] tracker error {"error":"Error: bind EINVAL 0.0.0.0:6969"}` — и ни одной строки `tracker listening` за всё время (0 вхождений за 7 суток при 10 рестартах). Читается однозначно: «трекер не поднялся». На деле `ss -lntup` показывает и tcp, и udp на 6969 за pid'ом primary, а `curl` на `:6969/announce` отвечает корректным bencode. Сервис работает, лог утверждает обратное.
- **Корень, частный:** `bittorrent-tracker` при `{ udp: true }` поднимает **два** сокета — udp4 и udp6, — а `listen(port, '0.0.0.0')` отдаёт один и тот же адрес обоим. udp6-сокет на IPv4-литерале падает с `EINVAL` (не `EADDRNOTAVAIL` и не `EADDRINUSE` — отсюда ложный след «повторный бинд» / «конфликт портов»). Лечится адресом по протоколам: `listen(port, { http: '0.0.0.0', udp: '0.0.0.0', udp6: '::' })`.
- **Корень, общий и более полезный:** колбэк `listening` у этой библиотеки считает `!!http + !!udp4 + !!udp6` и срабатывает, **только когда готовы все три**. Один упавший сокет — и колбэк не вызывается никогда. То есть обработчик ошибки печатает отказ, а лог успеха молчит: **виден отказ подсистемы, не виден успех сервиса**. Этот перекос и есть грабля: по логу нельзя отличить «не поднялся вовсе» от «поднялся частично».
- **Как проверять такое за минуту:** не по логу, а по факту — слушает ли кто-то порт (`ss -lntup`) и отвечает ли эндпоинт. Лог здесь свидетель ненадёжный по построению.
- **Контроль перед правкой** (иначе чинишь вслепую): поднять ту же библиотеку локально обоими способами. Замер 06.09.2026 на свободных портах: `'0.0.0.0'` → `listened: false`, `bind EINVAL`; `{ http, udp, udp6: '::' }` → `listened: true`, ошибок нет. Прод-симптом воспроизводится на ноутбуке за две секунды.
