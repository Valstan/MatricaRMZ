# M212 — синоним должности перестал работать: каноническая форма должна совпадать с нормализацией

**Область:** подбор нормы по должности / строковые ключи / синонимы

- **Симптом:** профессию в приказе переименовали («Электромонтер по ремонту электрооборудования» → «Слесарь-электрик по ремонту электрооборудования»), синоним в `POST_SYNONYMS` добавили — а автоподбор нормы у сотрудников-электриков всё равно перестал находить: карточка СИЗ пустая, норма не подбирается.
- **Корень:** `postKey()` сначала прогоняет строку через `normalizeLookupText()`, а тот **превращает дефис в пробел** (`replace(/["'`.,;:!?()[\]{}<>/\\|+-]+/g, ' ')`). Каноническая (правая) форма синонима возвращается из `postKey` **как есть**, мимо нормализации. Если в правой форме стоит дефис («слесарь-электрик …»), то два входа дают разные ключи: должность из штатки → «слесарь-электрик …» (дефис, как в правой форме), а профессия из приказа → «слесарь электрик …» (пробел, после нормализации). Проверка «оба дают один ключ» падает, а выглядит это как «синоним есть, а не работает».
- **Лечение:** каноническую форму пишем **в том виде, какой даёт нормализация** — с пробелами: `['электромонтер по ремонту электрооборудования', 'слесарь электрик по ремонту электрооборудования']`. Сторож — `backend-api/src/tests/ppeOrderNormsPostKey.test.ts`: обе формы обязаны давать один ключ, иначе норма сотруднику не подберётся.
- **Общая форма:** любой «ключ совпадения», который сравнивает нормализованную строку с эталоном, требует эталона **в нормализованном виде**. Иначе первое же переименование (с дефисом, скобкой или кавычкой) разводит две стороны ключа. Смежная форма — M207 (фильтр по должности не находит сотрудника).
- **Поймано:** 2026-11-18, приведение сида приказа о СИЗ к официальной ЕТН: профессия 4581 переименована по ЕТН, а в штатке у сотрудников должность осталась «Электромонтер по ремонту электрооборудования» — без правильного синонима норма у электриков пропала бы (миграция 0122, PR #1788).
