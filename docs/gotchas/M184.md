# M184 — Новая колонка в синк-таблице: version-chained мигратор не спасает свежую БД

**Область:** [M184](#m184--новая-колонка-в-синк-таблице-version-chained-мигратор-не-спасает-свежую-бд)

- **Симптом:** на боевом парке всё живо, а свежая установка падает на синке с `SqliteError: no such column: "reminders_json"`. И падает не та операция, ради которой колонка добавлена, а любой прогон: выборка идёт по всем таблицам контракта.
- **Корень:** у клиента **два** пути применения схемы, и новую колонку надо класть в оба:
  1. `clientSchemaMigrations` — version-chained, работает только там, где версия уже проставлена (долгоживущая БД);
  2. `ensureClientSchemaParity` — безусловный, идемпотентный, отрабатывает на **свежей** БД.

  Свежая установка базлайнит `ClientSchemaVersion` сразу в текущую версию и цепочку шагов пропускает целиком. Значит колонка, добавленная только в цепочку, на свежей БД просто отсутствует. Третий путь — `drizzle/*.sql` по журналу: он создаёт **таблицы** (у заметок это `0004_notes_module.sql`), но колонки, добавленные позже, — нет.
- **Лечение:** колонку добавляем в безусловный путь обоих клиентов (electron `ensureClientSchemaParity` + его android-порт) с PRAGMA-проверкой: в SQLite нет `ADD COLUMN IF NOT EXISTS`, а повторный ALTER уронил бы транзакцию миграции. В version-chained шаг (13→14) колонка тоже нужна — для долгоживущих БД.
- **Как поймать рано:** гейт `pnpm -r test` в android-пакете гоняет настоящий `runSync` по свежей БД — он и упал. Живой парк такие БД не покажет: там версия проставлена давно, цепочка отработала при первом обновлении.
- **Правило для новой колонки в таблице синк-контракта:** колонка аддитивная и nullable → безусловный путь обоих клиентов + version-chained шаг + зеркало шага в android + контракт на сервере (PG) + `COALESCE`-защита от затирания старым клиентом (старый клиент шлёт `null` — это «не менялось», а не «очистить»).
