# M181 — Синк перестал ходить после обновления: в логе только `sync.run.start`, ни одного `sync ok`

**Область:** [M181](#m181--синк-перестал-ходить-после-обновления-в-логе-только-syncrunstart-ни-одного-sync-ok)

- **Симптом:** клиент работает, интерфейс живой, вход выполнен — а данные никуда не уходят. В `matricarmz.log` после старта процесса синка идут только строки `sync-worker sync sync.run.start id=… mode=incremental`, примерно раз в 10 с и раз в минуту, и **ни одной** из тех, что бывают у живого прогона: нет `sync ok pushed=`, нет `sync.run.done`, нет `sync pull attempt=…` (в сеть он даже не выходит), нет `sync failed` и нет `sync worker exited`. Процесс воркера при этом жив и не падает. В интерфейсе отказа не видно: индикатор знает только `idle/syncing/done`.
- **Когда видели:** 29.10.2026, релиз 3.94.0 (первый выпуск, где движок синка живёт в отдельном процессе). После автообновления на боевой машине за 1 ч 20 мин — 102 строки `sync.run.start` и **0** завершений.
- **Корень:** канал `utilityProcess` **асимметричен по форме события**. В главном процессе `child.on('message', listener)` отдаёт **само сообщение** (`electron.d.ts`, `UtilityProcess.on('message', listener: (message: any) => void)`), а в воркере `process.parentPort.on('message', …)` — обёртку `MessageEvent` с `.data`. Код читал `event.data` с обеих сторон, поэтому в main каждое сообщение воркера превращалось в `undefined` и молча выбрасывалось: готовность, прогресс, `runResult` и заявки `session:*`. Прогон в воркере доходил до чтения сессии, не получал ответа за `MAIN_CALL_TIMEOUT_MS` (10 с) — отсюда шаг ровно ~10 с между строками — и завершался веткой «нет сессии», которая пишет `auth required` только в БД и в буфер логов воркера. Наружу — тишина.
- **Почему тесты не поймали:** фейк в `syncProxy.test.ts` повторял **не ту** сторону контракта — эмитил `{ data: message }`, то есть ровно то, чего `UtilityProcess` не делает. Тест «проходил» на вымышленном контракте. Лечение: фейк эмитит само сообщение, как настоящий порт, плюс сторож `syncEngineProcess.guard.test.ts` сверяет, что main передаёт в `handleMessage` собственный параметр слушателя, а не `.data`.
- **Лечение сейчас:** обновить клиент на сборку с правкой. Вернуть синк на месте без обновления — только ручной откат на движок в главном процессе через `MATRICA_SYNC_WORKER=0` (переменная окружения, откат существовал с самого переезда).
- **Не путать с «нет сессии» по-настоящему:** та ветка законна (пользователь не вошёл), но теперь молчание моста пишется в лог отдельной строкой `session read: no answer from main`. Если видишь её — проблема в канале, а не в логине.
