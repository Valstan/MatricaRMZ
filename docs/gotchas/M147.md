# M147 — этап не по очереди: строка этапа — копия даты статуса карточки, значит править источник

**Область:** [M147](#m147--этап-не-по-очереди-строка-этапа--копия-даты-статуса-карточки-значит-править-источник)

- **Симптом:** в «Этапах ремонта» отметка «Отправлен заказчику» / «Принят заказчиком» стоит **раньше** «Разборка, дефектовки» — на месяцы и годы. Движок «по очереди» порядок не проверяет (он сортирует по дате), поэтому список молча показывает непорядок.
- **Корень (проверено на всех 13 движках, 30.09):** строки `shipped` / `accepted` — **побайтовая копия** `status_customer_sent_date` / `status_customer_accepted_date` карточки (маппинг `STATUS_TO_STAGE` в `backfillRepairStages.ts`, PR #1038). Совпадение до миллисекунды. Значит бэкфилл сработал верно, а **неверна дата в карточке**: у 9 из 13 «Принят заказчиком» осталось с прошлого ремонта, причём у 6 из них отгрузка 2026 года честная — испорчена ровно одна строка. След бэкфилла виден по совпадающим датам у разных двигателей (`09.04.25` у 4, `05.12.24` у 2, `11.10.24` у 2).
- **Правило:** «этап стоит не по очереди» — сначала искать источник (`CARD_SOURCE_ATTR` в `reviewRepairStageOrder.ts`), и решать строку этапа и атрибут карточки **одним вердиктом**. Правка только строки оставила бы карточку старой, и расхождение вернулось бы при следующем переносе.
- **Смежное про `pg`:** `bigint`-колонка приходит из `pg` **строкой**. `new Date("1755196800000")` бросает `Invalid time value`, а `a < b` на строках уезжает на лексикографику. Ловится только на данных, где такие строки есть: на пустой dev-базе скрипт отрабатывает молча.
- **Смежное про lateral-агрегат по EAV:** `jsonb_object_agg(ad.code, av.value_json)` с привязкой только к `entity_type_id` сворачивает значения **всех** сущностей типа — карточка в отчёте достаётся чужому двигателю, и на одном движке это не видно. Нужна вторая привязка `av.entity_id = <конкретная сущность>`.
- **Смежное про очистку EAV-даты:** очистка — это SQL `NULL`, а не строка `"null"`. `value_json` проходит zod как строка, и `"null"` потом ломает любое приведение к дате (`invalid input syntax for type double precision: "null"`). Поймано на своём же разборе.
- **Смежное про печать даты (поймано на проде 30.09 в тот же день):** дата этапа хранится как полночь локальной машины оператора, то есть в ms это **21:00 UTC предыдущих суток**. Отчёт, печатающий `new Date(ms).toISOString().slice(0,10)`, показывает каждую строку **на сутки раньше** той даты, которую видит оператор, — и вердикт принимается не по тому дню. Печатать доменным `moscowDayKey` (экспортируемый, `Europe/Moscow`); приватную копию форматтера не заводить — это запрещено комментарием у самого хелпера. Тот же класс, что «сравнение дат по `at === at` ловит не тот дубль».
- **Инструмент:** `stages:review-order` (разбор → `--emit` шаблона решений → `--decisions … --apply`). Запись через журнал; решение принимается по совпадению с тем, что было на экране при разборе, иначе отказ поимённо. Автоматически двигать дату по эвристике «не раньше дефектовки» нельзя — это выдумывание события.
- **Амендмент 30.09 (первый прогон на проде):** копией карточки оказались **все** строки этапов, а не только отгрузка/приёмка: `arrival` ← `arrival_date`, `disassembly_defect` ← `defect_date`. Значит источник ищется по общему правилу «какая строка чьей копией является», а не точечно по двум кодам. Плюс два дефекта самого отчёта, пойманных именно этим прогоном: печать даты по UTC (см. выше) и ⚠ на каждой строке, включая `arrival`, которому раньше дефектовки и полагается.
