# M196 — Чистка каталога обновлений выбирает инсталлятор по времени файла, а не по версии: свежий релиз удаляется, старый остаётся

**Область:** [M196](#m196--чистка-каталога-обновлений-выбирает-инсталлятор-по-времени-файла-а-не-по-версии-свежий-релиз-удаляется-старый-остаётся)

- **Симптом:** после выката на проде в каталоге обновлений лежит **старый** инсталлятор, а свежий
  исчез — при этом `scp`/`mv` отчитывались кодом 0, `/updates/status` продолжает показывать прежнюю
  версию, и выкат выглядит как «сложилось», хотя клиентам отдаётся не то. В нашем выкате v3.115.0
  (10.11.2026) этого не произошло только потому, что файлы переносились через `mv` из каталога
  **вне** `/opt/matricarmz/updates` — `mv` сохраняет mtime залитого файла, и он оказался новее
  предыдущего релиза.

- **Корень:** на боксе стоит path-юнит `matricarmz-updates-prune.path`
  (`PathChanged=/opt/matricarmz/updates`) со скриптом `/usr/local/bin/matricarmz-updates-prune`.
  Скрипт выбирает, что оставить, так:

  ```bash
  mapfile -t exes < <(ls -1t "$UPDATES_DIR"/MatricaRMZ-Setup-*.exe 2>/dev/null || true)
  ```

  `ls -1t` — это сортировка **по времени модификации**, а НЕ по номеру версии. Дальше
  `KEEP_COUNT=1` (в юните) оставляет первый файл из этого списка, а всё остальное из каталога
  удаляет. Значит, **побеждает тот `.exe`, у которого свежий mtime**, а не тот, где выше версия.

  Проверено в песочнице на боевом скрипте (прода, `/tmp`, `rm` заменён на `echo`): при
  `3.114.0` с mtime 08.11 и `3.115.0` с mtime 05.11 чистка удалила **новый** `3.115.0.exe` вместе с
  его `.blockmap` и оставила **старый** `3.114.0.exe`. Сервер при этом выбирает инсталлятор по
  версии (`pickLatestInstaller` → `compareSemver`), то есть клиентский `latest.json` указывал бы на
  несуществующий файл — 404 на инсталлятор и blockmap, клиенты не видят обновления.

  Почему mtime может оказаться старше у свежего релиза: `scp -p`/`rsync -a` сохраняют время
  исходного файла (артефакт собран на раннере в другое время, чем предыдущий релиз ехал на прод);
  восстановление из копии или с другого каталога тянет за собой старые метки; `mv` внутри одной ФС
  сохраняет mtime источника.

- **Диагностика:** (1) сравнить, что на диске, с тем, что отдаёт сервер:
  `ls -lt /opt/matricarmz/updates/*.exe` и `cat /opt/matricarmz/updates/latest.json` — если
  `fileName` в манифесте указывает на отсутствующий файл, дело в чистке; (2) посмотреть правило
  отбора: `cat /usr/local/bin/matricarmz-updates-prune` (ищите `ls -1t` и `KEEP_COUNT`); (3)
  проверить, что сработало: `journalctl -u matricarmz-updates-prune.service --since "10 мин назад"`.

- **Лечение:** переносить артефакты в каталог обновлений **атомарно и с правильным mtime**:
  1. заливать в каталог **вне** `/opt/matricarmz/updates` (например `~/upload/`) — там чистка не
     смотрит (path-юнит реагирует на `PathChanged=/opt/matricarmz/updates`);
  2. переносить на место `mv` **в пределах одной ФС** (проверить: `stat -c %d` для обоих каталогов
     даёт один девайс) — `mv` атомарен, и сканер манифеста никогда не увидит полузалитый файл
     (это снимает ловушку **M40**);
  3. **после переноса — принудительно освежить mtime**: `touch` на `.exe` и его `.blockmap`
     (не раньше, чем `.exe` и `.blockmap` уже на месте). Это делает свежий релиз «новее» для
     `ls -1t` при любом происхождении меток;
  4. проверить, что после чистки на месте остался нужный файл:
     `ls -lt /opt/matricarmz/updates/` — первой строкой должен идти инсталлятор текущего релиза.

  Обходной путь, если `touch` недоступен: положить свежий `.exe` последним (mv блокмапа и `latest.yml`
  — после него), тогда `ls -1t` поставит его первым. Следить, чтобы `latest.yml` и `.blockmap`
  пережили чистку: `.blockmap` держится только рядом со своим `.exe`, а `latest.yml` — в белом
  списке скрипта.

  Связано с [**M194**](M194.md): там — файлы под промежуточными именами исчезали из-за белого
  списка имён; здесь — файл с финальным именем исчезает из-за **порядка отбора по mtime**. Оба
  симптома дают одно и то же «залилось, а файла нет», поэтому проверять надо обе причины.
  Правило выката — `AGENTS.md` §Release process, шаг 7; факт выката — `docs/machines/es-vps.md`.
