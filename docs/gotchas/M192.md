# M192 — Артефакт деплоя затирал миграции клона: миграция, приехавшая после сборки, исчезала с бокса

**Область:** [M192](#m192--артефакт-деплоя-затирал-миграции-клон-миграция-приехавшая-после-сборки-исчезала-с-бокса)

- **Симптом:** миграция применена и в базе проде, и на боксе — а **файла миграции на боксе нет**. Следующий `db:migrate` её не видит; если её откатить, повторно применить уже нечем. Поймано 06.11.2026: миграция `0122` (догон доменного правила по видам срока) применена на проде, а её `.sql` исчез из `~/MatricaRMZ/backend-api/drizzle/` сразу после выката `0121` в тот же день.

- **Корень:** `scripts/prod-ops/deploy-backend.sh` раскладывал поверх клона **все** пути из своего списка `PATHS`, а в списке был `backend-api/drizzle`. Артефакт `backend-dist` собран с коммита **выката**, и в нём лежала папка миграций того коммита. Распаковка делала `rm -rf` + `cp -a` — то есть затирала миграции клона (свежие, из `git pull`) файлами из более старой сборки. Кто «прав»: клон или артефакт — вопрос не философский, а технический: **исходники принадлежат клону, артефакт несёт только сборку.**

- **Диагностика:** на боксе `ls backend-api/drizzle/*.sql` не показывает миграции, которых нет в теге; при этом `git status` в клоне чист (значит, файлы затирает **выкат**, а не человек). Сверка: `git log --oneline <тег>..main -- backend-api/drizzle/` — миграции, приехавшие после сборки.

- **Лечение:** миграции **не кладутся в артефакт** и **не раскладываются выкатом** — они приезжают на бокс только через `git pull` из клона. `PATHS` в `deploy-backend.sh` и список упаковки в `.github/workflows/backend-dist.yml` исправлены (PR #1581), плюс **сторож в самом скрипте**: после раскладки `git status --short -- backend-api/drizzle` обязан быть пустым — иначе выкат встаёт **до** рестарта (миграции разошлись с HEAD — иначе правка данных молча не доедет до прода).
