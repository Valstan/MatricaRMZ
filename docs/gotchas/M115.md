# M115 — сырой байт NUL в исходнике делает файл невидимым для поиска по коду

**Область:** инструменты / аудит

- **Симптом:** файл не находится грепом ни по одной строке, которая в нём точно есть. Никакой ошибки: `grep` печатает `Binary file … matches` (или вовсе молчит под `-l`), `ripgrep` пропускает такой файл по умолчанию.
- **Корень:** в файле есть байт NUL — обычно как разделитель составного ключа, вписанный **самим символом** вместо escape-последовательности (`` `${a}<NUL>${b}` ``). Инструменты определяют бинарность по наличию NUL в начале файла, а не по расширению.
- **Чем опасно:** файл выпадает из **каждого** сплошного поиска — ревизии, аудита секретов, сторожей человекочитаемых подписей, любого «проверил весь код грепом». Аудит при этом рапортует «чисто»: отрицательный результат неотличим от «не смотрел». Найдено 07.09.2026 ровно так — своим же аудитом, который эти файлы не увидел: `shared/src/domain/payments.ts`, `backend-api/src/services/engineInventoryLinesService.ts` (там NUL внутри ключа детерминированного UUID) и `backend-api/src/services/snapshotCrypto.test.ts`.
- **Диагностика и защита:** сторож `shared/src/domain/sourcesAreText.guard.test.ts` обходит `*/src` и падает на любом файле с NUL. Разово: `grep -rlI '' <dir>` печатает только текстовые файлы — разница со списком всех и есть невидимые.
- **Лечение:** заменить байт на escape-последовательность. Строка получается **побайтово та же**, поэтому хеши и детерминированные идентификаторы не меняются — правка безопасна для уже существующих данных.
