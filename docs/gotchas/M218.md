# M218 — Миграция drizzle выбирается по `created_at`, а не по хэшу: «несовпадение хэша в журнале» ≠ «будет переиграна»

**Область:** миграции БД (`backend-api/drizzle/`, `backend-api/src/database/migrate.ts`), drizzle-orm 0.45.2, прод-бокс `matricarmz`

**Смежная половина темы:** [M-письмо в мозг от 20.11](../../mailbox/to-brain/2026-11-20-migration-sql-bez-zapisi-v-zhurnale.md) — файл миграции **без записи** в журнале молча не применяется; это грабля про вторую половину того же места (запись есть, а сверяется не то, что кажется).

- **Симптом:** в `drizzle.__drizzle_migrations` лежит запись, хэш которой **не совпадает** с sha256 файла
  миграции на диске (у нас: `0024_act_completeness_seed.sql` — в базе `3a8fd218…`, в файле `c5d55605…`).
  Из этого сделали вывод, что `db:migrate` на проде **переиграет сид** (972 строки INSERT по маркам и
  деталям), и по гейту #025 заморозили миграции на проде целиком. Страх оказался ложным — но решение
  «не пускать db:migrate на прод» осталось и требовало отдельного гейта.

- **Корень:** drizzle-orm 0.45.2 (`node_modules/drizzle-orm/pg-core/dialect.cjs`, `migrate()`) выбирает
  миграции **не по хэшу**, а по времени:
  `select id, hash, created_at from drizzle.__drizzle_migrations order by created_at desc limit 1` →
  последняя применённая; применяется та миграция, у которой `migration.folderMillis` (поле `when` в
  `drizzle/meta/_journal.json`) **больше** `created_at` последней. Хэш файла пишется в журнал рядом, но
  **никогда не сверяется**. Отсюда: миграция с `when` января 2026 не переиграется, сколько бы раз файл
  ни меняли. «Неприменённая по хэшу» ≠ «будет применена повторно».

- **Диагностика:** смотреть не «совпал ли хэш», а какие миграции **по правилу drizzle** ещё не применены:

  ```sql
  select max(created_at) from drizzle.__drizzle_migrations;
  ```

  Дальше — записи в `drizzle/meta/_journal.json`, у которых `when` больше этого числа (у нас после
  20.11.2026 таких нет: `max(created_at)` = 1795160400000 = `when` миграции `0134_print_forms`).
  Сверка хэшей — только для справки, как «файл не менялся после применения».

- **Лечение:** адресное применение одной транзакцией — SQL миграции **+** строка журнала:

  ```sql
  INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('<sha256 файла>', <when из _journal.json>);
  ```

  `created_at` = `when` из `_journal.json`, `hash` = sha256 файла — ровно то, что записал бы сам drizzle.
  Тогда и будущий `db:migrate` — no-op, и хэш сходится. Так применены на проде `0122_ppe_etn_alignment`
  (17.11) и `0134_print_forms` (20.11).

- **Чего НЕ делать:** не пугаться «неприменённых по хэшу» миграций и не замораживать прод-гейт из-за
  этого страха; но и не пускать `db:migrate` на проде вслепую — гейт #025 нужен по существу (запись в
  живые данные), а не из-за мнимого переигрывания сида. Перед адресным применением сверять хэш файла на
  боксе с локальным (`.gitattributes` держит `*.sql` в LF — байты совпадают) и класть всё в одну
  транзакцию: ошибка откатывается целиком.
