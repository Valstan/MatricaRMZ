# M228 — строка значения атрибута попала в БД сервера, но не в журнал: клиенты её никогда не видят

**Область:** сервер (`backend-api/src/services/sync/syncWriteService.ts`, `applyPushBatch.ts`) + клиентская реплика (`electron-app`), любая таблица `attribute_values`

- **Симптом:** в подсказках поля выбора «новые не видны» — контрагент есть в списке (список читает строгую таблицу `erp_counterparties`), а в поле выбора его нет, хотя в базе он есть, его можно выбрать и отредактировать (промт КАРМАНА #146, 25.11.2026: ООО «Досааф», «Туполева», «Петренко, Татьяна Геннадьевна» и второй «Петренко…»). Шире: у контрагента в локальной реплике **нет подписи** (значений-атрибутов) ⇒ в списках по EAV он выходит под коротким id.
- **Корень (установлено на живых данных):** строки значений атрибутов попадают в БД сервера **без записи в журнал** (`ledger_tx_index`), а журнал — единственный источник для pull. На 25.11.2026 таких строк было **2 228 из 54 944** живых `attribute_values` (`last_server_seq IS NULL`); у `entities` таких нет ни одной. След на клиенте: у ВСЕХ машин реплика по `attribute_values` обрывалась на одном и том же моменте (max `updated_at` = 1795607871625 = 14:57:51 MSK), тогда как на сервере строки были до 14:57:55.993 ⇒ **реплики замерли, новые значения атрибутов до них не доехали ни разу.**
- **Почему молча:** журнал — лог ИЗМЕНЕНИЙ, и «no-op» строка (содержимое совпало с серверным) в него не пишется намеренно (`isUnchangedAttributeValueRow`, `findUnchangedAttributeValueRows` — правило против раздувания журнала, инцидент 03.11.2026). Но **сравнение идёт по ПАРЕ (`entity_id` + `attribute_def_id`), а не по id**: если пара уже есть на сервере (возможно, под другим id), клиентская строка выпадает из журнала — и её id никогда не становится известен остальным клиентам. Точный путь, на котором строка оказалась в БД без журнала, при разборе не был дописан до конца; кандидаты — фильтр no-op и remap по паре в `applyPushBatch`.
- **Диагностика (проверяемо):** 1) `select count(*) from attribute_values where deleted_at is null and last_server_seq is null` — на сервере ненулевое число ⇒ строки в БД без журнала; 2) снимок клиента (`diagnostics_snapshots`, `scope='client'`): `tables.attribute_values.maxUpdatedAt` против серверного `max(updated_at)` — у клиента отстаёт ⇒ реплика замерла; 3) `ledger_tx_index` по `row_id` строки — пусто ⇒ в журнале её нет.
- **Лечение (выбрать владельцу):** правило «no-op» должно сравнивать строку **по id** (или по паре, но с явной передачей id серверной строки), чтобы клиентская строка всегда получала запись в журнале; плюс — клиенту после полной пересборки реплики (`force_full_pull_v2`) это не чинит само по себе: строки, не попавшие в журнал, не приедут никогда, нужен бэкфилл из БД в журнал. **Симптом у промта #146 закрыт отдельно**: поле выбора контрагента переведено на общий источник со списком (строгая таблица + EAV) — см. PR #2029.
- **Поймано:** 2026-11-25, разбор машины PC63 по промту КАРМАНА #146. Сторож: `electron-app/src/renderer/src/ui/utils/counterpartyOneSource.guard.test.ts` (один источник для поля и списка).
- **Правило на будущее:** **«в БД есть» и «клиент это видит» — разные утверждения.** Проверять надо номер в журнале (`last_server_seq`), а не наличие строки в таблице: строка без номера не приедет ни на одну машину, и симптом выглядит как «подсказка не работает», а не как «синк сломался».
