# M182 — Тест с внешним архиватором краснеет на Windows: виновато чтение свежезаписанного файла, а не процесс

**Область:** [M182](#m182--тест-с-внешним-архиватором-краснеет-на-windows-виновато-чтение-свежезаписанного-файла-а-не-процесс)

- **Симптом:** `clientOpsArchive.test.ts` («читает и архив с именами в UTF-8») изредка красный на локальном прогоне — «Test timed out in 5000ms» при длительности теста ~10 000 мс. На CI (Linux) — всегда зелёный. Разбираемый код при этом отрабатывает за 0 мс.
- **Когда видели:** 31.10.2026, релиз 3.98.0 (прогон гейта на PR #1531) — и раньше, 15.10.2026. Воспроизводится и в одиночном прогоне файла (примерно в одном прогоне из двух-трёх), при параллельном прогоне пакета — чаще. Это **не перегруз**: одиночный прогон на свободной машине тоже краснеет.
- **Корень (замер с инструментацией):** задержка сидит **между возвратом `execFileSync` и `readFileSync` архива** — то есть в чтении файла, который только что записал внешний процесс:

  ```
  [PROBE] spawn end in 18 ms
  [PROBE] built in 10043 ms      ← readFileSync свежезаписанного zip
  [PROBE] read in 0 ms, entries=1
  ```

  Чтение блокирует **антивирус** (на этой машине Defender, real-time protection включён): он держит хэндл свежесозданного файла, и `readFileSync` ждёт его освобождения — до ~10 с. Ни `7za`, ни флаг `-mcu=on` ни при чём: сам `7za` отрабатывает за 20–60 мс, `-mcu=on` вне vitest — 19–20 мс на 40 итерациях подряд. На Linux такого блокировщика нет, поэтому CI зелёный.
- **Почему раньше винили `-mcu=on`:** задержка прилетала именно к тесту с этим флагом — просто потому, что он читал свежий файл вторым по счёту. Причина — чтение, а не флаг. Наблюдение 15.10 («7za с `-mcu=on` висит 10 с») было симптомом, а не причиной.
- **Почему тест падает, хотя «всё зелёное»:** `execFileSync` — синхронный вызов, прервать его нельзя. Vitest отмечает таймаут на 5-й секунде, но тест дорабатывает до конца (поэтому длительность ~10 с, а не 5) и уже после этого уходит в красный.
- **Лечение:** вся внешняя работа (запуск `7za` + чтение его вывода) уехала в `beforeAll` с явным бюджетом (180 с), а тесты проверяют только разбор готового буфера. Проверяемая логика — миллисекунды; бюджет по умолчанию (5 с) — не контракт для синхронного вызова внешнего процесса.
- **Общее правило:** в тестах, где файл пишет внешний процесс и его сразу читают, **самая медленная часть — чтение, а не запись**. Либо давай чтению отдельный бюджет (хук с большим таймаутом), либо читай раньше, чем файл заберёт сканер. И: «красный только на моей машине» — не повод закрыть флейк как «нерегресс» — сначала найти, **что именно** блокируется.
