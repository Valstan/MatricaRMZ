# M223 — после merge в коде остался маркер `<<<<<<< HEAD`: конфликт «разрешён» глазами, а тесты падают «Unexpected "<<"»

**Область:** git-flow / merge (любой файл репозитория; в этот раз — `electron-app/src/renderer/src/ui/listKit.guard.test.ts`)

- **Симптом:** после `git merge` конфликт «разрешён вручную», `git status` показывает чистое дерево, `git add` проходит без вопросов — а гейт падает с невнятным `Unexpected "<<"` (vitest/esbuild) или с ошибкой парсинга. Сборка `tsc` может при этом быть зелёной: маркер стоит в строке, где парсер терпим.
- **Корень:** `git add` **не проверяет**, остались ли маркеры конфликта в файле, — он просто берёт содержимое как есть. Ручное разрешение конфликта («вырезал среднюю часть, оставил обе стороны») легко оставляет один маркер, если удалять не всё. `git status` маркеры **не показывает**: конфликт считается разрешённым по факту индекса.
- **Почему молча:** дерево «чистое», коммит проходит, PR зелёный по части гейтов — а красный падает только там, где этот файл импортируется. Симптом уезжает от причины: «сломалось тестирование» вместо «в коде остался текст конфликта».
- **Диагностика:** `git grep -n -E '^(<<<<<<<|>>>>>>>|=======$)' -- .` — по всему репозиторию, не по конфликтному файлу. Проверять **после** каждого ручного разрешения и перед коммитом.
- **Лечение:** маркеры вырезать целиком; если нужно сохранить обе стороны — свести их руками в один текст (как в `docs/SESSION_HANDOFF.md` при слиянии релизной ветки). **Держать правило:** маркер в коде = красный гейт, а «чистое дерево» ≠ «код в порядке».
- **Родня в коде:** конфликтные файлы этой нитки: `electron-app/src/renderer/src/ui/listKit.guard.test.ts` (гард кита), `docs/SESSION_HANDOFF.md`, `docs/zavod/PROGRAM_EFFECTS.md`.
- **Правило на будущее:** после ручного разрешения конфликта — **всегда** прогонять поиск маркеров по репозиторию. `git status` и `git add` тут не помощники: они проверяют индекс, а не содержимое.
