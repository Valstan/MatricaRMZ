# M102 — «Клиент пушит, но ни разу не пуллил»: `sync_state.client_id` при push — это id ПОЛЬЗОВАТЕЛЯ

**Область:** sync / диагностика

- **Симптом:** в `sync_state` есть строки с голым uuid без префикса hostname (`0693eca7-…`, `b1aac85c-…`, `system`), у них `last_pushed_at` свежий, а `last_pulled_at` пуст и `last_pulled_server_seq = 0`; у настоящих машин (`PC19-…`) наоборот — `last_pushed_at` всегда `NULL`. Выглядит как «неизвестная машина, которая только шлёт» — и на неё уходит разбор.
- **Корень:** `syncWriteService.ts` передаёт в `applyPushBatch` `client_id: actor.id || actor.username || 'server'` — то есть **id аккаунта**, а pull пишет `sync_state` под настоящим `clientId` машины. Одна таблица, два разных ключа. `0693eca7-…` = аккаунт `mubvera`, машина — PC19 на 3.19.0.
- **Диагностика:** голый uuid в `sync_state` — сначала `select id, login from users where id = '<uuid>'`, и только потом искать машину. Машина — по `client_settings` того же логина (`last_seen_at`, `last_version`).
- **Следствие для отчётов:** колонка «Последняя отправка» (`reports.ts`, `syncState.lastPushedAt`) у машин **всегда пуста**, а у «аккаунтов» показывает время. Не чинить заменой ключа задним числом: `sync_state` читают диагностика и отчёты, а push-ключ виден ещё и в `logSkip` (`client_id`). Правка — отдельный PR: писать в push настоящий `clientId` из тела запроса и мигрировать строки.
- **Соседняя грабля того же дня:** строки, пропущенные сервером как `missing_dependency`, оставались `pending` и уходили в **каждый** push (PC19 — 8 нарядов на 4 несуществующих двигателя, раз в 22 с, неделю, без единой ошибки на экране). С 3.20.0 клиент возвращает в очередь зависимость, если она есть локально, иначе помечает строку `error` (`sync/dependencyRequeue.ts`).
- **Поймано:** 2026-09-04 при разборе первого critical-event, дошедшего в Telegram после починки канала.
