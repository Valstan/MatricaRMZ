# M110 — `.ps1` с кириллицей без BOM: падение выглядит синтаксической ошибкой, а виновата кодировка

**Область:** скрипты / Windows

- **Симптом:** свежий скрипт `scripts/client-ops/*.ps1` не разбирается вовсе. Парсер сыплет «Непредвиденная лексема "…"», «Отсутствует закрывающий знак ")"», а при запуске — «не удалось найти позиционный параметр, принимающий аргумент "<мусор>"». Номера строк указывают на совершенно исправные места, и в аргументе — нечитаемая каша вместо русского текста.
- **Корень:** Windows PowerShell 5.1 (`powershell.exe`, не `pwsh`) файл **без BOM** читает в кодировке ANSI текущей системы. Русские строки распадаются на байты, часть которых для парсера — обычные символы, и он честно спотыкается на них как на синтаксисе. То есть сообщение об ошибке описывает следствие, а причина на два уровня ниже.
- **Как отличить за секунду:** `node -e "const b=require('fs').readFileSync(f); console.log(b[0]===0xEF&&b[1]===0xBB&&b[2]===0xBF)"`. Соседние рабочие скрипты в репозитории лежат с BOM — это и есть контроль.
- **Лечение:** сохранять `.ps1` в **UTF-8 с BOM**. Инструменты, пишущие файлы, BOM по умолчанию не ставят, поэтому его надо добавить явно: `fs.writeFileSync(f, Buffer.concat([Buffer.from([0xEF,0xBB,0xBF]), buf]))`.
- **Отдельно про временные файлы:** та же грабля бьёт по одноразовым `.ps1`, которые агент пишет через heredoc для проверки чего-нибудь. Если такой файл ASCII-only — проблемы нет; как только в нём появляется русская строка (хоть в комментарии), он ломается тем же способом. У нас это дважды за один заход увело разбор в сторону: сначала «сломан скрипт», потом «неверный набор параметров cmdlet», а сломана была кодировка обоих временных файлов.
- **Поймано:** 2026-09-06 при добавлении `lan-share-firewall.ps1`. Родня: G21 (Windows-инструменты по умолчанию пишут UTF-16 и превращают код-файл в `Bin` для git) — тот же класс «редактор молча выбрал не ту кодировку», другой конец.
- **Обратная сторона того же класса — уже испорченный файл в репозитории** (поймано 19.10.2026): запись M153 в этом файле лежала в **cp1251** (внесена 14.10), а 15.10 её прочитали как UTF-8 и записали обратно — 555 русских знаков стали заглушками `U+FFFD` («◻»). Запись осталась на месте, строки не потерялись, но **грепом по симптомам не находится**: искать её стало нечем, и для поиска её просто нет. Глазами и через консоль это не диагностируется — вывод PowerShell врёт в обе стороны, а `read` показывает «крякозябры» одинаково и для чужой кодировки, и для заглушек. Считать надо байты: заглушка — это ровно `EF BF BD`. Лечение: `git log -- <файл>` плюс `git cat-file blob <ревизия>:<путь>` по ревизиям — найти последнюю чистую, восстановить из неё байты и **решить исходную кодировку** (`new TextDecoder('windows-1251').decode(байты)`), после записи сверить: ноль `U+FFFD`, диф ровно на пострадавшие строки.
