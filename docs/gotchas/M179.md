# M179 — новая таблица контракта: строки приехали, клиент их выбросил и уехал вперёд

**Область:** [M179](#m179--новая-таблица-контракта-строки-приехали-клиент-их-выбросил-и-уехал-вперёд)

- **Симптом:** данные «есть на сервере, но не у клиентов» — при этом ни ошибки, ни красного теста, ни строки в логе. 28.10.2026: на проде номер РМЗ (`RMZ451`) выдан всем **2574** живым двигателям, а в цеху «двигателям не присвоены номера». В логе живого клиента всё зелено: `sync ok pushed=0 pulled=3 cursor=3660857`.
- **Корень:** инкрементальный pull отдаёт строки по `last_server_seq > since`, а клиент сдвигает курсор **всегда** — даже когда часть строк применить не смог. Сборка, в `applyPulledChanges` которой нет `case` для таблицы, молча выбрасывает её строки (switch без `default` — ошибки нет) и записывает в `LastPulledServerSeq` курсор **за** ними. Строки становятся недостижимы навсегда: обновление клиента, рестарт, повторный pull — ничего не вернёт, потому что они позади `since`.
- **Инцидент 28.10.2026:** таблица `erp_engine_numbers` появилась в 3.91.0. Клиенты 3.90.0 успели протащить её строки (`3642969…3653935`) до обновления и выбросили 2580 штук. После обновления курсор стоял на `3660857` — за всеми номерами. Диагноз снялся одним сравнением: `min/max(last_server_seq)` номеров против `since=` в логе клиента.
- **Почему не поймали раньше:** сервер отдаёт строки по контракту (`SyncTableRegistry`), клиент принимает по своему `switch` — две стороны одного договора, и расхождение между ними не проверял никто. Живой пример был в самом файле: `erp_engine_instances` сервер отдавал, клиент не упоминал ни разу.
- **Лечение случившегося:** проштамповать строки заново через журнал — `corepack pnpm -F @matricarmz/backend-api sync:restamp -- --tables=<table> --all` (dry-run) → `sync:restamp:apply -- --tables=<table> --all`. Содержимое не меняется, только номер доставки; клиенты забирают ближайшим pull. 28.10.2026: 2580/2580, новые seq `3660858…3663437`, клиент забрал `pulled=400 + 2000 + 180`.
- **Чтобы не повторилось (3.92.0):** (1) сторож `pullApplyCoverage.guard.test.ts` — у каждой таблицы контракта обязан быть `case`, проверено контролем (снятие ветки `erp_engine_instances` даёт красный); (2) `default` в switch больше не молчит: незнакомая таблица пишется в журнал дырок (`sync/pullGaps.ts`, настройка `sync.pullGaps`) и на старте синхронизации добирается полным состоянием (`/ledger/state/snapshot?table=`) — **не двигая глобальный курсор**.
- **Порядок выката (AGENTS.md §Release process):** выкатил таблицу или залил в неё строки скриптом — проверь доставку на живом клиенте (`sync ok pulled=N cursor=…`), и если строки уже позади курсора — restamp. Журнал дырок лечит задним числом и только те таблицы, чьё падение он застал; для уже проехавших он не свидетель.
- **Сторожа:** `electron-app/src/main/services/sync/pullApplyCoverage.guard.test.ts` (2), `electron-app/src/main/services/sync/pullGaps.test.ts` (8).
- **Пул:** родня [G368](https://github.com/Valstan/brain_matrica/blob/main/cross-project-ideas/GOTCHAS.md#g368) — «курсор едет, а строки не доезжают» (там причина была в штампе, здесь — в незнании таблицы); [G127](https://github.com/Valstan/brain_matrica/blob/main/cross-project-ideas/GOTCHAS.md#g127) — «инкремент необратим: чего курсор не принёс, того уже не вернуть».
