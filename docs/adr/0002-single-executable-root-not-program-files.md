# ADR-0002 — Весь исполняемый контур клиента под одним корнем; Program Files отвергнут

- **Статус:** Accepted (решение владельца 2026-08-04; фазы 1–2 реализованы)
- **Дата:** 2026-08-04
- **Контекст-источник:** владелец получил рекомендацию «не раскладывайте исполняемые файлы в `%APPDATA%` — запуск exe из AppData один из главных триггеров поведенческого анализа; watchdog лучше держать в папке установки» и попросил переделать установщик так, чтобы всё ставилось в одно место, желательно в Program Files, без мусора по компьютеру, и чтобы Касперский не ругался.
- **Связанные:** [ADR-0001](0001-client-install-update-architecture.md) (архитектура установки и обновления)

## Контекст

Проверка контура (12 агентов, факты сверены по коду и по шаблонам `app-builder-lib` 26.8.1) показала, что триггеров поведенческого анализа не один, а шесть, и место запуска среди них не главный:

1. **Ничего не подписано** — сертификата нет, релиз уходит unsigned. Это базовый множитель под всеми остальными эвристиками.
2. Сторож — неподписанный .exe в `%APPDATA%\MatricaRMZ`, запускаемый двумя задачами планировщика (при входе + каждые 15 минут).
3. Сторож скачивает .exe с сервера и запускает его молча (`/S`, скрытое окно) — сигнатура троянца-загрузчика.
4. Сторож раз в 15 минут поднимал скрытый `powershell` с COM `WScript.Shell` — LOLBin, AMSI, Script Block Logging.
5. Кэш обновлений — постоянный ~136-МБ `.exe` с предсказуемым именем в папке «Загрузки», самой сканируемой в Windows.
6. Транзитные `.exe` в `%TEMP%` (аварийное обновление и загрузка сторожа).

## Решение

**Program Files отвергнут.** Переезд туда возможен только через `perMachine: true`, а это `RequestExecutionLevel admin` прямо в манифесте установщика (`app-builder-lib/templates/nsis/installer.nsi`), и ключ `/S` его не подавляет. Цена:

- UAC на **каждое** обновление у каждого оператора;
- полная смерть тихого самовосстановления: сторож запускает установщик через `CreateProcess` (`exec.Command`), который на admin-манифесте вернёт `ERROR_ELEVATION_REQUIRED`, а ShellExecute-фолбэка в Go нет;
- автопереезда не бывает в принципе — `setInstallModePerUser` при `perMachine:true` вообще не компилируется, старый `InstallLocation` из HKCU больше не читается, то есть нужен разовый обход администратором каждой машины, а где UAC поднимут чужой учёткой — остаётся орфан на ~318 МБ;
- мина в `CleanupMatricaFiles`: `RMDir /r "$PROGRAMFILES64\MatricaRMZ"` в `.onInit` — новый каталог назывался бы ровно так, и установщик сносил бы боевую папку вместе с деинсталлятором до распаковки.

**Данные в Program Files невозможны технически**, независимо от режима установки: `$INSTDIR` безусловно уничтожается `RMDir /r` при каждом обновлении, каталог read-only для оператора, UAC-виртуализация не работает (x64 + манифест `asInvoker`), а общий `db-key.json` под DPAPI разных пользователей уничтожил бы реплику первого при входе второго. Данные остаются в профиле пользователя навсегда — и это не проблема: антивирус ловит исполняемое, а не SQLite.

**Что сделано вместо (план А):** весь исполняемый контур сведён под один корень `%LOCALAPPDATA%\Programs`, и убраны триггеры, которые ничего не стоят:

| Что | Было | Стало |
|---|---|---|
| Клиент | `%LOCALAPPDATA%\Programs\@matricarmzelectron-app` | без изменений |
| Сторож | `%APPDATA%\MatricaRMZ\` (Roaming) | `%LOCALAPPDATA%\Programs\MatricaRMZ-Watchdog\` |
| Кэш обновлений | `%USERPROFILE%\Downloads\MatricaRMZ-Updates` | `%LOCALAPPDATA%\Programs\MatricaRMZ-Updates` |
| Аварийный и сторожевой .exe | `%TEMP%` | тот же кэш обновлений |
| Поиск процесса клиента | `tasklist` | `CreateToolhelp32Snapshot` (stdlib) |
| Папка рабочего стола | `powershell -Command [Environment]::GetFolderPath` | `SHGetKnownFolderPath` (stdlib) |
| Создание ярлыков | `powershell` + COM `WScript.Shell` из сторожа | клиент, `MatricaRMZ.exe --restore-shortcuts` (нативный `shell.writeShortcutLink`) |
| `RMDir /r` по `$PROGRAMFILES*` | был (мёртвое легаси) | убран |

Сторож остаётся **сиблингом** каталога установки, а не его подпапкой: one-click-апдейт заменяет каталог установки целиком, и сторож исчезал бы ровно в момент сорванного обновления, ради которого существует.

## Последствия

**Хорошо.** После выката ни одного `.exe` продукта нет вне `%LOCALAPPDATA%\Programs` — одно правило исключения на эту папку плюс два доверенных приложения закрывают весь исполняемый контур. Раньше это было физически невозможно: exe жили в четырёх независимых местах. UAC не появляется ни разу, переустановка на местах не нужна, данные не двигаются, миграция едет обычным автообновлением.

**Честные ограничения.** `%LOCALAPPDATA%\Programs` — по-прежнему профиль пользователя, эвристика «исполнение из user-writable расположения» формально остаётся (мягче, чем Roaming: туда ставятся VS Code и Slack). Гарантии, что Касперский замолчит **без** настройки доверенной зоны, нет. Не закрывается этим решением вообще: отсутствие подписи, persistence через две задачи планировщика, скачивание и тихий `/S`-запуск установщика, DPAPI-rekey базы. Это неотъемлемая цена модели «клиент сам обновляется и сам чинится без прав администратора».

**Подпись отложена** (решение владельца 2026-08-04): самоподписанный сертификат работает только там, где корень разложен в Trusted Root / Trusted Publishers, а домена и централизованного управления на заводе нет. Вернуться к вопросу, если появится домен/GPO или возможность купить сертификат публичного CA — это единственная мера, гасящая множитель под всеми остальными эвристиками.

**Что нужно сделать руками на каждой машине** (один раз): в Касперском завести исключение на папку `%LOCALAPPDATA%\Programs` и — обязательно — добавить `MatricaRMZ.exe` и `matricarmz-watchdog.exe` как **доверенные приложения** с «не проверять активность». Одного файлового исключения мало: поведенческий анализ (HIPS / System Watcher) гасится именно доверенным приложением.

## Порядок выката

Фазы 1 (NSIS + пути) и 2 (сторож + headless-режим клиента) выпущены одним релизом: они связаны — новый сторож ищет ярлыки и запускает клиент по новым правилам, а новый установщик кладёт его по новому пути. Первый релиз после этого **обязательно принимать вживую на одной машине** до раскатки: ошибки в `installer.nsh` и в сторожевом Go-коде не ловятся ни линтером, ни тестами — только реальной установкой (проверять `schtasks /Query /TN "MatricaRMZ\Watchdog Periodic" /V` и `watchdog.log`).
