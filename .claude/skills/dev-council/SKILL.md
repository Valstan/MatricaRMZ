# dev-council

Совет доменных советников программы: их ответы → **вердикт** → план → код → **независимая проверка кода**. Канон — [`docs/council/PROTOCOL.md`](../../../docs/council/PROTOCOL.md); реестр и уставы — [`docs/advisors/ROSTER.md`](../../../docs/advisors/ROSTER.md). Этот файл — адаптер: ведёт по шагам, правила не дублирует (ADR-0011).

## Когда загружать (триггер)

- новая сущность, новая граница (право, роль, арендатор), миграция схемы, изменение прав;
- фича задевает **две и более зоны** (карточка · склад · печать · синхронизация · оболочка);
- есть подозрение, что **уже есть готовый обработчик**, а предлагается писать новый (главная жалоба владельца);
- перед крупным релизом-фичей — сквозной проход по ветке (несколько PR одной фичи).

**Не триггер:** рутинная правка, исполнение уже принятого решения, механическая работа, «расскажи, что в репо». Совет ради разговора — вред.

## Что сделать

1. **Первая линза — глобальные обработчики** (до всего остального). Вопрос: **есть ли уже готовый модуль, который это делает?** Ищи **первым делом в реестре** ([`docs/GLOBAL_MODULES.md`](../../../docs/GLOBAL_MODULES.md)), потом в карте ([`docs/CODEBASE_MAP.md`](../../../docs/CODEBASE_MAP.md)) и в ките домена (`shared/src/domain/*`, `electron-app/src/renderer/src/ui/{hooks,components,utils}/*`, `backend-api/src/services/*`). Найден ⇒ план пишет «**внести в существующий**», а не «написать своё».
2. **Заведи совет:** каталог `docs/council/<YYYY-MM-DD>-<тема>/`, шаблоны — [`docs/council/_template/`](../../../docs/council/_template/). Бриф пишется **первым**; первая строка брифа — результат глобальной линзы.
3. **Созыв советников по зонам задачи** (реестр → устав → зона). Режим: консультация (1 зона) · тройка (2–3 зоны) · полный совет (новая сущность/граница/миграция/права).
4. **Ответ каждого** — по контракту протокола (≤1 страницы): вердикт + уверенность · 2–3 варианта с ценой · чем проверяется за день · что заставит передумать · **источники `файл:строка`**.
5. **Отчёт о покрытии** — в брифе, в каждом ответе и в вердикте: `dimensions_done` и `dimensions_failed` (что **не** проверено и почему). Непокрытое измерение, не названное явно, считается проваленным.
6. **Вердикт** (`99-verdict.md`): решение · **раздел «кто против и почему»** · расхождения · покрытие · «передумаем, если…» · что уходит в `docs/pending/` и в план.
7. **Конвейер кода** (если совет приводит к коду): кодер → **проверяющий (вторая роль, не тот же советник)** → доработка → повторный проход. Проверяющий проверяет четыре вещи: (а) всё ли из плана сделано, (б) ошибки и уязвимость, (в) избыточность и повторяющиеся инструкции, (г) **недостаточность функционала против плана**. Право вернуть работу на доработку — перечнем конкретных правок; автор отвечает **пунктами**.

## Формат вывода (в тело PR или в план)

```
Совет: <режим> (<советники>) · глобальная линза: <найден готовый модуль (файл:строка) | не найден, где искали>
покрытие: dimensions_done: [...] · dimensions_failed: [...]
вердикт: <одна строка> · кто против: <кто и чем> · что уходит в план: <ссылка>
```

## Чего не делать

- **Не выдавать права**: совет советует, решение — за владельцем, исполнение — по гейтам (`AGENTS.md` §Autonomy).
- **Не делать прод-операции**: миграции на проде, деплой, правки живых данных — никогда.
- **Не дублировать заводскую линзу**: она отдельная и обязательная для производственного потока (`.claude/skills/factory-lens`); совет её **заменяет**, а не отменяет.
- **Не выдумывать новый механизм**: совет собирает существующие части проекта (кит, реестры, карта, сторожи, гейты).
- **Не писать в чужую зону**: конфликт правок — повод остановиться и спросить, а не «поправить мимо».
- **Не вызывать совет ради совета**: нет вопроса, на который нужен ответ, — нет совета.
