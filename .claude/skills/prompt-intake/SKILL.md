# prompt-intake

Порядок приёма нового задания в Матрице РМЗ. Канон — [`docs/PROMPT_INTAKE.md`](../../../docs/PROMPT_INTAKE.md);
мозг проекта — [`docs/BRAIN.md`](../../../docs/BRAIN.md); роли и уставы — [`docs/advisors/ROSTER.md`](../../../docs/advisors/ROSTER.md);
протокол совета — [`docs/council/PROTOCOL.md`](../../../docs/council/PROTOCOL.md). Этот файл — **адаптер**: ведёт по
шагам, правила не дублирует (ADR-0011).

## Когда загружать

- пришло новое задание: промт из раздела КАРМАНА, заявка владельца, пункт PENDING, задача из поля;
- нить возобновляется после обрыва и непонятно, на какой стадии приёма она стоит;
- нужно понять, кого звать: «это мелочь или надо совет?».

**Не триггер:** задание уже разобрано и идёт по плану — тогда работает `dev-council` или кодер.

## Что сделать

1. **Прочитать задание целиком** — вместе с критериями приёмки и рисками. Критерии приёмки — это и есть план.
2. **Поднять опыт** (не начинать с нуля): `docs/PENDING_FOLLOWUPS.md` · `docs/GOTCHAS.md` ·
   `docs/GLOBAL_MODULES.md` · `docs/council/INDEX.md` · `docs/advisors/<slug>/INDEX.md` и `memory/` ·
   `.claude/skills/` · `docs/COMPLETED.md`. Список — `docs/PROMPT_INTAKE.md` §3.
3. **Определить класс** — мелочь / крупное / спорное — и маршрут:

   | Класс | Маршрут | Кто зовётся |
   |---|---|---|
   | мелочь | координатор → программист | 1–2 роли, совет **не созывается** |
   | крупное | координатор → совет → программист → критик → тестер | разведчик + зональные по затронутым зонам + по признакам эффективщик/скептик/антрополог |
   | спорное | координатор → совет (шут + скептик обязательны) → развилка владельцу | шут, скептик, эффективщик, зональные по теме |

4. **Собрать состав по зонам**, не по симпатии; **максимум 5 ответов** на совет; «простая задача — один эксперт».
5. **Завести разбор:** папка совета `docs/council/<YYYY-MM-DD>-<тема>/` (шаблоны — `docs/council/_template/`)
   и/или запись разбора `docs/intake/<YYYY-MM-DD>-<тема>.md` (шаблон — `docs/intake/_template.md`).
6. **Написать план нитки** в `docs/plans/<slug>.md` — по пунктам, каждый проверяем.
7. **Вести нитку:** программист → критик → тестер → сбор приёмки по чек-листу «план выполнен»
   (`docs/PROMPT_INTAKE.md` §5).

## Формат вывода (в тело PR или в запись разбора)

```
маршрут: <мелочь | крупное | спорное> — почему
кто позван: <роль — зона> (не созывались: <роль — почему>)
что решил совет: <одна строка> · кто против: <кто и чем> · покрытие: done/failed
что сделал программист: <пункты плана> · гейты: <зелёные>
стенд: <прогнан | не требовался: почему>
осталось: <что не сделано и почему>
```

## Чего не делать

- **Не разбирать задание заново при каждом новом** — для этого приём и заведён: опыт поднимается на шаге 2.
- **Не звать совет ради совета**: рутинная правка, исполнение принятого решения, механическая работа — совет не созывается.
- **Не звать всех ролей сразу**: роли включаются по-разному — в мелкой задаче совета нет вовсе.
- **Не пересоздавать роль под задание**: роли заведены один раз и обновляются.
- **Не выдавать права и не делать прод-операции**: совет советует, решение — за владельцем, исполнение — по гейтам (`AGENTS.md` §Autonomy).
- **Не заводить второе хранилище опыта**: находки идут в `docs/advisors/<slug>/memory/`, `docs/gotchas/`, `docs/pending/`, `mailbox/to-brain/`.
