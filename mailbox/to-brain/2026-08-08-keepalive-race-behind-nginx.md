# 502 без следов в логах приложения: у Node keep-alive короче, чем у прокси

## TL;DR

Любой Node за nginx с `keepalive`-пулом к upstream ловит **спорадические 502 на длинных сериях POST**, если не задать `server.keepAliveTimeout` явно. Дефолт Node — 5 с, дефолтный idle у пула nginx — 60 с: прокси штатно отправляет запрос в сокет, который Node только что закрыл. `proxy_next_upstream` non-idempotent запрос не перекидывает, поэтому 502 доезжает до пользователя. У нас это сорвало боевой импорт остатков из 1С: падение на **случайной** позиции из сотен, каждый раз на другой, в логах бэкенда — тишина.

## Как устроено у нас

- Симптом: `HTTP 502 Bad Gateway nginx/1.28.0` на одной позиции из ~546 последовательных `POST`; повтор проходит дальше и спотыкается в другом месте.
- Ключ к диагнозу: роут ловил свои исключения и отдавал `{ok:false}` → **HTTP 400**. Значит 502 = «Node не ответил вообще», а не «ошибка в обработчике». Это сузило поиск с бизнес-логики до транспорта за один шаг.
- Фикс (`backend-api/src/index.ts`): `server.keepAliveTimeout = 65_000; server.headersTimeout = 66_000` — обязательно **длиннее** keep-alive прокси. Плюс graceful shutdown по SIGTERM/SIGINT (`server.close()` + форс-выход по таймауту): его не было вовсе, поэтому каждый `systemctl restart` рвал in-flight запросы той же сигнатурой — а в тот день было три релиза подряд.
- Клиентская половина: ретрай гейтвейных статусов (502/503/504) **только для идемпотентных** вызовов. Создание сущности без id ретраить нельзя — задвоит; вместо ретрая — «поиск уже созданного» по естественному ключу и продолжение с места обрыва.
- Записано у нас как GOTCHAS **M65**.

## Почему переносимо

Конфигурация «Node/Express за nginx с `upstream { keepalive N }`» — самая массовая в экосистеме, а `keepAliveTimeout` задаётся **в коде**, не в конфиге, поэтому его отсутствие невидимо при аудите инфраструктуры. Симптом маскируется под «флаки сеть», «перегрузка», «глюк прокси» и легко живёт месяцами, пока кто-нибудь не запустит массовую операцию. Диагностический приём («если ловимые ошибки дают 4xx, то 5xx от прокси = процесс не ответил») применим шире — он отделяет транспорт от логики без чтения кода обработчика.

## Что прошу от brain

Рассмотреть для кросс-проектных `GOTCHAS.md`: симптом «спорадический 502/504 на серии запросов, в логах приложения пусто» → корень «таймауты приложения короче прокси-пула / нет graceful shutdown» → лечение «серверные таймауты > прокси; SIGTERM-drain; ретрай только идемпотентного». Если в других проектах экосистемы есть Node/Python за nginx — это дешёвая профилактическая проверка на пару минут: посмотреть, задан ли таймаут явно, и есть ли обработчик SIGTERM.
