# Молчащее переименование строки = бесконечный круг правок

## TL;DR

В клиент-серверной синхронизации есть три места, где сервер **обязан сказать клиенту, кто он**, — и каждое из них стоит денег, если сервер молчит. Самое дорогое — молчание о **переименовании**: сервер принимает клиентскую строку, но хранит её под своим id. Клиент подтверждение получает, снимать нечего (id не тот) — и шлёт ту же строку снова. Год такого обмена дал 3.9 млн записей в журнале на одном клиенте.

## Как устроено у тебя

В MatricaRMZ клиент (Electron) держит локальную реплику и шлёт изменения на сервер пачками; сервер пишет их в общий журнал (`ledger_tx_index`) и отдаёт остальным клиентам по номеру. Три места, где сервер и клиент обязаны совпасть по идентичности строки:

1. **Новая серверная таблица должна стоять в трёх реестрах сразу** — список зеркал (обработчик, который снимает «pending» и ставит номер), полный снимок для холодной машины и инкрементальный pull. Пропуск любого: (1) — издатель переотправляет строки каждый тик, журнал пухнет; (2) — свежая машина остаётся без модуля; (3) — живые клиенты не получают строки никогда. Поймали на своих же таблицах: каждый PR был зелёный, потому что сторож проверял только «зеркало → обе карты pull», а не наоборот.

2. **Переименование id строки обязано доезжать до клиента.** Значения атрибутов хранятся по паре «сущность + поле», и если строка уже есть, сервер подменяет клиентский id своим. Про это подмену сервер **не сообщал** (в отчёте о переименованиях были только типы сущностей и атрибутов). Клиент не мог выровнять id, `pending` не снимался никогда, сервер принимал и журналировал ту же строку снова и снова — 4 000 раз за сутки на одной строке. Раздувание было не «где-то в синке», а у одного клиента: видно по `actor_username` в журнале и по тому, что `updated_at` в payload не менялся — менялся только служебный номер.

3. **Журнал изменений должен писать только реальные изменения.** Пока сервер писал каждый пришедший push как изменение, журнал превращался в склад повторов (3.9 млн строк, 3 ГБ, диск бокса на 89%). Правило простое: содержимое не изменилось → записи в журнале нет, а подтверждение клиенту уходит как раньше. Это спасло старых клиентов, которые не понимают переименование: они перестали раздувать журнал сразу, ещё до обновления.

**Диагностика, которая сработала:** «записей в журнале заметно больше, чем строк в таблице» — это первый признак повторов. Дальше — группировка журнала по `actor_username`: если один клиент даёт 90% трафика, дело в нём, а не в системе. И третий признак: `payload` повторов отличается только служебными полями (`last_server_seq`, `sync_status`) — значит, содержимое не менялось и повтор можно не писать.

## Почему переносимо

Любая offline-first система с журналом изменений (работа офлайн + синхронизация + журнал) имеет те же три места. Типичные симптомы, которые выдают эту ошибку:

- клиент «долбит» сервер, а данные не меняются (проверяется по журналу: одна и та же строка десятки раз);
- «pending» не снимается ни при каких условиях;
- сервер-сайд размер базы растёт быстрее, чем реальные правки.

Отдельно ценно правило «**журнал — лог изменений, а не лог приходов**»: как только журнал начал расти по факту прихода, а не изменения, его объём перестаёт быть полезной метрикой и становится мусором.

И ещё: **идентичность строки — общий контракт**, а не деталь реализации. Если сервер вправе переименовать строку (или сгенерировать ей id, или схлопнуть дубли по ключу), это обязано быть в контракте явно — иначе клиент не сможет снять отметку «отправлено», и разница между «успешно синхронизировано» и «застряло навсегда» будет невидима.

## Что просишь от brain

1. **Проверь свои проекты на молчаливое переименование.** Ищи места, где сервер принимает клиентский id, но может заменить его своим (upsert по уникальному ключу, дедупликация, «уже есть такая строка»). Если клиент не узнаёт о подмене — он будет повторять вечно.
2. **Сторож на «зеркало → карты pull» нужен и в обратную сторону.** Проверка «всё, что сервер отдаёт, обязано быть и в зеркалах» ловит пропуск, который проверка «зеркало → отдаём» пропускает.
3. **Возьми на заметку правило:** в журнале изменений не пишется приход, не изменивший содержимое. Это дешевле, чем потом чистить миллионы строк (и чистка — уже не «откат», а необратимая операция).
4. **Если у тебя есть свой формат отчёта о переименованиях** — стоит держать его явным контрактом и проверять, что клиент его читает (у нас он был, но только для двух сущностей из трёх нужных).
