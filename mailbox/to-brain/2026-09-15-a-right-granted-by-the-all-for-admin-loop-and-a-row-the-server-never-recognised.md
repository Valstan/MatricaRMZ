# Право, которое «сняли у всех», и строка, которую сервер не узнавал

Владелец пожаловался: «доступ к редактированию ведомостей вразнобой — слишком много людей допущено, видимо, администраторы». Право `work_sheets.edit` ни одна операторская роль не давала — и тест это закреплял. Но admin / superadmin / легаси `user` получали его молча.

## Находка 1 — «поимённое» право живёт в трёх местах, не в одном

`defaultPermissionsForRole` раздаёт ВСЕ коды циклом (`for code of PermissionCode: all[code] = true`) и вычитает короткий список admin-only. Новый код по умолчанию попадает в «всё админу». Свойство «выдаётся поимённо» держится только если код **явно исключён из цикла** (`= r === 'superadmin'`), как у нас уже было с `audit.view` — и об этом никто не вспомнил при заведении следующего такого права.

Класс: у права три точки, где оно «есть»: (а) цикл ролей на сервере, (б) гейт клиента, (в) серверный гейт записи. Зелёный тест на (б) ничего не говорит про (а). Сторож теперь проверяет буквальную строку исключения в бэкенде.

## Находка 2 — строка, которую сервер различает не по тому полю, по которому она отличается

Строка ведомости уезжает обычным синком как `operations` типа `repair_history_entry` — тот же тип, что ручная запись мастера в историю ремонта. Отличает их только `meta_json.entryType === 'sheet'`. Серверная политика (`ledgerAuthz`) видела лишь `operation_type` и требовала `operations.edit` (есть у мастеров); admin / `user` обходили requirement вовсе. Гейт `work_sheets.edit` стоял только в IPC клиента — то есть снять право «у всех» было бы правдой только для честного клиента.

Вопрос-детектор для любой сущности, которую пишут через синк: **«по какому полю сервер узнаёт эту строку?»** Если по одному лишь типу, а различие в meta — сервер её не узнаёт. Лечение — политика читает meta (`isWorkSheetRowWrite`), а backstop стоит ДО ветки обхода для не-операторских ролей и грузит права и для admin.

У нас — GOTCHAS **M135**, PR #938.
