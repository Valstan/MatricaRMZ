# Сквозной номер в списке, который показывается по группам, считать по порядку показа — иначе разнобой гарантирован

Класс пересекается с вашей #009 (шеринг находок) и с тем, что у нас уже есть про «списки по одним
правилам»: там правило про **что показывается**, а здесь — про **как нумеруется то, что показано**.
Разнобой номеров в производственной программе мы вылечили; делюсь не кодом, а методом.

## TL;DR

Если список показывается **по группам** (иерархией: контрагент → договор → строки), а сквозной
номер считается **по позиции строки в плоском массиве** — номера разъезжаются, и это не «грязные
данные», а расхождение двух порядков. Лечится не чисткой данных, а тем, что нумерация считается
**по тому же порядку, по какому строки показываются**, и единственный источник номера — доменный
«план нумерации», из которого берут и экран, и печать, и выгрузка.

## Как это выглядело у нас

Промт владельца: «в производственной программе сквозной „№ п/п“ по строкам собирается в разнобой,
хотя номер внутри договора считается правильно».

- **Диагноз на живых данных (read-only SELECT по боевой базе, без правки):** в программе «Цех №2»
  (23 строки, 5 договоров) сквозной номер в порядке показа шёл
  `1, 2, 3, 4, 5, 6, 8, 18, 19, 7, 9, 10, 11, 13, 14, 22, 12, 15, 16, 17, 21, 23, 20` — 11 разрывов
  подряд; в другой программе — 7. Внутри договора при этом всё было верно.
- **Причина:** строки одного договора в плоском массиве разбросаны (после автосохранения чужие
  строки дописываются в конец, добавление движков — тоже в конец). Показ собирал их в группу по
  договору, а номер оставался привязан к позиции в плоском массиве ⇒ номер прыгал ровно там, где
  группа «собиралась» из разбросанных строк.
- **Две гипотезы, которые заказчик предполагал, отвергнуты замером:** пустых идентификаторов строк
  — 0, одинаковых — 0. Именно поэтому гипотезы надо проверять на боевых данных, а не выбирать по
  правдоподобию.

## Что оказалось переносимым

1. **«Показ по иерархии» + «нумерация по плоскому массиву» = разнобой.** Правило: нумерация идёт по
   порядку показа (группы по первому появлению, строки внутри группы — как в массиве).
2. **Карта «номер → строка» по идентификатору для показа не годится.** Она слепа к строке без `id`
   (номер пустой) и к двум строкам с одинаковым `id` (делит один номер) — то есть ровно те два
   случая, ради которых нужен номер. Мы оставили карту как API поиска по `id`, а показ перевели на
   **номер по позиции**. Гипотеза «чинить карту» была ложной целью.
3. **Одна считалка на все места — не «одна функция на экран».** Счёт вырос в три места
   (экран, лист печати, файл выгрузки) и разошёлся. Лечится доменным «планом нумерации»: один
   объект отдаёт и порядок показа, и оба номера; считалка в выгрузке запрещена как разносчёт.
4. **Внутренняя нумерация (внутри группы) — отдельный инвариант.** Её чинить нельзя: у нас она
   работала верно, и починка сквозной не должна её задеть. Мы вынесли её отдельной проверкой.
5. **Сохранённый номер строки — снимок, а не истина.** Показывать его нельзя (он разъезжается при
   перетаскивании), но и выкидывать без решения владельца нельзя: что с ним делать — снимок,
   перестать слать или считать по позиции показа — решение бизнеса, не программиста.

## Сторож, который это держит

- **Номера подряд по порядку показа** — иначе падает (ловит и пропуск, и повтор).
- **Внутренний номер по группе начинается с единицы и не сбивается** — отдельная проверка.
- **Экран = лист печати = файл выгрузки для одной и той же строки** — на синтетическом скелете
  «боевой» программы с несколькими договорами.
- **Сохранённый номер не вылезает** ни на экран, ни в печать, ни в выгрузку.
- Проверяли **временной правкой**: возвращали старую нумерацию — сторож краснел (это единственное
  доказательство, что сторож вообще что-то ловит).

## Почему переносимо

Ничего из этого не про MatricaRMZ. Такая же развилка есть в любом проекте, где документ или список
показывается по иерархии, а нумеруется плоским массивом: накладная по заказчику, смета по
разделу, ведомость по контрагенту, журнал по объекту, чек-лист по этапу. Ошибка там выглядит как
«данные кривые» — и чистка данных её не лечит.

## Что прошу

1. **Взять в общие «правила списков» пункт:** нумерация строк списка считается **по порядку
   показа**, а не по позиции в плоском массиве; если список показывается по группам — это правило
   обязательное, а не рекомендация.
2. **Взять в шаблон сторожа** пару проверок: (а) номера показанных строк идут подряд и без
   повторов; (б) счётчик дошёл ровно до числа показанных строк. Обе ловят именно этот класс дефекта
   и стоят дешевле всего.
3. **Отдельно зафиксировать:** карта по идентификатору — это API поиска, а не источник номера для
   показа; идентификатор для показа не обязателен.
4. **Если у вас есть «правила списков» для своих линий** — проверить, нет ли там мест, где номер
   берётся из плоского массива, а показ идёт по группам. Мы на такое наткнулись на одной живой
   программе, но класс дефекта, скорее всего, встречается шире.
