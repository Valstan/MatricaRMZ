# Медленный обход папок: гипотеза владельца была неверна, а killer — не тот, кого ждали

**TL;DR.** Владелец описал «поиск по папкам ползёт по одной папке» и предположил причину:
**«переполнен индекс»**. Проверили — индекса не было **вообще**: ни кэша, ни карты, каждый
поиск начинал полный обход с нуля. Реальный killer — **отдельный запрос метаданных (размер и
дата) на КАЖДОЙ файл обхода**: на дереве в 18 564 файла эти запросы съели **90 % времени**
(2 798 мс из 3 112 мс). Снятие лишних запросов + ограниченный параллелизм обхода дали на тех
же данных **×28…×38**. Переносимо: правило «меряй по фазам ДО оптимизации» и «per-file
metadata в обходе ФС — главный убийца на сетевой папке» работают для любого клиента, который
обходит папки.

## Что было

Модуль «Поиск по папкам» клиента: оператор добавляет папки с фотографиями двигателей и ищет
по названию. Обход шёл **строго последовательно** (`await walk(child)` — папка ждёт папку), и
на **каждый файл** делался отдельный запрос метаданных со своим потолком ожидания. Ни кэша,
ни индекса не было: `await walk(source.path, '', 0)` — полный обход с нуля на каждый запрос.

Симптом, который описал владелец: «на второй папке обход ползёт по одной папке» (первая —
«тёплая», вторая — «холодная»). Это ровно то, что даёт отсутствие кэша: стоимость поиска
пропорциональна числу файлов, а не «индекс переполнен».

## Чем меряли (метод, который стоит повторить)

Написали инструмент, который обходит **одно и то же дерево** двумя режимами и считает фазы
отдельно: «чтение папок» (`readdir`), «метаданные» (`stat`), число запросов, общее время.

| Дерево | «как было» (по одной папке + stat каждого файла) | «как стало» (параллельно, без лишних stat) | Выигрыш |
|---|---|---|---|
| 1 198 папок, 18 564 файла | 3 112 мс, из них **2 798 мс метаданные** | **81 мс**, метаданных 0 | **×38** |
| 201 папка, 4 000 файлов | 220 мс, из них 172 мс метаданные | 13 мс | ×17 |

Вывод, который ушло в код: **метаданные на каждый файл — это 90 % времени обхода**, а сами
папки читаются быстро. На локальном SSD это «всего» 2,8 с на 18 тысяч файлов; на сетевой
папке каждый такой запрос — **сетевой круг**, поэтому разрыв больше.

Отдельно: гипотеза «переполнен индекс» проверялась **по коду** (`git show origin/main:...` —
ни `Map`-а с кэшем, ни карты), и отвергнута за секунды. На «поиск переполненного индекса»
истратили бы часы.

## Что переносится

1. **Правдоподобная гипотеза о причине может быть полностью неверна — и проверяется дёшево.**
   «Переполнен индекс» звучало убедительно, но индекса не было. Сверка с кодом стоила минуту
   и сняла целый ложный путь оптимизации.
2. **Меряй по фазам, а не «всё вместе».** Пока обход — один вызов, видно только «долго».
   Разделение на «чтение папок» / «метаданные» / «число запросов» показало, где именно время.
3. **Per-file metadata в обходе ФС — главный убийца на сетевой папке.** Метаданные нужны
   для показа в карточке, а не для совпадения по имени. Убрали их из пути поиска: размер
   берём **одним проходом** только для файлов, попавших в результат.
4. **Индекс как отдельный фоновый процесс, а не «кеш в том же потоке».** Обход большой
   папки — это долго и это сеть; в главном процессе окно замирает. Сделали отдельный
   `utilityProcess` (как у нас уже есть для чтения базы и синка), с паузой между чтениями
   папок и со **сторожем**: не уложился в разумный срок — процесс гасится, в журнал пишется
   запись, в интерфейсе появляется предупреждение. Молчащее фоновое дело выглядит как
   «программа всё делает», пока она на самом деле висит.
5. **Два пути к одному результату должны считаться одним правилом.** Поиск по диску и поиск
   по карте индекса отдают совпадения через **один** сборщик; иначе «поиск по индексу» был бы
   вторым правилом со своим (чуть другим) результатом, и это тихо разъехалось бы.

## Чего не делали и что осталось за владельцем

Индекс кладём в **машинно-локальное хранилище клиента**, а не рядом с папкой: модуль только
читает, а прав на запись в сетевую папку может не быть. Правило устаревания (карта протухла →
идём по диску, иначе оператор не найдёт свежий файл), порог «карте не старше суток» и «строить
карту автоматически или по кнопке» — это **развилки владельца**, они закрыты по умолчанию и
вынесены в PENDING. Замер на боевой сетевой папке — за владельцем: на локальном SSD разрыв
×28…×38, на его сети будет больше.

Письмо — отчёт, ничего не просим. Тема новая: про «зелёный гейт ≠ работающий гейт» (проверка
подставным нарушением) brain уже знает — здесь другое, про измерение причины медленного обхода.
