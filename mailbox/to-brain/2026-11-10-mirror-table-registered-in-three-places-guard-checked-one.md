# Зеркало синхронизации — это шов из трёх регистраций, и сторож держал только одну

**Одна строка:** у клиент-серверной реплики «строку ведёт серверная дверь, клиент только
читает» есть ТРИ места регистрации, а проверка закрывала только одно из них; вторая и третья
регистрации молча делали две разные поломки — журнал пух и пустая реплика на свежей машине.

## Что случилось (10.11.2026, переверстка модуля «Производственная программа»)

Модуль плана производства писался и принимался по отдельности (каждый этап — свой PR,
каждый PR зелёный). Таблицы плана завели в контракт синхронизации (`tables.ts`, `dto.ts`,
`registry.ts`), владение объявили серверным — и всё, казалось, сделано. Строки писала
серверная дверь, клиент читал реплику.

Потом владелец пожаловался: «двигатель пропадает из плана и возвращается». Разбор вскрыл
**две** независимые поломки, и обе — из-за неполной регистрации:

1. **Журнал пух.** Издатель зеркала публикует строки, у которых `sync_status='pending'`.
   Снимает этот флаг обработчик в `applyPushBatch` (`SERVER_MIRROR_TABLES`). Таблицы плана в
   этом списке не стояли → флаг никогда не снимался → **издатель переотправлял те же строки
   каждый тик (раз в минуту), и журнал рос лишними записями вечно**.

2. **Холодный снапшот был пуст.** Инкрементальный pull читает журнал и работает, но
   «свежая машина» (или после пересоздания реплики) тянет таблицу целиком — через карту
   `PG_SYNC_TABLES` + `pullChangesSince`. Таблиц плана там тоже не было → **новый компьютер
   не получил бы планы никогда**, пока не дождался бы их по частям, через инкрементальный pull.

Плюс третья, менее очевидная: `stampRowSeq` (штамп `last_server_seq`) тоже идёт по карте
`PG_SYNC_TABLES` — без неё строки не получают номера журнала для инкрементального отбора
(`last_server_seq > since`).

## Почему сторож не поймал

Сторож «транспортного шва» был — и он проверял ровно две вещи:

- каждая таблица из `SERVER_MIRROR_TABLES` есть в `PG_SYNC_TABLES` и в `pullChangesSince`;
- каждая таблица **издателя СИЗ** есть в `SERVER_MIRROR_TABLES`.

Вторая проверка шла по **одному** издателю (СИЗ). Издатели новых зеркал — плана производства,
очереди рекламаций, умолчаний подписей — в список не попали, и их таблицы проходили как
«не зеркала», молча. Класс ровно тот, о котором brain уже писал (#166: шов живёт между
задачами, по-задачному ревью не виден): каждый PR был зелёным, шов образовался между ними.

## Что предлагаю в brain

1. **Сторож «издатель → зеркало» должен идти по ВСЕМ издателям, а не по выборочному
   списку.** Правило простое: если файл в каталоге издателей зеркала упоминает
   `SyncTableName.X`, то `X` обязан быть в `SERVER_MIRROR_TABLES` **и** в обеих картах
   pull. Список издателей пусть выводится из структуры каталога, а не пишется руками —
   иначе следующий новый издатель снова выпадет молча.
2. **Регистрация зеркала — один вызов, а не три записи в трёх местах.** Пока «три карты»
   живут раздельно, любой забытый список — это поломка, которая проявляется не сразу.
   Естественное место — реестр контракта: одна запись «это зеркало серверной двери», а карты
   pull и список обработчиков собираются из неё.
3. **Сторож должен ловить не только «есть/нет», но и последствие.** Проверка «издатель
   публикует, а снятия флага нет» — это ровно тот признак, по которому журнал пухнет;
   дешевле проверить его прямо, чем ловить по факту роста журнала.

## Вторая находка в этом же заказе (может, тоже в brain)

**Идентификатор строки, которую правит клиент, должен быть постоянным — иначе журнал
перевозит пары «удалить + вставить», и на экране строка моргает.** В модуле плана клиент
слал черновой id (`draft-…`), сервер заводил новый uuid, а старую строку снимал мягко;
журнал увозил пару, клиент применял её по очереди — между удалением и вставкой двигатель
**исчезал из плана** и через миг возвращался. Владелец видел это как «неправильно
сохраняется». Лечение простое: клиент шлёт `uuid`, который создаёт сам, сервер принимает
его (а чужой id, занятый другой сущностью, — не принимает).

Обобщение: **в системе с журналом изменений идентификатор строки — это часть её
идентичности, а не техническая деталь.** Если клиент может прислать свой id, сервер обязан
принять его (с проверкой на занятость) — иначе каждое сохранение порождает удаление и
вставку вместо правки, а любой читатель, применяющий журнал по порядку, увидит «мигание».
