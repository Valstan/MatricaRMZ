# Дочерний процесс Electron падает на старте из-за импорта, а не из-за вызова

Перенос тяжёлой работы из главного процесса в `utilityProcess` (Electron 43) упёрся в стену, которую не подсказывает ни документация, ни текст ошибки. Две вещи, обе неочевидные:

1. **В `utilityProcess` из модуля `electron` доступны только `net` и `systemPreferences`.** Ни `app`, ни `safeStorage`, ни `dialog`, ни `BrowserWindow`. Код, который «просто читает версию» или «расшифровывает токен», в главном процессе работает годами, а в воркере не имеет права на существование.
2. **Выход сборки — ESM, поэтому статический импорт имени, которого у модуля нет, роняет процесс при загрузке:** `SyntaxError: The requested module 'electron' does not provide an export named 'app'`. Это не «ошибка при вызове функции» — процесс умирает до первой строки собственной логики, и снаружи это выглядит как «воркер мгновенно падает без причины». Диагностика съедает время именно потому, что ищешь ошибку в своём коде, а её там нет.

**Лечение — провайдеры, а не условные импорты.** Всё платформенное движок берёт через узкие интерфейсы, которые главный процесс устанавливает явно при старте: путь к данным, версия, лог, перезапуск (один провайдер); расшифровка сессии (второй — она возможна только там, где живёт ключ ОС: `safeStorage` есть лишь в main); источник ключей E2E (третий). «Импорта по умолчанию» нет намеренно: дефолтная реализация в провайдере тянет `safeStorage` в граф воркера и роняет линковку — то есть страховка сама становится отказом.

Второй капкан того же сорта: **путь к файлу воркера main обязан передать явно.** Внутри чанка `import.meta.url` указывает на `dist/main/chunks/`, а не на `dist/main/`, и `join(dirname(...), 'worker.js')` тихо ищет файл не там. Сборка воркера — отдельный вход той же сборки, путь — параметр.

## Почему переносимо

Класс шире Electron: **недоступный в дочернем процессе платформенный API проявляется как падение при загрузке модуля, а не как ошибка вызова** — тот же симптом есть у worker-потоков в других рантаймах, где платформенные модули не резолвятся, а линкуются статически. Приём «платформенное — только через явно установленные провайдеры, без дефолтов» переносится на любой проект, который выносит движок из главного процесса.

## Что просим у Мозга

Завести запись класса «дочерний процесс: платформенный API недоступен → падение при загрузке, а не при вызове» с двумя разпознаваемыми якорями симптома (`does not provide an export named`, «воркер мгновенно падает без стека») и приёмом «провайдеры ставятся явно».
