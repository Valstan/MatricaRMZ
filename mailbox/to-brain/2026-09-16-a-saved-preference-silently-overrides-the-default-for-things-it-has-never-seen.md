# Сохранённая настройка перекрывает умолчание для того, чего не видела

## Что случилось

Релиз v3.36.0 добавил в список двигателей три колонки дат, объявленных «скрытыми по умолчанию» (`useColumnLayout(id, allColumnIds, defaultHidden)`). Юнит-тесты домена, typecheck, lint — зелёные. Живой CDP-смоук на стенде показал все три колонки **видимыми**.

Причина: хук применял `defaultHidden` только при отсутствии сохранённой раскладки. Если запись есть — новые id из кода просто дописывались в порядок, а `hidden` брался из записи, где новых колонок нет по определению. У любого оператора, хоть раз переставившего колонку (а раскладка ещё и роумится через профиль), каждая будущая колонка выезжала бы на экран сразу.

## Класс

**Persisted-предпочтение × дефолт для новых элементов.** Запись пользователя описывает только то, что существовало в момент её сохранения. Дефолт для элемента должен применяться, если элемента *нет в записи*, а не если *нет записи*. Ошибка одинаково выглядит в раскладках колонок, наборах виджетов, списках уведомлений, порядке вкладок, включённых фичах — везде, где есть «сохранённый набор» и «новый пункт с дефолтом».

Починка — чистая функция `layoutFromPersisted(persisted, allIds, defaultHidden)`: новые для записи id из `defaultHidden` скрываются, виденные оператором не трогаются. Тест на четыре случая.

## Почему заметили

Только потому, что гейт для UI-правок — живой прогон, а не «тест зелёный» (ст. 4 конституции, «verified, not exercised»). Стенд к тому же хранил роумленную раскладку суперадмина — свежий профиль клиента её не сбросил, и это оказалось удачей: чистый стенд дефект бы не показал. Урок для стендов: **держать хотя бы одного пользователя с «пожившими» настройками**, иначе класс «сохранённое × новое» невидим.
