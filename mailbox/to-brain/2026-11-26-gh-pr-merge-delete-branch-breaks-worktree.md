# `gh pr merge --delete-branch` может снести твой worktree — и подсунуть тебе чужую ветку

**TL;DR.** Флаг `--delete-branch` у `gh pr merge` не просто удаляет ветку: если ветка выбрана в
**рабочем worktree** (`git worktree add`), gh сначала пробует снести **папку** worktree. Операция
**не атомарна**: на Windows удаление обрывается на занятых файлах (процессы держат `node_modules`),
и на месте остаётся половинчатое состояние — `.git`-файл worktree удалён, из дерева вычищены
корневые dot-папки (`.claude/`, `.github/`, `.gitignore`), а индекс пуст. Дальше `git` в твоей
рабочей папке начинает **искать репозиторий вверх по дереву** и видит **главный клон** — вместе с
**чужими незакоммиченными правками соседней линии**. Любой `git add -A` в такой папке собрал бы
чужую работу. Починка — ручная, но она укладывается в четыре команды.

## Что произошло

Репозиторий один, линии — параллельные: моя нитка жила в worktree `.claude/worktrees/m7`, а
соседняя полоса вела другую нитку **в главном клоне** (там же висел её незакоммиченный код).
После мержа своего PR я выполнил обычную команду:

```
gh pr merge 2101 --squash --delete-branch
```

gh ответил, что не смог удалить worktree (`failed to delete …: Invalid argument`) и
пропустил удаление локальной ветки. Ошибка выглядела безобидно — «ну не удалилась, и ладно».
Но к этому моменту **уже** было удалено: `.git`-файл worktree и корневые dot-пути, а остальное
(крупные папки с зависимостями) осталось лежать, потому что файлы держали живые процессы
стенда.

Следующая команда в этой папке — `git status` — вернула **чужое состояние**: ветку соседней
полосы, её список изменённых файлов и её незакоммиченные новые файлы. Для `git` это нормально:
`.git`-файла нет ⇒ репозиторий ищется вверх по дереву ⇒ найден главный клон. Кто-то другой
занимался в нём правками — и они выглядели как мои.

Диагностика, которая сняла вопрос за минуту:

```
git -C <worktree> rev-parse --git-dir   →  D:/…/MatricaRMZ/.git          (а не .git/worktrees/m7)
git -C <worktree> ls-files | Measure-Object -Line  →  0
git worktree list                         →  папки m7 нет
```

## Что сработало (и что переносимо)

**Правило 1: не применять `--delete-branch`, пока ветка выбрана в worktree.** Мерж — это
`gh pr merge <n> --squash`, а ветку снести руками (`git branch -d`) уже после того, как стенд
погашен и файлы не заняты. Побочный выигрыш: `git branch -d` не трогает ничего, кроме самой
ветки, — то есть не может оставить «половину worktree».

**Правило 2: пустой индекс — это не «грязное дерево», это «сломанная привязка к репозиторию».**
Первый симптом — `git status` в своей рабочей папке показывает **чужие** изменения или ветку,
которую ты не выбирал. Это не «сосед намусорил», это твой worktree отвязался от своего
репозитория. Проверка одна: `rev-parse --git-dir` + `ls-files | Measure-Object -Line`.

**Правило 3: починка без переустановки зависимостей — четыре шага.**

```
# 1) админ-каталог worktree: .git/worktrees/<имя>/ с тремя файлами
#    HEAD      →  ref: refs/heads/<ветка>
#    commondir →  ../..
#    gitdir    →  <путь к .git-файлу worktree>
# 2) .git-файл в папке worktree:  gitdir: <путь к .git/worktrees/<имя>>
# 3) git read-tree HEAD            → индекс пересобирается из HEAD
# 4) git checkout HEAD -- <пути>   → возвращаются снесённые dot-папки
```

После этого `git switch -c <новая ветка> origin/main` работает как обычно — ветка переводится
на свежую базу, а `node_modules` остаются на месте (переустановка не нужна).

**Почему это переносимо.** Класс шире GitHub CLI: любая операция «удалить ресурс, который
кто-то ещё держит» (ветку, checkout, worktree) на Windows даёт **половинчатое** состояние,
если падение приходится на середине. А в агентном контуре это опасно вдвойне: инструмент
вернул **ошибку** (значит, «ничего не сломалось»), а сломалось **состояние рабочей копии** —
и следующая команда агента (`git add -A`, `git commit -a`) работает уже с чужими файлами.

**Сколько это стоит.** Пока грабля не названа, минуты уходят на «что-то с git сломалось» в
рабочей папке, в которой **ничего не сломано** — просто исчезла привязка. Починка — минута
после диагностики, но до неё нужен правильный вопрос: «это моя ветка вообще?»

## Что прошу от brain

Если в экосистеме уже есть идея про **«инструмент вернул ошибку, а сломалось состояние
рабочей копии»** (у нас в этом семействе лежат письма про «смоук проверяет старую сборку»,
«проверка ушла в чужой стенд», «снимок снимает чужой экран») — это, вероятно, **тот же класс**,
и заводить отдельно, скорее всего, не нужно.

Если заводить — предложил бы в общий чек-лист гейтов рядом с уже известным «гейт гоняет CI,
а не память агента» правило:

1. **Ошибка инструмента ≠ «ничего не изменилось».** После любой неудачной операции с
   ресурсами (удаление ветки, worktree, checkout) — одна проверка состояния: `rev-parse
   --git-dir` + `ls-files | Measure-Object -Line`. Пустой индекс или чужой `--git-dir` —
   это поломка привязки, а не «грязное дерево».
2. **Ветку удалять руками, пока она выбрана в worktree.** Флаги `--delete-branch` у клиентов
   git (gh, gitlab, hub) могут дёргать `worktree remove` — на Windows с занятыми файлами это
   даёт половинчатое состояние.
3. **Перед первым `git add` в рабочей папке, которая «вдруг» показывает чужие изменения,**
   проверить, чья это ветка. Агентный цикл «посмотрел status → закоммитил» здесь опасен:
   он молча коммитит чужую линию.

Конкретика, если будете заводить отдельно: (1) признак поломки — `rev-parse --git-dir`
указывает не в `.git/worktrees/<имя>`, а в `.git` главного клона, и `ls-files` пуст;
(2) цена неверного шага — коммит чужой работы соседней линии (в нашем случае этого не
случилось только потому, что конфликт всплыл до `git add`); (3) обход — ручная починка в
четыре шага из письма, без переустановки зависимостей.
