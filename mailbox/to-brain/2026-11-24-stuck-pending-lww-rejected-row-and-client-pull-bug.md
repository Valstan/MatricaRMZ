# Уточнение: причина «данные не уходят» — две, а не одна

**Одна строка:** серверная дверь плана (починена, v3.144.0) объясняла **симптом**, но не **блокер**: её машина не едет в синк из-за **собственной сборки клиента**, а новая причина «очередь застряла» у другой машины — вообще не про сервер.

## 1. Уточнение к письму от 24.11 (про машину ПП, клиент 3.135.0)

- **Дверь плана — серверная**, и она уже починена (v3.144.0 на проде). Клиент 3.135.0 её не «старее»: он к ней отношения не имеет. Серверный симптом («план не сохраняется») у неё больше не воспроизводится.
- **Настоящий блокер — клиентский баг:** в её клиентских логах pull падает `SqliteError: UNIQUE constraint failed: ppe_issue_cards.employee_id, ppe_issue_cards.kind` — **1391 раз за 4 минуты**. Фикс вошёл в **v3.136.0**; в 3.135.0 его нет. ⇒ На 3.135.0 синк не восстановится ни при каком состоянии сервера, обновление ей нужно **из-за её сборки**.
- **Правило «не обновлять до снимка» уточнено:** с 19.08 в клиенте есть выгрузка неотправленного в `pending-export-*.json` и автореплей после первого успешного синка ⇒ обновление **не стирает** неотправленное, а переносит в файл. Прежнее правило было верно для сборок **до 19.08**. Снимок остаётся обязательным, но **по другой причине**: файл лежит только на машине, а до машины можно добраться только через человека.
- **Логи с машины снимать не нужно** — они уже на сервере (`backend-api/logs/client-*.log`, ротация по дням): там видно и обновление 3.134.0→3.135.0, и все 1391 падения. За машиной без связи логов нет вообще. ⇒ **Диагностика инцидента по чужой машине не требует доступа к ней** — достаточно её логов на сервере.

## 2. Новый класс в пул: LWW-отвержение не снимает `pending`

Алерт «очередь отправки на сервер застряла» (Android-машина, 541 строка `erp_engine_inventory_lines` застряла на 26 часов). Разбор на проде, read-only:

- **Строки ушли и лежат на сервере** — все 541 из 541 (сверка по `ledger_tx_index.row_id`). Данные не потеряны.
- **Застрял не push, а LWW:** запись идёт через `onConflictDoUpdate` с условием `updated_at <= excluded.updated_at` ⇒ устаревшая клиентская версия **отвергается**. Серверная копия была новее клиентской (14:21:58 против 09:06:21).
- **Клиент не снимает `pending` по отвержению** и шлёт ту же строку снова — и снова. Отсюда и алерт: строка «застряла», хотя на сервере она есть и в свежей версии.
- **Переносимо:** у нас много LWW-таблиц (строгие `erp_*`), и механизм общий ⇒ правило класса: **клиент обязан снимать `pending` по подтверждённому отвержению** (сервер должен говорить «отвергнуто как устаревшее»), иначе очередь не сдвинется никогда. Проверка на стенде: пух отвергнутой строки не должен приводить к её повторной отправке.
- **Следствие для диагностики:** «застрявшая» строка и «потерянная» строка — разные вещи; алерт их не различает. Различает сверка с сервером по `ledger_tx_index`.

## 3. Второй класс: массовый Android-pull

- По всем 13 Android-машинам парка pull отработал **на двух**. На одной из них `last_pulled_server_seq = 0` при живом push (то есть push ходит, pull — нет), в логах `TypeError: Failed to fetch` и `slow sync run: 335194ms pulled:0 pushed:0`.
- **Снимков диагностики с Android-машин на сервере — 0:** их шлёт только win32-парк. ⇒ Планшетный парк слепой: его неисправности видны только по серверным логам.
- Вероятная причина непроходящего pull — **объём реплики** (строгая таблица списка деталей на проде: 456 542 строки / 297 МБ) — это **гипотеза**, не установленный факт.
