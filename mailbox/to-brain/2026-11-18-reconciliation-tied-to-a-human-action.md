# Урок: сверка, привязанная к действию человека, — это не сверка данных

**Дата:** 18.11.2026 · **Откуда:** MatricaRMZ, перепроверка модуля оплаты двигателей (промты КАРМАНА #18/#19, PR #1794).

## Что было

В модуле оплаты двигателей по договору у каждого двигателя есть «место» (слот) в конкретном разделе договора (основной договор или ДС N). Сверка «двигатель ↔ место ↔ раздел» считалась **внутри карточки договора при её открытии** — обычный `useEffect` в интерфейсе.

Аудит по прод-данным (18.11.2026, v3.133.0, только SELECT):

- привязано к договору **1703 двигателя**;
- **1010 без раздела** (`contract_section_number` пуст) → не попадают ни в одно место, не участвуют в разнесении аванса и **не видны ни в одной секции карточки** (списки секций фильтруются по разделу, а раздела нет);
- **53 «сироты»** — раздел есть, места нет;
- **9** посажены в место другого раздела;
- мест без двигателя — 3009, из них **55 с деньгами на 34,4 млн ₽** («деньги ждут двигателя»).

## Корень

Разъезд держался на трёх разных местах, и все три — следствие одного решения: **сверка живёт в экране, а не в данных**.

1. Двигатель без раздела отфильтровывался из выборки сверки (`attached` собирается из движков с непустым разделом) → место ему не назначалось никогда.
2. Движок с разделом, но без места чинился **только при открытии карточки** — то есть «починилось» значило «у того оператора в карточке всё в порядке».
3. Движок, посаженный в место чужого раздела, тоже ждал открытия карточки.

База при этом выглядит **связной**: `contract_id` заполнен, движок в списке договора есть. Битым выглядит не список связей, а производные срезы (места, деньги, разнесение аванса) — и их никто не сверяет, потому что сверка живёт в UI.

## Что сделали

- Домен `planBulkEnginePlacement` — раскладка пачки чистой функцией, с предпросмотром до записи: место — **только своей марки**, занятое место **не трогаем**, своих мест не хватило → место **сверх плана** отдельным счётчиком (риск «движок попал не в тот слот», который владелец назвал прямо, закрыт тремя правилами).
- Раздел для движка без раздела берётся **из строк плана договора** (где запланирована марка), а не угадывается; автоподстановка в «основной договор» была бы misallocate денег: раздел определяет, к какому ДС относится аванс.
- Массовое действие в карточке договора: галочки → «Разложить по слотам» / «Перенести пачкой» → предпросмотр → итог → откат к снимку.

## Переносимо

1. **Сверка, запускаемая действием человека, — это не сверка данных, а надежда на то, что кто-то зайдёт.** Разъезд живёт месяцами, а признак «починилось» — «у меня в карточке всё в порядке». Если сверка может быть вынесена в отдельный процесс (скрипт/задача/кнопка «сверить»), она обязана быть.
2. **Запись без дискриминатора = запись вне всех разрезов.** Если иерархия выражена заполнением поля («договор → раздел»), то «привязан, но раздел не указан» — не мусор, а законное состояние, которое надо **либо** автозаполнять по плану, **либо** выносить в явную задачу оператору. Молча исключать его из выборки — значит терять запись без следа.
3. **Связка есть, а производного объекта нет — это отдельный счёт.** Один SQL («привязано N, посажено M, из них без раздела K») стоит делать на данных по расписанию, а не «посмотреть глазами на проде»: в списке связей всё корректно, ломаются только производные срезы.
4. **Деньги, ожидающие объект, — хороший индикатор.** 55 мест с деньгами без двигателя (34,4 млн ₽) показали проблему за один запрос; просто «много пустых мест» её бы не показало.

## Где ещё может повториться

Любая связь «строка → слот/позиция/корзина», где слот создаётся по плану, а привязка строки к слоту идёт из другой сущности. Признак: «связь проставлена, а в производном объекте пусто, и чинится открытием экрана».
