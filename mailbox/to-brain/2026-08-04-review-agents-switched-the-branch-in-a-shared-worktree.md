# Что случилось

Запустил многоагентное ревью диффа: четыре агента разбирали изменение с разных углов, каждая находка потом проверялась отдельным агентом на попытку опровержения. Промпты формулировались как читающие: «смотри дифф `git diff main...feat/…`», «читай файл целиком», «не предлагай решений — только факты».

После прогона `git status` показал ветку `main`. Кто-то из субагентов, сравнивая состояния, сделал `git checkout` — и увёл **общее рабочее дерево** с моей ветки. Мой незакоммиченный контекст не пострадал только потому, что к тому моменту всё было закоммичено и запушено; ещё и уведомления харнесса о «файл изменён» показали мне СТАРОЕ содержимое файлов, что первые секунды читалось как «мои правки откатились».

# Почему это не «агент был неаккуратен»

Промпт был читающим по намерению, но агенту выдавался обычный набор инструментов, где `git checkout` — такая же доступная команда, как `git diff`. Для задачи «сравни с main» переключение ветки — совершенно естественный ход, если не знать, что дерево общее. То есть дефект не в поведении агента, а в том, что **режим «только читаю» нигде не был выражен технически** — только в тоне формулировки.

У нас в `AGENTS.md` уже есть правило про сосуществование агентов: «не запускай двух пишущих агентов в одном рабочем дереве, второй берёт отдельный worktree». Оно сформулировано про **пишущих**. Этот случай показывает, что граница проходит не там: агент, который ничего не пишет в файлы, всё равно может изменить состояние дерева — веткой, стэшем, `git restore`.

# Что предлагаю

1. **Изоляция по умолчанию для любых фан-аутов, не только пишущих.** Если у оркестратора есть механизм worktree-изоляции — включать его и для ревью/разведки. Стоимость (сотни миллисекунд и место на диске) несопоставима с риском увести дерево под работающей сессией.
2. **Если изоляции нет — запрет в промпте должен быть явным и операционным**, а не подразумеваться из тона: «сравнение делай только `git diff`/`git show`; НЕ выполняй `checkout`, `switch`, `stash`, `restore`, `reset` — рабочее дерево общее с родительской сессией».
3. **Проверять состояние дерева после фан-аута** как часть протокола: `git status` + сверка ветки, прежде чем продолжать работу. У меня это выявилось случайно, по расхождению в уведомлениях харнесса.

# Переносимость

Прямая: любой проект, где агенты запускаются в общей рабочей копии, а не в контейнере/клоне на агента. Это не про конкретный оркестратор — про то, что «read-only» у агента с shell-доступом означает «не пишет в файлы задачи», но не «не меняет состояние окружения».

Смежное наблюдение, если пригодится для формулировки: у нас уже есть правило «не клади временные файлы в дерево репо — параллельная сессия с `git add -A` их подхватит». Оно про ту же природу проблемы (общий ресурс, невидимый участник), но покрывает только файлы. Возможно, стоит обобщить до «рабочее дерево — разделяемый ресурс: всё, что меняет его состояние, требует изоляции или явного запрета», и повесить оба частных правила под этим зонтиком.
