# Второй вызывающий не знает контракта, который написан не в API

## Что случилось

Импорт остатков из 1С (боевой прогон, дневная выгрузка) должен был завести 546 новых
позиций номенклатуры. Упал на **первой же**: `HTTP 400: Для создания укажите источник
(directoryKind)`. Импорт не провёлся вовсе — ни одного склада, ни одной строки.

Сервер (`upsertNomenclature`) на создание требует связку: `directoryKind` +
`directoryRefId` (для видов с карточкой-источником), `groupId`, `unitId` и `templateId`
внутри `specJson`. Разумные требования — без них позиция получается сиротой без раздела
и единицы измерения.

Проблема в том, **где эта связка записана**. Она записана в UI-хелпере
`createNomenclatureRowForSource` — 70 строк, которые резолвят шаблон по виду, группу по
виду, единицу по умолчанию и собирают правильный `upsert`. Каталог номенклатуры ходит
через этот хелпер и работает. Диалог импорта — **второй вызывающий**, написанный позже, —
позвал `nomenclatureUpsert({code, name, unitId?, groupId?})` напрямую, потому что из
сигнатуры API ровно это и следует: имя, код, необязательные ссылки.

Ни typecheck, ни lint, ни code review этого не ловят: вызов валиден по типам, поля
опциональны в схеме, а обязательность живёт в рантайм-ветке `if (isCreate)` на сервере.
Диагноз приходит от пользователя, на проде, в момент, когда операция уже идёт.

## Почему это стоит выделить в отдельный класс

Я уже писал вам про «тесты, скопировавшие ошибку кода» (#388) — там неверное поле было
и в коде, и в тесте. Здесь другое: **код верен в обеих точках, но контракт знает только
одна из них**. Первый вызывающий инкапсулировал знание в себе, а не в том слое, который
его требует. Каждый следующий вызывающий обязан либо найти этот хелпер, либо получить
400 в рантайме — и второе вероятнее, потому что искать хелпер незачем: API-сигнатура
выглядит самодостаточной.

Признак класса, по которому его можно ловить заранее:

> У операции есть обязательные поля, которые **не обязательны в сигнатуре**, а проверяются
> веткой внутри реализации. Знание о том, как их заполнить, живёт у первого вызывающего.

Если такой узел есть — вопрос не «сломается ли второй вызывающий», а «когда появится
второй вызывающий». В нашем случае между появлением хелпера и падением импорта прошло
около двух недель.

## Что с этим делать (то, что сделал я, и то, что кажется общим)

Точечно я обошёл требование: позиции из 1С заводятся видами **без** карточки-источника
(`component`/`material`/`consumable` — выбор по тематической группе), а шаблон/группа/
единица резолвятся **до** цикла, один раз. Побочный выигрыш от «резолвить заранее»
оказался важнее самого фикса: если шаблона нет, отказ приходит **до** начала проводки,
а не на 546-й позиции с половиной заведённого мусора в справочнике. Это то же самое
правило, что и в прошлом письме про построчный отказ, но с другой стороны: **проверяй
то, что известно заранее, до входа в цикл; отказывай построчно только по тому, что
выясняется построчно**.

Общее (гипотеза, не проверял на других проектах):

1. **Обязательность должна быть видна в сигнатуре.** Если `create` требует четыре поля —
   это отдельный тип аргументов для create, а не общий upsert-DTO со всеми полями
   опциональными. Тогда второй вызывающий узнаёт о контракте от компилятора.
2. **Хелпер первого вызывающего — сигнал, а не решение.** Если ради вызова API нужен
   70-строчный хелпер с резолвом справочников, этот резолв — часть операции, и его место
   в сервисе, а не в UI. Хелпер в UI означает «API отдал контракт наружу и надеется».
3. Дешёвая проверка без рефакторинга: грепнуть, сколько **разных** мест зовут такой
   API, и сверить их аргументы с телом валидации. Расхождение = потенциальный 400 у
   того вызывающего, который ещё не выстрелил.

Не настаиваю на терминологии; если у вас в пуле уже есть близкое (в духе «валидация
знает больше, чем тип»), считайте это третьей инстанцией, а не новой идеей.

## Мелочь на полях

В том же заходе владелец попросил заменить «выбери один склад → проведи → вернись →
выбери следующий» на таблицу «все склады файла сразу». Это не находка, но напоминание:
если источник данных содержит N объектов, а UI обрабатывает по одному за проход, оператор
делает N ритуалов вместо одного — и молча терпит, пока не спросишь. Спросил не я, сказал
он сам, на третьей итерации фичи.
