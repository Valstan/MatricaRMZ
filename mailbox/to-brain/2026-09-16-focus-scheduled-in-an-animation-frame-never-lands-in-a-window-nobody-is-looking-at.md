# Фокус, назначенный на кадр анимации, не доезжает в окне, на которое не смотрят

## Что случилось

Делали правку строки прямо в списке: щелчок по ячейке превращает строку в редакторы, и курсор
обязан встать в ту колонку, по которой щёлкнули. Наводку фокуса отложили в
`requestAnimationFrame` — из осторожности: ряды виртуализированы, и хотелось дать таблице
дорисоваться.

Живой e2e-прогон по CDP показал: курсор не встаёт **никуда**. Ни в кликнутую колонку, ни в
запасную. При этом всё остальное на экране работало — строка раскрывалась, поля принимали ввод,
сохранение шло.

Причина: окно стенда не активно (прогон идёт «мимо глаз»), а в неактивном или перекрытом окне
кадры анимации не приходят — колбэк `requestAnimationFrame` просто никогда не вызывается.
Код, который «отработает на следующем кадре», в фоне не отрабатывает вовсе.

## Почему это стоит вынести в класс

1. **Тесты этого не ловят и поймать не могут.** Юнит-тесты проверяли модель рядов, сторожа —
   разметку и правила, типы и линт были зелёные. Дефект живёт ровно в стыке «браузер + окно не
   в фокусе», и виден только живым прогоном.
2. **В проде оно бы «работало».** У оператора окно активное, кадр приходит, курсор встаёт.
   То есть дефект воспроизводится у тех, кто гоняет автоматические прогоны, и прячется от
   ручной проверки — худший вид расхождения.
3. **Правило общее, а не про фокус.** Любое «сделать после отрисовки» через `rAF` — замер
   размеров, доскролл к элементу, наводка курсора, снятие плейсхолдера — молча не выполнится в
   фоновом окне. Если действие обязано случиться, `rAF` не годится как единственный путь.

## Лечение, которое у нас прижилось

Пробовать **синхронно** в эффекте: к моменту эффекта нужный узел уже в DOM, если он попал в
текущий коммит. Кадр оставить **запасным** — на случай, когда узла ещё нет (список прокручен
от начала, ряд вне окна виртуализации):

```
if (tryFocus()) { done.current = id; return; }
const frame = requestAnimationFrame(() => { if (tryFocus()) done.current = id; });
return () => cancelAnimationFrame(frame);
```

## Второй слой той же ловушки (стоил отдельного круга)

Отметку «этому редактору фокус уже наводили» мы сперва ставили **до** кадра. В React StrictMode
эффект прогоняется дважды: первый проход ставит отметку и планирует кадр, очистка кадр отменяет,
второй проход упирается в собственную отметку и уходит ни с чем. Итог — фокус не наводится
никогда, причём только в dev-сборке.

Правило: **отметка «сделано» ставится там же, где делается дело** — внутри колбэка, после
успеха, а не рядом с планированием. Иначе отмена отложенной работы оставляет систему в
состоянии «считаем, что сделали», не сделав.

## Что мы забрали себе

- В профиль машины и в правила стенда: подозрительный к фокусу/замеру шаг проверять живым
  прогоном, а не доверять «на кадре сработает».
- В код: `rAF` — только как запасной путь, синхронная попытка первой.

Ответа не требуется — кладём как переносимый урок.
