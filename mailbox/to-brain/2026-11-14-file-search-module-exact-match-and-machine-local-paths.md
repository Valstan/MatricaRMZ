# Поиск по файлам: три переносимых правила

**Как нашлось.** Промт КАРМАНА #32 (владелец, 13.11.2026): «Модуль поиска информации по файлам: выбор источников, свежие версии перед каждым поиском, результаты с копированием и переносом в карточку двигателя». План #33 — разбор, свежесть, результаты, перенос. Модуль сделан 14.11.2026 (PR #1732), смоук 13/13 PASS.

**Находка 1 — «своё место настроек пользователя» ≠ «профиль пользователя».** Задание говорит: «программа запоминает пути к этим файлам». Самое естественное место — профиль пользователя (он так и называется «личные настройки»). Но профиль **роумится**: он лежит на сервере и приезжает на любую машину пользователя. А путь к файлу на другой машине **невалиден** — и список, который уехал на сервер, приносит на другой компьютер ровно одно: недоступные файлы. Правильно: **машинно-локальное хранилище** (у нас — key/value `sync_state`, карта по пользователю). Признак класса: в настройке лежит **путь на конкретной машине** (файл, папка, каталог, принтер) → она не должна роумиться; лежит **предпочтение работы** (раскладка, фильтры, шаблоны) → должна.

**Находка 2 — в связке «файл → учёт» совпадение только точное.** Модуль ищет номер двигателя в файлах оператора и показывает справа карточку из базы, чтобы перенести найденное. Очевидная соблазнительная оптимизация — взять «похожий» номер («41» против «41/26», «Д-100» против «Д-10») и показать «похожую» карточку. Это ловушка: перенос данных из файла в учёт **по нестрогому совпадению = запись не туда**, и заметить это нельзя — запись проходит гейты (номер уникален, формат сходится), просто в чужую карточку. Правило: **в «файл → учёт» — только точное совпадение; неоднозначность («41» у трёх двигателей) — это вопрос оператору («уточните номер с годом»), а не выбор первого**. Тот же ход работает в обратную сторону: автоперенос разрешён только при совпадении типа и формата, при несовпадении — объяснение, а не тихая запись.

**Находка 3 — недоступный файл в списке источников не должен ронять поиск.** Файлы оператора живут на его диске и в его сети: диск мог отвалиться, файл мог быть переименован, сетевая папка могла лечь. Правильный порядок: **показать полный путь и сказать «откройте заново», поиск по остальным файлам продолжить**. Наш первый смоук это показал буквально: фикстура лежала по относительному пути, главный процесс её не нашёл — и модуль отработал ровно как задумано (путь в блоке «не прочитались», остальные файлы ищутся дальше). Побочная выгода: «свежая версия перед каждым поиском» (перечитывание файла) бесплатна именно потому, что неудача ловится поимённо.

**Как проверялось.** Домен (матчинг строк и абзацев, предпросмотр переноса, недостающие характеристики) — 12 тестов; чтение файлов в главном процессе (xlsx через `exceljs`, docx через `JSZip` + чистую `docxXmlToText`, текст) — 7; точный поиск двигателя — 5; IPC — 3; сторож страницы — 7. Живой смоук: раздел открывается, файл виден, строка Excel найдена целиком с наименованиями столбцов, справа карточка с перечнем недостающих, предпросмотр переноса открывается, кнопка копирования кладёт значение в буфер, **файл на диске не изменился**. План нити — `docs/plans/file-search-module-2026-11.md`.

**Что переносимо в другие проекты.**

1. **Настройка с путём на машину — машинно-локальная; профиль — для того, что едет между машинами.** Профиль роумится, и роум списка файлов = список недоступных файлов.
2. **Перенос извне в учёт — только по точному совпадению.** Неоднозначность — вопрос оператору, «похожее» — не ответ.
3. **Список внешних источников — fail-soft по элементу:** один недоступный файл = сообщение с путём и продолжение поиска, а не отказ всей операции.
