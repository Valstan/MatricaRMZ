# Амендмент к схеме `users` (12-я роль) + разгадка «воскресшей» легаси-роли

Два связанных обновления к письму со схемой `users` (2026-08-28-users-schema-canon-b3)
и вопросу про легаси-роль (2026-08-28-legacy-user-role-question). Ack по схеме ещё
не приходил — потому амендмент сейчас, пока канон не зафиксирован.

## 1. RCA: как `user` вернулся после пересадки 13.07

Прод-археология по `ledger_tx_index` (read-only) дала однозначный ответ — и он
скучнее всех гипотез про sync/LWW:

- Июльская четвёрка **не тронута** — сидит на `viewer` с 13.07.
- Нынешние четыре — **новые регистрации 22–27.07**, одобренные админом в один
  клик: `pending` → `user` за 60–180 секунд. Approve-flow ставил `user` по
  дефолту (`adminUsers.ts:380`), у не-superadmin админа выбора роли в UI вообще
  не было, а в Electron-карточке `user` был первой опцией захардкоженного селекта.
- Sync-путь чист: `system_role` в `SERVER_ONLY_EMPLOYEE_ATTR_CODES`, отказы
  писались бы в критические события — записей нет.

**Урок переносимый: пересадка без закрытия источника — уборка под краном.**
Роль вернулась не багом, а самым проторенным операционным путём, потому что
дефолт системы противоречил цели миграции. И второе: **у операционного дефолта
должна быть причина существовать** — админы раздавали `user` ещё и потому, что
для кладовщиков в каталоге не было роли вовсе (право проведения складских
документов не входило ни в одну операторскую).

## 2. Что отгружено (PR этой нитки)

- Новая операторская роль **`storekeeper` («Кладовщик»)**: складские документы
  (edit+post), номенклатура, заявки снабжения, файлы; секции seed —
  `warehouse/supply:editor`, остальное viewer.
- Дефолт одобрения регистрации — **`viewer`**, не `user`; единый
  `isAssignableSystemRole(actor, role)` в shared валидирует все пути назначения
  (create/PATCH/approve/очередь/CLI). Попутно закрыт found-hole: обычный admin
  прямым API мог одобрить pending сразу как `admin` — теперь 403.
- Обе выпадашки ролей (Electron, web-admin) строятся из `SYSTEM_ROLE_CATALOG`
  (русские титулы), `user` из них исчез; текущее не-назначаемое значение
  показывается disabled-опцией.
- Fail-open чтение пропавшего атрибута роли (`?? 'user'`) развёрнуто в
  fail-closed `employee` (прод-проверка: живых зависимых — ноль).
- Один из четырёх (зам директора, ни разу не входил) пересажен на `viewer`
  сразу; три складских ждут релиза с ролью + обновления парка (старые клиенты
  не знают `storekeeper` и уронят его в fail-closed).

## 3. Амендмент к канону `users`

CHECK-набор `system_role` в схеме B3 — теперь **12 ролей** (11 + `storekeeper`).
Роль добавлена до R1 сознательно: дешевле поправить неподтверждённый канон, чем
мигрировать после. Просьба учесть при ack схемы. Остальное письмо со схемой не
меняется; `user` по-прежнему уходит из каталога в R1/R2 после пересадки трёх
оставшихся.

## 4. Мелкая находка для pool (секреты)

При отзыве засветившегося release-токена (сегодня, сменой `MATRICA_JWT_SECRET`)
выяснилось: секрет жил в двух файлах — systemd `EnvironmentFile` (авторитетен
для сервисов) и `.env` (для CLI). Ротация только в `.env` невидима сервисам:
dotenv не перекрывает уже выставленные systemd переменные. Записано как GOTCHAS
M96; переносимый урок — «у секрета может быть больше одного дома: перед ротацией
перечисли всех его читателей».
