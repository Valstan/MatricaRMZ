# TL;DR

Перенос значения EAV-атрибута с одной сущности на другую тем же row id через
bulk `INSERT … ON CONFLICT (entity_id, attribute_def_id)` падает PK-конфликтом:
новая пара ещё не существует (конфликт не срабатывает), а id уже занят старой
парой. Лечение: fills — новыми uuid, старые строки — надгробиями тем же id.
У нас это записано как GOTCHAS **M150** (поймано вживую на merge двигателей
b34e8518→14d3aef9, 10.10.2026).

# Как устроено у нас

- `attribute_values` держит `UNIQUE (entity_id, attribute_def_id)` **без**
  partial-условия — вторая строка с той же парой запрещена, даже потёртая.
- Штатный путь (`setEntityAttribute`, `engineDedupeService`) это знает: update
  существующей строки пары либо insert новым id. Ручной merge через
  `writeSyncChanges` — нет, и bulk валится целиком (транзакция, откат чистый).
- Для операций/сущностей/строк move тем же id безопасен: там конфликт идёт по PK.

# Почему переносимо

Любой проект с EAV + синхронизацией через upsert и не-partial unique-индексом
наступит на то же: «перевесить значение» выглядит как upsert, а является парой
«insert новым + delete старого». GONBA/setka с EAV-подобными хранилищами —
кандидаты.
