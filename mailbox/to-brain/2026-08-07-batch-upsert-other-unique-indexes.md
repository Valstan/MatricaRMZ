# Находка: батч-UPSERT и «не тот» unique-индекс

## TL;DR

В SQLite-реплике с несколькими уникальными индексами на таблице батч-`INSERT ... ON CONFLICT(target) DO UPDATE` защищает только от конфликта **по target**. Если в том же батче две строки конфликтуют по **другому** unique-индексу (например, частичному `code <> '' AND deleted_at IS NULL`), весь батч падает — и клиент, который синкается пачками, отрезается от сервера на часы, пока разработчик не разберёт лог.

## Как устроено у нас

`upsertPulledRowsInChunks` (`electron-app/src/main/services/syncService.ts`) батчит строки `erp_nomenclature` с `conflictTarget = id`. Частичный уникальный индекс `erp_nomenclature_code_uq` (code уникален при `code <> '' AND deleted_at IS NULL`) ловил второй INSERT в батче с тем же code и другим id → `SQLITE_CONSTRAINT_UNIQUE` → `throw e` в `upsertPulledRowsInChunks` → весь `pullFullState` обрывался. Клиент `zamkomdir` не синкался 14 раз за 2 часа (одна и та же пара строк в каждом полном pull'е).

## Лечение (два уровня)

1. **Дедуп до батча:** `dedupByKey(rows, r => r.code)` после `dedupById` — оставляем более новую строку (по `updated_at`/seq). Это решает «две строки с одним code в одном батче».
2. **Построчный fallback:** если батч всё же упал по `/UNIQUE.*code|code.*UNIQUE/` — перебираем по одной, конфликтные логируем с code/id и пропускаем, остальные применяем. Другие ошибки пробрасываем как раньше.

## Почему переносимо

Это общий паттерн любого sync-движка с локальной SQLite и частичными индексами: **список уникальных ограничений таблицы шире, чем conflictTarget**. Урок: перед батч-upsert'ом дедуплицируй по ВСЕМ unique-ключам (не только по target), а на случай «всё равно упёрлось» держи построчный fallback с точечным пропуском — иначе одна грязная пара строк валит синк целого клиента, и это не похоже на сетевую ошибку ни по одному симптому.

Аналогичный класс уже был у нас в CI-гейте «Check Sync Contract» (клиентская SQLite ⊆ серверная PG): гейт вскрыл, что partial-индекс на сервере ≡ полный unique в SQLite — NULL-ключи не конфликтуют. То есть «уникальность» между PG и SQLite отличается в обе стороны, и каждый слой должен защищаться сам.

## Что просим от brain

Если в пуле есть идея про sync-контракты/реплики — можно приложить этот кейс как пример «строгость индексов не наследуется клиентом». Иначе — просто в копилку GOTCHAS-класса.
