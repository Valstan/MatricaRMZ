# Локальный MiniMax на клиенте: код готов, один развилка — к владельцу

Нитка по промтам КАРМАНА **#59** (задача) + **#62** (план v2) + решения **#61** (D-243) и **#63**
(D-244). Зона — клиент: серверный MiniMax-воркер (промты #56/#57, PR #1900/#1904) не трогали.

## Что сделано

Клиентский модуль `electron-app/src/main/services/localMiniMax/`: клиент «Кармана» (выдача и
продление аккаунта, заголовки комнаты и машины), профиль MiniMax Code (токен-стор с ключом от пути
авторизации), **молчаливый** запуск (`windowsHide`, не `detached` — грабля M214), read-only мост к
локальной реплике (MCP-сервер `db_schema`/`db_table`/`db_query`), резерв с машины (DeepSeek,
Anthropic-совместимый эндпойнт, **клиентский** ключ) и оркестратор с честными отказами. Плюс путь
записи ответа: клиент берёт свой вопрос в работу (`status=processing`) и кладёт ответ сам; серверная
дверь — одна новая ветка в `aiChatPushPolicy.ts`. Гейты зелёные, 34 новых юнит-теста.

Открытые шаги — комната «Кармана» для клиентов, рантайм в сборке и смоук на живой машине — в
`docs/pending/lokalnyy-minimax-na-kliente-privyka-i-runtaym.md`.

## Открытый вопрос плана закрыт: MCP в `mcode exec` работает

План #62 п. 8 сомневался, поддерживает ли `mcode exec` MCP-серверы в неинтерактивном режиме.
**Поддерживает.** Проверено по пакету `@minimax-ai/code` 0.7.4 (тот же, что стоит на боксе):
рантайм сам подхватывает проектный `.mcp.json` из рабочего каталога — правило общее с Desktop и
ACP; отдельно есть глобальный `mcp.json`, бюджет discoverystdio-MCP — `MCODE_MCP_STDIO_DISCOVERY_TIMEOUT_MS`
(по умолчанию 30 с). То есть read-only доступ агента к локальной базе — штатная конструкция, а не
костыль.

**Побочная находка, важная для портфеля:** локальная реплика «Матрицы» **зашифрована** (SQLCipher,
ключ под DPAPI), поэтому открыть её из процесса агента нельзя — ключ доступен только Electron. Мы
сделали мост: базу держит приложение, агент спрашивает по **именованному каналу Windows** (без
порта и без правила брандмауэра), пишущие операторы отбивает сам SQLite (`Statement.reader`). Если
в портфеле появится ещё один потребитель локальной базы извне Electron — это готовый образец.

## Развилка к владельцу: порядок цепочки D-243 несовместим с claim'ом

D-243 задаёт цепочку **локальный MiniMax → MiniMax на проде → DeepSeek (с клиента) → DeepSeek
(на проде)**. Мы сделали **локальный MiniMax → DeepSeek с клиента → сервер**. Расхождение не по
формулировке, а по механике:

1. **Пока клиент держит вопрос, серверный воркер его не берёт** — иначе ответили бы оба и
   платный DeepSeek сгорел бы впустую. Значит, prod-MiniMax вторым звеном не получает шанса:
   либо он получает его только для вопросов, которые клиент не взял.
2. **Локальный MiniMax и prod-MiniMax берут аккаунты из одного бесплатного пула.** Когда пул пуст
   (сейчас он пуст почти всегда), второе звено всё равно не ответило бы.
3. **«DeepSeek с клиента» третьим звеном без серверной координации не получается:** сервер после
   неудачи prod-MiniMax сразу уходит на свой DeepSeek (fail-open, D-243) — платный вызов успевает
   раньше клиентского.

**Что это даёт по деньгам:** при исчерпанном пуле платит **клиентский** ключ, а не серверный —
ровно смысл D-244 №3 («ключ DeepSeek для клиентов — отдельный: свой баланс, своя ротация; продовый
DeepSeek остаётся последним страховочным звеном»).

**Если нужен буквальный порядок D-243**, нужна серверная правка: сервер должен выждать окно, прежде
чем уходить на свой DeepSeek (иначе клиент не успевает). Это правка в зоне первой нитки
(`llmProvider`/`aiChatAnswerService`) — в эту нитку мы её не вносили.

**Просим решения:** (а) оставляем порядок «MiniMax → клиентский DeepSeek → сервер», или
(б) правим серверное fail-open, чтобы клиентское звено успевало раньше.

## Ещё одно отклонение, мелкое

План #62 п. 6 предлагал источники ответа `local_minimax` / `minimax_prod` / `deepseek_client` /
`deepseek_server`. Серверные два уже названы `engine` / `deepseek` первой ниткой — их писатель в
чужой зоне, поэтому оставлены как есть; добавлены два клиентских. Смысл полон, набор из четырёх.

## Переносимая находка (в pool)

**Дешёвое локальное звено + серверный fail-open без claim'а = платим дважды.** Клиентский движок
берёт вопрос в работу (`status=processing`), а серверный воркер такие строки не берёт; ответ
кладёт автор своего вопроса через ту же push-политику. Это общий класс для любой цепочки
«дешёвое звено на машине → дорогое на сервере»: без явного владения вопросом платный вызов
происходит параллельно с бесплатным. Проверено тестами на push-политике.
