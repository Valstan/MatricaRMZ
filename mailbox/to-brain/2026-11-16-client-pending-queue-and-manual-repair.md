# Клиент копит неотправленные строки молча: как увидеть очередь без доступа к машине и как починить её вручную

Инцидент 16.11.2026 (оператор СИЗ, клиент PC63): клиент опубликовал на сервер сущность нового сотрудника, но **не опубликовал её атрибуты** — ФИО, должность, табельный номер, даты. Серверное зеркало СИЗ берёт сотрудников по ФИО, поэтому без атрибутов не было ни карточки СИЗ, ни сотрудника в списках — у всей партии. Шестеро таких сотрудников накопились за неделю.

## Что переносимо

**1. Очередь клиента видна только из клиентского снимка.** `diagnostics_snapshots` со `scope='client'` — единственный источник pending/error по таблицам клиента без доступа к его ПК: `payload_json->'tables'-><table>->'pendingCount'` и `errorCount`, плюс список pending-сущностей по типам с подписями (`entityTypes.<type>.pendingItems`). Логи клиента лежат на его машине, `audit_log` показывает только действия оператора. Наш снимок показал: 617 зависших строк `attribute_values` при нуле на всех остальных машинах парка — по этому счётчику инцидент и был найден.

**2. Autoheal при `critical` упирается в дневной бюджет и скипается молча.** В журнале это видно как `autoheal_signal` уровня `critical` рядом с `autoheal → action=skip, reason=daily_budget_exceeded` — дрейф не лечится, пока бюджет не восстановится. Лечение можно поставить руками **тем же путём, что использует autoheal**: `setClientSyncRequest(clientId, {id, type, at, payload})` → `client_settings.sync_request_type`. Бюджет при этом не проверяется — команда уходит клиенту сразу, и клиент её исполняет.

**3. Команды починки не равны по силе.** `reset_sync_state_and_pull` — только сброс курсора плюс обычный синк: зависшие строки он **не** разгребает. `force_full_pull_v2` (и `deep_repair`) — пересборка реплики из сервера: очередь обнуляется, локальные строки, которых нет на сервере, исчезают. `reinstall` — команда для внешнего watchdog'а, приложение её не исполняет и не подтверждает. Выбор по симптому: «курсор догнал, а данные не те» → `force_full_pull_v2`.

**4. Потерянную карточку можно восстановить без потерь.** Когда клиент создал сущность, но не отправил атрибуты, **данные остаются в `card_drafts` (kind='recovery')** — это снимок формы, который клиент публикует по ходу правки. Из него атрибуты восстанавливаются как обычные `attribute_values` через журнал синка: принадлежат они оператору, а не «наша догадка». Мы так вернули шестерых сотрудников (77 атрибутов) и прогнали зеркало.

## Правило (предложение)

Считать «клиент опубликовал сущность без атрибутов» самостоятельным классом инцидента: он не виден ни в данных, ни в аудите, а сотрудник просто исчезает из списков. Сторож — сверка по журналу: сущности без единого `attribute_values` дольше N минут.

## Незакрыто

Точный путь, на котором клиент перестал отправлять пакет с атрибутами, в коде не найден: сервер отвергнутых строк не видел, а снимок показывает только счётчики. Нужен лог клиента (`matricarmz.log`) или воспроизведение на стенде.
