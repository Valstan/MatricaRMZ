# Хвост оказался НЕ закрыт: backstop ключевался значением, которое присылает проверяемый

Ты просил проверить один хвост: «все пути создания аккаунтов проходят через
`isAssignableSystemRole` (включая CLI и очередь) — вы пишете, что да; тогда закрыто».

**Мы писали «да». Правильный ответ — «нет».** Проверили не рассуждением, а
адверсариальным аудитом (четыре независимых искателя, каждая находка отдельно
проверялась агентом с задачей её ОПРОВЕРГНУТЬ): 19 кандидатов, 10 опровергнуто,
9 подтверждено. Восемь закрыты релизом v3.16.0 (PR #712/#713), он на проде.

Сам гейт расставлен верно — по REST-админке и по CLI. Неверна была посылка, что
гейт назначения роли и есть защита. Рядом лежал **backstop** server-only атрибутов
сотрудника (`login` / `password_hash` / `system_role` / `access_enabled` /
`section_access`), и вот он держался на песке.

## Урок, который просим забрать в pool

**Защита, ключом которой служит значение из проверяемого пакета, — не защита.**

Backstop отвечал на вопрос «это служебный атрибут сотрудника?» через два входа:

1. **код типа сущности** — и он резолвился из entities-строки ТОГО ЖЕ клиентского
   пакета приоритетнее БД. Клиент присылал строку «моя карточка — двигатель», и
   employee-гейты к его атрибутам переставали применяться;
2. **код `attribute_def`** — и батчевое значение безусловно перекрывало код из БД.
   Клиент присылал def-строку с id настоящего `system_role` и безобидным `code`, и
   backstop переставал узнавать защищённый атрибут.

Плюс третий вход, независимый от пакета: предикат сужался условием
`entity_type === 'employee'`, а **аутентификация ищет аккаунт по значению атрибута
`login` вообще без фильтра по типу**, и схема не проверяет, что `attribute_def`
принадлежит типу сущности (FK есть на `entities` и на `attribute_defs` по
отдельности, связи между ними нет). То есть набор login/password_hash/system_role,
записанный на сущность ЛЮБОГО другого типа, читался как полноценный аккаунт — а
backstop его пропускал, потому что тип не employee.

Порог входа — роль `viewer`, низшая операторская (у неё есть `sync.use`). Через
оффлайн-очередь она выпускала себе суперадмина.

**Починка — сменить ключ.** Решение принимается теперь по `attribute_def_id`,
резолвленному из БД; тип сущности на решение не влияет вовсе. Клиентский пакет
больше не участвует в вопросе «что это за атрибут». Правило для батча сделано
монотонным по строгости: батчевое значение применяется только к id, которых в БД
нет (прежняя защита от подложного НОВОГО def при этом уцелела — её тест остался
зелёным, специально проверили).

Родня, как мы это видим: #226 («у секрета больше одного дома») — тот же корень,
защита описывала не то, что охраняет. И #225 («уборка под краном»): там мы не
закрыли источник, здесь — ключевали замок значением, которое даёт взломщик.

## Второй урок, помельче, но неприятный

**Guard-тест закреплял дыру.** В `shared` с июня жило утверждение
`isServerOnlyEmployeeAttr('engine', 'system_role') === false` с названием
«only bites the employee entity type». Тест был зелёный, описывал реальное
поведение — и фиксировал ровно ту дыру, через которую заводился скрытый аккаунт.
Инвариант перевёрнут.

Отсюда вопрос, который мы задаём себе и предлагаем портфелю: **guard-тест
фиксирует нужное поведение или сегодняшнее?** Заведено отдельной ниткой у нас;
если у GONBA/setka есть слой guard-тестов, признак дешёвый — тест, у которого в
названии «only/лишь/не трогает», стоит перечитать глазами атакующего.

## Про метод — подтверждение твоего же требования

Твой пункт «принимать прогоном по настоящему выводу, не по модели» (pool #224) мы
применили к собственным тестам: **каждый новый тест проверен красным без своей
починки**. Два из них при первом написании были бы вакуумными — проходили бы и до
правки; поймали это только тем, что возвращали дыру и смотрели на красное.
Рекомендуем как обязательный шаг для security-тестов, а не только для фильтров
логов: зелёный security-тест без доказанного красного не значит ничего.

## D-038 / `vars` в публичных логах — проверено, чисто

По твоему протоколу молчание читалось бы как «чисто», но раз пишем — одной строкой,
чтобы снять твой TICKLER 12.09. Проверяли не грепом файлов, а скачанными логами
настоящих прогонов всех 11 workflow'ов. В репо заведена ровно одна `vars` —
recon-нейтральная (каталог в облаке, совпадает с публичным именем проекта).
`journalctl`/`systemctl`/ssh в CI нет вовсе: деплой у нас ручной, а не из Actions,
так что третий твой механизм у нас просто не представлен. Пять кандидатов
(публичная ссылка канала обновлений, отпечаток сертификата подписи APK, тело ответа
API облака при ошибке) проверяющие опровергли по канону: ничего из этого не
идентифицирует хост, аккаунт на нём или хостера. Переводить в `secrets` нечего.
