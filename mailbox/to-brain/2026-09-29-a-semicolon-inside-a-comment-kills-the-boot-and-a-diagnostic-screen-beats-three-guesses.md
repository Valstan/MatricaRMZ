# Точка с запятой внутри комментария роняет загрузку клиента, а диагностика стоит трёх догадок

Планшетный клиент после установки не стартовал: красный экран «Не удалось запустить приложение: Execute: not an error (code 0)». Десктоп, unit-тесты, CI — всё зелёное. Три релиза 28.09, чтобы добраться до истины: **3.48.0 — ложный фикс, 3.49.0 — диагностика, 3.50.0 — истинный фикс.** Две переносимые вещи.

## 1. Класс: комментарий с `;` внутри ломает разбиение SQL-миграции на мобильном плагине

Наша миграция `0026_inventory_lines_has_own_number.sql` начиналась с комментария, внутри которого стояло «…под собственный номер;». Плагин Capacitor SQLite режет скрипт по `;\n` **до** снятия комментариев: комментарий с `;` даёт фантомную границу, следом идёт кусок из одних комментариев, после их снятия остаётся пустая строка → `execSQL(";")` → нативная ошибка `"not an error (code 0)"` → boot падает. На десктопе (better-sqlite3) тот же файл проходит без единого замечания.

Симптом обманывает дважды. Сообщение абсурдно («not an error», код 0) — читается как поломка окружения или харнесса, а не как «в моём SQL точка с запятой в комментарии». И ложная теория была не просто правдоподобна — она объясняла всё: `DROP INDEX IF EXISTS` через `execSQL` якобы падает на недостающем индексе (у нас ровно такой дроп добавили в клиентский паритет за неделю до падения). Теория дала «фикс», который уехал в 3.48.0 и на планшете ничего не изменил. Опровергло её только устройство: на недостающем индексе `IF EXISTS` тихо успешен.

**Переносимые правила:**

- **SQL, уезжающий на клиент, линтером на CI, а не на устройстве.** Дешёвая проверка «`;` внутри `--`/`/* */` комментария» ловит этот класс в любом будущем файле до выката. Стоит одной регуляркой.
- **Снимать комментарии до сплита, а не после, и пропускать пустые операторы.** Наши сторожи: `stripSqlLineComments` перед разбиением + пропуск пустых чанков + юнит-гейт «каждый чанк каждого `.sql` после чистки не даёт пустых элементов» — регрессия в любом новом файле ловится в пакете, а не на планшете.
- **Название грабли должно нести истинную причину.** У нас запись сначала легла с заголовком-догадкой («DROP INDEX IF EXISTS падает») — индекс граблей, по которому ищут, предлагал лечить не то. Переписали под факт, ложную теорию пометили внутри; симптом остался первым ключом поиска.

## 2. Когда падение видно только на чужом устройстве, диагностика — это релиз

Единственное, что разрешило тупик, — экран 3.49.0, показывающий **версию приложения и точный SQL, на котором упало**. Первый же запуск на планшете дал строку и колонку. До этого два релиза ушли на чтение кода и правдоподобные объяснения, каждое из которых «подтверждалось» логикой файла, но не воспроизводилось.

**Правило:** если баг живёт вне вашего окружения (чужая ОС, чужой дисплей, чужая сеть), первый релиз делают **диагностическим**: версия + место падения + виновные данные прямо в ошибке, которую видит человек. Такой релиз не «ничего не чинит» — он покупает истину за один запуск вместо трёх релизов догадок. Симптом класса: вы читаете файл, а не наблюдаете падение.

Смежная дыра той же истории: **самообновление не спасает клиент, который не стартует** — Android-самообновление у нас мертво, пока приложение не поднимается, фикс пришлось ставить APK-файлом руками. Апдейтер и его канал обязаны переживать сломанный основной код, иначе аварийный путь недостижим ровно тогда, когда он нужен.
