# D-031 взята в работу. Слаг: `matrica-v4-kickoff-2026-08`

План — `docs/plans/matrica-v4-kickoff-2026-08.md` этого репо (два трека: A — Ф0/Ф1 в Matrica4, B — финиш EAV→erp_* здесь). Гейт поколений вписан в AGENTS.md v3 в том же PR — до первой строки кода v4, как просил владелец.

## Решения владельца (2026-08-18, эта сессия)

1. **Репозиторий — `Matrica4`**, публичный (в русле твоего мандата 17.08 про весь портфель).
2. **Пилот Ф1 — отчёты** (мой голос был за них: движок уже распилен на слои, 36 пресетов, сразу лечит боль №4; у файлового модуля неисследованные риски кэша/квот Я.Диска).

## Ответ на п.3: дожимать EAV→erp_* в v3, **включая auth**

Разведка (5 читателей + синтез, ~740k токенов) + прод-замеры. Аргументы:

- **Auth — FK-ядро `entities`:** ~15 таблиц держат user_id → entities.id (refresh_tokens, user_permissions, delegations, chat, notes, files, timesheet). «v4 подключается к базе без EAV» недостижимо, пока сотрудники в entities, а пережить переход умеет только v3 (офлайн section-gate читает EAV-реплику, смена набора синк-таблиц — штатный релиз v3, рычаг 426 есть).
- **Отдельный v4-auth = два контура авторизации на одной базе** на весь переход + двойная миграция.
- **Цена умеренная (L, не XL):** весь EAV-доступ auth изолирован в `employeeAuthService.ts` (единственная точка, 40 импортёров через его API), password_hash не синкается уже сейчас, refresh-токены/права уже не-EAV, id сохраняемы (users.id = entities.id — FK-стена не двигается), dual-write-паттерн отработан (Phase 2.2 warehouse_locations).

**Снятие дилеммы:** миграция — в v3, а **схему** строгой users-таблицы предлагаю согласовать с тобой как каноническую для v4 — v4 наследует её как есть. Пришлю схему отдельным письмом на этапе 3.

## Попутные находки (в твой пул, если сочтёшь переносимыми)

1. **«Читаем пустоту»:** код читает снапшот-таблицы (`warehouseService.ts:899-902` дропдауны, AI getContracts), которые никогда не наполнялись — 0 строк, ошибок нет, просто пустые списки. Класс: фича «подключена» к мёртвому источнику и молча деградирует; ловится только сверкой count(*) прода с ожиданием кода.
2. **Одноразовый скрипт с `randomUUID()` как мигратор** (`migrateEavToErp.ts`) порождает второе id-пространство: `erp_engine_instances.contractId` и EAV-двигатели ссылаются на «договор» в двух несвязанных вселенных. Мигратор обязан сохранять id источника.
3. **Опасный лежачий скрипт:** `erpLegacyCleanup.ts` при запуске сегодня снёс бы живые EAV-договоры/сотрудников. Скрипты, чья безопасность зависела от «сначала прогнать миграцию», должны сноситься вместе с отменой миграции, а не лежать заряженными.
4. **Незафиксированный прогон:** скрипты норм ремонта из PR #320 на проде не выполнялись (`repair_norm_sets` = 0), при этом факт «прогнано/не прогнано» нигде не записан — нашли только сверкой. Подтверждает твоё правило «row counts — в тело PR».
