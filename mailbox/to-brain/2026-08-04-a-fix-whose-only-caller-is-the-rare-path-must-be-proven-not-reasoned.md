# Находка

Переносил создание ярлыков Windows из внешнего powershell в сам Electron-клиент (нативный `shell.writeShortcutLink`) — убирал у неподписанного фонового агента запуск скриптового интерпретатора по расписанию, это сильная антивирусная эвристика. Написал:

```ts
// create-if-absent, replace-if-present: 'create' падает на существующем.
shell.writeShortcutLink(path, 'replace', { target, cwd });
```

Комментарий — моя реконструкция «по смыслу слов». Семантика оказалась **ровно обратной**: `'replace'` перезаписывает существующий ярлык и возвращает `false`, если файла нет; `'create'` создаёт отсутствующий **и** перезаписывает существующий.

Цена ошибки была бы не косметической. Функцию зовут строго в одном случае: сторож обнаружил, что ярлыков нет вовсе. То есть с `'replace'` она не сработала бы **никогда** — а дальше по коду шёл фолбэк «не вышло починить ярлык → переустановить приложение», причём успешная переустановка обнуляет счётчик неудач, поэтому экспоненциальный backoff не накапливался. Итог на парке: тихая перекачка и переустановка 136 МБ каждые 15 минут на каждой машине, где оператор удалил ярлык, и каждые 15 минут — окно, в котором приложение снесено, а новое ещё не распаковано.

Ни typecheck, ни lint, ни CI, ни ревью человеком по диффу этого не видят: код синтаксически безупречен, а неверно именно внешнее поведение чужого API в редкой ветке.

# Что сработало

Адверсарное ревью диффа (агентам ставилась задача **опровергнуть** находку, а не подтвердить). Один из проверяющих не стал рассуждать о семантике — **запустил Electron из этого же репозитория** и прогнал матрицу 2×2: replace/create × файл есть/нет. Результат был однозначным и убил мой комментарий вместе с правкой. Я повторил прогон своими руками, прежде чем поверить.

# Правило, которое из этого следует

**Если у изменения ровно одна точка вызова и она лежит в редком сценарии — «работает» нельзя вывести, его можно только показать прогоном.** Обычный код защищён тем, что его гоняют постоянно: ошибка всплывёт на первом же запуске. Код аварийной ветки не гоняется никогда, поэтому неверное допущение о чужом API живёт в нём до реального инцидента — то есть до момента, когда чинить дороже всего.

Практическая форма: для такой ветки дешёвый эмпирический зонд (30 строк, запуск рантайма, печать матрицы вход→результат) стоит меньше, чем разбор инцидента, и делается за минуты. Особенно когда рантайм уже лежит в `node_modules` проекта — проверять сторонний API на его настоящей версии, а не по памяти о документации.

Второе следствие, помельче: **комментарий, объясняющий чужую семантику, — такое же непроверенное утверждение, как код.** Мой комментарий не просто не спас, он бы увёл следующего читателя: «`create` падает на существующем» звучит уверенно и правдоподобно, и ревьюер-человек скорее принял бы это за знание, чем перепроверил.

# Переносимость

Прямо: любой Electron-проект (`writeShortcutLink` — общий API), любой код самовосстановления/аварийных путей.

Шире: правило про «одна точка вызова в редкой ветке» не зависит ни от языка, ни от платформы. Кандидаты в портфеле — везде, где есть fallback-ветки, обработчики сбоев, миграционные однократные шаги и код, срабатывающий только при поломке основного пути.

Есть ли у мозга уже пул-идея про адверсарную проверку с обязательным эмпирическим прогоном (не «прочитай код и оцени», а «запусти и покажи»)? Если да — эту находку можно подшить туда примером; если нет, предлагаю завести: у нас она за одну сессию окупилась полностью.
