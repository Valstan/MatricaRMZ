# Урок: сид-миграция пишет в базу, а не в журнал синхронизации — клиенты молча остаются без данных

**Дата:** 2026-11-18 · **Откуда:** MatricaRMZ, сверка приказных данных по официальной ЕТН (миграция 0122, PR #1788).

## Что было

Приказные данные о СИЗ пополнялись миграциями (0118 — базовый сид, 0119–0121 — новые профессии и заводские нормы). В интерфейсе кладовщика всё появлялось сразу и выглядело правильно. А **напечатанный бланк выдачи на клиенте парка выходил без этих строк** — то есть бумажка, ради которой всё и затевалось, печаталась по старым данным.

Проверка журнала синхронизации на проде показала: в журнале лежало **220 строк приказа из 241, 49 наборов норм из 63 и 333 позиции номенклатуры СИЗ из 424**. Не хватало ровно тех строк, которые добавили миграциями 0119–0121.

## Корень

Миграция вставляет строки с `sync_status = 'synced'` — так написаны все сид-миграции. Публикатор зеркала выбирает строки условием `sync_status <> 'synced'`: признак «не опубликовано» несёт **сама строка**, а не очередь. Миграция идёт мимо пути записи синхронизации (`writeSyncChanges`), поэтому её строки:

- не получают номера журнала;
- не попадают в журнал **никогда** — их нечем туда положить;
- остаются в базе навсегда, и база выглядит полной.

## Почему это так долго не замечали

Данные расходились только в одном месте — в том, из которого делают бумажку:

- интерфейс кладовщика читает приказ **по серверу** (REST) — там всё верно;
- печать бланка и отчёты строятся **по локальной реплике клиента** — там этих строк нет.

То есть «программа показывает правильно» и «парк получил данные» — это два разных утверждения, и проверка обычно смотрит на первое.

## Что сделали

- Скрипт `ppe:publish-seed` публикует в журнал то, что уже есть в базе: номенклатуру → профессии → приказные строки → наборы → строки наборов, **в порядке зависимостей** (клиент применяет строки по номеру журнала, и строка набора должна прийти после своей номенклатуры). Удалённые строки уходят тумбстоунами (`op = 'delete'`).
- Удаление в миграциях переведено на **мягкое** (`deleted_at` + `sync_status = 'pending'`): строка остаётся в базе, а реплика клиента получает тумбстоун и убирает её. Физический `DELETE` из миграции в реплику не попадает **вообще** — там нет ни номера журнала, ни tombstone.
- Проверка «сколько строк таблицы есть в журнале» — дешёвый тест на этот класс расхождения.

## Переносимо

1. **Сид-миграция — это запись в базу, а не запись в журнал синхронизации.** Если таблица зеркалится, строки сида надо доставить до журнала отдельно, иначе реплика клиента молча останется неполной.
2. **«Приложение показывает правильно» ≠ «парк получил данные».** Если часть функциональности читает сервер, а часть — реплику, расхождение видно только во второй части; проверять надо именно её (у нас — на печатной форме).
3. **Физический `DELETE` в миграции — это «удалено только у сервера».** Для зеркалируемых таблиц удаление должно быть мягким, иначе клиенты навсегда сохраняют то, что сервер забыл.
4. **Порядок публикации = порядок зависимостей.** Публикуешь «всё разом» — клиент применяет по номеру журнала, и строка может прийти раньше того, на что она ссылается.
5. **Сверка «строк в базе» и «строк в журнале»** — один SQL-запрос, который стоит делать после каждой миграции в зеркалируемую таблицу.

## Где ещё может повториться

Тот же класс — в любом проекте, где есть миграции-сиды и клиентская реплика: справочники, справочные таблицы, настройки, каталоги. Признак: «в админке всё есть, а на клиенте — нет».
