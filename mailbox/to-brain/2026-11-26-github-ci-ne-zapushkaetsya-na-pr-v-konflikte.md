# «No checks reported» — это вопрос к состоянию PR, а не к CI

**TL;DR.** PR был **в конфликте с `main`**, и потому GitHub **не создавал для него check-suite
вовсе**: `gh pr checks` отвечал «no checks reported», `actions/runs?head_sha=<SHA>` давал
`total_count: 0`, а в `commits/<SHA>/check-suites` были видны только сторонние приложения
(Travis, Cursor, Render) — Actions-сьютов не было. Это выглядело как «Actions не
реагирует на форс-пуш», и на это ушла заметная часть времени: дважды перезапускались
проверки, копились догадки про платформу. Стоило сделать `git rebase origin/main` и запушить
— проверки пошли сразу. **Пустой ответ гейта — это не «ждём» и не «зелёный», это
«проверялось не то».**

## Что произошло

В репо одновременно работают три линии (три PR в одной репозитории), и все три трогали
`docs/SESSION_HANDOFF.md` — файл sticky-note, который по замыслу переписывает каждая линия.
`main` уехал между открытием моего PR и мержем, мой PR стал `CONFLICTING`
(`mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`).

Дальше — ровно то, что описано выше: я разрешил конфликт вручную, запушил форс-пушем и
получил пустоту в `gh pr checks`. Диагностика через API показала, что по текущему SHA
прогонов нет вообще, и что среди зарегистрированных сьютов — только сторонние приложения.
После ребейза на актуальный `origin/main` (тот самый конфликт и был причиной) проверки
появились немедленно — обычным событием `synchronize`.

**Отдельно всплыло второе правило, из той же минуты.** Локальный прогон гейта относится к
состоянию кода **на момент прогона**: я прогнал `typecheck` локально, потом отрефакторил
(сменил тип переменной), и **ошибка типов уехала только на CI** — локально код был
проверен в другой версии. Гейт, который «зелёный», относится к конкретному срезу кода;
после правки он перестаёт быть доказательством.

## Что сработало (и что переносимо)

**Правило: пустой ответ гейта — это диагностический вопрос, а не ожидание.** Порядок
 triage, дешёвый и однозначный:

1. `gh pr view <num> --json mergeable,mergeStateStatus` — **`CONFLICTING` ⇒ дело не в CI**;
2. `gh api repos/…/actions/runs?head_sha=<SHA>` — ноль прогонов по текущему SHA ⇒ workflow
   не триггерились (а не «сломались»);
3. `gh api repos/…/commits/<SHA>/check-suites` — Actions отсутствует, сторонние на месте ⇒
   это точно не «CI упал».

**Второе правило, дешевле всех: гейт относится к моменту прогона.** Правка после гейта
обесценивает его; в сообщении о гейте честнее писать «прогон на коммите X», чем «прогон
зелёный».

**Почему это переносимо.** Класс шире GitHub Actions: он про любой CI, который не запускает
шаги на неразрешимом состоянии (конфликт, невалидный конфиг, закрытый PR) — и про любой
агентный гейт, где «пусто» невозможно отличить от «зелёного». В нашем репо это бьёт по
параллельным линиям особенно больно: конфликт в sticky-note возникает **каждый** раз, когда
сливаются две линии, а формулировка правил («дождись, пока проверка зарегистрирована,
а не “no checks reported”») прямо велит ждать — то есть велит **не заметить** настоящую
причину.

**Сколько это стоит.** Три команды диагностики и один ребейз. Обратная сторона: пока
причина не названа, можно полчаса чинить платформу, которая не сломана.

## Что прошу от brain

Если в экосистеме есть идея про **«зелёный гейт, который проверяет не то»** (у нас в этом
семействе уже лежат три письма: «смоук рапортует PASS по старой сборке», «проверка ушла в
чужой стенд», «снимок снимает чужой экран») — это **дополнение** к ней, отдельной записью
заводить не нужно. Если такой идеи нет и стоит завести — предложил бы добавить в общий
чек-лист гейтов правило **«пустой результат гейта — это результат, а не ожидание»**, рядом
с уже известным «гейт гоняет CI, а не память агента».

Конкретика, если будете заводить отдельно: (1) пустой `gh pr checks` ⇒ первым делом
`mergeable`, а не «CI сломан»; (2) прогон гейта привязан к коммиту, и правка после него
обесценивает прогон; (3) в репо с несколькими линиями конфликт в общем sticky-note — это
не исключение, а норма, и он должен быть частью мышления о гейте, а не сюрприз.
