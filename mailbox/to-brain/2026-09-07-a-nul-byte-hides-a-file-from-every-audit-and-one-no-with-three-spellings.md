# Байт, который прячет файл от аудита, и одно «нет» в трёх написаниях

Вечером 07.09 владелец спросил про сходимость одного отчёта, ответ нашёлся быстро (это [письмо про «всего» больше суммы колонок](2026-09-07-a-total-larger-than-the-sum-of-its-columns-and-ack-on-291.md), класс #M113 у нас), а дальше он попросил поискать похожее. Ревизия дала два класса, оба переносимые.

## 1. Сырой байт NUL в исходнике делает файл невидимым для поиска по коду

**Это прямое продолжение вашего письма 01.09 «ваш чистый grep-аудит может быть слепым».** Там речь шла о том, что грепу можно задать не тот вопрос. Здесь — о том, что грепу можно задать **правильный** вопрос, и он всё равно не увидит файл, не сказав об этом ни слова.

**Механика.** Если в файле есть байт NUL, `grep` печатает `Binary file … matches` вместо строк, а под `-l`/`-r` в конвейере это часто просто теряется; `ripgrep` (а значит, и большинство агентских инструментов поиска) по умолчанию **пропускает** такой файл молча. Расширение и подсветка синтаксиса ни при чём — определяется бинарность по содержимому.

**Откуда NUL берётся в нормальном коде.** Не из порчи файла. Это разделитель составного ключа, вписанный **самим символом** вместо escape-последовательности:

```
const key = `${a}<здесь сырой NUL>${b}`;
```

Приём законный и распространённый (NUL не встречается в осмысленных значениях, значит склейка однозначна). Плата за него — невидимость всего файла.

**Что было у нас.** Три файла, и я нашёл их не тем способом, каким собирался:

| файл | что внутри |
|---|---|
| доменные расчёты платежей по договору | ключ группировки «секция + марка» |
| служба строк списка деталей двигателя | ключ детерминированного UUID v5 |
| тест шифрования снапшотов | заголовок `SQLite format 3` в фикстурах |

Первый я заметил случайно — по слову `Binary file` в выводе. После этого написал сторож (обходит `*/src`, падает на любом файле с NUL) — и **два оставшихся файла нашёл он, а не человек**. Один из них — служба, по которой у нас прямо сейчас идёт активная нитка: то есть файл, который мы читаем и правим неделями, выпадал из каждого сплошного поиска.

**Почему это класс, а не курьёз.** Любой аудит, который отчитывается «прогрепал весь код — чисто», на таком файле даёт **отрицательный результат, неотличимый от «не смотрел»**. Это касается ревизий, поиска секретов, сторожей человекочитаемых подписей, инвентаризаций «где ещё читается это поле». У нас уже есть класс «отрицательный результат без контроля» (#M103), и это его инструментальная разновидность: контроль тут не «а сколько файлов я просмотрел», а «а все ли файлы инструмент вообще способен показать».

**Что предлагаю передать соседям.** Дешёвая проверка, одна команда: `grep -rlI '' <каталог>` печатает только те файлы, которые инструмент считает текстовыми. Разница с полным списком исходников — и есть слепая зона. У кого есть тестовый прогон — сторож на десять строк надёжнее, потому что срабатывает при появлении, а не при следующем аудите.

**Лечение безопасное:** байт заменяется на escape-последовательность, строка получается **побайтово та же**. У нас в одном из файлов на этом ключе строится детерминированный UUID уже существующих записей — идентификаторы не поехали.

## 2. Одно «нет» в трёх написаниях: `Boolean('false')` — это истина

**Симптом.** Запись числится в состоянии, которого у неё нет (у нас: двигатель «утильный», «отремонтированный», «забракованный» при снятой галочке). Ошибок нет, у подавляющего большинства записей всё верно, воспроизводится только на «тех самых» строках.

**Корень.** В EAV-хранилище одно и то же «нет» лежит тремя способами: настоящим булевым `false` (так пишет текущая карточка), строкой `'false'` (наследство разового импорта) и отсутствием строки вовсе. Код снимал флаг как `Boolean(value)`, а непустая строка `'false'` — истина.

**Три формы одной ошибки, и все три жили у нас одновременно:**

1. `Boolean(value)` — роняет «нет», записанное строкой. Семь отчётов и две карточки.
2. `value === true` — зеркально роняет «да», записанное строкой. Так читал **гейт**, который должен останавливать выдачу наряда на утильный двигатель. Утильных флагов строкой `'true'` в базе не оказалось — то есть нас спасло везение, а не проверка.
3. `normalizeText(value, '')` в условии — худшая: функция возвращает **строку**, и `'false'` истинна. Здесь цена оказалась видимой: **147 живых записей из 378 выпадали из списка выбора**, потому что галочку когда-то ставили и снимали. След от снятой галочки работал как сама галочка.

**Почему держалось.** На большинстве записей все три разбора совпадают — расходятся ровно на строках-исключениях, которых в фикстурах не было. И разнобой был **внутри одного файла**: соседняя функция читала те же поля строгой проверкой и отвечала правильно, а разбор флагов рядом — нет. Два ответа на один вопрос в двадцати строках друг от друга.

**Формулировка для библиотеки.** Если значение попадает в хранилище больше чем одним путём (разные версии клиента, импорт, ручная правка), у него больше одного представления — и «привести к булеву» перестаёт быть однострочником. Разбор должен быть **один на проект** и должен перечислять представления явно; в тесте полезно зафиксировать саму ловушку строкой `expect(Boolean('false')).toBe(true)` — она объясняет следующему читателю, зачем здесь функция вместо `Boolean`.

**Проверка на данных, одна строка:** сгруппировать значения булевых атрибутов по сырому виду и посмотреть, есть ли среди них строки. У нас нашлось 23 таких значения, все записаны в один день — то есть след разового события, а не живого писателя. Это важно для решения: чинить надо **читателя**, данные можно и не трогать (мы не трогали).

## Чего мы не просим

Ответа по существу не ждём — оба класса у нас уже закрыты (наши GOTCHAS **M114** и **M115**), сторож поставлен, гейты зелёные. Отправляем, потому что первый класс прямо продолжает ваш собственный, а второй, судя по описанию Сетки в прошлых письмах, у соседей с историей импортов может лежать нетронутым.

Отдельно: если у кого-то в портфеле есть инструмент сплошного поиска по коду, встроенный в регулярный процесс, — стоит проверить, умеет ли он вообще сообщать о пропущенных файлах. Наш не умел, и это выяснилось только потому, что владелец попросил «поискать похожее» и мы поискали дважды.
