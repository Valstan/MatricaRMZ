# Обрезка по тому же правилу, по которому сортируешь, навсегда запирает рейтинг

## Что случилось

Делали подсказку порядка в списках выбора: кого оператор выбирает чаще, тот выше. На точку
выбора хранится `{n, last}`, сортировка «чаще → свежее → алфавит». Чтобы хранилище не росло
без края, поставили кэп: держим лучших `N`, остальных отбрасываем — **по тому же компаратору**,
что и сортировка. Выглядит безупречно: одно правило и для показа, и для вытеснения, никакой
второй логики.

Ошибка вскрылась на сценарии «новый сотрудник»:

```
кэп занят N людьми, у каждого n≥2
новичка выбирают — он входит с n=1
обрезка сортирует и оставляет лучших N → новичок слабейший → вылетает
следующий выбор: его в хранилище нет, он снова входит с n=1 → снова вылетает
```

Сколько его ни выбирай — **n никогда не станет двойкой**. Каждая запись немедленно
уничтожается той же операцией, которая её создала. Рейтинг, набрав однажды `N` человек с
`n≥2`, больше не принимает никого и никогда: новый работник не может попасть в подсказку,
даже если он единственный, с кем оператор работает последний месяц.

Снаружи это не похоже на поломку. Подсказка работает — просто «почему-то не учит новых».
Никакой ошибки, никакого лога, данные целы.

## Почему юниты это пропустили

Тест на обрезку у нас был — и зелёный. Он заводил `N+5` человек подряд и проверял, что
остаётся `N`, а частый старожил переживает наплыв новичков. Обе проверки верные и обе слепы:
в них новичок появляется **в момент, когда кэп ещё не заполнен людьми с бо́льшим счётчиком**,
поэтому успевает закрепиться.

Дыра ровно в обратном порядке: сначала заполнить кэп «двоечниками», потом привести новичка.
Этот случай никому не приходит в голову написать, потому что в голове живёт картинка «кэш
наполняется», а не «кэш давно полон и к нему приходит чужой».

## Лечение

Элемент, которого только что коснулись, **обязан пережить обрезку** и вытеснить слабейшего из
остальных:

```js
function capScope(scope, protectedId) {
  const ids = Object.keys(scope);
  if (ids.length <= CAP) return scope;
  const kept = ids.filter((id) => id !== protectedId)
                  .sort(byRank).slice(0, CAP - 1);
  return { ...fromIds(kept), [protectedId]: scope[protectedId] };
}
```

Смысл: обрезка — это про то, кого ЗАБЫТЬ, а не про то, кого не пускать. Забывать разрешено
кого угодно, кроме того, о ком тебе прямо сейчас сообщили. Иначе операция «запомни» способна
закончиться тем, что ты не запомнил ничего.

## Правило шире случая

Всюду, где есть **счётчик + кэп + вытеснение по тому же счётчику** — LFU-кэши, «популярные
запросы», «часто используемые» в любом виде, топ-N чего угодно с порогом входа, — задай два
вопроса:

1. **Может ли новый элемент вообще войти?** Если правило входа совпадает с правилом
   выживания, а счётчик новичка минимален по определению, ответ «нет».
2. **Тест на вытеснение начинается с полного или с пустого хранилища?** Если с пустого, он
   проверяет наполнение, а не вытеснение. Тест обязан начинаться с ПОЛНОГО, причём полного
   элементами, которые сильнее новичка.

Чистый LRU этой болезнью не страдает (ключ «свежесть», и новичок по нему сразу первый) — она
специфична для LFU-подобных, и потому её легко не ждать, переезжая с recency на частоту.
Именно этот переезд мы и делали.
