# signing — подпись исполняемого контура Матрицы

**Что это.** Скрипт [`sign-matrica.ps1`](sign-matrica.ps1) подписывает всё, что Матрица
запускает на машине парка, собственным ключом (ADR-0003). После этого в Касперском
работает **одно правило** вместо списка исключений: включённая вкладка
«Доверенное системное хранилище сертификатов» помещает любое приложение, подписанное
доверенной подписью, в группу «Доверенные» — Касперский не проверяет его исполняемый
файл, не контролирует активность и не блокирует сеть.

**Связанные:** [ADR-0003](../../docs/adr/0003-signed-code-ecosystem-one-kaspersky-rule.md) ·
[ADR-0002](../../docs/adr/0002-single-executable-root-not-program-files.md) ·
[`client-ops/`](../client-ops/README.md) (текущий способ настройки доверенной зоны)

---

## Почему именно так

Доверие по подписи вместо доверия по пути. Сегодня доверенное приложение — это строка
пути: `...\Programs\MatricaRMZ\MatricaRMZ.exe`. Стоит electron-builder поменять разрядность
или имя каталога — строка перестаёт совпадать. По подписи совпадение не зависит ни от
пути, ни от версии, ни от хэша: подписал ключом — доверен на всех машинах парка и во всех
будущих релизах.

Для экосистемы (модули, расширения, харнесс, EXO-кластер с локальными нейронками) это
означает **ноль новых строк в настройках на модуль**.

## Ключ

Свой корневой CA Матрицы, самоподписанный, EKU «Подписывание кода»:

| Файл | Что | Где лежит |
|---|---|---|
| `codesign.pfx` | приватный ключ | **только CI-секрет и хранилище владельца. В репозиторий не коммитится** |
| `rootca.cer` | публичная часть корня | в репозитории можно; ставится на машины парка |

Самоподписанный — потому что публичный CA недоступен: западные УЦ РФ не обслуживают,
GlobalSign в июне 2026 отозвал сертификаты российских компаний, Microsoft Artifact
Signing — только США и Канада, корню НУЦ Windows не доверяет (ADR-0003, brain D-084).

**Ключ подписи — это доверие самому себе.** Кто получит `codesign.pfx`, тот сможет выпустить
файл, которому Касперский будет доверять на всём парке. Поэтому PFX живёт только в CI.

## Режимы

### Создать CA (один раз, на машине владельца)

```powershell
.\sign-matrica.ps1 -Mode NewCa -PfxPath .\codesign.pfx -CerPath .\rootca.cer -Password '<пароль>'
```

Создаёт `codesign.pfx` (RSA-3072, SHA-256, 10 лет) и `rootca.cer`. PFX сразу же остаётся
в `Cert:\CurrentUser\My` — этот экземпляр надо экспортировать в CI-секрет и **удалить**
из хранилища, чтобы приватный ключ жил в одном месте.

### Подписать (в CI или локально)

```powershell
.\sign-matrica.ps1 -Mode Sign -PfxPath .\codesign.pfx -Password '<пароль>' -Target C:\out\MatricaRMZ
```

Пароль можно не передавать: берётся из `CSC_KEY_PASSWORD`. Уже подписанные файлы
пропускаются (`AlreadySigned`), так что повторный прогон безопасен. Расширения по умолчанию
`.exe,.dll,.node` — меняются ключом `-IncludeExt`.

### Поставить корень в доверенные (на машине парка)

```powershell
.\sign-matrica.ps1 -Mode InstallRoot -CerPath .\rootca.cer -CertStore CurrentUser
```

Работает **без прав администратора и без диалога**. Это неочевидно и стоит знать:

- `certutil -user -addstore Root` — **зависает** на невидимом диалоге подтверждения
  (в неинтерактивной сессии — тупик);
- `Import-Certificate` в PowerShell — отвечает «Для данной операции пользовательский
  интерфейс запрещен»;
- рабочий путь — только .NET API `X509Store('Root','CurrentUser').Add()`, он отрабатывает
  молча. Скрипт использует именно его.

**Установка идёт очень долго — от 45 секунд до нескольких минут** (замерено на PC79:
первая установка нового корня — 207 с, повторная того же сертификата — 9,4 с; в
`TrustedPublisher` на том же .NET API — 3 мс). Разница не в сертификате: у него нет ни
CRL Distribution Points, ни AIA, цепочка строится локально — задержка на стороне Windows
при добавлении в хранилище `Root`. Это медленно, но **не зависание**, и скрипт печатает об
этом предупреждение, чтобы оператор не бросил установку, решив, что всё встало. На парке
этот шаг надо закладывать в развёртывание отдельно.

`-CertStore LocalMachine` требует прав администратора — и **это выбранный режим** (ADR-0003,
решение владельца 05.11): корень Матрицы кладётся в машинное хранилище, потому что решение
о доверии принимает служба Касперского — она работает от SYSTEM и читает машинные хранилища;
корень в профиле пользователя служба не видит. Ставит администратор, один раз на машину,
отдельным повышенным шагом: установщик клиента корень не ставит (клиент per-user, прав админа
не требует — ADR-0002).

**Имя машинного хранилища задаётся параметром `-RootStoreName`:** `Root` («Доверенные корневые
центры», `Cert:\LocalMachine\Root`), `Trust` («Доверительные отношения в предприятии»,
Enterprise Trust, `Cert:\LocalMachine\Trust`), `TrustedPublisher` («Доверенные издатели»,
установка мгновенная).

**Рекомендуемый порядок на машине парка: положить корень в ОБА (`Root` и `Trust`).** Тогда выбор
в списке вкладки не важен: какое бы ни стояло, корень там есть, и цепочка для службы построится.
Проверено на PC79 06.11.2026 в системном контексте (от SYSTEM — так работает служба Kaspersky):
корень виден в обоих машинных хранилищах, цепочка подписанного клиента строится.

Время установки разное: в `Root` — **45–207 секунд** (Windows проверяет доверие, это НЕ
зависание), в `Trust` — мгновенно.

Справка KES: список «Доверенное системное хранилище сертификатов» — это системные (машинные)
хранилища, по умолчанию предлагается «Доверительные отношения в предприятии» (Enterprise Trust).
Раньше это была ловушка: корень клали в `Root`, а продукт по умолчанию смотрел в `Trust` —
подпись валидна, а доверия нет, и причина неочевидна. С двумя хранилищами ловушка снята.

### Установить корень на машине парка (одна команда)

`scripts/signing/install-root-on-machine.ps1` — ставит корень в оба машинных хранилища
(`LocalMachine\Root` и `LocalMachine\Trust`), сам поднимает права (UAC), проверяет, что
корень виден, и печатает оставшиеся шаги в окне Касперского (их продукт отдаёт только
человеку). Публичная часть корня лежит рядом — `scripts/signing/matrixarmz-rootca.cer`;
приватный ключ (`.pfx`) в репозиторий не попадает никогда (`*.pfx` в `.gitignore`).

#### А можно ли без прав администратора?

Да — для хранилища пользователя (`-Scope CurrentUser`): `Cert:\CurrentUser\Root` и
`\Trust` пишутся обычным пользователем, UAC не нужен.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\signing\install-root-on-machine.ps1 -Scope CurrentUser
```

Чего это даёт: программа сама доверяет серверу (TLS-цепочка строится по корню из
хранилища пользователя) и Windows показывает правильного издателя подписи EXE — всё
без единого повышения прав. Матрица и так работает без админа, поэтому этого хватает
для работы программы.

Чего это **не** даёт: доверия Касперского. Служба Касперского работает от SYSTEM и
смотрит **машинное** хранилище; пользовательское системным он не считает, поэтому
вкладка «Доверенное системное хранилище сертификатов» без корня в машинном хранилище
останется без толку. Настройку Касперского программно не поменять (Самозащита) —
галочку включает человек.

Итог по шагам на машину парка: машинный шаг (один раз, под админом) + галочка в
Касперском — нужны для доверия Касперского; шаг `-Scope CurrentUser` — по желанию,
чтобы программа доверяла серверу без прав админа.

### Где лежит корень прямо сейчас (read-only)

`scripts/signing/trust-root-probe.ps1` — опрос машины: где корень (машинные и
пользовательские хранилища) и подписан ли текущий EXE нашим ключом. Ничего не меняет —
это проверка, а не действие.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\signing\trust-root-probe.ps1 -Human
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\signing\trust-root-probe.ps1   # JSON
```

Почему через .NET `X509Store`, а не `Get-ChildItem Cert:\...`: провайдер PowerShell для
`Cert:` тянет за собой консоль и на больших хранилищах заметно медленнее; .NET API — тот же,
которым ставится корень, значит проверка и установка смотрят в ОДНО и то же хранилище.

Подпись EXE читается через `X509Certificate::CreateFromSignedFile` — это ИМЕННО встроенная
подпись файла. `Get-AuthenticodeSignature` для этой задачи не годится: он берёт подпись из
каталога подписей Windows и на переименованном файле показывает чужого издателя
(ADR-0003, замер 5).

### Программа проверяет и ставит корень сама

Клиент делает это сам, без человека: при запуске (то есть и после установки, и после
обновления) он опрашивает машину и, если корня нет в профиле пользователя, ставит его туда
молча — без прав администратора. Если корня нет в **машинном** хранилище, программа
показывает окно с инструкцией для администратора и кнопкой «Установить на всю машину»
(она запускает тот же `install-root-on-machine.ps1` и просит права через UAC).

Файлы едут с клиентом как `extraResources` (`electron-app/scripts/build-trust-assets.mjs`):
публичная часть корня, скрипт установки и проба. Скрипты `.ps1` **подписываются в CI**
(шаг «Sign trust scripts»): неподписанный `.ps1` Касперский удаляет на лету, ещё до того,
как для него заведено исключение (M94).

### Проверить (read-only)

```powershell
.\sign-matrica.ps1 -Mode Verify -Target "$env:LOCALAPPDATA\Programs\MatricaRMZ"
```

Печатает статус подписи каждого `.exe`/`.dll`/`.node` и имя подписавшего. `-Json` — для
машинного разбора.

## Что подписывать

| Что | Файл |
|---|---|
| Клиент | `MatricaRMZ.exe` |
| Деинсталлятор | `Uninstall MatricaRMZ.exe` |
| Сторож | `matricarmz-watchdog.exe` (в ресурсах и рядом с установкой) |
| Апдейтер | `matricarmz_update.exe`, `installer.exe` |
| Нативные модули | `better_sqlite3.node`, `test_extension.node`, `better_sqlite3-multiple-ciphers` |
| Рантайм Electron | `ffmpeg.dll`, `libEGL.dll`, `libGLESv2.dll`, `dxcompiler.dll`, `vk_swiftshader.dll`, `vulkan-1.dll` |

`d3dcompiler_47.dll` и `dxil.dll` подписаны Microsoft — их не трогаем.

**Кто подписал файл — решаем по отпечатку, а не по статусу цепочки.** `Get-AuthenticodeSignature`
возвращает `Valid` и для подписи Microsoft, и для нашей: статус значит «подпись есть и цепочка
сходится», а не «подписаны мы». Если бы скрипт пропускал любой `Valid`, DLL Microsoft остались бы
в «Доверенных» по подписи Microsoft, а не по нашей. Поэтому подписываем всё, кроме файлов,
которые уже подписаны **нашим** сертификатом (идемпотентность). `signtool` кладёт нашу подпись
в таблицу сертификатов поверх чужой — файл получает обе, и доверенным он становится по нашей.

## Конвейер выпуска

`electron-builder` подписывает сам (клиент, инсталлятор, деинсталлятор, DLL, `.node`) —
в [`.github/workflows/release-electron-windows.yml`](../../.github/workflows/release-electron-windows.yml)
переменные `CSC_LINK`/`CSC_KEY_PASSWORD` уже прокинуты, не хватает только самого сертификата.
В `electron-app/package.json` → `build.win` включено:

```jsonc
"signExts": [".dll", ".node"],   // DLL Electron и нативные модули
```

Опции `signDlls` в electron-builder **нет** (в версии 26.8.1 сборка падает с
`configuration.win has an unknown property 'signDlls'`) — DLL подписываются через `signExts`.

Сторож подписывается **отдельно**: он собирается ДО electron-builder и кладётся в
`extraResources` как готовый файл, поэтому electron-builder его не трогает.

Весь контур подписи и его проверки — [`ci-sign-artifacts.ps1`](ci-sign-artifacts.ps1):

```powershell
# предпроверка ключа (до сборки)
.\ci-sign-artifacts.ps1 -Mode Electron

# подпись сторожа
.\ci-sign-artifacts.ps1 -Mode Watchdog -Target .\electron-app\build\watchdog\matricarmz-watchdog.exe

# подпись скриптов PowerShell, которые едут в клиент (проверка и установка корня доверия)
.\ci-sign-artifacts.ps1 -Mode Scripts -Target .\scripts\signing

# проверка собранного релиза
.\ci-sign-artifacts.ps1 -Mode Verify -ReleaseDir .\electron-app\release
```

> **Почему `-Mode Scripts` не требует, чтобы раннер доверял нашему корню.** Наш корень
> самоподписанный, и CI-раннер ему не доверяет: `Set-AuthenticodeSignature` в этом случае
> возвращает статус `UnknownError` («цепочка упирается в корень, которому не доверяет
> поставщик»), **но подпись при этом пишется** — с сертификатом и меткой времени RFC 3161
> (проверено на PC79: файл подписан, `SignerCertificate` и метка времени на месте). Поэтому
> критерий приёмки здесь — **факт подписи в файле**, а не статус цепочки: на машине парка,
> где корень стоит, статус будет `Valid`. Критерий прежний — «подпись есть», и он же
> ловит случай, когда подпись не записалась вовсе.

### Поведение при отсутствии и при битом сертификате

| Ситуация | Что происходит |
|---|---|
| `CSC_LINK` не задан | Предупреждение, сборка идёт дальше **неподписанной**, релиз выпускается. Парк не остаётся без релизов из-за отсутствия ключа |
| `CSC_LINK` задан, PFX битый/неверный пароль | **Сборка останавливается** с читаемым сообщением. Внутри electron-builder тот же случай падает невнятным «cannot extract publisher name» |
| `CSC_LINK` задан, ключ годный | Сборка подписана; проверка `-Mode Verify` требует, чтобы **каждый** артефакт был подписан нашим ключом |
| Проверка без `CSC_LINK` | Нестрогая: сообщает, сколько подписано и сколько нет, но **не роняет** сборку |

## Локальная проверка: куда собирать, чтобы не мусорить

Проверку подписи **нельзя** делать в штатном `electron-app/release` — там останется
~95 МБ на каталог, который потом не удаляется: файл `app.asar` держит посторонний
процесс, а сам каталог помечен EFS (M191). Собирайте в отдельный каталог и уносите
потом:

```powershell
node electron-builder/cli.js --win --x64 --dir --config.directories.output=release-sign-test
```

Замер на PC79 05.11.2026: с сертификатом — **15 PE внутри `win-unpacked` подписаны нашим
ключом, ни одного без подписи**, плюс подписан сам инсталлятор; без сертификата —
`EXITCODE=0`, релиз неподписанный (парк не остаётся без релизов).

> **Локальная сборка требует повышения прав.** На Windows без Developer Mode electron-builder
> падает на распаковке `winCodeSign` (нужны симлинки; `AllowDevelopmentWithoutDevLicense=1` и
> `SymlinkEvaluation=1` не помогают — привилегия выдаётся только при повышении прав, M190).
> На GitHub-раннере проблемы нет.

## Кто подписал файл — читать из таблицы сертификатов PE

`Get-AuthenticodeSignature` **не годится** для этого вопроса: для файла, ранее
подписанного Microsoft, он показывает подписавшего Microsoft даже после замены подписи
нашей (PowerShell 5.1 берёт подпись из каталога подписей Windows, а не из таблицы
сертификатов файла). Источник истины — `signtool verify /pa /v`: строка `Issued to:` и код
возврата. На этом построена проверка `-Mode Verify`. Подробнее — [M189](../../docs/gotchas/M189.md).

## Граница возможного

- **Подпись не отменяет исключения на данные.** SQLite-база, логи, `db-key.json`, каталог
  обновлений, `%TEMP%` — это не исполняемые файлы, подпись их не покрывает. Эти строки
  остаются в списке исключений.
- **Подписанный код ≠ доверенный издатель.** Windows и SmartScreen относятся к
  самоподписанному сертификату иначе, чем к публичному: предупреждение «неизвестный
  издатель» при запуске и возможная ругань SmartScreen на загрузку инсталлятора никуда не
  денутся. Для Касперского это неважно, для оператора — может быть заметным шумом.
- **Подписать своим ключом можно только то, что мы собираем сами.** Скачанное со стороны
  или собранное из чужого репозитория под нашу подпись не получится: либо подпись чужая,
  либо её нет. Для своего кода вопрос закрыт, для чужого нужен отдельный путь.
- **Одна настройка в Касперском — ручной шаг.** `avp.com` не умеет менять доверенную зону
  (в списке команд только `EXPORT`/`IMPORT`/`SCAN`/…), а Самозащита блокирует правку
  конфигурации извне. Настоящее «одно правило на весь парк без ручных действий» — переход на
  KES + Kaspersky Security Center, где доверенная зона и Application Control с правилом по
  сертификату разъезжаются политикой сами. Это отдельное решение с лицензией и доменом.
